for_each, count, dynamic, lifecycle & dependencies

Meta-arguments turn static configuration into dynamic infrastructure, and lifecycle rules decide whether a change updates or destroys. Both directly control what a plan does to production, so this is a lesson about consequences rather than syntax.

By the end of this lesson you can

  • Explain the index-shift problem and why for_each is preferred
  • Convert count to for_each without destroying anything
  • State the plan-time requirement on for_each keys and work around it
  • Use all four lifecycle rules, and know their limitations
  • Explain create_before_destroy and when it cannot work on Azure
  • Use precondition and postcondition as guardrails

for_each

for_each.tf
# over a SET — each.key and each.value are identical
resource "azurerm_storage_container" "layers" {
  for_each = toset(["raw", "bronze", "silver", "gold"])

  name               = each.value
  storage_account_id = azurerm_storage_account.lake.id
}
# addresses: azurerm_storage_container.layers["raw"] …


# over a MAP — key and value differ, which is where the power is
resource "azurerm_storage_data_lake_gen2_filesystem" "layers" {
  for_each = {
    raw    = { retention = 2555, tier = "Cool" }
    bronze = { retention = 1095, tier = "Hot"  }
    silver = { retention = null, tier = "Hot"  }
    gold   = { retention = null, tier = "Hot"  }

  name               = each.key
  storage_account_id = azurerm_storage_account.lake.id

  properties = {
    retention_days = base64encode(tostring(coalesce(each.value.retention, 0)))

}

The plan-time requirement

the error you will eventually hit
Error: Invalid for_each argument

  on rbac.tf line 4, in resource "azurerm_role_assignment" "this":
   4:   for_each = toset(azurerm_storage_container.layers[*].id)

The "for_each" value depends on resource attributes that cannot be determined
until apply, so Terraform cannot predict how many instances will be created.
To work around this, use the -target argument to first apply only the
resources that the for_each depends on.

Terraform must enumerate every instance during plan. Keys derived from attributes that only exist after apply make that impossible. The fix is always the same: key on static input, not on computed attributes.

the fix
# ✗ keys come from resource IDs — unknown at plan time
resource "azurerm_role_assignment" "bad" {
  for_each     = toset(values(azurerm_storage_container.layers)[*].id)
  scope        = each.value
  # ...
}

# ✓ keys come from the same static input that drove the containers.
#   The unknown ID moves into the VALUE, which is allowed.
resource "azurerm_role_assignment" "good" {
  for_each = var.medallion_layers          # a set of names — static

  scope                = azurerm_storage_container.layers[each.key].id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = azurerm_user_assigned_identity.ingest.principal_id
  principal_type       = "ServicePrincipal"
}
The rule

for_each keys must be known at plan time. for_each values may be unknown. Whenever you hit this error, look for a way to key on the variable that generated the resources rather than on the resources themselves.

dynamic blocks

for_each on a resource creates multiple resources. dynamic creates repeated nested blocks inside one resource. Introduced in Lesson 03; here is the pattern that matters most.

the conditional-block idiom
resource "azurerm_linux_function_app" "ingest" {
  # ...

  # Include the identity block only when an identity is wanted, and
  # choose its shape based on which kind.
  dynamic "identity" {
    for_each = var.identity_type == "none" ? [] : [var.identity_type]

    content {
      type         = identity.value
      identity_ids = identity.value == "UserAssigned" ? [azurerm_user_assigned_identity.ingest.id] : null
    }
  }

  site_config {
    dynamic "ip_restriction" {
      for_each = var.allowed_ip_ranges

      content {
        name       = "allow-${ip_restriction.key}"
        ip_address = ip_restriction.value
        action     = "Allow"
        priority   = 100 + index(keys(var.allowed_ip_ranges), ip_restriction.key)
      }
    }
  }
}
Readability cost is real

HashiCorp's documentation explicitly warns that overusing dynamic makes configuration hard to read and maintain. If you can write three literal blocks, write three literal blocks — a reviewer can see them, and a plan diff on a literal block is much easier to interpret.

The lifecycle block

RuleEffectUse for
create_before_destroyOn replacement, create the new resource before destroying the oldMinimising downtime — where the name allows it
prevent_destroyAny plan that would destroy this resource fails at plan timeData lakes, key vaults, production databases
ignore_changesIgnore drift on named attributesAttributes another system owns
replace_triggered_byForce replacement when another resource or attribute changesRebuilding a dependent when its dependency changes

lifecycle accepts literals only

prevent_destroy = var.is_production does not work — Error: Variables not allowed. The lifecycle block is evaluated too early for variable resolution. This is the single most common frustration with it, and the practical answer is to separate environments into different root modules (Lesson 17) so production can hardcode true. ignore_changes and replace_triggered_by take references, but the booleans do not.

prevent_destroy

prevent-destroy.tf
resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location
  # ...

  lifecycle {
    prevent_destroy = true
  }
}
what it does when someone tries
Error: Instance cannot be destroyed

  on lake.tf line 1:
   1: resource "azurerm_storage_account" "lake" {

Resource azurerm_storage_account.lake has lifecycle.prevent_destroy set, but
the plan calls for this resource to be destroyed. To avoid this error and
continue with the plan, either disable lifecycle.prevent_destroy or reduce
the scope of the plan using the -target flag.
What it protects against, and what it does not
  • ✓ An accidental terraform destroy.
  • ✓ A change to a ForceNew attribute that would silently replace the resource — this is the case that saves data.
  • ✓ Removing the resource block from configuration.
  • ✗ Somebody deleting it in the portal. Use an Azure resource lock for that.
  • ✗ Deleting the resource group it lives in — Terraform's protection is per resource.
  • ✗ A deliberate attacker: it is one line to remove.

ignore_changes

ignore-changes.tf
resource "azurerm_linux_function_app" "ingest" {
  # ...

  lifecycle {
    ignore_changes = [
      # The deployment pipeline sets this. Terraform must not unset it.
      app_settings["WEBSITE_RUN_FROM_PACKAGE"],

      # Azure Policy appends governance tags.
      tags["CreatedOnDate"],
      tags["Owner"],
    ]
  }
}

resource "azurerm_network_security_group" "databricks" {
  # ...

  lifecycle {
    # Databricks injects its own required rules into this NSG.
    ignore_changes = [security_rule]
  }
}
Two ways to misuse it

Too broad. ignore_changes = all makes Terraform stop reconciling the resource entirely — it will create it and then never notice any difference again. That is almost never what you want, and it turns a managed resource into an unmanaged one that merely appears in state.

Used to silence a real problem. If a plan keeps proposing a change you do not want, the question is who is changing this and why. Ignoring it hides a genuine conflict — often two configurations managing the same resource, which is a design bug that ignore_changes will let you live with for a year before it bites.

create_before_destroy

create-before-destroy.tf
resource "azurerm_user_assigned_identity" "ingest" {
  name                = "id-ingest-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location

  lifecycle {
    create_before_destroy = true
  }
}
It often cannot work on Azure

Both resources exist simultaneously, so they need different names — and most Azure resources have a unique name within their scope, with storage accounts, Key Vaults and Function Apps unique globally. create_before_destroy on a storage account fails with “name already taken” because the old one still holds it. It works when the name is generated (a random_id suffix), or on resources without a name conflict. Note also that it propagates: Terraform applies it to dependents too, which can widen a replacement more than you expected.

replace_triggered_by

replace-triggered-by.tf
resource "azurerm_linux_function_app" "ingest" {
  # ...

  lifecycle {
    # If the identity is replaced, the app must be recreated to pick up
    # the new principal — otherwise it silently keeps the old, now-invalid one.
    replace_triggered_by = [azurerm_user_assigned_identity.ingest.id]
  }
}

precondition and postcondition

Where validation can only inspect a single variable, conditions can reference anything — which makes them the right tool for cross-cutting guardrails.

conditions.tf
resource "azurerm_storage_account" "lake" {
  # ...

  lifecycle {
    # Checked BEFORE the resource is created or updated.
    precondition {
      condition     = !(var.environment == "prod" && var.allow_public_access)
      error_message = "Production storage accounts must not allow public network access."
    }

    precondition {
      condition     = var.environment != "prod" || var.replication_type != "LRS"
      error_message = "Production requires zone- or geo-redundant replication, not LRS."
    }

    # Checked AFTER apply, against the real resource.
    postcondition {
      condition     = self.is_hns_enabled
      error_message = "The lake account must have the hierarchical namespace enabled."
    }
  }
}
check blocks — non-blocking assertions

A check block (Terraform 1.5+) reports a warning rather than failing, and can contain scoped data sources. Use it for continuous validation — “is the lake's private endpoint actually resolving?” — where you want visibility in every plan without blocking deployments on a transient condition.

depends_on, revisited

Lesson 05 covered the basics. Two refinements now that you have modules:

depends_on at module level is coarse
# ✗ Waits for EVERYTHING in the networking module — including resources
#   the storage module does not care about. Serialises unnecessarily.
module "storage" {
  source     = "./modules/storage"
  depends_on = [module.networking]
}

# ✓ Pass the specific output through as an input. This creates a precise
#   edge and documents what the dependency actually is.
module "storage" {
  source                = "./modules/storage"
  privatelink_subnet_id = module.networking.privatelink_subnet_id
}
depends_on can widen replacements

When a depends_on target is replaced, Terraform may conservatively plan to replace the dependent too, because it cannot reason about what the dependency provided. A reference-based edge is more precise: it knows exactly which attribute is consumed, so it can tell whether the change actually matters.

Immutable infrastructure

Everything in this lesson serves one idea: with immutable infrastructure you replace rather than modify, so a resource's configuration always matches what was deployed and there is no accumulated hand-editing. Terraform's replacement mechanics are the engine for that.

Where immutability works well

  • Compute — VM scale sets, container images, Function App code
  • Configuration — NSG rules, app settings, policies
  • Anything stateless: replace freely

Where it does not

  • Data. A storage account, a database, a lake — replacing means migrating, which is a project.
  • Resources with globally unique names — the old one holds the name.
  • Anything with long provisioning time and a hard dependency chain.
The practical policy for a data platform

Treat stateless resources as replaceable and stateful ones as precious. Concretely: prevent_destroy on every data-bearing resource, an Azure resource lock as a second layer that works outside Terraform, and a CI gate that fails when a plan contains a delete action unless a human sets an explicit override flag. Lesson 18 implements that gate.

Level 1 · Understand Predict the plan

Four containers exist, created with count over ["raw","bronze","silver","gold"]. Someone reorders the list to ["bronze","gold","raw","silver"] — alphabetical, for tidiness. No other change.

What does the plan say, and what is the real-world consequence?

Show answer

All four are destroyed and recreated.

IndexWasNowAction
[0]rawbronzereplace
[1]bronzegoldreplace
[2]silverrawreplace
[3]goldsilverreplace

Plan: 4 to add, 0 to change, 4 to destroy. Container name is ForceNew, so every index whose name changed must be replaced — and destroying a container deletes everything in it. A purely cosmetic reordering deletes the entire data lake.

With for_each = toset(...), sets are unordered and the keys are the names, so reordering the literal produces no change at all. That is the whole argument, in one example.

Level 2 · Implement Environment-driven resources

Write configuration where:

  • Containers are created from a map, each with its own access tier.
  • Private endpoints exist only when var.enable_private_endpoints is true — one per required subresource.
  • A role assignment is created per container per identity, from an access matrix.
  • The storage account cannot be destroyed by a plan.
  • A precondition rejects a production configuration that allows public network access.
Show answer
solution
variable "enable_private_endpoints" {
  type    = bool
  default = true
}

variable "environment" {
  type = string
}

variable "allow_public_access" {
  type    = bool
  default = false
}

locals {
  containers = {
    raw    = { tier = "Cool" }
    bronze = { tier = "Hot" }
    silver = { tier = "Hot" }
    gold   = { tier = "Hot" }
  }

  access_matrix = {
    databricks = { raw = "Storage Blob Data Reader", silver = "Storage Blob Data Contributor" }
    functions  = { raw = "Storage Blob Data Contributor" }
  }

  # cross-product, stably keyed
  assignments = {
    for a in flatten([
      for who, layers in local.access_matrix : [
        for layer, role in layers : { who = who, layer = layer, role = role }
      ]
    ]) : "${a.who}-${a.layer}" => a
  }

  pe_subresources = var.enable_private_endpoints ? {
    blob = "privatelink.blob.core.windows.net"
    dfs  = "privatelink.dfs.core.windows.net"
  } : {}
}

resource "azurerm_storage_account" "lake" {
  name                          = local.sa_name
  resource_group_name           = azurerm_resource_group.analytics.name
  location                      = var.location
  account_tier                  = "Standard"
  account_replication_type      = "GZRS"
  is_hns_enabled                = true
  public_network_access_enabled = var.allow_public_access

  lifecycle {
    prevent_destroy = true

      condition     = !(var.environment == "prod" && var.allow_public_access)

  name               = each.key
  storage_account_id = azurerm_storage_account.lake.id

  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location
  subnet_id           = azurerm_subnet.this["privatelink"].id

Two design points worth noting. First, for_each over a map that is empty when disabled is cleaner than count for the conditional endpoints — it also gives per-instance keys, so adding a third subresource later is a one-line change. Second, every for_each key here comes from a local derived from variables, so all of them are known at plan time.

Level 2 · Implement Guard a production resource four different ways

Write every layer of protection you can express in Terraform for the production data lake, then name the one thing none of them can stop.

Include a precondition that makes an insecure production configuration fail at plan time.

Show solution
guards.tf
resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location

  account_tier             = "Standard"
  account_replication_type = var.replication
  is_hns_enabled           = true

  public_network_access_enabled = var.allow_public_access
  shared_access_key_enabled     = var.allow_shared_keys

  lifecycle {
    # 1 - Any plan that would destroy this FAILS at plan time. Covers an
    #     accidental destroy, removing the block, AND - most valuably - a
    #     change to a ForceNew attribute that would silently replace it.
    #     Must be a literal: prevent_destroy = var.is_prod does NOT work.
    prevent_destroy = true

    # 2 - Cross-value rules that a variable validation cannot express,
    #     because validation can only see its own variable.
    precondition {
      condition     = !(var.environment == "prod" && var.allow_public_access)
      error_message = "Production storage must not allow public network access."
    }

    precondition {
      condition     = !(var.environment == "prod" && var.allow_shared_keys)
      error_message = "Production storage must not permit shared key access."
    }

    precondition {
      condition     = var.environment != "prod" || contains(["GZRS", "RAGZRS", "ZRS"], var.replication)
      error_message = "Production requires zone- or geo-redundant replication."
    }

    # 3 - Verified AFTER apply against the real resource.
    postcondition {
      condition     = self.is_hns_enabled
      error_message = "The lake must have the hierarchical namespace enabled."
    }
  }
}

# 4 - An Azure-side lock, which works even outside Terraform.
resource "azurerm_management_lock" "lake" {
  name       = "no-delete-lake"
  scope      = azurerm_storage_account.lake.id
  lock_level = "CanNotDelete"
  notes      = "Production data lake. Removal requires a change request."
}
ci-gate.sh
# 5 - The pipeline gate, from Lesson 18. Terraform-side guards protect
#     against Terraform; this protects against the plan reaching apply.
terraform show -json tfplan > plan.json

DESTROYS=$(jq '[.resource_changes[]
  | select(.change.actions | index("delete"))] | length' plan.json)

if [ "$DESTROYS" -gt 0 ] && [ "${ALLOW_DESTROY:-false}" != "true" ]; then
  echo "::error::Plan destroys $DESTROYS resource(s)."
  jq -r '.resource_changes[] | select(.change.actions | index("delete"))
         | "  - " + .address' plan.json
  exit 1
fi

What none of them stops: someone with portal access deleting the resource by hand. prevent_destroy and preconditions only constrain Terraform; the management lock is the only one of the five that applies outside it — and even that can be removed by anyone with Microsoft.Authorization/locks/delete.

Which is the real lesson: these are layers, not a solution. The durable control is removing standing portal write access to production and routing every change through the reviewed pipeline. Note too that prevent_destroy cannot be driven by a variable — the lifecycle block takes literals only, which is one concrete reason to keep production in its own root module.

Find four problems.

Show answer

1 · prevent_destroy with an expression.

Error: Variables not allowed. The lifecycle block accepts only literals. Fix by separating environments into different root modules so production hardcodes true — or accept it everywhere, which for a data lake is defensible.

2 · create_before_destroy on a globally unique name.

Both accounts would exist at once, and both want stanalyticsprodweu01. The apply fails with StorageAccountAlreadyTaken. It also conflicts with prevent_destroy — the two together mean “never destroy, but when you do, create first”, which is incoherent. Remove it.

3 · ignore_changes = all.

Terraform will create the account and then never reconcile it again. Change account_replication_type in code and nothing happens; someone disables HTTPS in the portal and no plan reports it. This turns a managed resource into an unmanaged one that merely appears in state. Name the specific attributes you genuinely need to ignore, or none.

4 · for_each keyed on computed IDs.

Container IDs are unknown until apply, so Terraform cannot enumerate the instances during plan: The "for_each" value depends on resource attributes that cannot be determined until apply. Key on the static input instead:

fix
resource "azurerm_role_assignment" "containers" {
  for_each = var.medallion_layers      # static set of names

  scope                = azurerm_storage_container.layers[each.key].id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = azurerm_user_assigned_identity.ingest.principal_id
  principal_type       = "ServicePrincipal"
}

A fifth, smaller point: principal_type is missing, which risks a PrincipalNotFound race when the identity is created in the same apply.

Interview questions

What is the difference between count and for_each?

count takes a number and keys instances by integer index; for_each takes a set or map and keys them by a meaningful string. The practical difference is that instance keys become state addresses, so removing an element from the middle of a count list shifts every later index and causes unrelated resources to be destroyed and recreated — on storage containers, that deletes data. With for_each, removing one element affects exactly that one. I use count only for conditional creation with ? 1 : 0, and for_each for everything else.

Why might for_each fail with “value depends on resource attributes”?

Because Terraform must enumerate every instance during plan, so for_each keys have to be known before anything is created. Keying on something computed — a resource ID, a managed identity's principal ID — makes that impossible. The fix is to key on the same static input that generated those resources and put the unknown value in the for_each value or in the resource body, which is allowed. If the dependency genuinely spans a creation boundary, that is a signal to split into two applies rather than to reach for -target.

What does prevent_destroy do, and what are its limits?

It makes any plan that would destroy the resource fail at plan time — which protects against an accidental destroy, against removing the block from configuration, and most valuably against a change to a ForceNew attribute that would silently replace the resource. Its limits: it does not stop someone deleting the resource in the portal, it does not protect against deleting the whole resource group, it cannot be set from a variable because lifecycle accepts only literals, and it is one line for anyone to remove. So it is one layer, alongside Azure resource locks and a CI gate on destroy actions.

When is ignore_changes appropriate?

When another system legitimately owns an attribute — a deployment pipeline setting WEBSITE_RUN_FROM_PACKAGE, Azure Policy appending tags, Databricks injecting NSG rules, an autoscaler changing node counts. Always name the specific attributes; ignore_changes = all stops Terraform reconciling the resource at all, which makes it effectively unmanaged. And I would be suspicious of using it to silence a recurring diff without understanding the cause — that is often two configurations fighting over the same resource, which is a design problem it merely postpones.

Why does create_before_destroy often fail on Azure?

Because both instances exist simultaneously and most Azure resources require a unique name within their scope — with storage accounts, Key Vaults and Function Apps unique globally. Creating the replacement fails because the original still holds the name. It works when names are generated with a random suffix, or on resources without a naming conflict. It is also worth knowing that Terraform propagates it to dependent resources, which can make a replacement wider than you intended.

How do you protect production data from a bad Terraform change?

Layers. prevent_destroy on data-bearing resources so a plan fails rather than proceeding. Azure resource locks, which work even outside Terraform. Separate state and separate credentials per environment, so a dev pipeline cannot reach production. A CI gate that parses the plan JSON and fails on any delete action unless a human sets an override. Mandatory plan review with the reviewed plan applied via -out. And reading every plan for # forces replacement, which is the comment that precedes most accidental data loss.

Key takeaways

  • for_each for collections, count only for ? 1 : 0. Index shifting destroys data.
  • for_each keys must be known at plan time; values need not be.
  • Convert count to for_each with moved blocks, and verify with an empty plan.
  • lifecycle accepts literals only — no variables in prevent_destroy.
  • ignore_changes names specific attributes. all makes the resource unmanaged.
  • create_before_destroy conflicts with globally unique Azure names.
  • Preconditions express rules that span several values, which validation cannot.

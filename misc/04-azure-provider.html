The AzureRM provider & authentication

The provider is the bridge between Terraform's cloud-agnostic core and the Azure Resource Manager API. This lesson explains every line of the boilerplate you will copy a hundred times, the Azure identity hierarchy underneath it, and the four ways to authenticate — ranked by how much you should trust them.

By the end of this lesson you can

  • Explain what a provider plugin is and how core communicates with it
  • Write and justify a required_providers version constraint
  • Explain the features {} block and why it is mandatory
  • Place tenant, subscription, management group and resource group in the right hierarchy
  • Choose an authentication method per context: laptop, CI runner, Azure-hosted compute
  • Configure multiple subscriptions or regions with provider aliases

What a provider actually is

A provider is a separate executable that Terraform downloads during init and runs as a child process, communicating over gRPC on a local socket. It is not a library, not a module, and not part of the terraform binary.

Each provider does three things:

  1. Publishes a schema. “I offer a resource type called azurerm_storage_account; it has these arguments, with these types, these are required, these force replacement when changed, these are computed.” This is what terraform validate checks against.
  2. Implements CRUD. For each resource type: Create, Read, Update, Delete — each mapping to one or more ARM REST calls, including polling the long-running operation until Azure says it finished.
  3. Handles authentication. It acquires an OAuth 2.0 token from Entra ID and attaches it to every request.

The boilerplate, line by line

versions.tf — the block you will write in every project
terraform {
  required_version = ">= 1.9.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 5.0"
    }
  }
}

provider "azurerm" {
  features {}

  subscription_id = var.subscription_id
}
LineWhat it does
terraform { } The settings block. It configures Terraform itself, not any infrastructure. It may contain only literal values — no variables, no expressions, because it is read before variable evaluation.
required_version Constrains the CLI version. Terraform refuses to run if the local binary does not satisfy it. Use a floor (>= 1.9.0) rather than a pessimistic pin — you want colleagues on newer CLIs to work, you just need the features you rely on.
required_providers Declares which providers this module needs. Without it Terraform would have to guess from resource-type prefixes — which it did in very old versions, and which breaks for third-party providers.
source = "hashicorp/azurerm" Registry address, short for registry.terraform.io/hashicorp/azurerm. The namespace matters: hashicorp/azurerm and databricks/databricks are different publishers.
version = "~> 5.0" Version constraint. See below.
provider "azurerm" { } Configures an instance of the plugin: which subscription, which credentials, which behaviours. Separate from required_providers, which only declares the dependency.
features {} Mandatory, even when empty. See below.
subscription_id Required for plan and apply since v4. Can come from ARM_SUBSCRIPTION_ID instead.

Version constraints

ConstraintAllowsVerdict
version = "5.4.0"Exactly 5.4.0Too rigid for a root module; sensible in some regulated environments. Prefer the lock file for exactness.
version = "~> 5.0"≥ 5.0.0 and < 6.0.0Standard for a root module. Allows minor and patch updates, blocks the breaking major.
version = "~> 5.4.0"≥ 5.4.0 and < 5.5.0Patch-only. Useful when a specific minor has a bug you are avoiding.
version = ">= 5.0"Anything from 5.0 upward, including 6.xCorrect for a shared child module, which should not over-constrain its consumers. Wrong for a root module — a major release will land silently.
omittedAnythingNever do this.
Constraint vs lock file

The version constraint says what is acceptable. The .terraform.lock.hcl says what was actually chosen. Together: a broad-ish constraint keeps you upgradeable, and the committed lock file keeps every machine identical until someone deliberately runs terraform init -upgrade. Do not try to achieve reproducibility with the constraint alone.

The features {} block

It looks like pointless ceremony. It is not: it is where you configure the provider's behaviour for operations that Azure treats specially, particularly around deletion.

features — a realistic configuration
provider "azurerm" {
  subscription_id = var.subscription_id

  features {
    resource_group {
      # Default is false. When false, destroying a resource group that still
      # contains resources Terraform does not manage will FAIL rather than
      # silently deleting them. Keep it false.
      prevent_deletion_if_contains_resources = true
    }

    key_vault {
      # Azure soft-deletes key vaults. If you destroy and immediately
      # re-create one with the same name, creation fails unless the
      # soft-deleted vault is purged or recovered first.
      purge_soft_delete_on_destroy    = false   # true only in throwaway dev
      recover_soft_deleted_key_vaults = true
    }
  }
}
These flags have real consequences

purge_soft_delete_on_destroy = true means a terraform destroy permanently and irrecoverably deletes the vault and every secret in it, bypassing Azure's safety net. That is convenient in an ephemeral dev subscription where you re-create the same vault name repeatedly, and it is a serious liability anywhere else. Set it per environment, not globally.

The Azure hierarchy you are deploying into

Terraform's scope arguments — for role assignments, policies and locks — refer to positions in this tree, so it is worth getting straight now.

LevelWhat it isTerraform relevance
Tenant One Entra ID directory. Identified by a GUID. Contains all identities. ARM_TENANT_ID. Managed by the azuread provider, not azurerm.
Management group A container for subscriptions, used to apply policy and RBAC to many at once. A valid role-assignment scope: /providers/Microsoft.Management/managementGroups/mg-analytics.
Subscription The billing and quota boundary. Resources belong to exactly one. subscription_id on the provider. Environment separation is very often subscription separation.
Resource group A named container within a subscription, in a specific region. Deleting it deletes everything inside. Nearly every resource takes resource_group_name. The most common RBAC scope.
Resource The actual thing. Has a resource ID. The finest-grained RBAC scope — e.g. granting access to one container in one storage account.

Authentication — four methods, ranked

The provider looks for credentials in a fixed order and uses the first it finds. What you should use depends entirely on where the code is running.

1 · Azure CLI — for local development

shell
az login
az account set --subscription "00000000-0000-0000-0000-000000000000"
az account show --query '{sub:id, tenant:tenantId, user:user.name}' -o table

# Terraform picks this session up automatically — nothing to configure
terraform plan

The provider reads the token cache the CLI maintains. It uses your identity, so your plan is limited by your own RBAC. That is a feature: if you cannot create a role assignment by hand, your Terraform should not be able to either.

2 · OIDC / workload identity federation — for CI/CD

This is the modern answer and the one to name in an interview. Instead of storing a client secret in your CI system, you register a federated credential on an Entra ID app registration that trusts tokens issued by your CI platform for a specific repository, branch or environment.

provider config for OIDC
provider "azurerm" {
  features {}

  use_oidc        = true
  subscription_id = var.subscription_id
  tenant_id       = var.tenant_id
  client_id       = var.client_id   # the app registration's client ID — not a secret
}

In practice you set none of this in HCL and use environment variables instead, so the same code runs unchanged on a laptop. Lesson 18 builds the full pipeline including the federated credential itself.

3 · Managed identity — for Terraform running on Azure compute

provider config for managed identity
provider "azurerm" {
  features {}
  use_msi         = true
  subscription_id = var.subscription_id
}

The VM or container fetches a token from the Azure Instance Metadata Service at a link-local address. Azure manages the credential lifecycle entirely — there is nothing to rotate and nothing to leak. Only usable when the runner is Azure-hosted.

4 · Service principal with a client secret — the fallback

environment variables — never in HCL
export ARM_CLIENT_ID="00000000-0000-0000-0000-000000000000"
export ARM_CLIENT_SECRET="$(read from your secret store — never a literal in a file)"
export ARM_TENANT_ID="00000000-0000-0000-0000-000000000000"
export ARM_SUBSCRIPTION_ID="00000000-0000-0000-0000-000000000000"

terraform plan   # provider picks these up with no HCL configuration at all

A client secret is a password. It expires (max two years, and Azure now defaults new ones much shorter), it must be rotated, and anyone who obtains it has whatever access the principal has, from anywhere on the internet. A certificate (ARM_CLIENT_CERTIFICATE_PATH) is a meaningful improvement. OIDC is better than both.

ARM_CLIENT_IDService principal / app registration ID. Not a secret.

Why credentials never go in the configuration

never-do-this.tf
provider "azurerm" {
  features {}
  subscription_id = "00000000-0000-0000-0000-000000000000"
  client_id       = "11111111-1111-1111-1111-111111111111"
  client_secret   = "abc123~ThisIsASecretAndNowItIsInGitForever"   # ✗✗✗
  tenant_id       = "22222222-2222-2222-2222-222222222222"
}

Four distinct failures, each sufficient on its own:

  1. Git history is permanent. Deleting the line in a later commit does not remove it — anyone with clone access can read it forever. Remediation means rotating the credential, not editing the file.
  2. Secret scanners find it in minutes. Public repositories are continuously scraped. There are documented cases of leaked cloud credentials being exploited within minutes of a push.
  3. It may land in state. Provider configuration is not itself stored in state, but this habit generalises to resource arguments that are.
  4. It destroys portability. One hardcoded subscription means the same code cannot deploy dev and prod — which is the entire point of IaC.
The rule

Credentials come from the environment (env vars, a CLI session, a federated token, an instance metadata endpoint) — never from the configuration. Non-secret identifiers such as subscription_id and client_id are fine as variables, and are usually supplied per environment via tfvars or CI variables anyway.

Multiple provider configurations

A single configuration often needs to touch two subscriptions — for instance, a private DNS zone in a shared connectivity subscription while everything else lives in the workload subscription.

aliases.tf
provider "azurerm" {
  features {}
  subscription_id = var.workload_subscription_id
  # no alias → this is the default configuration
}

provider "azurerm" {
  alias           = "connectivity"
  features {}
  subscription_id = var.connectivity_subscription_id
}

# uses the default provider
resource "azurerm_storage_account" "lake" {
  name                     = local.sa_name
  resource_group_name      = azurerm_resource_group.analytics.name
  location                 = var.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  is_hns_enabled           = true
}

# explicitly uses the aliased one — in the OTHER subscription
resource "azurerm_private_dns_zone" "blob" {
  provider            = azurerm.connectivity
  name                = "privatelink.blob.core.windows.net"
  resource_group_name = var.connectivity_rg_name
}

Passing providers into modules

Child modules inherit the default provider automatically. To give a module an aliased one, pass it explicitly — and the module must declare that it expects it.

root main.tf
module "private_endpoints" {
  source = "./modules/private-endpoints"

  providers = {
    azurerm              = azurerm               # default → module's default
    azurerm.connectivity = azurerm.connectivity  # alias → module's alias
  }

  storage_account_id = azurerm_storage_account.lake.id
  subnet_id          = module.network.privatelink_subnet_id
}
modules/private-endpoints/versions.tf
terraform {
  required_providers {
    azurerm = {
      source                = "hashicorp/azurerm"
      version               = ">= 5.0"
      configuration_aliases  = [azurerm.connectivity]   # declares the expectation
    }
  }
}
Common mistake · declaring a provider block inside a reusable module

A child module should contain required_providers but not a provider block. A module that configures its own provider cannot be used with for_each or count, cannot be removed cleanly (Terraform needs the provider configuration to destroy the resources it created), and takes configuration decisions away from the root module. Terraform warns about this; take the warning seriously.

What changed in azurerm 5.0

⚠ Reading older repositories and tutorials

These provider-level changes catch people out when they copy from a v3/v4 example. Resource-level renames are flagged in the lessons where they appear.

v3 / v4v5
skip_provider_registration = trueRemoved. Use resource_provider_registrations = "none".
Resource providers auto-registered by defaultDefault is now none — nothing is registered automatically. Set "legacy" to restore old behaviour, or register providers out of band.
subscription_id optionalRequired for plan and apply (from v4). validate still works without it.
enable_rbac_authorization on Key Vaultrbac_authorization_enabled
enable_https_traffic_only on storagehttps_traffic_only_enabled
storage_account_name on containersstorage_account_id
Resource provider registration in restricted subscriptions

Azure requires each resource provider namespace (Microsoft.Databricks, Microsoft.KeyVault…) to be registered on a subscription before you can create resources in it. Registration needs subscription-level write permission, which a least-privilege deployment principal often lacks — which is exactly why v5 defaults to none. If you hit MissingSubscriptionRegistration, have a subscription owner run az provider register --namespace Microsoft.Databricks once, rather than widening your pipeline's permissions.

Exercises

Level 1 · Understand Pick the auth method

Choose an authentication method and justify it in one line:

  1. A data engineer running terraform plan on their laptop against a dev subscription.
  2. A GitHub Actions workflow deploying to production on merge to main.
  3. A self-hosted Azure DevOps agent running on an Azure VM.
  4. A contractor's build server hosted outside Azure with no OIDC support.
Show answer
  1. Azure CLI. az login, zero configuration, and the engineer's own RBAC bounds what they can do — so their Terraform cannot exceed their own permissions.
  2. OIDC workload identity federation. No stored secret, and the federated credential is bound to repo:org/repo:environment:prod, so a feature branch cannot deploy production even if a workflow file is tampered with.
  3. Managed identity (use_msi). The VM is Azure-hosted, so it can get a token from the instance metadata endpoint with nothing to rotate.
  4. Service principal with a certificate, falling back to a client secret. Whichever you choose: store it in a real secret manager, scope the principal to only the resource groups it needs, and set a short expiry with rotation automated.

Level 2 · Implement Make a module accept an aliased provider

Write a modules/private-dns child module that creates a private DNS zone in the connectivity subscription and links it to a VNet in the workload subscription — so it needs both provider configurations.

Show the module's provider declaration, the resources, and the call from the root module.

Show solution
modules/private-dns/versions.tf
terraform {
  required_version = ">= 1.9.0"

module "dns_blob" {
  source = "./modules/private-dns"

  providers = {
    # left = the name INSIDE the module, right = the configuration out here
    azurerm              = azurerm

The mapping direction in the providers block trips people up: the key is the name the module uses internally, the value is the configuration in the calling module. Without configuration_aliases, Terraform rejects the call with provider configuration not present, because the module never declared that it expects a second one.

Level 3 · Troubleshoot Four errors on a fresh clone

A new joiner clones the repository and hits these in sequence. Diagnose each.

  1. Error: Insufficient features blocks — at least 1 "features" blocks are required
  2. Error: building account: could not acquire access token to parse claims: no valid authentication method found
  3. Error: subscription ID could not be determined and was not specified
  4. Error: Failed to query available provider packages — no available releases match the given constraints ~> 4.0, >= 5.0
Show answer

1 — The provider "azurerm" block is missing features {}. It is mandatory even when empty. Purely a configuration error; no Azure call was made.

2 — No credentials available. They have not run az login, and no ARM_* environment variables are set. The provider tried every method in order and found nothing.

3 — They are logged in, but no subscription is selected and none is configured. Since v4 the subscription ID must be explicit. Fix with az account set --subscription <id>, or set ARM_SUBSCRIPTION_ID, or pass -var. Note this error does not appear on terraform validate, which is why validate-only CI misses it.

4 — Conflicting constraints. The root module asks for ~> 4.0 while a child module (or a second required_providers block) demands >= 5.0; no single version satisfies both. Run terraform providers to see which module requires what, then align them — usually by upgrading the root and dealing with the v5 renames.

Interview questions

What is a Terraform provider?

A plugin binary that Terraform core runs as a child process and talks to over gRPC. It publishes a schema of resource and data-source types, implements CRUD for each of them against a real API, and handles authentication. Core itself knows nothing about Azure — the plugin architecture is what lets thousands of providers ship independently of the CLI.

How should Terraform authenticate to Azure in a CI/CD pipeline?

With OIDC workload identity federation. You register a federated credential on an Entra ID app registration that trusts tokens from your CI platform for a specific repository and environment; the runner exchanges a short-lived OIDC token for an Azure access token. No secret is stored anywhere, there is nothing to rotate, and the trust is scoped so that a feature branch cannot deploy production. If the platform does not support OIDC, a service principal with a certificate is the next best option, and a client secret the last.

Why is the features {} block required even when empty?

It is where provider-level behaviours are configured, chiefly around deletion semantics that Azure treats specially — whether destroying a resource group that still contains unmanaged resources should fail, and whether a soft-deleted Key Vault should be purged or recovered. Making it mandatory forces the author to acknowledge that these behaviours exist. In practice you should almost always set the Key Vault and resource group options rather than leaving it empty.

What does version = "~> 5.0" mean, and how does it relate to the lock file?

The pessimistic constraint operator: at least 5.0.0 and less than 6.0.0 — minor and patch updates are allowed, the next major is not. The constraint defines what is acceptable; the lock file records what was actually selected plus checksums. So the constraint keeps you upgradeable and the committed lock file keeps everyone reproducible. For a shared child module I would use a floor like >= 5.0 instead, so as not to over-constrain consumers.

How do you deploy to two subscriptions from one configuration?

Declare a second provider "azurerm" block with an alias and its own subscription_id, then set provider = azurerm.<alias> on the resources that belong there, or pass it into a module via the providers map. The module must declare configuration_aliases in its required_providers. The deployment identity needs appropriate rights in both subscriptions — which is often a reason to reconsider and split the configurations instead.

What is the difference between the azurerm and azuread providers?

azurerm manages Azure Resource Manager resources — anything with a subscription-scoped resource ID. azuread manages Entra ID directory objects such as groups, app registrations and service principals, through Microsoft Graph. They are separate because they are different APIs with different permission models: ARM uses Azure RBAC, Graph uses directory roles and application permissions, and a principal that can create storage accounts typically cannot create groups.

Why should credentials never appear in .tf files?

Because git history is permanent — removing the line later does not remove it from the repository, so the only real remediation is rotating the credential. Public repositories are continuously scanned by automated tooling, and leaked cloud credentials have been exploited within minutes of a push. It also breaks portability: hardcoding a subscription means the same code cannot deploy multiple environments. Credentials belong in the environment — env vars, a CLI session, a federated token, or an instance metadata endpoint.

Key takeaways

  • A provider is a separate binary speaking gRPC to core and REST to Azure. It owns the schema, the CRUD implementation and authentication.
  • required_providers declares the dependency; the provider block configures an instance of it. They are different things.
  • ~> 5.0 in root modules, >= 5.0 in shared child modules, and let the lock file provide exactness.
  • features {} is mandatory and worth configuring — especially the Key Vault purge behaviour.
  • Authenticate from the environment: CLI locally, OIDC in CI, managed identity on Azure compute, secrets last.
  • v5 changed provider-level defaults: no automatic resource provider registration, and subscription_id is required.

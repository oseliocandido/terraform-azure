The hierarchical namespace

Azure Blob Storage and ADLS Gen2 are the same service. There is no separate “Data Lake” product to provision — ADLS Gen2 is a storage account with one flag set:

the entire difference
is_hns_enabled = true

That flag replaces a flat key–value object store with a real filesystem, and the consequences are large enough that getting it wrong means rebuilding your lake.

Why a data engineer specifically cares

CapabilityFlat blobADLS Gen2Why it matters
Atomic directory rename No — copy + delete per blob Yes — single metadata operation The big one. Spark and Hadoop commit protocols write to a temporary directory and rename it on success. On flat storage that “rename” is thousands of copy operations, which is slow, expensive, and not atomic — a failure mid-commit leaves partial results.
Directory-level ACLs No — permissions are per container Yes — POSIX-style ACLs on directories and files Lets you grant a team access to silver/finance/ without giving them the whole silver layer.
Directory listing cost Prefix scan across all blobs Tree traversal Listing a partition in a lake with millions of files is dramatically faster.
Recursive delete Enumerate and delete each blob One operation Dropping an old partition is instant instead of a batch job.
abfss:// driver Works, degraded Full support The ABFS driver used by Databricks, Synapse and Fabric is designed for the DFS endpoint.
You cannot turn it on later

is_hns_enabled is ForceNew. Discovering after six months and 40 TB that your lake is a flat blob account means creating a new account and migrating everything. Azure does offer an in-place upgrade path through its own tooling for some cases, but Terraform will not do it — it will plan a destroy and recreate. Set it correctly on day one.

Common mistake · creating both for the same name

Since they are two views of one object, defining a container "raw" and a filesystem "raw" means two Terraform resources fighting over one Azure object. Whichever applies second reports “already exists”, and if both somehow enter state, every plan shows churn. Pick one resource type per name and stay consistent across the whole account.

Control plane vs data plane — the failure everyone hits

This deserves its own section because it produces one of the most confusing errors in Azure Terraform.

the error, in full
Error: creating Container "raw" (Account "stanalyticsdevweu01"):
executing request: unexpected status 403 (403 This request is not authorized
to perform this operation.) with AuthorizationFailure:
This request is not authorized to perform this operation.

  with azurerm_storage_container.raw,
  on main.tf line 58, in resource "azurerm_storage_container" "raw":
  58: resource "azurerm_storage_container" "raw" {

The storage account was created fine two seconds earlier. Three possible causes, in order of likelihood:

  1. The storage firewall now blocks you. You set network_rules { default_action = "Deny" } in the same apply. The account was created (control plane, unaffected), then the container creation went to the data plane and was rejected because your runner's IP is not in ip_rules.
  2. You have no data-plane role. Contributor on the resource group lets you manage the account but grants no access to the data. Reading and writing blobs requires Storage Blob Data Contributor or similar — a separate role. This surprises people constantly and is covered fully in Lesson 08.
  3. Shared key access is disabled and the provider fell back to it. With shared_access_key_enabled = false, the provider must use Entra ID for data-plane calls. Set storage_use_azuread = true on the provider.
the fixes
# 1 · Tell the provider to use Entra ID (not account keys) for data-plane calls.
provider "azurerm" {
  features {}
  storage_use_azuread = true
}

# 2 · Allow the deployment runner through the firewall.
resource "azurerm_storage_account" "lake" {
  # ...
  network_rules {
    default_action             = "Deny"
    bypass                     = ["AzureServices"]
    ip_rules                   = var.deployment_agent_ip_ranges
    virtual_network_subnet_ids = var.allowed_subnet_ids
  }
}

# 3 · Grant the deployment identity a DATA role, and wait for it before
#     creating data-plane objects.
resource "azurerm_role_assignment" "deployer_data" {
  scope                = azurerm_storage_account.lake.id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = data.azurerm_client_config.current.object_id
}

resource "azurerm_storage_container" "raw" {
  name               = "raw"
  storage_account_id = azurerm_storage_account.lake.id

  # No data flows from the role assignment, so no implicit edge exists.
  # This is one of the legitimate uses of depends_on.
  depends_on = [azurerm_role_assignment.deployer_data]
}
RBAC propagation delay

Even with depends_on, Azure role assignments can take up to a few minutes to become effective. An apply that creates the role assignment and immediately uses it can still fail with a 403 — and succeed on a retry with no code change. This is a genuine, well-known Azure behaviour, not a Terraform bug. In pipelines the pragmatic answers are: grant the deployment identity its data roles once, out of band, or accept a retry, or insert a time_sleep resource. Prefer the first.

A medallion data lake in Terraform

lake.tf — the data lake, complete
variable "medallion_layers" {
  description = "Data lake layers, with their retention and access-tier policy."

  type = map(object({
    tier_after_days     = optional(number)   # move to Cool after N days
    archive_after_days  = optional(number)   # move to Archive after N days
    delete_after_days   = optional(number)   # delete after N days (null = keep)
  }))

  default = {
    raw = {
      tier_after_days    = 30
      archive_after_days = 90
      delete_after_days  = 2555   # ~7 years, a common regulatory floor
    }
    bronze = {
      tier_after_days   = 180
      delete_after_days = 1095
    }
    silver = {
      tier_after_days = 365
    }
    gold = {}                     # always hot, never auto-deleted
  }
}

resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = var.environment == "prod" ? "GZRS" : "LRS"
  access_tier              = "Hot"

  # --- what makes it a data lake ---
  is_hns_enabled = true

  # --- security posture ---
  https_traffic_only_enabled      = true
  min_tls_version                 = "TLS1_2"
  allow_nested_items_to_be_public = false
  shared_access_key_enabled       = false   # Entra ID only — no account keys
  public_network_access_enabled   = false   # reachable only via private endpoint
  default_to_oauth_authentication = true

  # --- data protection ---
  blob_properties {
    versioning_enabled  = true
    change_feed_enabled = true

    delete_retention_policy {
      days = var.environment == "prod" ? 30 : 7
    }

    container_delete_retention_policy {
      days = var.environment == "prod" ? 30 : 7
    }
  }

  # --- identity, so the account can reach a customer-managed key ---
  identity {
    type = "SystemAssigned"
  }

  tags = merge(local.common_tags, {
    data_classification = "confidential"
  })

  lifecycle {
    prevent_destroy = true   # see Lesson 15
  }
}

resource "azurerm_storage_data_lake_gen2_filesystem" "layers" {
  for_each = var.medallion_layers

  name               = each.key
  storage_account_id = azurerm_storage_account.lake.id

  properties = {
    # ADLS Gen2 filesystem properties must be base64-encoded
    layer = base64encode(each.key)
  }

  depends_on = [azurerm_role_assignment.deployer_data]
}

Lifecycle management

A lifecycle policy is a control-plane resource — one policy document per storage account, containing many rules. It is not per container, which means you cannot express it with for_each over containers; you need a dynamic block instead. This is a good example of the schema dictating the HCL shape.

lifecycle.tf
resource "azurerm_storage_management_policy" "lake" {
  storage_account_id = azurerm_storage_account.lake.id

  dynamic "rule" {
    for_each = var.medallion_layers

    content {
      name    = "lifecycle-${rule.key}"
      enabled = true

      filters {
        prefix_match = ["${rule.key}/"]
        blob_types   = ["blockBlob"]
      }

      actions {
        base_blob {
          tier_to_cool_after_days_since_modification_greater_than    = rule.value.tier_after_days
          tier_to_archive_after_days_since_modification_greater_than = rule.value.archive_after_days
          delete_after_days_since_modification_greater_than          = rule.value.delete_after_days
        }

        # With versioning enabled, old versions accumulate and cost money.
        version {
          delete_after_days_since_creation = 90
        }
      }
    }
  }
}
Two things about lifecycle policies
  • They are evaluated by Azure roughly once a day, not immediately. Do not expect a tier change the moment you apply.
  • Archive tier has an early-deletion penalty (180 days) and rehydration takes hours. Never archive anything a query might need — which is why gold in the example above has no tiering at all.

Locking the account down

ArgumentSet it toWhy
shared_access_key_enabledfalseDisables the two account keys entirely. They are shared secrets that grant full data access, cannot be scoped, and are almost never rotated. With them off, every access must be an Entra ID identity — which means it is auditable and revocable.
public_network_access_enabledfalseThe account is reachable only through private endpoints. The strongest control available.
min_tls_version"TLS1_2"The only accepted value in current provider versions. Older ones allowed TLS 1.0/1.1.
allow_nested_items_to_be_publicfalsePrevents anyone from ever setting a container to public. In v5 this now defaults to false, but set it explicitly — explicit beats inherited.
https_traffic_only_enabledtrueRejects plain HTTP. Default is true; state it anyway.

Network rules

network.tf
resource "azurerm_storage_account" "lake" {
  # ...
  network_rules {
    # Deny everything not explicitly allowed below.
    default_action = "Deny"

    # "AzureServices" lets trusted first-party services through — needed by
    # some Azure integrations. It is broader than people assume: understand
    # what it admits before enabling it.
    bypass = ["AzureServices"]

    # Allow specific public IPs, e.g. the CI runner's egress range.
    # CIDR /31 and /32 are not accepted here — use the bare address for /32.
    ip_rules = ["203.0.113.10"]

    # Allow specific subnets — requires the Microsoft.Storage service
    # endpoint on those subnets.
    virtual_network_subnet_ids = [azurerm_subnet.databricks_host.id]
  }
}
Service endpoints vs private endpoints

virtual_network_subnet_ids uses service endpoints: traffic stays on the Azure backbone but the storage account keeps its public IP and public DNS name, and the firewall decides who gets in. A private endpoint gives the account a private IP inside your VNet, so it is reachable with no public exposure at all. Private endpoints are the stronger control and what you want in production. Lesson 11 builds them, including the DNS wiring that everyone gets wrong once.

Encryption

LayerTerraformNotes
Microsoft-managed keys Default — nothing to configure AES-256 at rest, always on, cannot be disabled. Sufficient for most workloads.
Customer-managed keys azurerm_storage_account_customer_managed_key Key lives in your Key Vault. You control rotation and can revoke access to the data by revoking the key. Requires the account to have a managed identity with Key Vault Crypto Service Encryption User.
Infrastructure encryption infrastructure_encryption_enabled = true A second, independent encryption pass. ForceNew — must be set at creation.
In transit https_traffic_only_enabled, min_tls_version Always.
The CMK circular dependency

Customer-managed keys create a genuine ordering puzzle: the storage account needs a managed identity, that identity needs a role on the Key Vault, and only then can the key be attached. This is why azurerm_storage_account_customer_managed_key is a separate resource rather than a block inside the account — splitting it breaks the cycle. When you see a provider offer a separate resource for something that looks like it should be an argument, a dependency cycle is usually the reason.

What all this puts in state

terraform state show azurerm_storage_account.lake (abridged)
$ terraform state show azurerm_storage_account.lake

# azurerm_storage_account.lake:
resource "azurerm_storage_account" "lake" {
    id                          = "/subscriptions/.../storageAccounts/stanalyticsdevweu01"
    is_hns_enabled              = true
    primary_access_key          = (sensitive value)
    primary_blob_connection_string = (sensitive value)
    primary_blob_endpoint       = "https://stanalyticsdevweu01.blob.core.windows.net/"
    primary_dfs_endpoint        = "https://stanalyticsdevweu01.dfs.core.windows.net/"
    secondary_access_key        = (sensitive value)
    shared_access_key_enabled   = false
    ...
}
“(sensitive value)” means redacted from output — not encrypted in state

The raw state file contains primary_access_key, secondary_access_key and every connection string in plaintext. Anyone who can read the state blob has full control of your data lake, regardless of their Azure RBAC on the storage account itself.

Two mitigations, and you want both. First, put state in a remote backend with encryption and restrictive RBAC (Lesson 10). Second — and more effective — set shared_access_key_enabled = false, so those keys are not usable even if leaked. That single argument turns a critical exposure into an inert one.

Common mistakes

Creating one container and using directories for layers

data/raw/, data/bronze/… inside a single container looks tidier but costs you control: lifecycle rules can still use prefix filters, but container-level RBAC scoping disappears, and you cannot delete a whole layer atomically. Separate containers per medallion layer is the standard for good reasons.

Forgetting that the DFS endpoint needs its own private endpoint

A private endpoint targets a specific subresource_name. For ADLS Gen2 you need both blob and dfs — plus the matching private DNS zones, privatelink.blob.core.windows.net and privatelink.dfs.core.windows.net. Creating only blob produces a lake that Spark cannot reach while the portal appears to work fine. Lesson 11.

Setting account_replication_type = "GRS" and assuming failover is automatic

GRS replicates asynchronously to a paired region, but reading the secondary requires RA-GRS, and failover is a manual operation you must initiate. For a data lake, also check that your replication choice is compatible with HNS — ZRS, GZRS and RAGZRS have specific requirements, and the provider documents that some combinations of account_tier, account_kind and HNS restrict the allowed values.

Exercises

Level 1 · Understand Diagnose the 403

An apply creates azurerm_storage_account.lake successfully and then fails creating azurerm_storage_container.raw with 403 ... AuthorizationFailure. The engineer says: “But I'm Owner on the subscription!”

Explain why Owner is not necessarily enough, and list what you would check.

Show answer

Owner is a control-plane role. It grants full management of the storage account — create, configure, delete, and read the account keys — but by itself it grants no data-plane access. Reading and writing blobs requires a data role such as Storage Blob Data Contributor, which even Owner does not implicitly include.

What to check, in order:

  1. Does the configuration set network_rules { default_action = "Deny" }? If so, is the runner's public IP in ip_rules?
  2. Is public_network_access_enabled = false with no private endpoint reachable from where Terraform runs?
  3. Is shared_access_key_enabled = false without storage_use_azuread = true on the provider? Then the provider tried to use a key that does not work.
  4. Does the identity have a Storage Blob Data role at account or container scope?
  5. Was such a role assigned in this same apply? Then it may simply be RBAC propagation delay — retry.

Owner does let you read the access keys, so with shared_access_key_enabled = true the provider often works anyway — which is why disabling shared keys is the moment most teams first meet this distinction.

Level 2 · Implement Environment-aware lake

Write an azurerm_storage_account that behaves differently per environment:

  • dev — LRS, public network access allowed, shared keys allowed, 7-day soft delete.
  • prod — GZRS, public network access disabled, shared keys disabled, 30-day soft delete, versioning on, infrastructure encryption on.
  • Both — HNS enabled, TLS 1.2, no public blobs, tagged consistently.
  • Only prod should be protected against destruction.
Show answer
solution
variable "environment" {
  type = string
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be one of: dev, test, prod."
  }
}

locals {
  is_prod = var.environment == "prod"
}

resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = local.is_prod ? "GZRS" : "LRS"

  is_hns_enabled                    = true
  https_traffic_only_enabled        = true
  min_tls_version                   = "TLS1_2"
  allow_nested_items_to_be_public   = false
  infrastructure_encryption_enabled = local.is_prod

  public_network_access_enabled = !local.is_prod
  shared_access_key_enabled     = !local.is_prod

  blob_properties {
    versioning_enabled = local.is_prod

    delete_retention_policy {
      days = local.is_prod ? 30 : 7
    }
  }

  tags = local.common_tags
}
The catch in the last requirement

You cannot write prevent_destroy = local.is_prod. The lifecycle block accepts only literal values — it is evaluated before variables in some contexts, so no expressions are permitted. Terraform errors with Variables not allowed. The real solutions are to keep environments in separate root modules or state (Lesson 17), so the production configuration can hardcode prevent_destroy = true, or to enforce it outside Terraform with an Azure resource lock. This limitation catches almost everyone the first time.

Level 2 · Implement Write the lifecycle management policy

Each medallion layer needs its own retention behaviour. Write an azurerm_storage_management_policy driven by this variable, where a layer with no settings produces no rule at all, and the whole policy resource disappears if no layer has any.

variables.tf
variable "medallion_layers" {
  type = map(object({
    cool_after_days    = optional(number)
    archive_after_days = optional(number)
    delete_after_days  = optional(number)
  }))

  default = {
    raw    = { cool_after_days = 30, archive_after_days = 90, delete_after_days = 2555 }
    bronze = { cool_after_days = 180, delete_after_days = 1095 }
    silver = { cool_after_days = 365 }
    gold   = {}
  }
}

Also expire non-current blob versions after 90 days, since versioning is enabled on this account.

Show solution
lifecycle.tf
locals {
  # A layer needs a rule only if it sets at least one action.
  layers_with_rules = {
    for k, v in var.medallion_layers : k => v
    if v.cool_after_days != null || v.archive_after_days != null || v.delete_after_days != null
  }
}

resource "azurerm_storage_management_policy" "lake" {
  # A policy with zero rules is invalid, so create the resource conditionally.
  count = length(local.layers_with_rules) > 0 ? 1 : 0

  storage_account_id = azurerm_storage_account.lake.id

  # A policy is ONE resource containing MANY rules, so this is a dynamic
  # block - not for_each on the resource. The schema dictates the shape.
  dynamic "rule" {
    for_each = local.layers_with_rules

    content {
      name    = "lifecycle-${rule.key}"
      enabled = true

      filters {
        prefix_match = ["${rule.key}/"]
        blob_types   = ["blockBlob"]
      }

      actions {
        base_blob {
          # null means "no action" - the provider omits the field entirely.
          tier_to_cool_after_days_since_modification_greater_than    = rule.value.cool_after_days
          tier_to_archive_after_days_since_modification_greater_than = rule.value.archive_after_days
          delete_after_days_since_modification_greater_than          = rule.value.delete_after_days
        }

        # Versioning without this is the most common cause of runaway
        # storage cost: every overwrite keeps the old blob forever.
        version {
          delete_after_days_since_creation = 90
        }
      }
    }
  }
}

Three judgements being tested. The count guard, because a management policy with no rules is rejected by the API. The dynamic block rather than for_each on the resource, because Azure allows exactly one policy per storage account containing many rules. And passing null straight through for unset actions, which the provider correctly omits.

Two operational notes worth knowing: Azure evaluates lifecycle policies roughly once a day, so nothing happens the moment you apply; and Archive has a 180-day early-deletion penalty with rehydration measured in hours, which is why gold deliberately has no tiering at all.

Level 2 · Implement Lock the account down with customer-managed keys

Harden the lake for production: no shared keys, no public network access, infrastructure encryption, and encryption with a customer-managed key from your own Key Vault.

The CMK part contains a genuine ordering puzzle. Write it, and explain in one sentence why the provider offers a separate resource rather than an argument on the storage account.

Show solution
lake-cmk.tf
resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = "GZRS"
  is_hns_enabled           = true

  # --- hardening ---
  shared_access_key_enabled         = false   # Entra ID only
  public_network_access_enabled     = false   # private endpoints only
  https_traffic_only_enabled        = true
  min_tls_version                   = "TLS1_2"
  allow_nested_items_to_be_public   = false
  default_to_oauth_authentication   = true
  infrastructure_encryption_enabled = true    # ForceNew - decide at creation

  # The account needs an identity BEFORE it can be granted access to the key.
  identity {
    type = "SystemAssigned"
  }

  tags = local.common_tags

  lifecycle {
    prevent_destroy = true
  }
}

# The account's identity must be able to wrap/unwrap the key.
resource "azurerm_role_assignment" "lake_cmk" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Crypto Service Encryption User"
  principal_id         = azurerm_storage_account.lake.identity[0].principal_id
  principal_type       = "ServicePrincipal"
}

resource "azurerm_key_vault_key" "lake" {
  name         = "cmk-lake"
  key_vault_id = azurerm_key_vault.main.id
  key_type     = "RSA"
  key_size     = 4096

  key_opts = ["unwrapKey", "wrapKey"]

  rotation_policy {
    automatic {
      time_before_expiry = "P30D"
    }
    expire_after         = "P365D"
    notify_before_expiry = "P29D"
  }
}

# A SEPARATE resource - this is the point of the exercise.
resource "azurerm_storage_account_customer_managed_key" "lake" {
  storage_account_id = azurerm_storage_account.lake.id
  key_vault_id       = azurerm_key_vault.main.id
  key_name           = azurerm_key_vault_key.lake.name

  # The role must be effective before the account can reach the key.
  depends_on = [azurerm_role_assignment.lake_cmk]
}

Why a separate resource: a cycle. The storage account needs a managed identity; that identity needs a role on the vault; only then can the key be attached to the account. If the key were an argument on azurerm_storage_account, the account would depend on a role assignment that depends on the account — and Terraform would reject the configuration with Cycle:. Splitting the attachment into its own resource breaks it.

A general heuristic worth carrying: whenever a provider gives you a separate resource for something that looks like it should be an argument — role assignments, CMK attachment, NSG associations — a dependency cycle is usually the reason.

Level 3 · Troubleshoot Why will this fail?
broken.tf
resource "azurerm_storage_account" "lake" {
  name                     = "my-data-lake"
  resource_group_name      = azurerm_resource_group.analytics.name
  location                 = "West Europe"
  account_tier             = "Premium"
  account_replication_type = "GRS"
  is_hns_enabled           = true
  min_tls_version          = "TLS1_0"

  network_rules {
    default_action = "Deny"
  }
}

resource "azurerm_storage_container" "raw" {
  name                  = "Raw"
  storage_account_name  = azurerm_storage_account.lake.name
  container_access_type = "blob"
}

Find every problem. There are at least seven.

Show answer
  1. name = "my-data-lake" — hyphens are not allowed. Storage account names are 3–24 lowercase alphanumeric characters only. Also almost certainly taken globally.
  2. account_tier = "Premium" with account_replication_type = "GRS" — Premium supports only LRS and ZRS. And with HNS enabled, Premium requires account_kind = "BlockBlobStorage", which is not set here.
  3. min_tls_version = "TLS1_0" — no longer an accepted value; the only permitted value is TLS1_2.
  4. network_rules with default_action = "Deny" and nothing allowed — the provider requires at least one of ip_rules or virtual_network_subnet_ids when the default action is Deny. Even if it applied, the container creation below would then fail with a 403.
  5. storage_account_name on the container — removed in azurerm v5. Must be storage_account_id = azurerm_storage_account.lake.id.
  6. name = "Raw" — container names must be lowercase, 3–63 characters, letters, digits and hyphens.
  7. container_access_type = "blob" — this makes blobs publicly readable without authentication. Never do this for a data lake. It will also fail outright, because allow_nested_items_to_be_public defaults to false in v5.

A bonus eighth: location = "West Europe" is valid but inconsistent with the lowercase-no-spaces convention used elsewhere in the course, and it hardcodes the region instead of referencing azurerm_resource_group.analytics.location.

Real-world scenarios

Scenario

“Our storage costs have tripled and nobody knows why. The lake looks the same size.”

Likely causes, all Terraform-visible:

  • Versioning without a version lifecycle rule. versioning_enabled = true keeps every overwritten blob forever. A daily-overwritten Delta table silently accumulates hundreds of versions. Fix: add a version { delete_after_days_since_creation = N } action to the management policy.
  • Soft delete retention set high. Deleted blobs still bill for the retention window.
  • Change feed enabled and never consumed. It writes a log that grows forever.
  • Archive rehydration. Somebody queried archived data, which rehydrates it to Hot and bills for the transition — and the early-deletion penalty if it was archived under 180 days ago.

The lesson: versioning_enabled, change_feed_enabled and soft delete are one-line changes with unbounded cost implications. Pair each with a lifecycle rule in the same commit.

Interview questions

What is the difference between Azure Blob Storage and ADLS Gen2?

They are the same service; ADLS Gen2 is a storage account with the hierarchical namespace enabled. HNS turns the flat key–value namespace into a real directory tree, which gives atomic directory renames, POSIX-style ACLs on directories and files, faster listings and cheaper recursive deletes. The atomic rename is the one that matters most for analytics, because Spark's commit protocol renames a temporary output directory on success — on flat blob storage that is thousands of copy-and-delete operations and is not atomic. In Terraform it is is_hns_enabled = true, and it is ForceNew, so it must be right at creation.

Why might creating a storage container fail when creating the storage account succeeded?

Because they use different APIs with different authorisation. The account is a control-plane resource on management.azure.com, governed by Azure RBAC roles like Contributor and unaffected by the storage firewall. The container is a data-plane object on the blob or dfs endpoint, which requires a data role such as Storage Blob Data Contributor and is subject to the firewall. So an apply that sets default_action = "Deny", or runs as an identity with only management permissions, creates the account and then gets a 403 on the container.

How would you organise a data lake's containers in Terraform?

One container per medallion layer — raw, bronze, silver, gold — created with for_each over a map so each layer can carry its own retention and tiering configuration. Separate containers rather than directories in one, because it lets you scope RBAC per layer, apply distinct lifecycle rules, and delete a layer atomically. On an HNS account I would use azurerm_storage_data_lake_gen2_filesystem rather than azurerm_storage_container, since it exposes ACLs and owner settings.

Why disable shared access keys on a storage account?

Because the two account keys are shared secrets that grant unrestricted access to all data, cannot be scoped to a container or an operation, carry no identity so their use is unattributable in logs, and are rarely rotated. They are also written in plaintext into Terraform state, so anyone who can read the state file effectively owns the lake. Disabling them forces every access through Entra ID, which is scoped, auditable and revocable. The trade-off is that every consumer — including Terraform itself, via storage_use_azuread — must be able to authenticate with an identity.

How do you control storage costs for a lake in Terraform?

An azurerm_storage_management_policy with per-prefix rules: tier raw data to Cool after 30 days and Archive after 90, delete after the regulatory retention period, and — critically — add a version action to expire old blob versions if versioning is enabled, since that is the most common cause of runaway cost. I would also avoid archiving anything queryable, because rehydration takes hours and archive has a 180-day early-deletion penalty. And I would tag consistently so cost analysis can attribute spend.

What is stored in Terraform state for a storage account, and why does it matter?

Every attribute the API returns, including primary_access_key, secondary_access_key and the connection strings — in plaintext. Terraform redacts them from CLI output as “(sensitive value)”, but does not encrypt them in the state file. So state must live in a remote backend with encryption at rest and tightly scoped RBAC, and ideally you set shared_access_key_enabled = false so that even if state leaks, the keys in it are unusable.

What happens if you change is_hns_enabled on a live account?

Terraform plans a destroy and recreate — the plan shows -/+ with # forces replacement — because the hierarchical namespace is fixed at creation in the Azure API. Applying it deletes the account and every byte in it. If a lake genuinely needs to move from flat blob to ADLS Gen2, that is a data migration project: create a new account, copy with AzCopy or a Spark job, repoint consumers, then decommission. I would also put prevent_destroy on the account so a careless apply cannot do it.

Key takeaways

  • ADLS Gen2 is a storage account with is_hns_enabled = true. It is ForceNew — get it right on day one.
  • Containers and filesystems are the same object through different endpoints. Pick one resource type per account.
  • Control plane ≠ data plane. Contributor does not grant data access, and the storage firewall does not affect account creation but does affect container creation.
  • One container per medallion layer, driven by for_each over a map that also carries lifecycle policy.
  • shared_access_key_enabled = false is the single highest-value security argument on the resource — it neutralises the keys sitting in your state file.
  • Versioning, soft delete and change feed all cost money forever unless paired with a lifecycle rule.

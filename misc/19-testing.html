Testing, scanning & policy as code

Every tool here catches a different class of problem, and each has a boundary it cannot cross. Knowing what each one cannot catch is more useful than knowing how to run them, because that is where the incidents come from.

By the end of this lesson you can

  • Place each tool on a spectrum from cheap-and-shallow to expensive-and-deep
  • Write native terraform test files, including mocked providers
  • Choose between static analysis, plan-time policy and cloud-side policy
  • State precisely what each tool cannot catch
  • Set up pre-commit hooks that make the whole thing automatic

The spectrum

The one that catches the most, per unit of effort

Policy checks on the plan JSON. Static analysis reads your HCL and cannot resolve variables, modules or computed values — so it misses anything conditional. A plan has all of that resolved into concrete before/after values for exactly the resources that will change. If you adopt one thing from this lesson, adopt that.

fmt and validate

shell
terraform fmt -check -recursive -diff    # CI: fails on unformatted files
terraform validate                       # needs init; makes no cloud calls

tflint

A linter that goes beyond schema validation. With the Azure ruleset it knows real Azure constraints — invalid VM sizes, deprecated resource types, region names that do not exist.

# Built-in rules worth enabling explicitly
rule "terraform_required_version"   { enabled = true }
rule "terraform_required_providers" { enabled = true }
rule "terraform_unused_declarations" { enabled = true }
rule "terraform_documented_variables" { enabled = true }
rule "terraform_documented_outputs"   { enabled = true }
rule "terraform_naming_convention" {
  enabled = true

terraform test

The native testing framework (Terraform 1.6+). Test files live in tests/ or alongside the module, named *.tftest.hcl. Each run block executes a plan or an apply and asserts against the result.

modules/storage/tests/defaults.tftest.hcl
# Values shared by every run block in this file.
variables {
  name                = "sttestanalytics001"
  resource_group_name = "rg-test"
  location            = "westeurope"
}

# ---------------------------------------------------------------
# Run 1 · plan mode — fast, no resources created, no cost.
#         Asserts on what the module WOULD create.
# ---------------------------------------------------------------
run "secure_by_default" {
  command = plan

  assert {
    condition     = azurerm_storage_account.this.is_hns_enabled == true
    error_message = "The storage module must always enable the hierarchical namespace."
  }

  assert {
    condition     = azurerm_storage_account.this.min_tls_version == "TLS1_2"
    error_message = "TLS 1.2 must be enforced."
  }

  assert {
    condition     = azurerm_storage_account.this.allow_nested_items_to_be_public == false
    error_message = "Public blob access must never be allowed."
  }

  assert {
    condition     = azurerm_storage_account.this.public_network_access_enabled == false
    error_message = "Public network access must default to disabled."
  }
}

# ---------------------------------------------------------------
# Run 2 · the containers are created from the input map.
# ---------------------------------------------------------------
run "creates_requested_containers" {
  command = plan

  variables {
    containers = {
      raw    = { delete_after_days = 2555 }
      bronze = {}
      silver = {}
      gold   = {}
    }
  }

  assert {
    condition     = length(azurerm_storage_data_lake_gen2_filesystem.this) == 4
    error_message = "Expected four filesystems, one per requested container."
  }

  assert {
    condition = alltrue([
      for k in ["raw", "bronze", "silver", "gold"] :
      contains(keys(azurerm_storage_data_lake_gen2_filesystem.this), k)
    ])
    error_message = "Every requested container must be created, keyed by name."
  }
}

# ---------------------------------------------------------------
# Run 3 · a variable validation rule must REJECT bad input.
# ---------------------------------------------------------------
run "rejects_invalid_name" {
  command = plan

  variables {
    name = "ST-Invalid-Name"     # uppercase and hyphens
  }

  expect_failures = [
    var.name,
  ]
}

# ---------------------------------------------------------------
# Run 4 · the lifecycle policy is only created when needed.
# ---------------------------------------------------------------
run "no_policy_without_rules" {
  command = plan

  variables {
    containers = {
      gold = {}     # no retention settings at all
    }
  }

  assert {
    condition     = length(azurerm_storage_management_policy.this) == 0
    error_message = "No management policy should be created when no container has lifecycle rules."
  }
}

Apply-mode tests

tests/integration.tftest.hcl
# command = apply CREATES REAL RESOURCES and destroys them afterwards.
# It costs money and takes minutes. Run it on a schedule or before a
# module release — not on every commit.

run "setup" {
  module {
    source = "./tests/setup"    # a helper module creating the resource group
  }
}

run "creates_a_working_lake" {
  command = apply

  variables {
    name                = run.setup.storage_account_name
    resource_group_name = run.setup.resource_group_name
    location            = "westeurope"
    containers          = { raw = {}, bronze = {} }
  }

  assert {
    condition     = output.dfs_endpoint != ""
    error_message = "The module must expose a DFS endpoint."
  }

  assert {
    condition     = can(regex("^https://.*\\.dfs\\.core\\.windows\\.net/$", output.dfs_endpoint))
    error_message = "The DFS endpoint must be a well-formed ADLS Gen2 URL."
  }
}
Apply-mode tests are real infrastructure

They create resources in a real subscription and bill for them. Terraform destroys them at the end of the file, but a crashed test run can leak resources — so use a dedicated sandbox subscription with a nightly cleanup and a budget alert. Names must also be unique per run, or two concurrent CI jobs collide.

Mocked providers

Terraform 1.7 added mocking, which lets you run apply-mode tests with no cloud access at all — fast, free, and usable on a pull request from a fork.

tests/mocked.tftest.hcl
mock_provider "azurerm" {
  # Give computed attributes plausible fake values so assertions can run.
  mock_resource "azurerm_storage_account" {
    defaults = {
      id                   = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-test/providers/Microsoft.Storage/storageAccounts/sttest001"
      primary_dfs_endpoint = "https://sttest001.dfs.core.windows.net/"
    }
  }
}

run "outputs_are_wired_correctly" {
  command = apply     # no real Azure call — the provider is mocked

  variables {
    name                = "sttest001"
    resource_group_name = "rg-test"
    location            = "westeurope"
    containers          = { raw = {}, gold = {} }
  }

  assert {
    condition     = output.dfs_endpoint == "https://sttest001.dfs.core.windows.net/"
    error_message = "The module must expose the storage account's DFS endpoint."
  }

  assert {
    condition     = length(output.container_scopes) == 2
    error_message = "One RBAC scope must be exposed per container."
  }
}
CatchesCannot catch
Wrong defaults, broken output wiring, conditional logic that produces the wrong resource count, validation rules that fail to reject bad input, regressions when refactoring a module Plan mode: anything the API decides — name collisions, quota, policy. Mocked mode: anything real, since the provider is fake; a mock will happily accept a configuration Azure would reject.

the common tools
# Checkov — the broadest rule set for Terraform, with Azure coverage
checkov -d terraform/ --framework terraform --compact

# scan a PLAN instead of the HCL — far fewer false positives,

checkov -f plan.json --framework terraform_plan

typical Azure findings
CKV_AZURE_59  Ensure that Storage accounts disallow public access
CKV_AZURE_33  Ensure Storage logging is enabled for Queue service
CKV_AZURE_44  Ensure Storage Account is using the latest version of TLS
CKV_AZURE_43  Ensure Storage Account name follows naming rules
CKV_AZURE_109 Ensure that Key Vault disables public network access
CKV_AZURE_110 Ensure that Key Vault enables purge protection

CKV_AZURE_206 Ensure that Storage Accounts use replication
CatchesCannot catch
Known misconfiguration patterns: public blob access, weak TLS, missing encryption, no purge protection, over-broad network rules, missing diagnostic settings Business-logic problems — the wrong container getting the wrong role is a perfectly secure configuration that is also completely wrong. Also anything requiring a plan: when scanning raw HCL it cannot resolve variables or module inputs, which is the main source of false positives and false negatives.
Scan the plan, not the HCL

public_network_access_enabled = var.allow_public is unresolvable in static analysis — the tool either guesses or skips. In the plan JSON it is a concrete true or false for the specific environment being deployed. Scanning plans dramatically reduces both false positives and missed findings, at the cost of needing cloud credentials to produce the plan.

Policy as code

Where it runsToolStrengthWeakness
Before apply, on the plan OPA / Conftest, or a jq script (Lesson 18) Blocks a bad change before it exists. Can express anything, including “no destroys”. Only sees changes Terraform makes. A portal change bypasses it entirely.
Before apply, managed HCP Terraform Sentinel Integrated, with cost estimation and a mature policy language Requires HCP Terraform / Enterprise
In the cloud, continuously Azure Policy Catches everything — portal changes, other tools, other teams. Can deny at the ARM layer or auto-remediate. Failures appear at apply time as opaque errors; feedback is late and the message is unhelpful
policy/deny-public-storage.rego
package terraform.analytics

import rego.v1

# Deny any storage account that will end up publicly reachable.
deny contains msg if {
    some change in input.resource_changes
    change.type == "azurerm_storage_account"
    "create" in change.change.actions
    change.change.after.public_network_access_enabled == true

    msg := sprintf(
        "%s enables public network access. Use a private endpoint instead.",
        [change.address],
    )
}

# Deny role assignments at subscription scope.
deny contains msg if {
    some change in input.resource_changes
    change.type == "azurerm_role_assignment"
    "create" in change.change.actions
    regex.match(`^/subscriptions/[^/]+$`, change.change.after.scope)

    msg := sprintf(
        "%s is scoped to the whole subscription. Scope to a resource group or resource.",
        [change.address],
    )
}

# Warn — do not block — on anything being destroyed.
warn contains msg if {
    some change in input.resource_changes
    "delete" in change.change.actions

    msg := sprintf("%s will be destroyed.", [change.address])
}
running it
terraform show -json tfplan > plan.json
conftest test --policy policy/ plan.json
Azure Policy is the backstop, not a replacement

Plan-time policy gives fast, clear feedback but only governs what Terraform does. Azure Policy governs everything, including a portal change at 2am — but the feedback is a deployment failure with an opaque message, often minutes into an apply. Use both: plan-time policy for developer experience, Azure Policy for actual enforcement. And if Azure Policy denies a deployment, the fix is to encode the same rule at plan time so the next person finds out in ten seconds instead of ten minutes.

Hooks are convenience; CI is enforcement

Pre-commit hooks are trivially bypassed with git commit --no-verify, and a new joiner will not have installed them. They exist to give you fast feedback. Every one of these checks must also run in CI, where it cannot be skipped. Running them only locally is a common and comfortable mistake.

Exercises

Level 1 · Understand Which tool catches it?

Name the cheapest tool that catches each, or “none”:

  1. storage_acount_id — a typo in an argument name.
  2. container_access_type = "blob" on a data lake container.
  3. A storage account name already taken by another Azure customer.
  4. A module refactor that silently stops creating the lifecycle policy.
  5. Granting the BI team Contributor at subscription scope.
  6. An engineer disabling a firewall rule in the portal.
  7. Putting the gold layer in the same container as raw — a design mistake.
Show answer
  1. terraform validate — the provider schema has no such argument.
  2. Checkov or Trivy — a classic public-access rule. A plan-time policy would also catch it.
  3. None until apply. Only the Azure API knows. validate checks the character rules; global uniqueness needs a real call.
  4. terraform test — exactly the regression an assertion on the resource count catches, and nothing else would.
  5. Plan-time policy (OPA/Conftest or the jq gate from Lesson 18). Static analysis usually cannot resolve the scope expression; the plan has it concretely.
  6. Azure Policy, or scheduled drift detection. No pre-apply tool sees changes Terraform did not make.
  7. None. No tool reviews architecture. This needs a human, which is why code review is not optional.
Level 2 · Implement Test the networking module

Write a .tftest.hcl for a networking module that asserts:

  • Every subnet in the input is created.
  • Subnets are correctly carved from the VNet CIDR with cidrsubnet().
  • Delegated subnets have exactly one delegation; others have none.
  • An overlapping subnet CIDR is rejected by validation.
  • No real Azure resources are created.
Show answer
modules/networking/tests/subnets.tftest.hcl
variables {
  name                = "vnet-test-weu-01"
  resource_group_name = "rg-test"
  location            = "westeurope"
  vnet_cidr           = "10.10.0.0/16"

  subnets = {
    privatelink = { newbits = 8,  netnum = 1, delegation = null }
    databricks  = { newbits = 8,  netnum = 2, delegation = "Microsoft.Databricks/workspaces" }
    functions   = { newbits = 10, netnum = 16, delegation = "Microsoft.Web/serverFarms" }
  }
}

run "creates_every_subnet" {
  command = plan

  assert {
    condition     = length(azurerm_subnet.this) == 3
    error_message = "One subnet must be created per entry in var.subnets."
  }

  assert {
    condition = alltrue([
      for k in keys(var.subnets) : contains(keys(azurerm_subnet.this), k)
    ])
    error_message = "Subnets must be keyed by their input name."
  }
}

run "cidr_arithmetic_is_correct" {
  command = plan

  assert {
    condition     = azurerm_subnet.this["privatelink"].address_prefixes[0] == "10.10.1.0/24"
    error_message = "cidrsubnet(10.10.0.0/16, 8, 1) must yield 10.10.1.0/24."
  }

  assert {
    condition     = azurerm_subnet.this["functions"].address_prefixes[0] == "10.10.4.0/26"
    error_message = "cidrsubnet(10.10.0.0/16, 10, 16) must yield 10.10.4.0/26."
  }
}

run "delegation_is_conditional" {
  command = plan

  assert {
    condition     = length(azurerm_subnet.this["privatelink"].delegation) == 0
    error_message = "A subnet with delegation = null must have no delegation block."
  }

  assert {
    condition     = length(azurerm_subnet.this["databricks"].delegation) == 1
    error_message = "A delegated subnet must have exactly one delegation block."
  }

  assert {
    condition     = azurerm_subnet.this["databricks"].delegation[0].service_delegation[0].name == "Microsoft.Databricks/workspaces"
    error_message = "The delegation must name the service given in the input."
  }
}

run "rejects_invalid_cidr" {
  command = plan

  variables {
    vnet_cidr = "not-a-cidr"
  }

  expect_failures = [
    var.vnet_cidr,
  ]
}

Everything is command = plan, so nothing is created and no cost is incurred — these can run on every commit. The cidr_arithmetic_is_correct run is the highest-value one: address-space errors are cheap to make, silent until deployment, and expensive to fix afterwards because resizing a subnet requires emptying it.

Level 2 · Implement Test outputs with a mocked provider

Plan-mode tests cannot assert on outputs that depend on computed attributes, because those are unknown until apply. Write a test using a mocked provider so you can assert on them with no cloud access at all.

Assert the DFS endpoint is wired through correctly and that one RBAC scope is exposed per container.

Show solution
modules/storage/tests/mocked.tftest.hcl
# Terraform 1.7+. The provider is replaced entirely, so command = apply
# creates nothing real - it is fast, free, and safe on a fork's pull request.
mock_provider "azurerm" {
  # Give computed attributes plausible values so assertions can run.
  mock_resource "azurerm_storage_account" {
    defaults = {
      id                   = "/subscriptions/00000000-0000-0000-0000-000000000000/resourceGroups/rg-test/providers/Microsoft.Storage/storageAccounts/sttest001"
      primary_dfs_endpoint = "https://sttest001.dfs.core.windows.net/"
      primary_blob_endpoint = "https://sttest001.blob.core.windows.net/"
    }
  }
}

variables {
  name                = "sttest001"
  resource_group_name = "rg-test"
  location            = "westeurope"
}

run "outputs_are_wired_correctly" {
  command = apply     # no real Azure call: the provider is a mock

  variables {
    containers = {
      raw  = {}
      gold = {}
    }
  }

  assert {
    condition     = output.dfs_endpoint == "https://sttest001.dfs.core.windows.net/"
    error_message = "The module must expose the storage account's DFS endpoint."
  }

  assert {
    condition     = length(output.container_scopes) == 2
    error_message = "One RBAC scope must be exposed per container."
  }

  assert {
    condition = alltrue([
      for scope in values(output.container_scopes) :
      can(regex("/blobServices/default/containers/[a-z0-9-]+$", scope))
    ])
    error_message = "container_scopes must be container-level RBAC scopes, not account-level."
  }
}

run "module_never_outputs_a_secret" {
  command = apply

  # A regression guard: someone adding an access-key output would copy a
  # credential into every caller's state.
  assert {
    condition     = !can(output.primary_access_key)
    error_message = "The storage module must not output an access key."
  }
}

The last assertion is the kind worth stealing. Security scanners flag over-permission but have no opinion about a module quietly starting to export a credential; a test can pin that as a property of the module's interface.

Know the boundary, though: a mock accepts configurations Azure would reject. It verifies your logic — defaults, output wiring, resource counts — and nothing about whether the resource can actually be created. Keep a small number of real apply-mode tests running on a schedule against a sandbox subscription for that.

Level 3 · Troubleshoot Every check passed, production broke

A change passes fmt, validate, tflint, Checkov and terraform test. It is applied to production. Databricks jobs immediately fail with 403 AuthorizationPermissionMismatch reading the silver layer.

the change
 locals {
   databricks_access = {
     raw    = "Storage Blob Data Reader"
-    bronze = "Storage Blob Data Contributor"
-    silver = "Storage Blob Data Contributor"
-    gold   = "Storage Blob Data Contributor"
+    bronze = "Storage Blob Data Reader"
+    silver = "Storage Blob Data Reader"
+    gold   = "Storage Blob Data Reader"
   }
 }

Why did every tool miss it, and what would have caught it?

Show answer

Why each tool missed it:

  • validate — the configuration is syntactically perfect and schema-valid. Storage Blob Data Reader is a real role name.
  • tflint — no lint rule is violated. Both role names are legitimate.
  • Checkov — the change makes permissions narrower. Security scanners flag over-permission, never under-permission. From a security standpoint this change is an improvement.
  • terraform test — unless someone wrote an assertion on the specific role granted per layer, there is nothing to fail. Tests assert what you thought to assert.
  • Plan-time policy — same: a policy denying over-broad roles has no opinion on roles that are too narrow.

The root cause is that this is a business-logic error, not a security or syntax error. Downgrading Databricks to read-only on the curated layers is a legitimate-looking, secure-looking change that breaks the platform's actual function.

What would have caught it:

  1. A test asserting intended behaviour, not just security posture. This is the real answer:
    the missing assertion
    run "databricks_can_write_curated_layers" {
  command = plan

  assert {
    condition = alltrue([
      for layer in ["bronze", "silver", "gold"] :
      azurerm_role_assignment.databricks_layers[layer].role_definition_name == "Storage Blob Data Contributor"
    ])
    error_message = "Databricks must retain write access to bronze, silver and gold; raw is read-only by design."
  }
}
  2. A human reviewer who understands the platform. The plan would have shown four role assignments being replaced — obvious to anyone who knows Databricks writes to silver.
  3. A smoke test after apply. A trivial job writing a file to silver and reading it back, run post-deploy, fails in seconds and can trigger a rollback.
The general lesson

Automated tools verify properties you thought to state. They cannot verify intent. Tests should assert what the platform is supposed to do — “Databricks can write silver” — not only what it must not do. And no amount of tooling removes the need for a reviewer who understands the system.

Interview questions

How do you test Terraform code?

In layers, cheapest first. fmt and validate for formatting and schema. tflint with the Azure ruleset for provider-aware lint and unpinned module sources. Security scanning with Checkov or Trivy — ideally against the plan JSON rather than raw HCL, so variables and module inputs are resolved. Native terraform test in plan mode for module logic, which is fast and free, plus mocked providers for apply-mode assertions with no cloud access. Apply-mode integration tests against a sandbox subscription on a schedule rather than every commit. And policy as code on the plan to block bad changes before they exist.

What can terraform validate not catch?

Anything requiring Azure, because it makes no network calls. A globally-taken storage account name, insufficient RBAC on the deployment principal, regional quota, an Azure Policy that denies the deployment, an overlapping subnet CIDR, or cross-argument rules the provider only enforces at apply time. It proves the configuration is well-formed; only plan proves it is achievable, and only apply proves it works.

What is policy as code, and where should it run?

Encoding organisational rules as executable checks rather than documentation. It runs in two places, and you want both. Before apply, against the plan JSON — with OPA/Conftest or Sentinel — which gives fast, precise feedback and can block a change before it exists, including rules like “this plan must not destroy anything”. And in the cloud, with Azure Policy, which catches everything including portal changes and other teams' tooling, but reports failures late and with poor error messages. Plan-time policy is for developer experience; Azure Policy is the actual enforcement boundary.

Why scan the plan rather than the HCL?

Because static analysis cannot resolve variables, module inputs or computed values. A line like public_network_access_enabled = var.allow_public is unknowable in the source — the scanner either guesses or skips it, producing both false positives and missed findings. In the plan JSON that value is a concrete boolean for the specific environment being deployed, along with the exact set of resources that will change. The trade-off is that producing a plan requires credentials and state access, so it happens later in the pipeline.

Are pre-commit hooks enough?

No. They are bypassable with git commit --no-verify and a new joiner will not have installed them, so they are a developer convenience for fast feedback rather than a control. Every check in the hooks must also run in CI where it cannot be skipped. Running them only locally is a common mistake because it feels like coverage.

What can no tool catch?

Whether the architecture is right, and whether a change matches intent. A configuration granting the wrong team access to the wrong data is syntactically valid, schema-valid, lint-clean and often more secure by a scanner's measure. Tools verify properties someone thought to state, which is why tests should assert what the platform is supposed to do — “Databricks can write to silver” — and not only what it must not do. And it is why human code review, by someone who understands the system, is not optional.

Key takeaways

  • Run cheap checks on every commit; expensive ones on a schedule. The order matters more than the tools.
  • Policy on the plan JSON is the highest-value single addition — it sees resolved values and actual changes.
  • terraform test in plan mode is fast and free. Mocked providers extend that to apply-mode assertions.
  • Security scanners flag over-permission, never under-permission. Test intent, not only posture.
  • Pre-commit hooks are convenience; CI is enforcement. Run everything in both.
  • No tool reviews architecture. That is what a human reviewer is for.

The Terraform workflow & CLI

init → validate → plan → apply → destroy is easy to memorise and easy to misunderstand. This lesson is about what Terraform is actually doing in each step — which files appear, which network calls happen, what gets locked, and why plan is the command you will spend most of your career reading.

By the end of this lesson you can

  • Describe precisely what terraform init downloads, writes and locks
  • Explain .terraform.lock.hcl — what it pins, why it is committed, and how to update it correctly
  • Say what validate catches and, more importantly, what it cannot
  • Read the phases of a plan: refresh, graph walk, diff
  • Use saved plan files, and explain why CI should always use them
  • Know which files belong in git and which must never be

The workflow is a loop, not a line

The canonical diagram is a straight line, which is misleading. In practice you spend nearly all your time cycling between plan and editing code, and init happens rarely.

terraform init

init prepares a working directory. It does four distinct jobs, and it is worth knowing them separately because they fail for different reasons.

terraform init — typical output
$ terraform init

Successfully configured the backend "azurerm"! Terraform will automatically
use this backend unless the backend configuration changes.

Initializing provider plugins...
- Finding hashicorp/azurerm versions matching "~> 5.0"...
- Installing hashicorp/azurerm v5.4.0...
- Installed hashicorp/azurerm v5.4.0 (signed by HashiCorp)

Terraform has created a lock file .terraform.lock.hcl to record the provider
selections it made above. Include this file in your version control repository

That .terraform/terraform.tfstate file is not your state

When you use a remote backend, Terraform writes a small file at .terraform/terraform.tfstate that records which backend is configured. It is a pointer, not your infrastructure state. Confusingly named; easy to panic about the first time you see it.

The dependency lock file

.terraform.lock.hcl is Terraform's equivalent of package-lock.json or poetry.lock. It records the exact provider version selected and the checksums of the packages for each platform.

.terraform.lock.hcl
# This file is maintained automatically by "terraform init".
# Manual edits may be lost in future updates.

provider "registry.terraform.io/hashicorp/azurerm" {
  version     = "5.4.0"
  constraints = "~> 5.0"
  hashes = [
    "h1:0S9gW0h6WkUHDPI9zJTHnPKMB0K7xL6vJ9r6yGmS0Xk=",
    "zh:1c2f0e8b8f...",
    "zh:2a91b3c4d5...",
    # ... one zh: entry per platform package
  ]
}
QuestionAnswer
Commit it? Yes, always. It is the difference between “everyone on the team and CI run provider 5.4.0” and “whoever ran init most recently got whatever was newest that day”.
What does it pin? Provider versions and their checksums. Not the Terraform CLI version, and not module versions (those are pinned in .terraform/modules/modules.json, which is not committed — module versions are pinned in the module block itself).
How do I upgrade a provider? terraform init -upgrade. This re-resolves within your version constraint and rewrites the lock file. Review the diff; it is a real change.
Why does CI fail with a checksum error? Usually because the lock file was generated on one platform only. Fix with terraform providers lock -platform=linux_amd64 -platform=windows_amd64 -platform=darwin_arm64 so all runner platforms are covered.
Common mistake · gitignoring the lock file

Some .gitignore templates found online include .terraform.lock.hcl. That is wrong and it is the cause of the classic “it worked on my machine, the pipeline produced a different plan” incident: a provider minor release changed a default, and only CI picked it up. Ignore .terraform/ (the directory); commit .terraform.lock.hcl (the file).

terraform fmt and terraform validate

These two are offline, fast, and belong in every pipeline and pre-commit hook.

fmt

shell
# rewrite files in place, recursively
terraform fmt -recursive

# CI mode: exit non-zero if anything is unformatted, change nothing
terraform fmt -check -recursive -diff

fmt enforces canonical formatting — indentation, and crucially the alignment of = signs within a block. It is not a linter: it has no opinion about your naming, structure or security. Its value is that it removes formatting from code review entirely.

validate

shell
terraform validate
# Success! The configuration is valid.

validate requires init to have run (it needs provider schemas) but makes no network calls to Azure and needs no credentials. Being precise about its boundary matters:

✓ validate catches

  • Syntax errors
  • Unknown or misspelled arguments for a resource type
  • Missing required arguments
  • Type mismatches (a string where a list is required)
  • References to undeclared variables or resources
  • Duplicate resource addresses
  • Invalid attribute values where the provider declares an enum

✗ validate cannot catch

  • A storage account name already taken globally
  • Insufficient RBAC permissions
  • Quota exhaustion in a region
  • A resource group that does not exist
  • Azure Policy denying the deployment
  • Cross-argument rules the provider only checks at apply
  • Anything that depends on real values, e.g. whether a subnet CIDR overlaps
The practical rule

validate proves the configuration is well-formed. Only plan proves it is possible, and only apply proves it works. A green validate in CI on a pull request from a fork — where you have no Azure credentials — is still worth running, because it catches the majority of typo-class errors for free.

terraform plan

This is the command that matters. Everything in Terraform operations is built on the discipline of reading plans carefully. Internally, plan has three phases.

Reading the change symbols

You will see five markers. Lesson 16 goes through full plan output line by line; here is the vocabulary:

SymbolMeaningDanger
+createLow — new resource
~update in placeLow to medium — the resource keeps its identity and data
-destroyHigh — verify this is intended
-/+destroy then create (replacement)Highest — the resource and anything inside it is deleted. On a storage account, that is your data.
+/-create then destroyReplacement with create_before_destroy set — safer ordering, but the name must be unique
Always read the last line

Plan: 3 to add, 1 to change, 0 to destroy. — if the destroy count is not what you expect, stop and find out why before doing anything else. In production pipelines this line is worth failing the build on: many teams gate on “destroy count must be zero unless a human sets an override flag”.

Saved plan files

A plan can be written to a file and applied later. This closes a real race: between reading a plan and approving it, somebody else could change the configuration or the infrastructure.

shell
# produce a plan file (binary)
terraform plan -out=tfplan

# inspect it later, without touching Azure
terraform show tfplan
terraform show -json tfplan | jq '.resource_changes[] | select(.change.actions[0]=="delete")'

# apply exactly this plan — no re-planning, no prompt
terraform apply tfplan
Why CI must use saved plans

When you run bare terraform apply, Terraform computes a fresh plan and asks you to confirm it. In a pipeline where a human approved the plan an hour ago in a pull request, applying without the saved file means you are applying something nobody reviewed.

terraform apply tfplan applies precisely the reviewed change set, and errors out if state has moved underneath it. Lesson 18 builds this into a real pipeline.

Common mistake · committing or publishing plan files

A saved plan contains the full attribute values of everything it touches — including values marked sensitive. Treat tfplan exactly like a state file: it is a secret. In CI, upload it as a protected artefact with a short retention, never to a public artefact store, and never commit it.

Plan flags you will actually use

FlagUse
-out=tfplanSave the plan for review and later apply.
-var-file=env/prod.tfvarsSupply environment-specific inputs. Lesson 07.
-destroyPreview a full teardown without running it.
-refresh=falseSkip the Azure read phase. Fast, but the diff may be based on stale state — use only for a quick sanity check, never before an apply.
-target=azurerm_storage_account.lakePlan only one resource and its dependencies. An escape hatch for recovering from a broken state, not a normal workflow — the docs say so explicitly.

On -target

If you find yourself reaching for -target regularly, that is a signal your state is too large or your modules are badly split — not that you have found a useful flag. Every targeted apply leaves the rest of your configuration un-reconciled, so the next full plan can surprise you.

terraform apply

apply executes the change set by walking the dependency graph. Concretely:

  1. Acquire the state lock. With the Azure backend this is a blob lease on the state blob. If another apply is running, you wait or fail.
  2. Re-plan (unless applying a saved plan file) and prompt for confirmation.
  3. Walk the graph in dependency order, up to 10 nodes in parallel (-parallelism=n to change).
  4. For each node, call the provider's Create/Update/Delete, which issues ARM API calls and polls the resulting long-running operation until Azure reports success.
  5. Write state after every individual resource — not at the end. This is what makes a half-failed apply recoverable.
  6. Release the lock and print outputs.
apply output
azurerm_resource_group.analytics: Creating...
azurerm_resource_group.analytics: Creation complete after 3s [id=/subscriptions/.../resourceGroups/rg-analytics-dev-weu-01]
azurerm_storage_account.lake: Creating...
azurerm_storage_account.lake: Still creating... [10s elapsed]
azurerm_storage_account.lake: Still creating... [20s elapsed]
azurerm_storage_account.lake: Creation complete after 27s [id=/subscriptions/.../providers/Microsoft.Storage/storageAccounts/stanalyticsdevweu01]

Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

Outputs:

lake_id = "/subscriptions/.../providers/Microsoft.Storage/storageAccounts/stanalyticsdevweu01"

Note the [id=...] on each completion line. That is the moment the resource's real Azure resource ID is written into state — the mapping that makes all future plans possible.

What happens when an apply fails halfway

This is not a disaster, and it is not a rollback

Terraform has no rollback. If resource 7 of 12 fails, resources 1–6 exist and are recorded in state; 8–12 were never attempted (or were attempted in parallel and may partially exist). Terraform stops, writes state, and reports the error.

The recovery is to fix the cause and run apply again. Because the operation is declarative and state is accurate, the second run creates only what is missing. The genuinely dangerous case is a resource that was created in Azure but whose state write failed — you then get “already exists” on retry, which you resolve with import (Lesson 16).

terraform destroy

destroy walks the graph in reverse dependency order and deletes everything in state. It is equivalent to terraform apply -destroy.

shell
terraform plan -destroy -out=tfdestroy   # review first — always
terraform apply tfdestroy
Destroy is for ephemeral environments

In a dev or PR-preview environment, destroying nightly is excellent practice — it keeps costs down and proves your configuration can build from nothing. In production, destroy is essentially never run, and the sensible controls are: prevent_destroy lifecycle rules on data-bearing resources (Lesson 15), Azure resource locks, and a pipeline that has no destroy path at all.

Note also that Azure soft-delete features interact with this. Destroying a Key Vault with purge protection enabled leaves it soft-deleted, and re-creating one with the same name will fail until it is purged — one of the most common “destroy then apply” failures. Lesson 09.

Exercises

Level 1 · Understand When must you re-run init?

Which of these require terraform init before the next plan will work?

  1. You added a new azurerm_storage_container resource block.
  2. You changed version = "~> 5.0" to version = "~> 5.4".
  3. You added a module "storage" { source = "./modules/storage" } block.
  4. You changed the backend's key from dev.tfstate to staging.tfstate.
  5. You cloned the repository onto a new laptop.
  6. You changed a value in dev.tfvars.
Show answer

Yes: 2, 3, 4, 5.

  • 2 — the provider constraint changed, so providers must be re-resolved.
  • 3 — new modules must be installed into .terraform/modules/.
  • 4 — backend configuration changed; Terraform will also ask whether to migrate the existing state.
  • 5 — .terraform/ is gitignored, so no providers are present at all.

No: 1 and 6. Adding a resource of an already-installed provider needs nothing new, and variable values are read at plan time.

Level 1 · Understand Where does validate stop?

A colleague says: “CI runs terraform validate on every PR, so we know the config is deployable.” Give three concrete counter-examples for an Azure data platform.

Show answer

Any three of:

  • The storage account name is already taken by another Azure customer — names are globally unique, and only an API call reveals it.
  • The service principal lacks Microsoft.Authorization/roleAssignments/write, so every role assignment will fail at apply time.
  • An Azure Policy in the subscription denies storage accounts with public network access enabled.
  • The subnet CIDR overlaps an existing subnet in the VNet.
  • A Key Vault of the same name is soft-deleted from a previous destroy and blocks creation.
  • The referenced resource group does not exist because it lives in another state.

All of these appear at plan or apply, never at validate, because validate makes no calls to Azure.

Level 2 · Implement A safe review-then-apply sequence

Write the exact command sequence to: apply the prod environment using env/prod.tfvars, in a way that (a) a human reviews the plan before anything changes, (b) exactly the reviewed change set is applied, (c) the run does not hang forever on a lock held by a colleague but waits a reasonable time, and (d) you can programmatically check whether the plan would destroy anything.

Show answer
shell
terraform init -backend-config=env/prod.backend.hcl

terraform plan \
  -var-file=env/prod.tfvars \
  -out=tfplan.prod \
  -lock-timeout=5m

# (a) human review — readable form
terraform show tfplan.prod

# (d) machine check: list anything being deleted or replaced
terraform show -json tfplan.prod \
  | jq -r '.resource_changes[]
           | select(.change.actions | index("delete"))
           | .address'

# (b) apply exactly what was reviewed
terraform apply -lock-timeout=5m tfplan.prod

Note that -var-file is not passed to apply when applying a saved plan — the variable values are already baked into the plan file. Passing it is an error, and that error confuses a lot of people the first time.

Level 2 · Implement Write a wrapper that makes the wrong-state mistake impossible

Your team keeps forgetting -reconfigure when switching environments, and once planned dev against prod state. Write tf.sh, taking an environment and a command, that removes the possibility.

It must reject an unknown environment, always re-init against the correct backend, save plans to an environment-specific filename, and refuse to apply when no plan exists.

Show solution
tf.sh
#!/usr/bin/env bash
set -euo pipefail

ENV="${1:?usage: ./tf.sh <dev|test|prod> <plan|apply|destroy-plan>}"
CMD="${2:?usage: ./tf.sh <dev|test|prod> <plan|apply|destroy-plan>}"

case "$ENV" in
  dev|test|prod) ;;
  *) echo "unknown environment: $ENV" >&2; exit 1 ;;
esac

PLAN_FILE="tfplan.${ENV}"

# -reconfigure every single time. The cached backend in .terraform/ is the trap.
init() {
  terraform init -reconfigure -backend-config="env/${ENV}.backend.hcl"
}

case "$CMD" in
  plan)
    init
    terraform plan -var-file="env/${ENV}.tfvars" -out="$PLAN_FILE" -lock-timeout=5m
    echo
    echo "Review it:  terraform show $PLAN_FILE"
    ;;

  destroy-plan)
    init
    terraform plan -destroy -var-file="env/${ENV}.tfvars" -out="$PLAN_FILE" -lock-timeout=5m
    ;;

  apply)
    [ -f "$PLAN_FILE" ] || {
      echo "no $PLAN_FILE - run './tf.sh $ENV plan' first" >&2; exit 1; }
    init
    terraform apply -lock-timeout=5m "$PLAN_FILE"
    rm -f "$PLAN_FILE"      # a consumed plan is stale; never re-apply it
    ;;

  *) echo "unknown command: $CMD" >&2; exit 1 ;;
esac

Two details worth keeping. -var-file goes to plan but not to apply — the values are already baked into the saved plan, and passing it there is an error that confuses people the first time they meet it.

And deleting the plan file after a successful apply stops someone re-applying a stale change set tomorrow. A plan file is a snapshot, not a build artefact you keep.

Level 2 · Implement Recover a half-failed apply

An apply died partway through with a network timeout. Re-running now gives:

terminal
Error: A resource with the ID "/subscriptions/.../storageAccounts/stanalyticsdevweu01"
already exists - to be managed via Terraform this resource needs to be imported
into the State. Please see the resource documentation for
"azurerm_storage_account" for more information.

Write the command sequence to diagnose and recover, with a comment explaining each step.

Show solution
recovery.sh
# 1 - What does Terraform believe it owns? The storage account will be ABSENT:
#     it was created in Azure, but the state write never happened.
terraform state list

# 2 - Confirm the resource really is there.
az storage account show \
  --name stanalyticsdevweu01 \
  --resource-group rg-analytics-dev-weu-01 \
  --query '{id:id, state:provisioningState}' -o json

# 3 - Adopt it with an import BLOCK rather than the CLI: previewable,
#     reviewable in a PR, and it leaves a record in git.
#     (written into imports.tf)
#
#     import {
#       to = azurerm_storage_account.lake
#       id = "/subscriptions/0000.../storageAccounts/stanalyticsdevweu01"
#     }

# 4 - The plan must show the import and NO other change to that resource.
#     Anything else means your config does not match what was really created.
terraform plan -out=tfplan
terraform show tfplan

# 5 - Apply: records the import, then creates whatever is still missing.
terraform apply tfplan

# 6 - Delete imports.tf once the import is recorded in state.

The idea to take away: this is not a corrupted deployment. State is written after each individual resource, so Terraform's record is accurate for everything it managed to write. The single resource that fell through the gap — created in Azure, missing from state — is precisely the case import exists for. Lesson 16 covers it properly.

Level 3 · Troubleshoot The pipeline that keeps producing different plans

A team reports the following symptoms:

  • Local plans are clean; the CI plan shows unexpected changes to resources nobody touched.
  • The problem started on a Tuesday and nobody changed any .tf file.
  • Their .gitignore contains .terraform*.
  • Their pipeline runs terraform init && terraform apply -auto-approve on merge to main.

Identify the two distinct problems and how you would fix each.

Show answer

Problem 1 — the lock file is being ignored.

The pattern .terraform* matches both .terraform/ and .terraform.lock.hcl. With no lock file committed, every init resolves the newest version satisfying the constraint. On Tuesday a new azurerm minor release changed a default or added a computed attribute, CI picked it up, local machines still had the old cached version — hence divergent plans.

fix
# .gitignore — be specific
.terraform/

# then commit the lock file, covering every platform CI and the team use
terraform providers lock \
  -platform=linux_amd64 \
  -platform=darwin_arm64 \
  -platform=windows_amd64
git add .terraform.lock.hcl

Problem 2 — apply -auto-approve with no reviewed plan.

Even once versions are pinned, the pipeline computes a brand-new plan at apply time and approves it automatically. Nobody ever sees what will happen. The fix is to plan on the pull request, publish the plan as an artefact and as a PR comment, gate the apply on an environment approval, and apply the saved file: terraform apply tfplan. Lesson 18 builds exactly this.

Interview questions

Walk me through the core Terraform workflow and what each command does.

init prepares the directory: initialises the backend and fetches existing state, installs modules, resolves and downloads provider plugins, and writes the dependency lock file. validate checks syntax and provider schema offline. plan refreshes state against the real infrastructure, builds the dependency graph, and produces a change set — it modifies nothing. apply takes the state lock and executes that change set in dependency order, writing state after each resource. destroy does the same in reverse to remove everything in state.

What is .terraform.lock.hcl and should it be committed?

It records the exact provider versions selected during init plus checksums for each platform package. It should absolutely be committed — it is what guarantees every developer and the pipeline use the identical provider build, so plans are reproducible. Update it deliberately with terraform init -upgrade, and use terraform providers lock -platform=... to include hashes for every OS your team and CI run on. It does not pin the CLI version or module versions.

What does terraform plan actually do?

Three phases. It refreshes — reading every resource in state from the provider API to learn its current real attributes. It evaluates variables, locals and data sources and builds the dependency graph. Then it diffs configuration against the refreshed state, asking the provider for each resource whether a given change can be applied in place or forces replacement. The result is a change set that can be printed and optionally saved with -out. Plan writes no infrastructure changes, though it may write a refreshed state.

Why would you use terraform plan -out in a pipeline?

To guarantee that what a human approved is exactly what gets applied. Without it, the apply step re-plans, so any change to code or infrastructure between review and apply silently makes it into production unreviewed. The saved plan also lets you inspect the change set as JSON for policy checks — for example, failing the build if the plan destroys anything. The plan file contains sensitive values, so it must be handled as a secret artefact.

What happens if terraform apply fails halfway through?

There is no rollback. Terraform stops, keeps everything already created, and records it in state — state is written after each individual resource, not once at the end. You fix the cause and re-run; because the model is declarative, only the missing resources are created. The awkward case is a resource created in Azure whose state write did not happen, which produces an “already exists” error on retry and is resolved by importing it.

What is the difference between validate and plan?

validate is offline and needs no cloud credentials — it checks that the configuration is internally consistent and matches provider schemas. plan authenticates to Azure, reads real resource state and produces an actual change set. Validate proves the config is well-formed; plan proves it is achievable against the current state of the subscription.

Someone suggests running terraform apply -target to speed up deployments. Your response?

I would push back. -target is documented as an escape hatch for recovering from errors, not a workflow. It applies a partial change set, leaving the rest of the configuration unreconciled, so state can drift from configuration in ways that surprise the next person to run a full plan. If plans are slow enough that this is tempting, the real fix is splitting state — smaller, independently applied configurations with a smaller blast radius.

Key takeaways

  • init does four things: backend, modules, providers, lock file. Re-run it when dependencies change, not when configuration changes.
  • Commit .terraform.lock.hcl; ignore .terraform/. Confusing the two causes divergent plans between laptops and CI.
  • validate is offline and proves well-formedness only. It cannot know about name collisions, permissions, quotas or policy.
  • plan = refresh + graph + diff. Read the summary line, and treat -/+ as a stop sign.
  • Saved plan files are how you guarantee the reviewed change is the applied change — and they are secrets.
  • There is no rollback. State is written per-resource, which is what makes a failed apply recoverable by simply re-running it.

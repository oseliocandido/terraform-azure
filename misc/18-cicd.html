CI/CD for Terraform

A Terraform pipeline is not a build pipeline with terraform apply at the end. The plan is the artefact, the human approval is the gate, and the whole design exists to guarantee one thing: what a human approved is exactly what gets applied.

By the end of this lesson you can

  • Explain why apply must not run unreviewed on every commit
  • Set up OIDC workload identity federation so no secret is stored anywhere
  • Build the plan-artefact → approval → apply flow in GitHub Actions and Azure DevOps
  • Enforce policy automatically on the plan JSON
  • Design environment promotion and per-environment approvals
  • Run scheduled drift detection

The shape of a Terraform pipeline

Why apply must not run unreviewed on every commit
  • Plans are not obvious from diffs. Removing one element from a list can destroy four resources. Changing a provider version can change a default. Only the plan shows this.
  • There is no rollback. Unlike application code, you cannot redeploy the previous version to undo a deleted storage account.
  • Infrastructure changes are often irreversible. Data is gone, a global name is released, a soft-deleted vault blocks recreation for 90 days.
  • Drift means the plan differs from what you expect. The same commit can produce a different plan tomorrow, because the cloud changed.

OIDC workload identity federation

The foundation. Instead of storing a client secret in your CI system, you register a federated credential on an Entra ID app registration that trusts tokens issued by your CI platform for a specific repository and environment.

setup.sh — run once by an administrator
#!/usr/bin/env bash
set -euo pipefail

APP_NAME="sp-terraform-analytics-prod"
REPO="contoso/analytics-platform"
SUB_ID="00000000-0000-0000-0000-000000000000"

# 1 · Create the app registration and its service principal.
APP_ID=$(az ad app create --display-name "$APP_NAME" --query appId -o tsv)
az ad sp create --id "$APP_ID"
SP_OID=$(az ad sp show --id "$APP_ID" --query id -o tsv)

# 2 · Federated credential for the PROD environment.
#     The subject must match GitHub's claim EXACTLY.
az ad app federated-credential create --id "$APP_ID" --parameters "{
  \"name\": \"github-prod\",
  \"issuer\": \"https://token.actions.githubusercontent.com\",
  \"subject\": \"repo:${REPO}:environment:prod\",
  \"audiences\": [\"api://AzureADTokenExchange\"]
}"

# 3 · A separate credential for pull requests — PLAN ONLY.
az ad app federated-credential create --id "$APP_ID" --parameters "{
  \"name\": \"github-pr\",
  \"issuer\": \"https://token.actions.githubusercontent.com\",
  \"subject\": \"repo:${REPO}:pull_request\",
  \"audiences\": [\"api://AzureADTokenExchange\"]
}"

# 4 · Least-privilege RBAC (Lesson 17).
az role assignment create --assignee "$SP_OID" --role "Contributor" \
  --scope "/subscriptions/$SUB_ID/resourceGroups/rg-analytics-prod-weu-01"

az role assignment create --assignee "$SP_OID" --role "Role Based Access Control Administrator" \
  --scope "/subscriptions/$SUB_ID/resourceGroups/rg-analytics-prod-weu-01"

az role assignment create --assignee "$SP_OID" --role "Storage Blob Data Contributor" \
  --scope "/subscriptions/$SUB_ID/resourceGroups/rg-tfstate-prod-weu-01/providers/Microsoft.Storage/storageAccounts/sttfstateprodweu01/blobServices/default/containers/tfstate"

echo "AZURE_CLIENT_ID = $APP_ID   # store as a repository variable — it is NOT a secret"
Two credentials, two privilege levels

Ideally the pull-request credential belongs to a different app registration with only Reader plus state read access — enough to plan, not enough to change anything. A pull request from a fork should never be able to obtain a token that can apply. If you use one identity for both, an attacker who can trigger a PR workflow has your apply permissions.

GitHub Actions

.github/workflows/terraform-plan.yml — on pull requests
name: Terraform Plan

on:
  pull_request:
    paths: ["terraform/**"]

permissions:
  id-token: write        # REQUIRED to request the OIDC token
  contents: read
  pull-requests: write   # to post the plan as a comment

env:
  TF_VERSION: "1.16.1"
  ARM_USE_OIDC: "true"
  ARM_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID_PLAN }}
  ARM_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}
  ARM_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }}

jobs:
  plan:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: terraform/environments/prod

    steps:
      - uses: actions/checkout@v4

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
          terraform_wrapper: false

      - name: Format check
        run: terraform fmt -check -recursive -diff
        working-directory: terraform

      - name: Init
        run: terraform init -backend-config=backend.hcl

      - name: Validate
        run: terraform validate

      - name: Plan
        id: plan
        run: |
          terraform plan -out=tfplan -lock-timeout=5m -no-color 2>&1 | tee plan.txt
          terraform show -json tfplan > plan.json

      - name: Policy check — no unexpected destroys
        run: |
          DESTROYS=$(jq '[.resource_changes[]
            | select(.change.actions | index("delete"))] | length' plan.json)
          echo "destroy_count=$DESTROYS" >> "$GITHUB_OUTPUT"
          if [ "$DESTROYS" -gt 0 ]; then
            echo "::warning::This plan destroys $DESTROYS resource(s)"
            jq -r '.resource_changes[]
              | select(.change.actions | index("delete"))
              | "  - " + .address' plan.json
          fi

      - name: Comment the plan on the PR
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            let plan = fs.readFileSync('terraform/environments/prod/plan.txt', 'utf8');
            // GitHub comments cap at 65 536 characters
            if (plan.length > 60000) {
              plan = plan.slice(0, 60000) + '\n\n... truncated — see the full plan in the job log';
            }
            const body = [
              '### Terraform plan — `prod`',
              '',
              '<details><summary>Show plan</summary>',
              '',
              '```terraform',
              plan,
              '```',
              '',
              '</details>',
            ].join('\n');
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body,
            });

      - name: Upload the plan artefact
        uses: actions/upload-artifact@v4
        with:
          name: tfplan-prod
          path: terraform/environments/prod/tfplan
          retention-days: 5     # short — the plan contains sensitive values
.github/workflows/terraform-apply.yml — on merge
name: Terraform Apply

on:
  push:
    branches: [main]
    paths: ["terraform/**"]

permissions:
  id-token: write
  contents: read

env:
  TF_VERSION: "1.16.1"
  ARM_USE_OIDC: "true"
  ARM_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}

jobs:
  dev:
    runs-on: ubuntu-latest
    environment: dev              # no reviewers configured — applies automatically
    env:
      ARM_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID_DEV }}
      ARM_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID_DEV }}
    defaults:
      run:
        working-directory: terraform/environments/dev
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - run: terraform init -backend-config=backend.hcl
      - run: terraform plan -out=tfplan -lock-timeout=10m
      - run: terraform apply -lock-timeout=10m tfplan

  prod:
    needs: dev                    # promotion: prod only after dev succeeds
    runs-on: ubuntu-latest
    environment: prod             # REQUIRED REVIEWERS configured in repo settings
    env:
      ARM_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID_PROD }}
      ARM_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID_PROD }}
    defaults:
      run:
        working-directory: terraform/environments/prod
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
      - run: terraform init -backend-config=backend.hcl

      - name: Plan
        run: terraform plan -out=tfplan -lock-timeout=10m

      - name: Fail on unapproved destroys
        run: |
          terraform show -json tfplan > plan.json
          DESTROYS=$(jq '[.resource_changes[]
            | select(.change.actions | index("delete"))] | length' plan.json)
          if [ "$DESTROYS" -gt 0 ] && [ "${{ vars.ALLOW_DESTROY }}" != "true" ]; then
            echo "::error::Plan destroys $DESTROYS resource(s). Set the ALLOW_DESTROY variable to override."
            jq -r '.resource_changes[] | select(.change.actions | index("delete")) | "  - " + .address' plan.json
            exit 1
          fi

      - name: Apply
        run: terraform apply -lock-timeout=10m tfplan
Where the approval gate actually lives

environment: prod is the mechanism. In the repository's Settings → Environments you configure required reviewers on prod; the job then pauses before its first step until a named human approves. Environment secrets and variables are also scoped there, so the prod client ID is not readable by a dev job. This is doing the real work — the YAML above is just wiring.

The compromise in the prod job above

It re-plans after the approval rather than applying the artefact from the pull request. That is a deliberate trade-off: the PR plan may be hours old and state may have moved, so applying it could fail or apply a stale change set. The mitigation is the destroy gate plus the fact that a human approved the same commit. The stricter alternative — download the PR's tfplan artefact and apply exactly that — gives a perfect approve-what-you-apply guarantee but fails if anything changed in between. Choose consciously; most teams re-plan and gate.

Azure DevOps

azure-pipelines.yml
trigger:
  branches: { include: [main] }
  paths:    { include: [terraform/**] }

pr:
  branches: { include: [main] }
  paths:    { include: [terraform/**] }

variables:
  TF_VERSION: "1.16.1"

stages:
  - stage: Validate
    jobs:
      - job: Checks
        pool: { vmImage: ubuntu-latest }
        steps:
          - task: TerraformInstaller@1
            inputs: { terraformVersion: $(TF_VERSION) }
          - script: terraform fmt -check -recursive -diff
            workingDirectory: terraform
            displayName: Format check

  - stage: Plan
    dependsOn: Validate
    jobs:
      - job: Plan
        pool: { vmImage: ubuntu-latest }
        steps:
          - task: TerraformInstaller@1
            inputs: { terraformVersion: $(TF_VERSION) }

          # The service connection uses Workload Identity Federation —
          # configure it as "Workload Identity federation (automatic)".
          - task: TerraformTaskV4@4
            displayName: Init
            inputs:
              provider: azurerm
              command: init
              workingDirectory: terraform/environments/prod
              backendServiceArm: sc-terraform-prod
              backendAzureRmResourceGroupName: rg-tfstate-prod-weu-01
              backendAzureRmStorageAccountName: sttfstateprodweu01
              backendAzureRmContainerName: tfstate
              backendAzureRmKey: analytics/prod.terraform.tfstate

          - task: TerraformTaskV4@4
            displayName: Plan
            inputs:
              provider: azurerm
              command: plan
              workingDirectory: terraform/environments/prod
              environmentServiceNameAzureRM: sc-terraform-prod
              commandOptions: '-out=$(Build.ArtifactStagingDirectory)/tfplan -lock-timeout=10m'

          - publish: $(Build.ArtifactStagingDirectory)
            artifact: tfplan

  - stage: Apply
    dependsOn: Plan
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      # A "deployment" job binds to an Environment, where approvals and
      # checks are configured — this is the gate.
      - deployment: Apply
        environment: prod
        pool: { vmImage: ubuntu-latest }
        strategy:
          runOnce:
            deploy:
              steps:
                - download: current
                  artifact: tfplan
                - task: TerraformInstaller@1
                  inputs: { terraformVersion: $(TF_VERSION) }
                - task: TerraformTaskV4@4
                  displayName: Apply the saved plan
                  inputs:
                    provider: azurerm
                    command: apply
                    workingDirectory: terraform/environments/prod
                    environmentServiceNameAzureRM: sc-terraform-prod
                    commandOptions: '$(Pipeline.Workspace)/tfplan/tfplan'
The platform-independent concepts

Strip away the YAML dialects and both pipelines are the same five ideas: federated authentication with no stored secret; a plan stage that produces a reviewable artefact; an automated policy check on that artefact; a human gate bound to a named environment; and an apply stage with a different, higher-privileged identity. Any CI system that can express those five will do.

Scheduled drift detection

.github/workflows/drift.yml
name: Drift Detection

on:
  schedule:
    - cron: "0 6 * * 1-5"
  workflow_dispatch:

permissions:
  id-token: write
  contents: read
  issues: write

jobs:
  drift:
    strategy:
      fail-fast: false
      matrix:
        environment: [dev, test, prod]
    runs-on: ubuntu-latest
    env:
      ARM_USE_OIDC: "true"
      ARM_CLIENT_ID: ${{ vars.AZURE_CLIENT_ID_PLAN }}
      ARM_TENANT_ID: ${{ vars.AZURE_TENANT_ID }}
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3

      - run: terraform init -backend-config=backend.hcl
        working-directory: terraform/environments/${{ matrix.environment }}

      - name: Plan
        id: plan
        continue-on-error: true
        working-directory: terraform/environments/${{ matrix.environment }}
        # -lock=false: a read-only check must not block a real deployment.
        # -detailed-exitcode: 0 = no changes, 1 = error, 2 = changes present.
        run: terraform plan -detailed-exitcode -lock=false -no-color

      - name: Open an issue if drift was detected
        if: steps.plan.outputs.exitcode == 2
        uses: actions/github-script@v7
        with:
          script: |
            await github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: `Drift detected in ${{ matrix.environment }}`,
              body: 'A scheduled plan found changes. See the workflow run for details.',
              labels: ['drift', '${{ matrix.environment }}'],
            });

Secrets in the pipeline

ValueSecret?Where it goes
ARM_CLIENT_IDNoA repository/environment variable. It is an identifier, useless without a matching federated credential.
ARM_TENANT_ID, ARM_SUBSCRIPTION_IDNoVariables.
ARM_CLIENT_SECRETYesNowhere — use OIDC and this does not exist.
Application secrets Terraform needsYesFetch at runtime from Key Vault with the pipeline identity, into TF_VAR_*. Never a repository secret, never a tfvars file.
The tfplan artefactYesShort retention, restricted access. It contains every planned attribute value.
Terraform stateYesThe backend, never an artefact.
Never set TF_LOG=DEBUG in a shared pipeline

Debug and trace logging include provider request and response bodies — which means secrets, access keys and connection strings land in the CI log, where they are typically readable by the whole engineering organisation and retained for months. If you must debug, do it in a private run and delete the logs afterwards.

Common mistakes

terraform apply -auto-approve on every push

The most common and most damaging. Nobody sees a plan, so nobody notices the destroy. It also re-plans at apply time, so even a reviewed PR is not what gets applied.

One identity for plan and apply

A pull request from a fork, or a contributor who can edit a workflow file, then has your apply permissions. Use separate app registrations: the PR identity gets Reader plus state read; the apply identity gets write access and is federated to an environment subject that pull requests cannot claim.

No lock timeout

Two runs overlap, the second fails instantly with a lock error, and someone force-unlocks it while the first is still applying. -lock-timeout=10m makes the second wait. Combine with concurrency limits so only one apply per environment runs at a time.

Not pinning the CLI version in CI

terraform_version: latest means a new minor release lands in your pipeline unannounced — and once a newer CLI writes the state file, older CLIs (including developer laptops) can no longer read it. Pin it, and upgrade deliberately.

Level 1 · Understand Critique this pipeline
.github/workflows/deploy.yml
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      ARM_CLIENT_ID: ${{ secrets.ARM_CLIENT_ID }}
      ARM_CLIENT_SECRET: ${{ secrets.ARM_CLIENT_SECRET }}
      ARM_TENANT_ID: ${{ secrets.ARM_TENANT_ID }}
      ARM_SUBSCRIPTION_ID: ${{ secrets.ARM_SUBSCRIPTION_ID }}
      TF_LOG: DEBUG
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform init
      - run: terraform apply -auto-approve

Find six problems.

Show answer
  1. apply -auto-approve with no plan step or review. Nobody ever sees what will change. A merged PR that removes one list element silently deletes containers.
  2. A stored client secret. Use OIDC — no secret, nothing to rotate, and the trust is scoped to a repository and environment.
  3. TF_LOG: DEBUG. Provider request bodies — including secrets and storage keys — are written to a log the whole organisation can read.
  4. No environment:, so no approval gate. Merging to main deploys straight to production.
  5. No CLI version pinning. A new release arrives unannounced, and once it writes state, older CLIs cannot read it.
  6. No lock timeout and no concurrency control. Two merges in quick succession produce overlapping applies and a lock error.

Also worth noting: no fmt, no validate, no policy check on the plan, no environment separation, and it deploys prod without ever having deployed dev.

Level 2 · Implement A policy gate on plan JSON

Write a script that fails the build when a plan does any of the following, and prints exactly what and why:

  • Destroys or replaces any storage account or Key Vault.
  • Sets public_network_access_enabled to true on any resource.
  • Creates a role assignment at subscription scope.
  • Creates any resource without a cost_center tag.
Show answer
scripts/policy-check.sh
#!/usr/bin/env bash
set -euo pipefail

PLAN_JSON="${1:-plan.json}"
FAILED=0

fail() { echo "::error::$1"; FAILED=1; }

# --- 1 · destruction of stateful resources ---
STATEFUL=$(jq -r '.resource_changes[]
  | select(.type == "azurerm_storage_account" or .type == "azurerm_key_vault")
  | select(.change.actions | index("delete"))
  | .address' "$PLAN_JSON")

if [ -n "$STATEFUL" ]; then
  fail "Plan destroys or replaces stateful resources:"
  echo "$STATEFUL" | sed 's/^/    /'
fi

# --- 2 · public network access being enabled ---
PUBLIC=$(jq -r '.resource_changes[]
  | select(.change.after.public_network_access_enabled == true)
  | select(.change.before.public_network_access_enabled != true)
  | .address' "$PLAN_JSON")

if [ -n "$PUBLIC" ]; then
  fail "Plan enables public network access on:"
  echo "$PUBLIC" | sed 's/^/    /'
fi

# --- 3 · subscription-scope role assignments ---
BROAD=$(jq -r '.resource_changes[]
  | select(.type == "azurerm_role_assignment")
  | select(.change.actions | index("create"))
  | select(.change.after.scope | test("^/subscriptions/[^/]+$"))
  | "\(.address) → \(.change.after.role_definition_name)"' "$PLAN_JSON")

if [ -n "$BROAD" ]; then
  fail "Plan creates subscription-scoped role assignments:"
  echo "$BROAD" | sed 's/^/    /'
fi

# --- 4 · missing cost_center tag on new resources ---
UNTAGGED=$(jq -r '.resource_changes[]
  | select(.change.actions == ["create"])
  | select(.change.after | has("tags"))
  | select((.change.after.tags // {}) | has("cost_center") | not)
  | .address' "$PLAN_JSON")

if [ -n "$UNTAGGED" ]; then
  fail "New resources missing a cost_center tag:"
  echo "$UNTAGGED" | sed 's/^/    /'
fi

if [ "$FAILED" -eq 1 ]; then
  echo ""
  echo "Policy check failed. Fix the issues above, or document an exception."
  exit 1
fi

echo "Policy check passed."
Two refinements worth knowing

Check 4 uses has("tags") so it does not fail on resource types that have no tags at all. And check 2 compares before and after, so it only fires on a resource newly becoming public rather than on every plan touching an already-public resource. For anything more elaborate than this, move to a real policy engine — Conftest with OPA, or Azure Policy evaluated at deployment time. Lesson 19.

Level 2 · Implement Write the pull-request plan workflow

Write a GitHub Actions workflow that runs on pull requests touching terraform/: format check, validate, plan, a policy check, and the plan posted as a PR comment.

It must authenticate with OIDC and no stored secret, and the identity it uses must be unable to change anything.

.github/workflows/terraform-plan.yml
name: Terraform Plan

on:
  pull_request:
    paths: ["terraform/**"]

# Least privilege for the GITHUB token, separate from Azure RBAC.
permissions:

concurrency:

  ARM_SUBSCRIPTION_ID: ${{ vars.AZURE_SUBSCRIPTION_ID }}

      run:
        working-directory: terraform/environments/prod

    steps:

      - uses: hashicorp/setup-terraform@v3
        with:
          terraform_version: ${{ env.TF_VERSION }}
          terraform_wrapper: false     # so we can capture raw stdout

        run: terraform fmt -check -recursive -diff

        run: terraform init -backend-config=backend.hcl

      - name: Policy check
        run: ../../../scripts/policy-check.sh plan.json

      - name: Comment the plan
        uses: actions/github-script@v7
        with:
          script: |
            const fs = require('fs');
            let plan = fs.readFileSync('terraform/environments/prod/plan.txt', 'utf8');
            if (plan.length > 60000) {
              plan = plan.slice(0, 60000) + '\n... truncated, see the job log';
            }
            await github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `### Terraform plan\n\n<details><summary>Show</summary>\n\n` +
                    '```terraform\n' + plan + '\n```\n\n</details>',
            });

      - name: Upload the plan

          name: tfplan-prod

Three security decisions worth naming. permissions: is set explicitly rather than inheriting the repository default, which is often write-all. The Azure identity is plan-only, so even someone who edits the workflow in a pull request cannot use it to change infrastructure. And the plan artefact has a short retention because it contains every planned attribute value, including sensitive ones.

concurrency with cancel-in-progress avoids two plans for the same branch queueing on the state lock — and terraform_wrapper: false is needed to capture clean stdout for the comment.

Level 2 · Implement Write the policy gate

Write scripts/policy-check.sh, taking a plan JSON file and failing the build on any of:

  • Destroying or replacing a storage account or Key Vault.
  • Newly enabling public_network_access_enabled.
  • Creating a role assignment at subscription scope.
  • Creating a taggable resource with no cost_center tag.

It must report every violation, not stop at the first, and must not fire on resources that were already non-compliant before this change.

Show solution
scripts/policy-check.sh
#!/usr/bin/env bash
set -euo pipefail

PLAN_JSON="${1:?usage: policy-check.sh <plan.json>}"
FAILED=0

fail() { echo "::error::$1"; FAILED=1; }

# 1 - destruction or replacement of stateful resources
STATEFUL=$(jq -r '.resource_changes[]
  | select(.type == "azurerm_storage_account" or .type == "azurerm_key_vault")
  | select(.change.actions | index("delete"))
  | "  - \(.address) [\(.change.actions | join(","))]"' "$PLAN_JSON")

if [ -n "$STATEFUL" ]; then
  fail "Plan destroys or replaces stateful resources:"
  echo "$STATEFUL"
fi

# 2 - NEWLY enabling public access. Comparing before and after means an
#     already-public resource does not fail every unrelated build.
PUBLIC=$(jq -r '.resource_changes[]
  | select(.change.after.public_network_access_enabled == true)
  | select((.change.before.public_network_access_enabled // false) != true)
  | "  - \(.address)"' "$PLAN_JSON")

if [ -n "$PUBLIC" ]; then
  fail "Plan enables public network access on:"
  echo "$PUBLIC"
fi

# 3 - role assignments at subscription scope
BROAD=$(jq -r '.resource_changes[]
  | select(.type == "azurerm_role_assignment")
  | select(.change.actions | index("create"))
  | select(.change.after.scope | test("^/subscriptions/[^/]+$"))
  | "  - \(.address) -> \(.change.after.role_definition_name // "custom role")"' "$PLAN_JSON")

if [ -n "$BROAD" ]; then
  fail "Plan creates subscription-scoped role assignments:"
  echo "$BROAD"
fi

# 4 - new taggable resources without cost_center.
#     has("tags") skips resource types that have no tags at all.
UNTAGGED=$(jq -r '.resource_changes[]
  | select(.change.actions == ["create"])
  | select(.change.after | type == "object" and has("tags"))
  | select((.change.after.tags // {}) | has("cost_center") | not)
  | "  - \(.address)"' "$PLAN_JSON")

if [ -n "$UNTAGGED" ]; then
  fail "New resources missing a cost_center tag:"
  echo "$UNTAGGED"
fi

if [ "$FAILED" -eq 1 ]; then
  echo ""
  echo "Policy check failed. Fix the issues above, or document an approved exception."
  exit 1
fi

echo "Policy check passed."

Two details that make this usable rather than annoying. Every check runs before exiting, so a reviewer sees all four categories at once instead of fixing them one build at a time. And check 2 compares before against after, so a resource that was already public does not fail every unrelated pull request — a gate that cries wolf gets disabled.

This is the highest-value automated check in the whole course: static analysis reads HCL and cannot resolve variables or module inputs, whereas the plan has concrete values for exactly the resources that will change. For anything more elaborate, move to Conftest with OPA rather than growing the jq.

Level 3 · Troubleshoot OIDC login fails
error
Error: building account: could not acquire access token to parse claims:
AADSTS70021: No matching federated identity record found for presented
assertion. Assertion Issuer: 'https://token.actions.githubusercontent.com'.
Assertion Subject: 'repo:contoso/analytics-platform:ref:refs/heads/main'.
Assertion Audience: 'api://AzureADTokenExchange'.

The federated credential was created with subject repo:contoso/analytics-platform:environment:prod. Diagnose and fix, and say what you would check if that were not the cause.

Show answer

Diagnosis: the subject does not match. The error helpfully prints what was presented — repo:contoso/analytics-platform:ref:refs/heads/main — against a credential registered for ...:environment:prod. GitHub only emits the environment: form when the job declares environment: prod. This job does not, so it got the branch form instead.

Fix — add the environment to the job (also the right fix, because it gives you the approval gate):

fix
jobs:
  apply:
    runs-on: ubuntu-latest
    environment: prod          # ← now the subject claim is environment:prod
    permissions:
      id-token: write          # ← without this, no token is issued at all
      contents: read

The alternative — registering a second federated credential for repo:contoso/analytics-platform:ref:refs/heads/main — also works but is worse: it means any push to main can deploy production with no approval gate.

If the subject were not the cause, check in this order:

  1. permissions: id-token: write is missing. Without it GitHub issues no OIDC token, and the error is a different one about no authentication method being found.
  2. Audience mismatch. It must be api://AzureADTokenExchange. The Azure login action sets this by default; a hand-rolled token request may not.
  3. Wrong ARM_CLIENT_ID. The federated credential is registered on one app registration; the workflow presented a different client ID.
  4. Wrong tenant. The exchange happens against a specific tenant.
  5. RBAC. If login succeeds but operations fail with 403, authentication worked and the problem is authorization — a Lesson 08 problem, not an OIDC one.

The general skill: read the assertion claims in the error. Azure tells you exactly what it received, and comparing that against what you registered resolves nearly every federation failure.

Interview questions

Describe a good Terraform CI/CD pipeline.

Two pipelines. On a pull request: format check, validate, lint and security scan, then a plan saved as an artefact, an automated policy check on the plan JSON, and the plan posted as a PR comment so reviewers see consequences rather than only the diff. On merge: apply to dev automatically, then apply to production behind a manual approval bound to a protected environment. Authentication is OIDC workload identity federation with separate identities for plan and apply, both least-privileged. Plus a scheduled drift-detection run using -detailed-exitcode and -lock=false.

Why shouldn't terraform apply run on every commit?

Because plans are not obvious from diffs — removing one list element can destroy four resources, and a provider version bump can change a default — and because there is no rollback. You cannot redeploy the previous version to bring back a deleted storage account. Infrastructure changes are frequently irreversible: data is gone, a globally unique name is released, a soft-deleted vault blocks recreation for up to 90 days. And drift means the same commit can produce a different plan tomorrow. A human looking at a plan is the last checkpoint before any of that.

What is workload identity federation and why use it?

A trust relationship registered on an Entra ID app registration that accepts short-lived OIDC tokens from an external issuer — GitHub Actions, Azure DevOps — for a specific subject such as repo:org/repo:environment:prod. The runner exchanges its OIDC token for an Azure access token. No secret is stored, nothing needs rotating, and because the trust is scoped to a subject claim, a feature branch cannot obtain a token that deploys production even if someone edits a workflow file. It replaces the client-secret pattern, which is a long-lived password sitting in a CI system.

Why save the plan to a file and apply that file?

So that what a human approved is exactly what gets applied. Bare terraform apply computes a fresh plan, so any change to code or infrastructure between review and apply reaches production unreviewed. Applying a saved plan also errors out if state has moved underneath it, which is a useful safety property. The trade-off is that a stale plan can fail, so many teams re-plan after approval and rely on the policy gate plus the fact that the approver signed off on the same commit — that is a conscious choice, not an oversight.

How do you handle secrets in a Terraform pipeline?

Mostly by not having them. OIDC removes the client secret entirely. Client ID, tenant ID and subscription ID are identifiers, not secrets, and belong in variables. Where Terraform genuinely needs a secret value, fetch it at runtime from Key Vault using the pipeline's own identity into a TF_VAR_ environment variable — never a repository secret, never a committed tfvars file. And treat the plan artefact and the state file as secrets themselves, because both contain plaintext values. I would also never enable TF_LOG=DEBUG in a shared pipeline, since it writes provider request bodies to the log.

How would you prevent a pipeline from accidentally destroying production?

Layers, none of which is sufficient alone. A policy gate parsing the plan JSON that fails the build on any delete action unless a human sets an explicit override variable. A required-reviewer approval bound to the production environment. prevent_destroy on data-bearing resources so the plan fails before CI even sees it. Azure resource locks, which work outside Terraform. Separate state and separate least-privileged identities per environment, so a dev pipeline cannot reach production at all. And the plan posted on the pull request, so the destroy is visible to a human before merge.

Key takeaways

  • Two pipelines: plan on pull requests, apply on merge. Different identities, different permissions.
  • OIDC federation removes the stored secret. The subject claim is the security boundary.
  • The plan is the reviewable artefact — post it on the PR, and treat the file itself as a secret.
  • Automate the policy check on plan JSON. Fail on unexpected destroys.
  • The approval gate lives in the CI platform's environment feature, not in the YAML.
  • Pin the CLI version, set a lock timeout, and never enable debug logging in a shared pipeline.

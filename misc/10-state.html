Terraform state & remote backends

State is the concept that separates people who use Terraform from people who understand it. Nearly every confusing behaviour — “it wants to recreate everything”, “it says it already exists”, “the plan is empty but the resource is gone” — is a state question wearing a disguise.

By the end of this lesson you can

  • Read a state file and explain the address-to-resource-ID mapping
  • Define drift precisely, and detect it deliberately with -refresh-only
  • Configure the Azure Storage backend correctly, including the bootstrap problem
  • Argue for a state isolation strategy in terms of blast radius
  • Recover from a lost, locked or corrupted state file

What state is

A JSON document recording, for every resource Terraform manages, the mapping between its configuration address and its real resource ID — plus a cached copy of every attribute the provider last read.

terraform.tfstate — the essential shape

  "terraform_version": "1.16.1",
  "serial": 42,
  "lineage": "8f2c1e4a-3b6d-4c9e-8a1f-2d5e7c9b0a3f",
  "outputs": {
    "lake_dfs_endpoint": {
      "value": "https://stanalyticsdevweu01.dfs.core.windows.net/",

FieldMeaning
versionState file format version (4 for years). Not your Terraform version.
terraform_versionThe CLI that last wrote it. An older CLI refuses to open state written by a newer one — a common CI failure when someone upgrades locally.
serialIncremented on every write. The backend uses it to detect that state moved underneath you.
lineageA GUID identifying this state's history. If it changes, you are looking at a different state — Terraform warns loudly, because it usually means someone pointed at the wrong backend.
modemanaged for resources, data for data sources.
instancesOne entry per instance. A plain resource has one; count adds index_key; for_each adds a string key.
dependenciesThe graph edges, recorded so Terraform can destroy in the right order even after you delete the configuration.

Why state exists — four jobs

Why Terraform cannot just query Azure instead

A reasonable question, and the answer sharpens the mental model. Suppose Terraform listed every resource in the subscription on each run. It still could not answer:

  • Which of these 400 resources are mine? There is no reliable marker. Tags are advisory and can be edited.
  • Which configuration address does this resource correspond to? Two storage accounts with identical settings are indistinguishable by inspection.
  • What did I create that has since been deleted? Detecting deletion requires knowing what should be there.
  • In what order must I destroy things after the code is gone? The dependencies were in the configuration you just deleted.

State is the answer to “what do I own, and what is it called in my code”. That is why deleting it is catastrophic rather than inconvenient.

Renaming a block is a state operation

Changing resource "azurerm_storage_account" "lake" to "data_lake" makes Terraform plan to destroy lake and create data_lake — because as far as state is concerned, one address disappeared and another appeared. The fix is a moved block, which renames the address in state without touching Azure. Lesson 16.

Drift

Drift is any difference between what state records and what actually exists in Azure — caused by something other than Terraform.

Detecting drift deliberately

refresh-only
# Show what has changed in Azure, WITHOUT proposing to change anything back.
terraform plan -refresh-only

# Accept reality into state (does not touch Azure).
terraform apply -refresh-only
refresh-only output
Note: Objects have changed outside of Terraform

Terraform detected the following changes made outside of Terraform since the
last "terraform apply" which may have affected this plan:

  # azurerm_storage_account.lake has changed
  ~ resource "azurerm_storage_account" "lake" {
        id                       = "/subscriptions/.../stanalyticsdevweu01"
      ~ account_replication_type = "LRS" -> "GRS"
      ~ tags                     = {
          + "AppliedByPolicy" = "true"
        }
    }

This is a refresh-only plan, so Terraform will not take any actions to undo
these changes.
The difference between the two commands

terraform plan refreshes and then proposes changes to make Azure match your code — it wants to revert the drift. terraform plan -refresh-only refreshes and reports, proposing only to update state. Use refresh-only when you want to understand a change before deciding whether the code or the cloud is right. This is the correct first move whenever a plan surprises you.

Automated drift detection

.github/workflows/drift.yml (excerpt)
on:
  schedule:
    - cron: "0 6 * * 1-5"   # weekday mornings

jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - run: terraform init -backend-config=env/prod.backend.hcl
      - id: plan
        # exit 0 = no changes, 1 = error, 2 = changes present
        run: terraform plan -var-file=env/prod.tfvars -detailed-exitcode -lock=false
        continue-on-error: true
      - if: steps.plan.outputs.exitcode == '2'
        run: echo "::warning::Drift detected in production"

Note -lock=false: a read-only drift check should not block a real deployment by holding the lock.

Do not reflexively run force-unlock

The lock exists because another operation is in progress. Breaking it while an apply is mid-flight means two processes writing state concurrently, which is how state gets corrupted.

First, read the lock info: who holds it and when was it created. If the timestamp is recent and the holder is a running pipeline, wait. Only if the process is genuinely dead — a cancelled CI job, a crashed laptop — should you run terraform force-unlock <LOCK_ID>. Prefer -lock-timeout=10m on your commands so concurrent runs queue instead of failing.

The Azure Storage backend

backend.tf
terraform {
  backend "azurerm" {
    resource_group_name  = "rg-tfstate-prod-weu-01"
    storage_account_name = "sttfstateprodweu01"
    container_name       = "tfstate"
    key                  = "analytics/prod.terraform.tfstate"

    # Authenticate the DATA plane with Entra ID rather than an account key.
    use_azuread_auth = true

    # In CI, federated credentials — no secrets stored anywhere.
    use_oidc  = true
    tenant_id = "00000000-0000-0000-0000-000000000000"
    client_id = "00000000-0000-0000-0000-000000000000"
  }
}
use_azuread_auth = true is not optional in practice

Without it, the backend authenticates to the state blob using a storage account key, which means every engineer and pipeline needs that key — a shared secret granting full access to every state file in the account. With it, access is governed by Azure RBAC (Storage Blob Data Contributor on the state container), which is scopeable, auditable and revocable. It also lets you set shared_access_key_enabled = false on the state storage account itself.

Partial configuration — one codebase, many environments

The backend block cannot use variables or expressions: it is read before variable evaluation. The supported approach is partial configuration — omit the varying parts and supply them at init.

backend.tf — the invariant part
terraform {
  backend "azurerm" {
    use_azuread_auth = true
    # everything else comes from -backend-config
  }
}
env/prod.backend.hcl
resource_group_name  = "rg-tfstate-prod-weu-01"
storage_account_name = "sttfstateprodweu01"
container_name       = "tfstate"
key                  = "analytics/prod.terraform.tfstate"
switching environments
terraform init -reconfigure -backend-config=env/prod.backend.hcl
terraform plan -var-file=env/prod.tfvars -out=tfplan
The -reconfigure trap

Terraform caches the backend configuration in .terraform/. Switching environments without -reconfigure (or -migrate-state) means Terraform may keep using the previous backend — so you plan dev's code against prod's state, or vice versa. This is a genuine cause of production incidents. It is also the strongest argument for a directory per environment (Lesson 17), where the backend is committed per directory and cannot be confused.

The bootstrap problem

The backend must exist before Terraform can use it. So who creates the storage account that holds the state? Three answers, and the third is what most teams do.

A · Create it manually, once

A documented az script, run once per subscription by an administrator. Not managed by Terraform at all. Simple, honest, and the state backend genuinely is foundational infrastructure that should not be destroyable by a Terraform apply.

B · A bootstrap configuration with local state

A small separate configuration that creates the state account, keeping its own state locally and committing it (it contains nothing sensitive if you disable shared keys). Reproducible, slightly circular.

C · Bootstrap, then migrate

Run once with local state, then add the backend block and run terraform init -migrate-state so the configuration ends up managing its own backend. Elegant but creates a resource that, if destroyed, takes its own state with it.

bootstrap.sh — option A, the pragmatic choice
#!/usr/bin/env bash
set -euo pipefail

LOCATION="westeurope"
RG="rg-tfstate-prod-weu-01"
SA="sttfstateprodweu01"
CONTAINER="tfstate"

az group create --name "$RG" --location "$LOCATION"

az storage account create \
  --name "$SA" --resource-group "$RG" --location "$LOCATION" \
  --sku Standard_GZRS \
  --kind StorageV2 \
  --min-tls-version TLS1_2 \
  --https-only true \
  --allow-blob-public-access false \
  --allow-shared-key-access false          # RBAC only — pairs with use_azuread_auth

# Versioning + soft delete: your undo button for state corruption
az storage account blob-service-properties update \
  --account-name "$SA" --resource-group "$RG" \
  --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 30 \
  --enable-container-delete-retention true --container-delete-retention-days 30

az storage container create \
  --name "$CONTAINER" --account-name "$SA" --auth-mode login

# A management lock so nobody deletes the state account by accident
az lock create --name "no-delete-tfstate" --lock-type CanNotDelete \
  --resource-group "$RG"
Blob versioning is the feature that will save you

With versioning enabled, every state write creates a new blob version. A corrupted or truncated state file is then recoverable by promoting the previous version — a two-minute fix instead of a day of terraform import. Turn it on before you need it. The snapshot = true backend option gives similar protection at the Terraform level.

Securing state

Read access to state is equivalent to read access to every secret

State contains storage account keys, generated passwords, Key Vault secret values you created or read, and connection strings — all in plaintext. Giving the whole engineering team Storage Blob Data Reader on the state container “so they can debug” hands them every credential in the platform. Grant it to the deployment identity and a small break-glass group only.

Why state must never go in git

ProblemConsequence
Plaintext secretsEvery credential in the platform is now in git history, permanently, readable by everyone with clone access.
No lockingTwo applies can run simultaneously against the same infrastructure with no protection.
Merge conflictsGit will happily produce a syntactically valid but semantically corrupt state file. There is no sensible way to merge two state files.
Stale readsAnyone who has not pulled is planning against out-of-date state, and their apply will try to recreate resources that exist.
It is not sourceState is generated data, like a build artefact or a database. Source control is for source.

State isolation and blast radius

“How many state files should we have?” is really “how large should a single failure be?”

Split state along lines where change frequency or ownership differ:

a typical layering for a data platform
tfstate container
├── platform/prod.tfstate        ← VNet, DNS zones, Key Vault      (rarely changes, network team)
├── data/prod.tfstate            ← ADLS, RBAC, Databricks workspace (weekly, platform team)
├── workloads/prod.tfstate       ← Functions, jobs, pipelines       (daily, product teams)
├── platform/dev.tfstate
├── data/dev.tfstate
└── workloads/dev.tfstate

Reading across state boundaries

option 1 — terraform_remote_state
data "terraform_remote_state" "platform" {
  backend = "azurerm"

  config = {
    resource_group_name  = "rg-tfstate-prod-weu-01"
    storage_account_name = "sttfstateprodweu01"
    container_name       = "tfstate"
    key                  = "platform/prod.tfstate"
    use_azuread_auth     = true
  }
}

resource "azurerm_private_endpoint" "lake" {
  subnet_id = data.terraform_remote_state.platform.outputs.privatelink_subnet_id
  # ...
}
The catch with terraform_remote_state

It requires read access to the entire other state file — including all its secrets — merely to read one output. That is a significant privilege escalation for what looks like a lookup. It also couples the two configurations tightly: renaming an output in the platform state breaks the consumer.

option 2 — data sources (usually better)
# Query Azure directly. No access to anyone else's state required.
data "azurerm_subnet" "privatelink" {
  name                 = "snet-privatelink-prod-weu-01"
  virtual_network_name = "vnet-platform-prod-weu-01"
  resource_group_name  = "rg-platform-prod-weu-01"
}

resource "azurerm_private_endpoint" "lake" {
  subnet_id = data.azurerm_subnet.privatelink.id
  # ...
}

The contract becomes the resource name rather than another team's state layout — looser coupling and far less privilege. The trade-off is that names must be predictable, which is exactly what a naming convention is for. A third option, cleaner still at scale, is publishing values to a well-known Key Vault or an Azure App Configuration store that both sides read.

Exercises

Level 1 · Understand Four state-shaped failures

Explain what happened and what to do:

  1. An engineer deletes terraform.tfstate locally, then runs apply. It fails partway with StorageAccountAlreadyTaken.
  2. Two engineers run apply at the same time against local state on their own laptops.
  3. A plan shows 0 to add, 0 to change, 0 to destroy — but the resource group was deleted in the portal an hour ago.
  4. CI fails with state snapshot was created by Terraform v1.16.1, which is newer than current v1.9.8.
Show answer
  1. Terraform believes it has created nothing, so it plans to create everything. Resources with globally unique names fail immediately; others may be created as duplicates. Recovery is importing each existing resource back into state — hours of work. This is the argument for a remote backend with versioning: you would simply restore the previous blob version.
  2. Two divergent states and a race. Each laptop's state records only its own creations; each apply may partially overwrite the other's work. There is no locking because a local file lock does not span machines. Neither state now reflects reality. This is the reason remote backends exist.
  3. The plan was run with -refresh=false, or the refresh failed silently. Without refresh, Terraform diffs configuration against stale state and sees no difference. Run terraform plan -refresh-only to see the truth — it will report the resource as gone.
  4. State format is forward-incompatible. Someone ran a newer CLI locally, which upgraded the state file; the older CI runner now refuses to read it. Fix by pinning the CLI version in CI to match (use required_version plus a version manager like tfenv). Do not try to downgrade state — there is no supported path.

Level 3 · Troubleshoot Prod plan wants to create everything

A pipeline that has run cleanly for months suddenly plans 47 to add, 0 to change, 0 to destroy against production. Nothing was deleted in Azure — the platform is serving traffic normally. The only recent change was a refactor moving environment configuration into env/*.backend.hcl files.

What happened, how do you confirm it, and how do you fix it without an outage?

Show answer

Diagnosis. Terraform is reading an empty or different state file. Almost certainly the backend key changed during the refactor — say from prod.terraform.tfstate to analytics/prod.terraform.tfstate. Terraform found no blob at the new key, created a fresh empty state, and therefore believes nothing exists.

Confirm — do not apply.

investigation
# How many resources does the current backend think it manages?
terraform state list | wc -l          # expect 0 or a small number

# What blobs actually exist in the container?
az storage blob list \
  --account-name sttfstateprodweu01 \
  --container-name tfstate \
  --auth-mode login -o table

# Confirm which backend this working directory is bound to
cat .terraform/terraform.tfstate | jq '.backend.config'

You will find the real state sitting at the old key, with serial in the hundreds and lineage matching the platform's history.

Fix. Point the configuration back at the correct key:

env/prod.backend.hcl
key = "prod.terraform.tfstate"   # the original, where the real state lives
verify
rm -rf .terraform
terraform init -backend-config=env/prod.backend.hcl
terraform state list | wc -l    # should now be 47
terraform plan -var-file=env/prod.tfvars   # should be "No changes"

If you genuinely want the new key, migrate rather than repoint: terraform init -migrate-state -backend-config=env/prod.backend.hcl, which copies the state blob and confirms first.

What would have happened on apply

Terraform would have tried to create 47 resources that already exist. Globally unique names (the storage account, the Key Vault) would fail immediately. Anything that can be duplicated would be created twice. And the new state would record only the successes, leaving you with two divergent state files and a partially duplicated production environment. Preventing exactly this is why a plan showing an unexpected number of creations must stop the pipeline.

Real-world scenarios

Scenario 4 from the brief

“A developer manually deleted a Terraform-managed resource in Azure.”

  1. Run terraform plan -refresh-only to see precisely what Terraform now believes is missing, without proposing any change.
  2. The next ordinary plan will show + create for that resource — Terraform's job is to restore the configured state.
  3. Decide whether recreating is safe. For a stateless resource — an NSG rule, a role assignment — just apply. For anything holding data, recreating gives you an empty resource, which may be worse than the deletion.
  4. If it should stay deleted, remove it from the configuration and from state (terraform state rm), or the next plan keeps proposing to recreate it.
  5. Prevent recurrence: Azure resource locks on production resource groups, prevent_destroy on data-bearing resources, and portal write access removed in favour of the deployment pipeline.

The judgement being tested is step 3 — recognising that Terraform's default answer, “recreate it”, is not always the right one.

“State is corrupted — the file is truncated and terraform plan fails to parse it.”

  1. Stop all pipelines. Another write could overwrite the last good version.
  2. Restore from blob versioning — the fastest path by far, and the reason you enabled it:

The takeaway an interviewer wants: blob versioning turns a catastrophe into an inconvenience, and it costs nothing to enable.

Interview questions

What is Terraform state and why does it exist?

A JSON document mapping each configuration address to the real resource it manages, plus a cached copy of that resource's attributes and its dependencies. It exists because there is no way to derive that mapping from the cloud: Azure cannot tell you which of 400 resources correspond to azurerm_storage_account.lake, which resources Terraform owns versus which another team created, or what has been deleted since the last run. It also records dependencies so Terraform can destroy in the correct order even after the configuration is deleted, and it enables locking so a team can share one source of truth.

Why shouldn't state be committed to git?

It contains every resource attribute in plaintext, including storage account keys, generated passwords and Key Vault secret values — committing it puts every credential in the platform into permanent git history. There is also no locking, so concurrent applies are unprotected; state files cannot be meaningfully merged, so git will happily produce a corrupt one; and anyone who has not pulled plans against stale state. Fundamentally it is generated data, not source.

How would you secure Terraform state on Azure?

A dedicated storage account with shared_access_key_enabled = false so access is Entra ID only, and use_azuread_auth = true in the backend to match. Blob versioning and soft delete for recovery. Public network access disabled with a private endpoint where the runners can reach it. RBAC scoped to the state container, granted to the deployment identity and a small break-glass group only — read access to state is equivalent to read access to every secret. A CanNotDelete management lock, diagnostic logging to Log Analytics, and separate containers or accounts per environment so a container-scoped role cannot reach production state.

What is state locking and how does the Azure backend implement it?

A mutex preventing two operations from writing state simultaneously, which would corrupt it. The azurerm backend uses a native blob lease on the state blob — no additional infrastructure, unlike the S3 backend which historically needed a DynamoDB table. If a lock is held you get an error naming the holder and the time it was acquired. The right response is usually to wait or use -lock-timeout; force-unlock should only be used when the holding process is genuinely dead, since breaking a live lock is how state gets corrupted.

What is drift and how do you detect it?

A difference between what state records and what actually exists in the cloud, caused by something other than Terraform — a portal edit, an Azure Policy appending tags, autoscaling, or another configuration managing the same resource. Terraform detects it in the refresh phase of every plan. To investigate it without proposing to revert it, use terraform plan -refresh-only. For continuous detection I would run a scheduled plan with -detailed-exitcode and alert on exit code 2, using -lock=false so the check does not block deployments.

How many state files should a platform have?

It is a blast-radius decision. One state for everything means slow plans, one lock blocking the whole team, and anyone who can change a tag being able to destroy production. Splitting per environment is non-negotiable. Beyond that I would split along seams where change frequency or ownership differ — typically a networking layer that changes rarely, a data-platform layer, and a workloads layer that changes daily. The cost is cross-state references, which I would satisfy with plain data sources querying Azure rather than terraform_remote_state, since the latter requires read access to the whole other state file and therefore all its secrets.

What happens if someone manually changes an Azure resource?

The refresh phase of the next plan picks up the new value, and Terraform proposes to change it back, because the configuration is the source of truth. For most attributes that is a harmless in-place update. The dangerous case is a change to a ForceNew attribute, where reverting means destroying and recreating the resource — on a storage account, that is data loss. Which is why the right first response to an unexpected plan is -refresh-only, to understand the change before deciding whether the code or the cloud should win.

Key takeaways

  • State maps configuration addresses to real resource IDs. Nothing else can supply that mapping.
  • State contains every attribute in plaintext. Read access to state ≈ read access to every secret.
  • Remote backend, always, for anything real. On Azure: blob storage with use_azuread_auth = true.
  • Enable blob versioning before you need it — it converts state corruption from a disaster into a two-minute restore.
  • Locking is a blob lease. Read the lock info before ever running force-unlock.
  • plan -refresh-only is the correct first move whenever a plan surprises you.
  • Split state by environment always, and by ownership/change-frequency seams beyond that.

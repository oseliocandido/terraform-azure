Production Terraform

There is no single correct repository structure, and anyone who tells you otherwise is selling something. What there is: a set of trade-offs, and one organising principle — blast radius — that resolves most of them.

By the end of this lesson you can

  • Evaluate repository structures against blast radius, coupling and cognitive load
  • Choose a state isolation strategy and defend it
  • Design naming and tagging conventions that survive contact with reality
  • Run a provider upgrade safely
  • Review someone else's Terraform pull request effectively
  • Scope a deployment identity to least privilege

The organising principle

Blast radius

How much can one mistake destroy? That question answers most structural decisions. A single state file containing your entire platform means a corrupted state, a bad apply or an over-permissioned pipeline can take everything. Splitting reduces the maximum damage — at the cost of coordination between the pieces. Every structure below is a different point on that trade-off.

Four repository structures

A · Flat single root

structure
terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── versions.tf
└── backend.tf

Works when

  • One environment, one team, a proof of concept
  • Under about thirty resources
  • Nothing in it is production

Breaks when

  • You add a second environment — there is nowhere to put the difference
  • Plans get slow because every resource is refreshed
  • Anyone who can change a tag can destroy production

B · One root, per-environment tfvars and backend

structure
terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── versions.tf
├── backend.tf              partial — key comes from -backend-config
├── modules/
│   ├── storage/
│   └── networking/
└── env/
    ├── dev.tfvars      dev.backend.hcl
    ├── test.tfvars     test.backend.hcl
    └── prod.tfvars     prod.backend.hcl
ProCon
Zero code duplication — one change reaches every environmentProd runs the same code path as dev, so a mistake can reach prod as easily
Structural drift between environments is impossibleEnvironments cannot differ structurally without conditionals accumulating
Small repository, easy to navigateForgetting -reconfigure plans dev's code against prod's state. This is a real incident, not a theoretical one
Fast to add an environmentOne pipeline must be parameterised carefully; approval gates are harder to differentiate

C · Directory per environment (the common default)

structure
terraform/
├── modules/
│   ├── networking/
│   ├── storage/
│   ├── key-vault/
│   ├── databricks/
│   └── functions/
├── environments/
│   ├── dev/
│   │   ├── main.tf            calls modules with dev inputs
│   │   ├── backend.tf         committed, hardcoded — cannot be confused
│   │   ├── terraform.tfvars
│   │   └── versions.tf
│   ├── test/
│   └── prod/
├── .github/workflows/
├── .gitignore
├── .terraform.lock.hcl        one per environment directory
└── README.md
ProCon
Backend is committed per directory — you cannot apply to the wrong stateThe main.tf files are similar; a change must be made in each
Environments can legitimately differ — prod has private endpoints, dev does notGenuine duplication, which can drift if nobody promotes changes
Per-directory permissions and per-environment pipeline approvals are naturalMore files to navigate
A reviewer sees exactly what prod has that dev lacksLock files can diverge between environments
On the duplication objection

“But dev and prod main.tf are 90% identical!” Yes — and that repetition forces promotion through environments. A change lands in dev, is applied and observed, and is then copied to prod as a separate, reviewed pull request. Many teams consider that a feature rather than a cost. If the duplication genuinely hurts, the answer is a thicker module, not a shared root.

D · Layered components (large platforms)

structure
terraform/
├── modules/
└── layers/
    ├── 10-platform/           VNet, DNS zones, Key Vault    · changes monthly
    │   ├── dev/ test/ prod/
    ├── 20-data/               ADLS, RBAC, Databricks ws     · changes weekly
    │   ├── dev/ test/ prod/
    └── 30-workloads/          Functions, jobs, pipelines    · changes daily
        ├── dev/ test/ prod/

state layout: platform/prod.tfstate, data/prod.tfstate, workloads/prod.tfstate
ProCon
Smallest blast radius — a workloads mistake cannot touch the networkCross-layer references needed; a full rebuild requires ordering
Fast plans; teams do not block each other on the state lockMany more pipelines to build and maintain
Per-layer deployment identities with genuinely different permissionsHigher cognitive load — “which layer owns this?” becomes a real question
Matches how the org is actually structuredOver-engineering for a small team
How to choose

Start at C for anything with a production environment. Move to D when you feel a specific pain: plans taking minutes, teams waiting on each other's locks, or a pipeline that needs permissions you are uncomfortable granting. Do not start at D — you will build coordination machinery for problems you do not have. And do not stay at B once real money or real data is involved, because the wrong-state failure mode is severe and depends entirely on human care.

State isolation and the identity that goes with it

Splitting state is only half the benefit. The other half is that each state can have a different deployment identity with different permissions.

LayerDeployment identity permissions
10-platform Network Contributor on the network resource group, Contributor on the platform resource group, Storage Blob Data Contributor on its own state container.
20-data Contributor on the data resource group, Role Based Access Control Administrator scoped to that resource group only, Reader on the network resource group so its data sources work.
30-workloads Contributor on the workloads resource group and nothing else. Cannot touch the lake or the network.
One identity for everything defeats the split

If all three pipelines use one service principal with Owner on the subscription, you have the coordination cost of split state with none of the safety. The permissions boundary is where the actual protection lives.

Naming and tagging

modules/naming/ — a shared convention
locals {
  # <type>-<workload>-<env>-<region>-<instance>
  region_short = {
    westeurope   = "weu"
    northeurope  = "neu"
    uksouth      = "uks"
    eastus       = "eus"
  }

  suffix = join("-", [
    var.workload,
    var.environment,
    local.region_short[var.location],
    format("%02d", var.instance),
  ])

  names = {
    resource_group  = "rg-${local.suffix}"
    virtual_network = "vnet-${local.suffix}"
    key_vault       = substr("kv-${local.suffix}", 0, 24)
    # no hyphens, lowercase, max 24
    storage_account = substr(lower(replace("st${local.suffix}", "-", "")), 0, 24)
    function_app    = substr("func-${local.suffix}", 0, 32)
    databricks      = "dbw-${local.suffix}"
  }
}
tagging
locals {
  common_tags = {
    workload         = var.workload
    environment      = var.environment
    managed_by       = "terraform"
    repository       = var.repository_url        # where the code lives
    terraform_layer  = "20-data"                 # which state owns this
    cost_center      = var.cost_center
    data_owner       = var.data_owner            # a team, not a person
    criticality      = var.criticality           # drives on-call and DR policy
  }
}
TagWhy it earns its place
managed_by = "terraform"Tells an engineer in the portal not to click. Also lets you find unmanaged resources with a policy query.
repositoryAnswers “where is the code for this?” — the single most common question during an incident.
terraform_layerAnswers “which state file owns this?” in a layered setup. Saves genuine time.
cost_centerMakes Azure Cost Management usable. Retrofitting this is painful.
data_ownerA team name. Person names go stale within a year.
Tags that cause permanent diffs

Never tag with timestamp(), a build number, or a commit SHA that changes on every run — every plan will then show a change on every resource, and people stop reading plans carefully, which defeats the entire control. If you want deployment traceability, put it in the state or in a separate log, not in a tag on 200 resources.

Version pinning and upgrades

the three levels of pinning
terraform {
  # 1 · CLI — a floor. You want colleagues on newer versions to work.
  required_version = ">= 1.9.0"

  required_providers {
    azurerm = {
      source = "hashicorp/azurerm"
      # 2 · Provider — pessimistic in a root module, a floor in a child module.
      version = "~> 5.0"
    }
  }
}

module "storage" {
  # 3 · Module — an immutable tag, never a branch.
  source = "git::https://github.com/contoso/tf-modules.git//storage?ref=v2.3.0"
}

# 4 · The lock file provides exactness. Commit it.

Upgrading a provider major version

the procedure
# 1 · Read the upgrade guide FIRST. It lists every rename and removal.
#     registry.terraform.io/providers/hashicorp/azurerm/latest/docs/guides/5.0-upgrade-guide

# 2 · Upgrade in DEV only. Branch, change the constraint, re-resolve.
git checkout -b chore/azurerm-5
sed -i 's/~> 4.0/~> 5.0/' environments/dev/versions.tf
cd environments/dev
terraform init -upgrade

# 3 · Fix what validate rejects — the renamed arguments.
terraform validate

# 4 · THE CRITICAL STEP: the plan must be empty.
terraform plan -out=tfplan
terraform show -json tfplan | jq '[.resource_changes[]
  | select(.change.actions != ["no-op"])] | length'
# → 0.  Anything else means the provider interprets your config
#        differently, and you must understand exactly why.

# 5 · Apply in dev, let it soak for a few days, then promote to test, then prod.
#     Commit the updated lock file at each step.
Step 4 is where the danger is

A major provider release can change a default. If allow_nested_items_to_be_public changes its default from true to false, a configuration that never set it now plans a change. Usually that is a good change — but on some resources a changed default forces replacement, and finding that out in production is the wrong time. A non-empty plan after a provider upgrade must be investigated line by line, never applied on the assumption that the provider knows best.

Reviewing a Terraform pull request

Reviewing infrastructure code is different from reviewing application code: the plan matters more than the diff. Here is a checklist that catches most real problems.

The plan — read this first

  • Does the destroy count match the intent stated in the description?
  • Any forces replacement? On what?
  • Anything unexpected being touched?
  • Does the plan match what the diff claims to do?

Security

  • Any secret literal, or a secret in an output?
  • New role assignments: right scope, or lazily at subscription level?
  • public_network_access_enabled newly set to true?
  • shared_access_key_enabled newly enabled?
  • Managed identity used, or a connection string?

Correctness

  • References rather than hardcoded strings?
  • for_each rather than count for collections?
  • New variables typed, described and validated?
  • depends_on — is it hiding a missing reference?
  • Any ignore_changes — is the reason documented?

Operability

  • Tags applied consistently?
  • Naming follows the convention?
  • prevent_destroy on anything new that holds data?
  • Is this reversible, and how?
  • Does the README need updating?
Post the plan on the pull request

A pull request without its plan is not reviewable — the diff shows intent, but only the plan shows consequence. A one-line change to a variable default can replace forty resources. Lesson 18 wires this in as an automatic PR comment.

The section that matters most is “Notes”

Inputs and outputs can be generated by terraform-docs and kept current by a pre-commit hook. What cannot be generated is why — why a resource is separate, why an argument is hardcoded, which decision this module is defending. That is what a colleague needs at 2am, and it is the part everyone leaves out.

Common mistakes

Workspaces for environments

Covered in Lesson 07 and worth restating here: workspaces share one backend and therefore one set of access controls, so anyone who can apply to dev can apply to prod. They also make structural differences awkward, requiring count hacks keyed on terraform.workspace. Use them for short-lived parallel copies — a per-pull-request preview environment — not for the dev/test/prod axis.

One giant state

Everything in one file means slow plans, one lock for the whole organisation, and a single corrupted blob that loses the record of your entire platform. Split by environment at minimum.

Owner on the subscription for the pipeline

It works, which is why people do it. It also means the pipeline can grant anything to anyone, including escalating its own privileges — so a compromised repository is a compromised subscription. Scope Contributor to resource groups, add Role Based Access Control Administrator only where role assignments are genuinely managed, and give each layer its own identity.

No drift detection

Without a scheduled plan, drift accumulates silently until someone runs an unrelated apply and gets a fifty-resource diff they cannot explain. A nightly plan -detailed-exitcode -lock=false that alerts on exit code 2 costs almost nothing and turns a quarterly crisis into a daily notification.

Exercises

Level 1 · Understand Choose a structure

Pick a structure and justify it in two sentences:

  1. A solo data engineer proving out a lake design in a personal subscription.
  2. A four-person team with dev and prod, one Databricks workspace, ~60 resources.
  3. A platform team of twelve supporting eight product teams, four environments, three regions, with a separate network team.
  4. A regulated bank where the network team must approve every network change and cannot see data resources.
Show answer
  1. A, flat single root. One environment, nothing at stake, and the ceremony of modules would slow down the actual goal of learning what the design should be.
  2. C, directory per environment. Sixty resources and a production environment justify module extraction and per-environment state; committed backends remove the wrong-state failure mode, which is the one that hurts most at this size.
  3. D, layered components. Twelve people and eight consumers means lock contention and slow plans are real; different teams owning different layers means different deployment identities, which is the actual reason to split.
  4. D, mandatorily. The requirement is a permissions boundary, not a code-organisation preference — the network layer needs its own state, its own pipeline, its own approvers and an identity with no access to data resources. No amount of directory structure achieves that without separate state.

The pattern: structure follows the permissions and ownership boundaries you need, not aesthetics.

Level 2 · Implement Least-privilege deployment identities

Define the exact Azure role assignments for three per-layer deployment identities in the layered structure: 10-platform, 20-data, 30-workloads. State the role and the scope for each, and say what each identity must not be able to do.

Show answer
rbac-bootstrap.sh — run once by an administrator
SUB="/subscriptions/$SUBSCRIPTION_ID"
TFSTATE_SA="$SUB/resourceGroups/rg-tfstate-prod-weu-01/providers/Microsoft.Storage/storageAccounts/sttfstateprodweu01"

# ---- 10-platform ----
az role assignment create --assignee "$SP_PLATFORM" --role "Contributor" \
  --scope "$SUB/resourceGroups/rg-network-prod-weu-01"
az role assignment create --assignee "$SP_PLATFORM" --role "Storage Blob Data Contributor" \
  --scope "$TFSTATE_SA/blobServices/default/containers/platform"
#   NOT: subscription-scope Contributor. NOT: access to the data or workloads containers.

# ---- 20-data ----
az role assignment create --assignee "$SP_DATA" --role "Contributor" \
  --scope "$SUB/resourceGroups/rg-analytics-prod-weu-01"
# It manages RBAC on the lake, so it needs assignment rights — but ONLY here.
az role assignment create --assignee "$SP_DATA" --role "Role Based Access Control Administrator" \
  --scope "$SUB/resourceGroups/rg-analytics-prod-weu-01"
# Read-only on the network, so its data sources resolve.
az role assignment create --assignee "$SP_DATA" --role "Reader" \
  --scope "$SUB/resourceGroups/rg-network-prod-weu-01"
az role assignment create --assignee "$SP_DATA" --role "Storage Blob Data Contributor" \
  --scope "$TFSTATE_SA/blobServices/default/containers/data"
#   NOT: Owner. NOT: write access to the network. NOT: User Access Administrator at
#   subscription scope, which would allow self-escalation.

# ---- 30-workloads ----
az role assignment create --assignee "$SP_WORKLOADS" --role "Contributor" \
  --scope "$SUB/resourceGroups/rg-workloads-prod-weu-01"
az role assignment create --assignee "$SP_WORKLOADS" --role "Reader" \
  --scope "$SUB/resourceGroups/rg-analytics-prod-weu-01"
az role assignment create --assignee "$SP_WORKLOADS" --role "Storage Blob Data Contributor" \
  --scope "$TFSTATE_SA/blobServices/default/containers/workloads"
#   NOT: any write access to the lake or the network. A workload deploy
#   must not be able to change a firewall rule or delete a container.

What each must not be able to do:

  • 10-platform: cannot touch the lake, the workspace or any workload. Cannot create role assignments anywhere.
  • 20-data: cannot modify the network. Cannot create role assignments outside its own resource group — which is what stops it granting itself Owner.
  • 30-workloads: cannot modify the lake, the network or any RBAC. It can read what it needs and deploy into its own resource group.
  • None of them can read another layer's state container, so none can read another layer's secrets.

The state-container scoping is the part most often missed, and it is what makes state splitting a security control rather than just a performance optimisation.

Level 2 · Implement Write the naming and tagging module

Every root module in the platform should derive names and tags identically. Write modules/naming that produces both.

It must enforce Azure's per-resource character rules — especially the 24-character lowercase alphanumeric limit for storage accounts and 32 for function apps — so callers cannot produce an invalid name by accident.

Show solution
modules/naming/main.tf
variable "workload" {
  type = string

  validation {
    condition     = can(regex("^[a-z][a-z0-9]{2,11}$", var.workload))
    error_message = "workload must be 3-12 lowercase alphanumeric characters starting with a letter."
  }
}

variable "environment" {
  type = string

  validation {
    condition     = contains(["dev", "test", "staging", "prod"], var.environment)
    error_message = "environment must be dev, test, staging or prod."
  }
}

variable "location" { type = string }

variable "instance" {
  type    = number
  default = 1
}

variable "extra_tags" {
  type    = map(string)
  default = {}
}

locals {
  region_short = {
    westeurope  = "weu"
    northeurope = "neu"
    uksouth     = "uks"
    eastus      = "eus"
  }

  # A missing region fails loudly here rather than producing a name
  # containing the literal string "null".
  region = local.region_short[var.location]

  suffix = join("-", [var.workload, var.environment, local.region, format("%02d", var.instance)])

  # For names that allow neither hyphens nor uppercase.
  compact = lower(replace(local.suffix, "-", ""))
}

output "suffix" { value = local.suffix }

output "names" {
  value = {
    resource_group  = "rg-${local.suffix}"
    virtual_network = "vnet-${local.suffix}"
    subnet_prefix   = "snet"
    nsg_prefix      = "nsg"

    # 3-24 chars, lowercase alphanumeric only, GLOBALLY unique.
    storage_account = substr("st${local.compact}", 0, 24)

    # 3-24 chars, alphanumerics and hyphens, GLOBALLY unique.
    key_vault = substr("kv-${local.suffix}", 0, 24)

    # Becomes a hostname; keep under 32 to avoid host ID collisions.
    function_app = substr("func-${local.suffix}", 0, 32)

    service_plan         = "asp-${local.suffix}"
    databricks_workspace = "dbw-${local.suffix}"
    databricks_connector = "dbac-${local.suffix}"
    user_identity        = "id-${local.suffix}"
    log_analytics        = "log-${local.suffix}"
  }
}

output "tags" {
  value = merge({
    workload    = var.workload
    environment = var.environment
    managed_by  = "terraform"
    # NEVER timestamp() or a build number here: every plan would then show
    # a change on every tagged resource, forever, and people stop reading plans.
  }, var.extra_tags)
}

The substr() calls are the module's real value. They mean a caller can add a longer workload name without discovering at apply time that their storage account name is 26 characters. The local.region_short[var.location] lookup is deliberate too: an unmapped region errors rather than silently interpolating null into every name.

This is the borderline case from Lesson 14 — a module that only computes values. It earns its place because three root modules consume it and it encodes rules that are genuinely easy to get wrong. Used once, it should be a locals block. Be able to argue it either way.

Level 2 · Implement Bootstrap least-privilege identities for three layers

You are splitting into 10-platform, 20-data and 30-workloads, each with its own state. Write the RBAC bootstrap giving each pipeline exactly what it needs.

For each identity, state explicitly what it must not be able to do. The state-container scoping is the part most teams miss.

Show solution
bootstrap-rbac.sh
#!/usr/bin/env bash
set -euo pipefail

SUB="/subscriptions/${SUBSCRIPTION_ID}"
TFSA="${SUB}/resourceGroups/rg-tfstate-prod-weu-01/providers/Microsoft.Storage/storageAccounts/sttfstateprodweu01"
CONTAINERS="${TFSA}/blobServices/default/containers"

# ---------------------------------------------------------------- platform
az role assignment create --assignee "$SP_PLATFORM" \
  --role "Contributor" --scope "${SUB}/resourceGroups/rg-network-prod-weu-01"

az role assignment create --assignee "$SP_PLATFORM" \
  --role "Storage Blob Data Contributor" --scope "${CONTAINERS}/platform"

#   MUST NOT: touch the lake, the workspace or any workload.
#   MUST NOT: create role assignments anywhere.
#   MUST NOT: read the data or workloads state containers.

# -------------------------------------------------------------------- data
az role assignment create --assignee "$SP_DATA" \
  --role "Contributor" --scope "${SUB}/resourceGroups/rg-analytics-prod-weu-01"

# It manages RBAC on the lake, so it needs assignment rights - but ONLY
# within its own resource group. "Role Based Access Control Administrator"
# is narrower than "User Access Administrator"; prefer it.
az role assignment create --assignee "$SP_DATA" \
  --role "Role Based Access Control Administrator" \
  --scope "${SUB}/resourceGroups/rg-analytics-prod-weu-01"

# Read-only on the network so its data sources resolve.
az role assignment create --assignee "$SP_DATA" \
  --role "Reader" --scope "${SUB}/resourceGroups/rg-network-prod-weu-01"

az role assignment create --assignee "$SP_DATA" \
  --role "Storage Blob Data Contributor" --scope "${CONTAINERS}/data"

#   MUST NOT: be Owner. MUST NOT: write to the network.
#   MUST NOT: hold assignment rights at SUBSCRIPTION scope - that would let
#             it grant itself Owner, which defeats the entire split.

# --------------------------------------------------------------- workloads
az role assignment create --assignee "$SP_WORKLOADS" \
  --role "Contributor" --scope "${SUB}/resourceGroups/rg-workloads-prod-weu-01"

az role assignment create --assignee "$SP_WORKLOADS" \
  --role "Reader" --scope "${SUB}/resourceGroups/rg-analytics-prod-weu-01"

az role assignment create --assignee "$SP_WORKLOADS" \
  --role "Storage Blob Data Contributor" --scope "${CONTAINERS}/workloads"

#   MUST NOT: write to the lake or the network.
#   MUST NOT: create any role assignment.
#   A daily workload deploy cannot change a firewall rule or delete a container.

The state-container scoping is what turns state splitting from a performance optimisation into a security control. Because state holds every resource attribute in plaintext, a pipeline that can read another layer's state can read that layer's secrets — so scoping each identity to its own container matters as much as scoping it to its own resource group.

Two refinements for a stricter environment: put each layer's state in a separate storage account, so even an account-scoped mistake cannot cross layers; and add an ABAC condition to the RBAC Administrator assignment limiting which role definitions it may assign.

Show answer

Blocking — this deletes production data.

1 · The variable change is not mentioned in the description and is the most dangerous line here. Removing "silver" from medallion_layers destroys the silver container and everything in it. If those containers use count, it is worse: gold shifts index and is destroyed and recreated too. This has nothing to do with the stated purpose of the PR. Ask whether it was an accidental paste, and require the plan to be posted.

2 · container_access_type = "blob" makes the reports publicly readable by anyone on the internet with the URL, with no authentication. Must be "private". It will also fail outright unless allow_nested_items_to_be_public is enabled, which itself would be a serious regression.

3 · Contributor at subscription scope for the BI team. That grants management of every resource in the subscription. They need Storage Blob Data Reader scoped to .../containers/reports. Also, the principal_id is a hardcoded GUID with no comment — assign to a named Entra ID group read via a data source instead, so joiners and leavers are handled outside Terraform.

4 · The output publishes an account key. It goes into state, and terraform output -raw reporting_key prints it for anyone who can read state. Remove it entirely; consumers should authenticate with an identity.

Non-blocking but should be fixed:

  • public_network_access_enabled = true and shared_access_key_enabled = true contradict the platform's posture. Justify or remove.
  • resource_group_name and location are hardcoded strings — use references, and the lowercase region form for consistency.
  • The name has no region or instance component and does not follow the convention.
  • No tags, so this resource will be invisible to cost allocation.
  • No prevent_destroy on a new production storage account.
The meta-lesson

A PR described as “small” contained a change that deletes production data, a public data exposure, a subscription-wide privilege grant and a leaked credential. Read the whole diff, not the description, and always read the plan. None of the four would be obvious from the title, and the destroy would have been unmissable in the plan output.

Interview questions

How would you structure a Terraform repository for a production data platform?

I would start with shared modules and a directory per environment, each with a committed backend configuration so it is structurally impossible to apply to the wrong state. As the platform grows I would split into layers by change frequency and ownership — networking, data platform, workloads — each with its own state and, critically, its own deployment identity with different permissions. I would decide based on blast radius: how much can one mistake destroy? I would avoid workspaces for environments, because they share a backend and therefore share access control.

What are the trade-offs of separate directories per environment?

The cost is duplication — the root modules are similar and a change must be made in each. The benefits are that the backend is committed per directory so you cannot apply dev's code to prod's state, environments can legitimately differ without conditionals accumulating, permissions and approvals are naturally per environment, and a reviewer can see exactly what prod has that dev lacks. Many teams also treat the duplication as a feature, because it forces changes to be promoted through environments rather than reaching prod the moment they merge.

How do you upgrade a provider major version safely?

Read the upgrade guide first — it lists every rename and removal. Then upgrade in dev only, on a branch: change the constraint, terraform init -upgrade, fix what validate rejects, and then the critical step: the plan must be empty. A major release can change a default, so a non-empty plan means the provider now interprets your configuration differently and you must understand exactly why before proceeding — on some resources a changed default forces replacement. Then apply in dev, let it soak, and promote to test and prod, committing the updated lock file at each step.

What do you look for when reviewing a Terraform pull request?

The plan first, because the diff shows intent and only the plan shows consequence — a one-line variable change can replace forty resources. Specifically: does the destroy count match the description, is anything marked forces replacement, and is anything unexpected being touched. Then security: secrets in code or outputs, role assignment scopes, anything re-enabling public access or shared keys. Then correctness: references rather than hardcoded strings, for_each rather than count, typed and validated variables, and whether any depends_on is hiding a missing reference. And I would insist the plan is posted on the PR automatically.

What permissions should a Terraform pipeline have?

The least that lets it do its job, scoped to resource groups rather than the subscription. Contributor on the resource groups it manages; Role Based Access Control Administrator only where it genuinely manages role assignments, and scoped to those resource groups so it cannot escalate its own privileges; Reader on resource groups it only reads from via data sources; and Storage Blob Data Contributor on its own state container only, so one layer's pipeline cannot read another layer's state and therefore another layer's secrets. Never Owner at subscription scope — that means a compromised repository is a compromised subscription.

How do you handle drift in production?

Detect it deliberately with a scheduled plan using -detailed-exitcode and -lock=false, alerting on exit code 2. Then investigate rather than react: what changed, and who changed it — the Azure activity log answers the second question, which usually explains the first. The response depends on cause: adopt an emergency fix into configuration and reconcile with apply -refresh-only; revert unauthorised changes after checking that reverting is not itself destructive; add ignore_changes where a system like Azure Policy legitimately owns an attribute; and treat two configurations managing one resource as a design bug to resolve.

Key takeaways

  • Blast radius answers most structural questions. Structure follows permissions and ownership boundaries.
  • Directory per environment for anything with production; layers when you feel a specific pain, not before.
  • Splitting state only pays off if each state has its own deployment identity with different permissions.
  • Pin at four levels: CLI floor, provider constraint, module tag, lock file.
  • A provider upgrade is safe when the plan is empty. Investigate anything else.
  • Review the plan, not just the diff — and never tag with values that change every run.

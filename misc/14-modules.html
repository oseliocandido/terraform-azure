Modules

A module is a directory of Terraform files with a deliberate input/output contract. The technical mechanism takes ten minutes to learn; the hard part is deciding where the boundaries go, which is an API design problem and the thing that separates a maintainable repository from a painful one.

By the end of this lesson you can

  • Explain root vs child modules, and why every directory is already a module
  • Design a module's inputs and outputs as a stable public API
  • Choose module sources and pin versions correctly
  • Refactor duplicated configuration into modules without destroying anything
  • Recognise the thin-wrapper anti-pattern and know when not to write a module
  • Use for_each on a module call

Every directory is a module

There is no special syntax that makes something a module. A module is simply a directory containing .tf files. You have been writing modules since Lesson 05 without noticing.

Root moduleChild module
Where you run terraformYesNo
Declares a backendYesNever
Declares provider blocksYesNever — only required_providers
Gets variable values fromtfvars, CLI, environmentThe calling module block
Outputs consumed byHumans, CI, other configurationsThe calling module
Contains environment decisionsYes — “prod uses GZRS”No — it accepts a replication type as input

Why modules exist

Good reasons

  • Encapsulation. “A data lake” is one concept; a caller should not need to know it is a storage account plus four filesystems plus a lifecycle policy plus two private endpoints.
  • Enforced standards. If every storage account comes from your module, every storage account has TLS 1.2, no public blobs and no shared keys — by construction, not by review.
  • Reuse across environments with different inputs.
  • A testable unit. terraform test operates on a module.
  • Smaller review surface. A change to the module is reviewed once, not in three environments.

Bad reasons

  • “Modules are best practice.” A module used once, with inputs mapping one-to-one onto a resource's arguments, adds indirection and nothing else.
  • Wrapping a single resource. The thin-wrapper anti-pattern — see below.
  • Making things look tidy. Fewer lines in main.tf is not the goal; a stable interface is.
  • Premature abstraction. Write it twice concretely. Extract on the third.

resource "azurerm_storage_management_policy" "this" {
  # Only create the policy if at least one container has a lifecycle rule.
  count = length([
    for c in var.containers : c
    if c.tier_after_days != null || c.delete_after_days != null
  ]) > 0 ? 1 : 0

  storage_account_id = azurerm_storage_account.this.id

  dynamic "rule" {
    for_each = {
      for k, v in var.containers : k => v
      if v.tier_after_days != null || v.delete_after_days != null
    }

    content {
      name    = "lifecycle-${rule.key}"
      enabled = true

      filters {
        prefix_match = ["${rule.key}/"]
        blob_types   = ["blockBlob"]
      }

      actions {
        base_blob {
          tier_to_cool_after_days_since_modification_greater_than = rule.value.tier_after_days
          delete_after_days_since_modification_greater_than       = rule.value.delete_after_days
        }
        version {
          delete_after_days_since_creation = 90
        }
      }
    }
  }
}

Designing the interface

A module's inputs and outputs are a public API

Every variable you add is a promise. Removing one, renaming one, or changing its type is a breaking change for every caller. Adding a required variable is breaking. Adding an optional one with a default is not. Think about this before publishing, because module interfaces are far harder to change than the resources behind them.

PrincipleApplied
Accept intent, not plumbing containers = { raw = { delete_after_days = 2555 } } — not a pre-built management policy JSON document. The module knows how to turn intent into resources.
Enforce the non-negotiables TLS 1.2 and “no public blobs” are hardcoded, not variables. If a caller could turn them off, the module is not enforcing a standard.
Default to secure allow_public_network_access = false. A caller must deliberately weaken it, and that appears in the diff.
Output IDs and scopes, never secrets container_scopes lets the caller make per-container role assignments without the module needing to know about identities.
Do not take a location from thin air Accept it as an input rather than defaulting it. A wrong-region resource is expensive to fix.
Take a tags map And merge it, so the caller's governance tags reach every resource inside.

Module outputs are not automatic

A root module does not expose a child's outputs to the outside world unless it declares its own output re-exporting them. This surprises people: terraform output shows nothing even though the module defines outputs.

Meta-arguments on module calls

for_each on a module
module "lake" {
  source   = "../../modules/storage"
  for_each = var.data_domains     # { finance = {...}, marketing = {...} }

  name                = "st${each.key}${var.environment}weu01"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location
  replication_type    = each.value.replication
  containers          = each.value.containers
  tags                = merge(local.common_tags, { domain = each.key })
}

# addresses become module.lake["finance"].id, module.lake["marketing"].id
output "domain_endpoints" {
  value = { for k, m in module.lake : k => m.dfs_endpoint }
}

count, for_each, depends_on and providers all work on module blocks. Note that depends_on at module level is coarse — it waits for everything in the target module — so prefer passing an output through as an input, which creates a precise edge.

Module sources and versioning

SourceExampleVersioning
Local path source = "../../modules/storage" None — it is whatever is in the repo. Fine for modules that live with their callers.
Public registry source = "Azure/avm-res-storage-storageaccount/azurerm" version = "~> 0.5"
Git over HTTPS source = "git::https://github.com/contoso/tf-modules.git//storage?ref=v1.4.0" The ref — always pin to a tag, never a branch
Git over SSH source = "git::ssh://git@github.com/contoso/tf-modules.git//storage?ref=v1.4.0" Same. Needed for private repos with SSH keys.
Private registry source = "app.terraform.io/contoso/storage/azurerm" version, with the registry enforcing semver
Common mistake · ?ref=main

Pointing a module source at a branch means the module's content can change under you between two runs of terraform init -upgrade, with no diff in your repository to explain it. Pin to an immutable tag or a commit SHA. This is the same discipline as pinning provider versions — and it matters more, because module changes create and destroy resources.

Azure Verified Modules

Microsoft publishes AVM — a set of Azure-maintained Terraform modules following a common specification, covering storage, networking, Key Vault and much else. They are worth knowing about: they encode a lot of Well-Architected guidance you would otherwise rediscover. They are also large and highly parameterised, which is a real cost in readability. A reasonable position is to use AVM for complicated resources you do not want to own, and write your own thin, opinionated modules where you want the standard to be yours.

Refactoring into modules without destroying anything

Moving a resource into a module changes its address — from azurerm_storage_account.lake to module.lake.azurerm_storage_account.this. To state, one resource disappeared and another appeared.

what happens without a moved block
  # azurerm_storage_account.lake will be destroyed
  - resource "azurerm_storage_account" "lake" { ... }

  # module.lake.azurerm_storage_account.this will be created
  + resource "azurerm_storage_account" "this" { ... }

Plan: 1 to add, 0 to change, 1 to destroy.
moved.tf — the fix
moved {
  from = azurerm_storage_account.lake
  to   = module.lake.azurerm_storage_account.this
}

moved {
  from = azurerm_storage_data_lake_gen2_filesystem.layers
  to   = module.lake.azurerm_storage_data_lake_gen2_filesystem.this
}
the plan afterwards
Terraform will perform the following actions:

  # azurerm_storage_account.lake has moved to module.lake.azurerm_storage_account.this
    resource "azurerm_storage_account" "this" {
        id = "/subscriptions/.../stanalyticsprodweu01"
        # (no changes)
    }

Plan: 0 to add, 0 to change, 0 to destroy.
This is the correct way to refactor

moved blocks are declarative, reviewable in a pull request, and applied as part of a normal plan — unlike terraform state mv, which mutates state immediately with no review and no record. Leave them in the repository for a release or two so colleagues on older checkouts are covered, then delete them. Lesson 16 covers moved, import and removed together.

Anti-patterns

The thin wrapper
modules/resource-group/main.tf
variable "name"     { type = string }
variable "location" { type = string }
variable "tags"     { type = map(string) }

resource "azurerm_resource_group" "this" {
  name     = var.name
  location = var.location
  tags     = var.tags
}

This adds nothing. It has the same arguments as the resource, enforces no standard, and now every caller must learn a second name for the same thing — plus you have lost direct access to any argument the wrapper forgot to expose. A module should hide complexity or enforce policy. If it does neither, use the resource.

Deep nesting

A root module calling a “platform” module calling a “data” module calling a “storage” module. Every layer must re-declare and forward every variable, so adding one input means editing four files, and reading a plan requires holding the whole tree in your head. Prefer flat composition: the root module calls several sibling modules and wires their outputs to each other. Two levels is usually the sensible limit.

A provider block inside a child module

Covered in Lesson 04 and worth repeating: a child module with its own provider block cannot be used with for_each or count, and cannot be cleanly removed because Terraform needs the provider configuration in order to destroy what it created. Child modules declare required_providers only.

The mega-module

One module taking eighty variables and building the entire platform. It cannot be tested in parts, cannot be reused partially, and every change touches everything. If a module's variable list does not fit on a screen, it is probably two modules.

Exercises

Level 1 · Understand Module or not?

For each, say whether you would write a module and why:

  1. A resource group. Used in every configuration.
  2. A data lake: storage account + four filesystems + lifecycle policy + two private endpoints + two DNS zones.
  3. The single Databricks workspace in your platform.
  4. A “private endpoint + DNS zone + VNet link” trio, needed for storage, Key Vault and Databricks.
  5. Your organisation's standard tagging scheme.
Show answer
  1. No. Thin wrapper. Same arguments as the resource, no complexity hidden, no policy enforced.
  2. Yes. Nine resources behind one concept, with real opinions to enforce — HNS, TLS, no public access, no shared keys. This is what modules are for.
  3. Probably not yet. Used once. Write it inline; extract it if a second workspace appears or another team wants your configuration. Premature abstraction costs more than duplication at n=1.
  4. Yes. Three coupled resources with a fiddly, easy-to-get-wrong relationship, needed three times. Highest-value module in the list.
  5. No — use a local. A module that only computes a value and outputs it is a very awkward function. Put the tag map in a locals block, or in a shared .tfvars.

The test: does it hide meaningful complexity, or enforce a standard that would otherwise depend on someone remembering? If neither, skip it.

Level 2 · Implement A private endpoint module

Write modules/private-endpoint creating a private endpoint, its private DNS zone and the VNet link. It should work for storage-blob, storage-dfs, Key Vault and Databricks, and it should not create a duplicate DNS zone when called several times for the same zone.

Consider carefully where the zone should live. Then write the calling code for a lake and a vault.

Show answer

The key design decision: the DNS zone must not be inside the module. Two calls for blob and dfs would each create a zone — fine — but two calls for two storage accounts' blob endpoints would try to create the same zone twice and fail. Zones are shared infrastructure with a different lifecycle from endpoints.

So the module creates only the endpoint and accepts a zone ID as input:

Level 2 · Implement Design a Key Vault module's public interface

Write modules/key-vault. Before writing resources, decide what belongs in the interface: what the caller controls, what the module hardcodes, and what it exposes.

Deliberately make some settings non-negotiable, and be able to justify each choice.

modules/key-vault/main.tf
data "azurerm_client_config" "current" {}

resource "azurerm_key_vault" "this" {
  name                = var.name
  resource_group_name = var.resource_group_name
  location            = var.location
  tenant_id           = data.azurerm_client_config.current.tenant_id
  sku_name            = var.sku_name

  # MODULE HARDCODES - a caller cannot weaken these. That is the point of
  # having a module at all: the standard is enforced by construction.
  rbac_authorization_enabled = true   # never access policies

  # CALLER CONTROLS
  purge_protection_enabled      = var.purge_protection_enabled
  soft_delete_retention_days    = var.soft_delete_retention_days
  public_network_access_enabled = var.public_network_access_enabled

  network_acls {
    default_action = var.public_network_access_enabled ? "Allow" : "Deny"
    bypass         = "AzureServices"
    ip_rules       = var.allowed_ip_ranges
  }

  tags = var.tags
}

locals {
  # Scope to a single secret when asked, otherwise the whole vault.
  # Computed here because a multi-line ternary is not valid inside an
  # argument - HCL needs it on one line, or hoisted like this.
  assignment_scopes = {
    for k, v in var.role_assignments :
    k => v.secret_name == null ? azurerm_key_vault.this.id : "${azurerm_key_vault.this.id}/secrets/${v.secret_name}"
  }
}

resource "azurerm_role_assignment" "this" {
  for_each = var.role_assignments

  scope                = local.assignment_scopes[each.key]
  role_definition_name = each.value.role
  principal_id         = each.value.principal_id
  principal_type       = each.value.principal_type
}

output "id"        { value = azurerm_key_vault.this.id }
output "name"      { value = azurerm_key_vault.this.name }
output "vault_uri" { value = azurerm_key_vault.this.vault_uri }

# Helper so callers can build @Microsoft.KeyVault(...) references without
# ever reading a secret value.
output "secret_reference" {
  description = "Function returning an app-setting reference for a secret name."
  value       = { for n in var.exposed_secret_names :
                  n => "@Microsoft.KeyVault(VaultName=${azurerm_key_vault.this.name};SecretName=${n})" }
}

# DELIBERATELY ABSENT: no azurerm_key_vault_secret resources, and no output
# of any secret value. Creating secrets here would write them into the
# caller's state in plaintext.

The interface design is the real content. rbac_authorization_enabled is hardcoded because a module that lets callers pick the legacy access-policy model is not enforcing a standard. Purge protection and network access are caller-controlled because they legitimately differ between an ephemeral dev vault and production.

And the most important line is the comment at the end. A vault module that offers to create secrets for you is a trap: it copies every value into the calling configuration's state. The module's job is the vault and its RBAC; populating it is somebody else's.

Interview questions

What is a Terraform module and why use one?

Any directory of Terraform files — the one you run terraform in is the root module, and any it calls with a module block is a child module. The reasons to extract one are encapsulating a concept so callers do not need to know its parts, enforcing standards by construction so every storage account the organisation creates has the right security posture, reuse across environments with different inputs, and having a testable unit. The reason not to is a wrapper that exposes the same arguments as the underlying resource — that adds indirection with no benefit.

What is the difference between a root module and a child module?

The root module is where you run Terraform. It configures the backend and the providers, holds the environment's decisions, and receives variable values from tfvars, the CLI and the environment. A child module never declares a backend or a provider block — only required_providers — receives its values from the calling module block, and should contain no environment-specific decisions, taking them as inputs instead.

How do you version modules?

For registry modules, a version constraint alongside the source. For git sources, a ?ref= pinned to an immutable tag or commit SHA — never a branch, because then module content can change between runs with no diff in your repository to explain it. Local path modules are versioned by the repository itself. In the module's own required_providers I would use a floor like >= 5.0 rather than ~> 5.0, so the module does not over-constrain the root modules consuming it.

How do you refactor existing resources into a module safely?

With moved blocks. Moving a resource into a module changes its state address, so without them Terraform plans to destroy the old address and create the new one — on a data lake that is data loss. A moved block declares the rename, is reviewable in a pull request, and is applied as part of a normal plan, unlike terraform state mv which mutates state immediately with no record. The verification is that the resulting plan shows zero changes, which is why the refactor should be its own commit with no functional changes mixed in.

How would you design a module's interface?

Treat inputs and outputs as a public API — removing or renaming one is a breaking change for every caller. I would accept intent rather than plumbing, so a caller passes a map of containers with retention policies rather than a pre-built lifecycle document. Hardcode the non-negotiables so a caller cannot weaken the standard, and default the rest to secure so weakening is visible in the diff. Output resource IDs and RBAC scopes so callers can wire things up, and never output secrets — that just copies them into the caller's state too. And take a tags map so governance tags reach everything inside.

When should you not write a module?

When it wraps a single resource with the same arguments — that hides nothing and enforces nothing. When it is used once, since duplication at n=1 is cheaper than premature abstraction; I would write it twice concretely and extract on the third. When it only computes a value, which is what locals are for. And I would avoid deep nesting: modules calling modules calling modules means every input must be forwarded through every layer, so adding one variable becomes a four-file change and reading a plan requires holding the whole tree in your head.

Key takeaways

  • Every directory is a module. The root one owns the backend and providers; child modules must not.
  • A module earns its place by hiding complexity or enforcing a standard. If it does neither, use the resource.
  • Inputs and outputs are a public API. Accept intent, hardcode non-negotiables, default to secure, never output secrets.
  • Pin git module sources to tags, never branches.
  • Refactor with moved blocks and verify the plan is empty. Never mix a refactor with a behaviour change.
  • Prefer flat composition in the root module over deep nesting.

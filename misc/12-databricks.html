Azure Databricks

Databricks is the clearest example in this course of a boundary you must understand: azurerm provisions the workspace, and the databricks provider configures everything inside it. Getting that split wrong produces a two-provider chicken-and-egg problem that people fight for days.

By the end of this lesson you can

  • Explain the control plane / compute plane split and what the managed resource group is
  • Provision a VNet-injected workspace with secure cluster connectivity
  • Say precisely which resources belong to azurerm and which to databricks
  • Wire Unity Catalog to ADLS Gen2 with an access connector and no secrets
  • Handle the two-provider bootstrapping problem
  • Decide what Terraform should manage inside a workspace, and what it should not

The architecture you are provisioning

The managed resource group is not yours to manage

Databricks creates a second resource group in your subscription holding cluster VMs, disks, a managed NSG and the DBFS root storage account. You can see it and you are billed for it, but you must not modify it — Databricks owns its contents and will fight you. In Terraform, never write resources into it and never import anything from it. The only thing you control is its name, via managed_resource_group_name.

Provisioning the workspace

databricks-workspace.tf
resource "azurerm_databricks_workspace" "this" {
  name                = "dbw-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  # premium is required for cluster ACLs, table ACLs, Unity Catalog,
  # IP access lists and private link. Use it for anything real.
  sku = "premium"

  # Name the managed resource group deliberately, or Azure generates
  # something like "databricks-rg-dbw-...-abc123".
  managed_resource_group_name = "rg-${local.suffix}-databricks-managed"

  # Secure cluster connectivity: no public IPs on cluster nodes.
  # Required when you disable public network access.
  public_network_access_enabled         = false
  network_security_group_rules_required = "NoAzureDatabricksRules"

  custom_parameters {
    no_public_ip = true

    virtual_network_id = azurerm_virtual_network.main.id

    public_subnet_name  = azurerm_subnet.this["databricks_host"].name
    private_subnet_name = azurerm_subnet.this["databricks_container"].name

    # These MUST reference the NSG association resources, not the subnets.
    # It is how Terraform learns the associations exist before the
    # workspace is created — a real ordering dependency.
    public_subnet_network_security_group_association_id =
      azurerm_subnet_network_security_group_association.databricks_host.id
    private_subnet_network_security_group_association_id =
      azurerm_subnet_network_security_group_association.databricks_container.id
  }

  tags = local.common_tags
}
“Public” and “private” subnet names are misleading

With no_public_ip = true — secure cluster connectivity — neither subnet has public IPs. Databricks' terminology comes from its original architecture: the public (host) subnet carries the node's primary NIC, and the private (container) subnet carries the container-side NIC. Both are private. Do not read public_subnet_name as “internet-facing”.

Two subresources, one zone

Databricks exposes databricks_ui_api (workspace UI and REST API) and browser_authentication (single sign-on browser flow), both resolving through privatelink.azuredatabricks.net. A full private-link deployment needs both, and the browser_authentication endpoint typically lives in the transit VNet rather than the workspace VNet. This is one of the more involved Azure networking setups — build it incrementally and test after each step.

The two-provider bootstrapping problem

The databricks provider needs the workspace's URL to configure itself — but the workspace does not exist until the apply runs. This is provider configuration depending on a resource attribute, which Terraform handles poorly.

the error
Error: Invalid provider configuration

Provider "registry.terraform.io/databricks/databricks" requires explicit
configuration. The host attribute is unknown during plan because it depends
on a resource that has not been created.

# or, later in the lifecycle:

Error: cannot delete storage credential: Provider configuration is
unavailable — the workspace this provider points at no longer exists.

Option A · Two root modules (recommended)

One configuration creates the Azure infrastructure including the workspace. A second, applied afterwards, configures the workspace contents and reads the workspace URL from a data source or an output.

Pro: no unknown provider configuration, ever; clean destroy ordering; the two change at very different rates anyway. Con: two applies and two pipelines.

Option B · One configuration, careful ordering

Provider configured from the workspace resource, with depends_on on the Databricks-side resources. Works on a first apply because Terraform defers the provider configuration.

Pro: one apply. Con: terraform destroy frequently breaks — Terraform may destroy the workspace before the objects inside it, then be unable to configure the provider to delete them.

option A — the second root module
# Read the workspace created by the platform configuration.
data "azurerm_databricks_workspace" "this" {
  name                = "dbw-${local.suffix}"
  resource_group_name = "rg-${local.suffix}"
}

provider "databricks" {
  host                        = data.azurerm_databricks_workspace.this.workspace_url
  azure_workspace_resource_id = data.azurerm_databricks_workspace.this.id
}

# Now every databricks_* resource has a provider configured from a
# data source — known at plan time, no ordering problem.
resource "databricks_cluster_policy" "standard" {
  name = "standard-job-cluster"

  definition = jsonencode({
    "spark_version" : {
      "type"  : "regex",
      "pattern" : "1[5-9]\\..*"
    },
    "autotermination_minutes" : {
      "type"      : "range",
      "maxValue"  : 60,
      "defaultValue" : 30
    },
    "node_type_id" : {
      "type"   : "allowlist",
      "values" : ["Standard_D4ads_v5", "Standard_D8ads_v5"]
    },
    "custom_tags.cost_center" : {
      "type"  : "fixed",
      "value" : var.cost_center
    }
  })
}
This is the general rule, not a Databricks quirk

Any time a provider's configuration depends on a resource created in the same configuration, split it into two applies. The same pattern appears with Kubernetes (cluster then manifests), PostgreSQL (server then databases) and Vault. Terraform's documentation is explicit that provider configuration should not depend on values unknown at plan time.

Key Vault-backed secret scopes

secret-scope.tf
resource "databricks_secret_scope" "kv" {
  name = "analytics-kv"

  keyvault_metadata {
    resource_id = azurerm_key_vault.main.id
    dns_name    = azurerm_key_vault.main.vault_uri
  }
}
Why this is the right kind of secret scope

A Key Vault-backed scope is a pointer: notebooks call dbutils.secrets.get("analytics-kv", "source-api-key") and Databricks resolves it from the vault at read time. Terraform stores only the vault's resource ID and URI — no secret values, consistent with Lesson 09. The alternative, a Databricks-backed scope populated with databricks_secret resources, puts every value in Terraform state. Use the Key Vault form.

What Terraform should and should not manage inside a workspace

✓ Good fit for Terraform

  • Cluster policies — governance rules that change rarely and must be reviewed
  • Unity Catalog structure — metastore, catalogs, schemas, external locations
  • Grants and permissions — access control belongs in code
  • SQL warehouses — long-lived, sized deliberately
  • Groups and service principals — identity structure
  • Secret scopes — the pointer, not the secrets

✗ Poor fit

  • Notebooks — belong in git, deployed by CI or Repos, not embedded in HCL
  • Jobs that change weekly — Databricks Asset Bundles are purpose-built for this and owned by the data team
  • Interactive clusters — created and destroyed by users; Terraform will fight them
  • Tables and views — that is DDL, owned by dbt or a migration tool
  • Anything autoscaled — node counts drift constantly
The dividing line

Terraform should own the platform — the guardrails, the access model, the structure. The data team should own the workloads — notebooks, jobs, pipelines, tables — through tools designed for them, chiefly Databricks Asset Bundles. Putting job definitions in Terraform means a data scientist changing a schedule needs an infrastructure pull request and an apply against production state. That is friction with no security benefit, and it is a common early mistake.

Common mistakes

Managing the injected NSG rules

Databricks writes its own required rules into the NSG on its subnets. Declaring inline security_rule blocks makes every plan propose deleting them. Keep the NSG bare, or add lifecycle { ignore_changes = [security_rule] }.

Passing subnet IDs where association IDs are required

public_subnet_network_security_group_association_id wants the ID of the azurerm_subnet_network_security_group_association resource. It happens to be the same string as the subnet ID, so passing the subnet works — and then the NSG association may not exist when the workspace is created, and the deployment fails with an obscure networking error. Reference the association resource so Terraform builds the correct edge.

Personal access tokens for provider authentication

Old examples authenticate the databricks provider with a PAT stored in a variable. That is a long-lived credential in state and in CI. Use azure_workspace_resource_id with Azure CLI or service principal authentication instead — the provider obtains a short-lived token from Entra ID.

Level 1 · Understand Which provider?

For each, name the provider and the resource:

  1. Create the Databricks workspace itself
  2. Grant Databricks read access to the gold container
  3. Create a catalog called analytics_prod
  4. Force all job clusters to auto-terminate after 30 minutes
  5. Give the analysts group SELECT on a schema
  6. Put the workspace in your own VNet
  7. Create a secret scope backed by Key Vault
Show answer
  1. azurerm — azurerm_databricks_workspace. It is an ARM resource.
  2. azurerm — azurerm_role_assignment on the container scope, with the access connector's principal ID. This is Azure RBAC, not a Databricks concept.
  3. databricks — databricks_catalog. Unity Catalog objects live behind the workspace/account API.
  4. databricks — databricks_cluster_policy.
  5. databricks — databricks_grants.
  6. azurerm — the custom_parameters block on the workspace resource. Networking is ARM.
  7. databricks — databricks_secret_scope with a keyvault_metadata block. The scope is a workspace object, even though it points at an Azure resource.

The heuristic that answers all of these: does it have an ARM resource ID? If yes, azurerm.

Write the complete chain giving a Databricks workspace read/write on silver and gold and read-only on raw, with no secrets anywhere, and register those locations in Unity Catalog. State which provider each resource uses.

solution
locals {
  lake_access = {
    raw    = "Storage Blob Data Reader"
    silver = "Storage Blob Data Contributor"
    gold   = "Storage Blob Data Contributor"
  }
}

# --- azurerm: the identity ---
resource "azurerm_databricks_access_connector" "unity" {
  name                = "dbac-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  identity { type = "SystemAssigned" }
}

# --- azurerm: the Azure-side permission, per container ---
resource "azurerm_role_assignment" "unity" {
  for_each = local.lake_access

  scope                = "${azurerm_storage_account.lake.id}/blobServices/default/containers/${each.key}"
  role_definition_name = each.value
  principal_id         = azurerm_databricks_access_connector.unity.identity[0].principal_id
  principal_type       = "ServicePrincipal"
}

# --- databricks: Unity Catalog's view of that identity ---
resource "databricks_storage_credential" "unity" {
  name = "sc-lake"

  azure_managed_identity {
    access_connector_id = azurerm_databricks_access_connector.unity.id
  }
}

# --- databricks: one external location per container ---
resource "databricks_external_location" "layers" {
  for_each = local.lake_access

  name            = "el-${each.key}"
  url             = "abfss://${each.key}@${azurerm_storage_account.lake.name}.dfs.core.windows.net/"
  credential_name = databricks_storage_credential.unity.name
  read_only       = each.value == "Storage Blob Data Reader"

  # The Azure role must exist and be effective before Unity Catalog
  # validates the location. No data flows, so depends_on is correct here.
  depends_on = [azurerm_role_assignment.unity]
}

Note read_only = each.value == "Storage Blob Data Reader" — the Unity Catalog setting is derived from the Azure role, so the two layers of permission cannot drift apart. Also note that Unity Catalog validates the external location on creation by attempting an access, which is why the depends_on matters and why RBAC propagation delay can make the first apply fail and the second succeed.

Level 2 · Implement Provision a VNet-injected workspace

Write the complete azurerm_databricks_workspace for production: injected into your own VNet, no public IPs on cluster nodes, no public network access, and a deliberately named managed resource group.

Include the subnets and NSG associations it depends on. One argument here is very commonly passed wrongly — get it right and say why it matters.

Show solution
databricks.tf
resource "azurerm_subnet" "databricks" {
  for_each = {
    host      = { netnum = 2 }
    container = { netnum = 3 }
  }

  name                 = "snet-databricks-${each.key}-${local.suffix}"
  resource_group_name  = azurerm_resource_group.network.name
  virtual_network_name = azurerm_virtual_network.main.name

  # Databricks requires /26 to /24 for these subnets; each node uses 2 IPs.
  address_prefixes = [cidrsubnet(var.vnet_cidr, 8, each.value.netnum)]

  service_endpoints = ["Microsoft.Storage", "Microsoft.KeyVault"]

  delegation {
    name = "databricks"
    service_delegation {
      name = "Microsoft.Databricks/workspaces"
      actions = [
        "Microsoft.Network/virtualNetworks/subnets/join/action",
        "Microsoft.Network/virtualNetworks/subnets/action",
        "Microsoft.Network/virtualNetworks/subnets/prepareNetworkPolicies/action",
        "Microsoft.Network/virtualNetworks/subnets/unprepareNetworkPolicies/action",
      ]
    }
  }
}

resource "azurerm_network_security_group" "databricks" {
  name                = "nsg-databricks-${local.suffix}"
  resource_group_name = azurerm_resource_group.network.name
  location            = var.location
  tags                = local.common_tags

  lifecycle {
    # Databricks injects its own required rules. Without this, every plan
    # proposes deleting them and Databricks re-adds them - a permanent diff.
    ignore_changes = [security_rule]
  }
}

resource "azurerm_subnet_network_security_group_association" "databricks" {
  for_each = azurerm_subnet.databricks

  subnet_id                 = each.value.id
  network_security_group_id = azurerm_network_security_group.databricks.id
}

resource "azurerm_databricks_workspace" "this" {
  name                = "dbw-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = var.location

  # premium is required for cluster ACLs, Unity Catalog and private link.
  sku = "premium"

  # Name it, or Azure invents something like databricks-rg-dbw-xxx-abc123.
  managed_resource_group_name = "${azurerm_resource_group.analytics.name}-databricks-managed"

  public_network_access_enabled         = false
  network_security_group_rules_required = "NoAzureDatabricksRules"

  custom_parameters {
    no_public_ip       = true
    virtual_network_id = azurerm_virtual_network.main.id

    public_subnet_name  = azurerm_subnet.databricks["host"].name
    private_subnet_name = azurerm_subnet.databricks["container"].name

    # THE ARGUMENT PEOPLE GET WRONG: these want the ID of the ASSOCIATION
    # resource, not the subnet. The strings happen to look similar, so
    # passing the subnet id "works" - and then the workspace can be created
    # before the NSG association exists, failing with an obscure network error.
    public_subnet_network_security_group_association_id =
      azurerm_subnet_network_security_group_association.databricks["host"].id
    private_subnet_network_security_group_association_id =
      azurerm_subnet_network_security_group_association.databricks["container"].id
  }

  tags = local.common_tags
}

Referencing the association resource is what creates the correct dependency edge: Terraform now knows the NSG must be attached to both subnets before the workspace is created. Reference the subnet instead and that ordering guarantee silently disappears.

On the naming: with no_public_ip = true neither subnet is internet-facing. “Public” and “private” are Databricks' historical terms for the host-side and container-side NICs on each node, not a statement about exposure.

Operationally: apply prod then prod-databricks; destroy prod-databricks then prod. The same rule applies to any provider configured from a resource you also create — Kubernetes, PostgreSQL, Vault.

Level 3 · Troubleshoot Destroy fails and leaves orphans

A team has one configuration containing the VNet, the workspace, and twelve databricks_* resources, with the provider configured from azurerm_databricks_workspace.this.workspace_url. terraform apply works. terraform destroy fails:

error
Error: cannot delete external location: Get "https://adb-1234.5.azuredatabricks.net/api/2.1/...":
dial tcp: lookup adb-1234.5.azuredatabricks.net: no such host

Explain the mechanism, get them unstuck, and give the structural fix.

Show answer

Mechanism. During destroy Terraform walks the graph in reverse. The Databricks objects depend on the workspace, so in principle they should be destroyed first — but the provider configuration also depends on the workspace, and Terraform does not model provider configuration as a graph node in the way you would need. In practice the workspace can be destroyed while its objects are still in state; the provider then cannot resolve the workspace URL, so deleting them is impossible. The resources are stuck in state pointing at something that no longer exists.

Getting unstuck. The workspace is gone, so its contents are gone with it. Remove the orphaned entries from state:

recovery
terraform state list | grep '^databricks_' | while read -r addr; do
  terraform state rm "$addr"
done

terraform destroy   # now completes on the remaining Azure resources

Structural fix — split into two root modules:

layout
terraform/
├── 10-platform/        VNet, storage, Key Vault, workspace, access connector
│   └── state: platform/prod.tfstate
└── 20-databricks/      catalogs, external locations, policies, grants
    └── state: databricks/prod.tfstate
    └── provider configured from a DATA SOURCE reading the workspace

Now the Databricks provider is configured from data.azurerm_databricks_workspace, which is known at plan time. Destroying is ordered naturally: tear down 20-databricks first, then 10-platform. This is the general answer whenever a provider's configuration would otherwise depend on a resource in the same configuration.

Interview questions

Describe the Azure Databricks architecture.

Two planes. The control plane runs in Databricks' own Azure subscription and hosts the web application, REST API, job scheduler and cluster manager. The compute plane runs in your subscription: when you start a cluster, Databricks provisions VMs into a managed resource group it creates in your subscription, attached either to a Databricks-managed VNet or, with VNet injection, to subnets you control. Your data never leaves your subscription. The managed resource group is visible and billable to you but owned by Databricks — you must not modify its contents.

How do you give Databricks access to ADLS Gen2 without credentials?

Create an azurerm_databricks_access_connector with a managed identity, grant that identity a Storage Blob Data role scoped per container, then on the Databricks side create a databricks_storage_credential referencing the access connector and one databricks_external_location per container. Unity Catalog then brokers access. No key, no service principal secret and no mount point with embedded credentials exists anywhere — and because the Azure role is per container, you can express policies like “read raw, write silver and gold”.

What is VNet injection and why use it?

Deploying the workspace's compute into subnets in your own virtual network rather than a Databricks-managed one. It matters because it lets cluster nodes reach private endpoints for storage and Key Vault, lets you apply your own NSGs, route tables and egress firewall, and lets you use secure cluster connectivity with no public IPs. It requires two delegated subnets — Databricks calls them the public/host and private/container subnets, though with no_public_ip neither is internet-facing — sized between /26 and /24, with NSG associations referenced from the workspace's custom_parameters.

Which Databricks resources should Terraform manage?

The platform, not the workloads. Terraform should own the workspace, networking, access connector and RBAC, plus the governance layer inside the workspace: cluster policies, Unity Catalog structure, external locations, grants, groups and SQL warehouses. It should not own notebooks, frequently changing jobs, interactive clusters or table DDL — those belong in git with Databricks Asset Bundles or dbt. Putting job definitions in Terraform means a schedule change needs an infrastructure pull request and an apply against production state, which is friction with no security benefit.

Why can configuring the Databricks provider be tricky?

Because it needs the workspace URL, which is an attribute of a resource that may not exist yet. Terraform requires provider configuration to be resolvable, and a configuration whose provider depends on a resource in the same apply plans awkwardly and often fails on destroy — the workspace can be deleted before the objects inside it, after which the provider cannot be configured to delete them, leaving orphaned state entries. The fix is to split into two root modules: one creating the Azure infrastructure, one configuring the workspace with its provider fed from a data source. That rule generalises to Kubernetes, PostgreSQL and any other provider configured from resources you also create.

How would you handle secrets that Databricks notebooks need?

A Key Vault-backed secret scope: databricks_secret_scope with a keyvault_metadata block pointing at the vault. Notebooks call dbutils.secrets.get and Databricks resolves the value from Key Vault at read time, so Terraform stores only the vault's resource ID and URI — no secret values in state. The alternative, a Databricks-backed scope populated with databricks_secret resources, writes every value into state and should be avoided. Better still, for Azure-to-Azure access, use the access connector's managed identity so there is no secret to store.

Key takeaways

  • azurerm owns anything with an ARM resource ID; databricks owns anything behind the workspace API.
  • The managed resource group belongs to Databricks. Name it, then leave it alone.
  • VNet injection needs two delegated subnets and the NSG association IDs, not the subnet IDs.
  • Access connector + role assignment + storage credential + external location = lake access with no secrets.
  • Split platform and workspace-contents into two root modules. A provider configured from a resource you create in the same apply will bite you on destroy.
  • Terraform owns guardrails; Asset Bundles and dbt own workloads.

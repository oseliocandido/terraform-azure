VNets, NSGs, private endpoints & private DNS

Private endpoints are two thirds networking and one third DNS — and the DNS third is where everyone loses a day. This lesson builds the network a data platform needs and explains the resolution chain precisely enough that you can debug it.

Planning the address space

Get this wrong and you cannot fix it without rebuilding — subnet address prefixes can be changed only if the subnet is empty, and VNet peering rejects overlapping ranges.

a data platform address plan
vnet-analytics-dev-weu-01        10.10.0.0/16     (65 536 addresses — generous, and free)
│
├── snet-privatelink              10.10.1.0/24     251 usable · private endpoint NICs
├── snet-databricks-host          10.10.2.0/24     251 usable · Databricks driver + executor VMs
├── snet-databricks-container     10.10.3.0/24     251 usable · Databricks container side
├── snet-functions                10.10.4.0/26      59 usable · delegated to Microsoft.Web
├── snet-agents                   10.10.5.0/27      27 usable · self-hosted CI agents
└── (reserved)                    10.10.6.0/24+                 future services
Azure reserves five addresses in every subnet

A /24 gives you 251 usable addresses, not 256: the network address, the broadcast address, and three that Azure keeps for the default gateway and DNS. A /29 therefore has 3 usable addresses, and /29 is the smallest subnet Azure accepts. Databricks additionally requires its host and container subnets to be between /26 and /24 — with two IPs consumed per cluster node, a /26 caps you at roughly 30 nodes.

network.tf — subnets from a typed variable
variable "vnet_cidr" {
  type    = string
  default = "10.10.0.0/16"
}

locals {
  # cidrsubnet(prefix, newbits, netnum):
  #   cidrsubnet("10.10.0.0/16", 8, 1) = "10.10.1.0/24"   (16 + 8 = /24)
  #   cidrsubnet("10.10.0.0/16", 10, 16) = "10.10.4.0/26" (16 + 10 = /26)
  subnets = {
    privatelink = {
      prefix            = cidrsubnet(var.vnet_cidr, 8, 1)
      service_endpoints = ["Microsoft.Storage", "Microsoft.KeyVault"]
      delegation        = null
    }
    databricks_host = {
      prefix            = cidrsubnet(var.vnet_cidr, 8, 2)
      service_endpoints = ["Microsoft.Storage", "Microsoft.KeyVault"]
      delegation        = "Microsoft.Databricks/workspaces"
    }
    databricks_container = {
      prefix            = cidrsubnet(var.vnet_cidr, 8, 3)
      service_endpoints = ["Microsoft.Storage", "Microsoft.KeyVault"]
      delegation        = "Microsoft.Databricks/workspaces"
    }
    functions = {
      prefix            = cidrsubnet(var.vnet_cidr, 10, 16)
      service_endpoints = ["Microsoft.Storage"]
      delegation        = "Microsoft.Web/serverFarms"
    }
  }
}

resource "azurerm_virtual_network" "main" {
  name                = "vnet-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location
  address_space       = [var.vnet_cidr]
  tags                = local.common_tags
}

resource "azurerm_subnet" "this" {
  for_each = local.subnets

  name                 = "snet-${replace(each.key, "_", "-")}-${local.suffix}"
  resource_group_name  = azurerm_resource_group.analytics.name
  virtual_network_name = azurerm_virtual_network.main.name
  address_prefixes     = [each.value.prefix]
  service_endpoints    = each.value.service_endpoints

  dynamic "delegation" {
    for_each = each.value.delegation == null ? [] : [each.value.delegation]

    content {
      name = "delegation"
      service_delegation {
        name = delegation.value
        actions = [
          "Microsoft.Network/virtualNetworks/subnets/join/action",
          "Microsoft.Network/virtualNetworks/subnets/action",
        ]
      }
    }
  }
}
Why cidrsubnet() rather than literal strings

With literals, changing the VNet's base range means editing every subnet by hand and getting one wrong. With cidrsubnet(), the whole plan shifts consistently when var.vnet_cidr changes, and dev/test/prod can occupy non-overlapping ranges from the same code. Verify your arithmetic in terraform console before applying — a mistake here is expensive to undo.

Common mistake · associations declared two ways

azurerm_subnet historically accepted inline network_security_group_id, and there is also a separate association resource. Using both for the same subnet makes them fight: each apply reports a change, undoing the other. Pick the separate association resource — it is the supported pattern and it works cleanly with for_each. The same applies to route table associations.

  name                = each.value

resource "azurerm_private_dns_zone_virtual_network_link" "storage" {
  for_each = local.storage_endpoints

  name                  = "link-${each.key}-${local.suffix}"
  resource_group_name   = azurerm_resource_group.analytics.name
  private_dns_zone_name = azurerm_private_dns_zone.storage[each.key].name
  virtual_network_id    = azurerm_virtual_network.main.id
  registration_enabled  = false
}

resource "azurerm_private_endpoint" "storage" {
  for_each = local.storage_endpoints

  name                = "pe-lake-${each.key}-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location
  subnet_id           = azurerm_subnet.this["privatelink"].id

  private_service_connection {
    name                           = "psc-lake-${each.key}"
    private_connection_resource_id = azurerm_storage_account.lake.id
    subresource_names              = [each.key]   # "blob" or "dfs"
    is_manual_connection           = false

  private_dns_zone_group {
    name                 = "pdz-${each.key}"
    private_dns_zone_ids = [azurerm_private_dns_zone.storage[each.key].id]
  }

  tags = local.common_tags
}
Why ADLS Gen2 needs two private endpoints

A private endpoint maps to one subresource. A storage account exposes separate endpoints for blob, dfs, file, queue, table and web. ADLS Gen2 clients use abfss://, which resolves through the dfs endpoint — but many tools, the portal's data browser included, use blob. Creating only the blob endpoint gives you a lake where the portal works fine and Spark fails with a name-resolution error. Create both, with both zones.

The zone name must be exact

Azure only auto-populates the A record when the zone uses the documented name. A typo — privatelink.blob.core.windows.com, or the region left in — creates a zone that silently resolves nothing. This produces a private endpoint that exists, shows “Approved”, and does not work.

How private endpoint DNS actually resolves

This is the part worth understanding properly, because it is where the failures are.

The one sentence that explains every private-endpoint DNS bug

Applications keep using the public hostname. Azure's public DNS returns a CNAME into privatelink.*. If the resolver can reach a private DNS zone with that name — because the zone is linked to the VNet the client sits in — the chain ends at a private IP. If not, it falls through to the public IP. So “it resolves to a public IP” always means the zone is missing, misnamed, not linked, or the client is using a resolver that cannot see it.

Common mistake · one zone shared by two different services

Microsoft's documentation explicitly warns against associating one private DNS zone with private endpoints of two different service types — it deletes the initial A record and breaks resolution for one of them. Create a zone per service type. The related trap: once a VNet is linked to privatelink.blob.core.windows.net, clients in that VNet may fail to resolve other storage accounts that have no private endpoint, because the private zone answers NXDOMAIN rather than falling through. Azure's “fallback to internet” option on the VNet link exists for exactly this.

The platform network, assembled

Outbound VNet integration for Functions

A private endpoint controls inbound access to a service. For a Function App to reach a private endpoint, you need the opposite: outbound VNet integration, which routes the app's egress through a delegated subnet.

functions-networking.tf
resource "azurerm_linux_function_app" "ingest" {
  # ...
  # Outbound: route egress through the delegated subnet.
  virtual_network_subnet_id = azurerm_subnet.this["functions"].id

  site_config {
    # Force ALL outbound traffic through the VNet, not just RFC1918 ranges.
    vnet_route_all_enabled = true
  }
}
The classic Functions + private endpoint failure

You disable public access on the storage account, add private endpoints, and the Function App stops working with Name or service not known or a 403. Cause: the app is not VNet-integrated, so its outbound traffic leaves from Azure's shared egress and cannot reach the private IP — or it is integrated but vnet_route_all_enabled is false, so only private ranges are routed and DNS still resolves publicly. You need integration and route-all and a linked private DNS zone.

Common mistakes

Databricks NSG rule drift

Databricks injects its own required security rules into the NSG attached to its subnets. If you manage security_rule blocks inline on that NSG, every plan will show Terraform removing Databricks' rules and Databricks re-adding them. Either keep the NSG bare (as in this lesson) and let Databricks own it, or use lifecycle { ignore_changes = [security_rule] }. Lesson 15.

Subnets sized for today

Changing a subnet's address prefix requires it to be empty — which for a Databricks subnet means deleting the workspace. Private address space is free and effectively unlimited; a /24 costs the same as a /28. Be generous, and leave gaps between allocations so you can grow one range without renumbering everything.

Private DNS zones in the workload resource group

Zones are usually shared infrastructure — one privatelink.blob.core.windows.net per landing zone, linked to many VNets. Creating a copy per workload works until two of them try to hold records for accounts in the same VNet, at which point resolution becomes ambiguous. In an enterprise landing zone the zones live in a central connectivity subscription and workloads reference them via a provider alias (Lesson 04) or a data source.

Exercises

Level 1 · Understand Why does Spark fail but the portal works?

A team disables public network access on their ADLS Gen2 account and creates one private endpoint with subresource_names = ["blob"] and the zone privatelink.blob.core.windows.net, linked to the VNet.

Browsing containers in the portal from a jump box in the VNet works. A Databricks notebook reading abfss://bronze@stanalyticsdevweu01.dfs.core.windows.net/ fails. Why, and what is the fix?

Show answer

The abfss:// driver targets the dfs endpoint — stanalyticsdevweu01.dfs.core.windows.net — and there is no private endpoint or private DNS zone for dfs. That name resolves via public DNS to the account's public IP, and public network access is disabled, so the connection is refused.

The portal's data browser uses the blob endpoint, which does have a private endpoint, so it works — which is exactly why this bug survives testing.

Fix: add the second endpoint and zone.

fix

  name                = "privatelink.dfs.core.windows.net"
  resource_group_name = azurerm_resource_group.analytics.name
}

resource "azurerm_private_dns_zone_virtual_network_link" "dfs" {
  name                  = "link-dfs"
  resource_group_name   = azurerm_resource_group.analytics.name
  private_dns_zone_name = azurerm_private_dns_zone.dfs.name
  virtual_network_id    = azurerm_virtual_network.main.id
}

resource "azurerm_private_endpoint" "lake_dfs" {
  name                = "pe-lake-dfs-${local.suffix}"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location
  subnet_id           = azurerm_subnet.this["privatelink"].id

  private_service_connection {
    name                           = "psc-lake-dfs"
    private_connection_resource_id = azurerm_storage_account.lake.id

General rule: enumerate every endpoint your consumers use, and create a private endpoint and zone for each. For a data lake that is nearly always blob and dfs together.

Level 2 · Implement Generalise the private endpoint pattern

Write configuration that creates private endpoints and private DNS zones for a variable set of targets — the lake (blob and dfs) and the Key Vault (vault) — with no repeated resource blocks, zones created only once each, and each VNet link created only once.

Show answer
private-endpoints.tf
locals {

Level 2 · Implement Write an NSG whose rules come from a variable

The Functions subnet needs a network security group with rules supplied by the caller, so the same module serves dev (permissive) and prod (locked down). Write the variable and the resource.

Priorities must be assigned automatically from the map order so a caller never has to think about collisions, and the whole thing must work with zero rules.

Show solution
nsg.tf
variable "nsg_rules" {
  description = "Security rules, keyed by name. Priority is derived from order."

  type = map(object({
    direction                  = string
    access                     = string
    protocol                   = optional(string, "Tcp")
    source_port_range          = optional(string, "*")
    destination_port_range     = string
    source_address_prefix      = optional(string, "*")
    destination_address_prefix = optional(string, "*")
    description                = optional(string)
  }))

  default = {}

  validation {
    condition = alltrue([
      for r in values(var.nsg_rules) : contains(["Inbound", "Outbound"], r.direction)
    ])
    error_message = "direction must be Inbound or Outbound."
  }

  validation {
    condition = alltrue([
      for r in values(var.nsg_rules) : contains(["Allow", "Deny"], r.access)
    ])
    error_message = "access must be Allow or Deny."
  }

  validation {
    # Azure allows priorities 100-4096; leave headroom above our block.
    condition     = length(var.nsg_rules) <= 100
    error_message = "At most 100 rules are supported by this module."
  }
}

locals {
  # keys() over a map is sorted, so priorities are deterministic between
  # runs. A non-deterministic order here would churn rules on every apply.
  rule_names = keys(var.nsg_rules)
}

resource "azurerm_network_security_group" "functions" {
  name                = "nsg-functions-${local.suffix}"
  resource_group_name = var.resource_group_name
  location            = var.location
  tags                = var.tags

  dynamic "security_rule" {
    for_each = var.nsg_rules

    content {
      name        = security_rule.key
      description = security_rule.value.description

      priority  = 100 + (index(local.rule_names, security_rule.key) * 10)
      direction = security_rule.value.direction
      access    = security_rule.value.access
      protocol  = security_rule.value.protocol

      source_port_range          = security_rule.value.source_port_range
      destination_port_range     = security_rule.value.destination_port_range
      source_address_prefix      = security_rule.value.source_address_prefix
      destination_address_prefix = security_rule.value.destination_address_prefix
    }
  }
}
env/prod.tfvars
nsg_rules = {
  allow-https-from-vnet = {
    direction                  = "Inbound"
    access                     = "Allow"
    destination_port_range     = "443"
    source_address_prefix      = "VirtualNetwork"
    destination_address_prefix = "VirtualNetwork"
    description                = "Internal HTTPS only."
  }
  deny-all-inbound = {
    direction              = "Inbound"
    access                 = "Deny"
    protocol               = "*"
    destination_port_range = "*"
    description            = "Explicit catch-all below the allows."
  }
}

The priority derivation is the interesting part. Stepping by 10 leaves room to insert a rule between two existing ones later, and deriving it from keys() — which is sorted for a map — makes the assignment deterministic. If priorities shuffled between runs, every apply would rewrite every rule.

There is a real limitation to notice: because priority follows alphabetical key order, deny-all-inbound sorts before allow-https-from-vnet and would therefore win. For a production module you would add an explicit optional priority field and only auto-assign when it is null. Spotting that ordering bug is the point of the exercise.

Level 2 · Implement Make the private endpoint pattern reusable

You now need private endpoints for the lake (blob and dfs), the Key Vault, and later the Function App. Write configuration that handles all of them with no repeated resource blocks, creates each DNS zone exactly once even when two endpoints share one, and can be switched off entirely for dev.

Zones must be created once per zone name, not once per endpoint.

Show solution
private-endpoints.tf
variable "enable_private_endpoints" {
  type    = bool
  default = true
}

locals {
  # Empty map when disabled: for_each over {} creates nothing, and needs
  # no count/conditional gymnastics.
  private_endpoints = var.enable_private_endpoints ? {
    lake_blob = {
      target = azurerm_storage_account.lake.id
      sub    = "blob"
      zone   = "privatelink.blob.core.windows.net"

    lake_dfs = {
      target = azurerm_storage_account.lake.id
      sub    = "dfs"

      target = azurerm_key_vault.main.id
      sub    = "vault"

      target = azurerm_linux_function_app.ingest.id
      sub    = "sites"

  private_service_connection {
    name                           = "psc-${each.key}"
    private_connection_resource_id = each.value.target
    subresource_names              = [each.value.sub]
    is_manual_connection           = false
  }

  # WITHOUT this block the endpoint exists, shows "Approved" in the portal,
  # and resolves nothing - because no A record is ever written into the zone.
  private_dns_zone_group {
    name                 = "pdz-${each.key}"
    private_dns_zone_ids = [azurerm_private_dns_zone.this[each.value.zone].id]
  }

  tags = local.common_tags
}

output "private_endpoint_ips" {
  value = {
    for k, pe in azurerm_private_endpoint.this :
    k => pe.private_service_connection[0].private_ip_address
  }
}

toset([for pe in ... : pe.zone]) is what makes this scale. Add a fifth endpoint sharing an existing zone and nothing breaks; without it you would get A resource with the ID ... already exists.

Note also that for_each over an empty map is a much cleaner way to express “disabled” than count = var.enabled ? 1 : 0 — you keep meaningful instance keys, and adding a sixth endpoint stays a one-line data change.

The apply succeeds. The endpoint shows as Approved in the portal. Clients still resolve the public IP. Find four problems.

Show answer

1 · No private_dns_zone_group — the main bug.

The zone exists but nothing ever writes an A record into it. That block is what tells Azure to register the endpoint's private IP in the zone. Without it, the zone is empty and resolution falls through to the public IP. This is the single most common private endpoint mistake, precisely because the apply succeeds and the portal shows green.

2 · No azurerm_private_dns_zone_virtual_network_link.

A private DNS zone is only visible to VNets it is linked to. Unlinked, it would not be consulted even if it did contain records.

3 · Missing the dfs endpoint and zone.

Only blob is configured, so ADLS Gen2 clients using abfss:// will not work — the failure from the previous exercise.

4 · The subnet is far too small.

A /29 yields three usable addresses after Azure's five reserved. Two storage endpoints plus a Key Vault endpoint already fills it, and the next one fails with no available IPs. Use a /24; the addresses are free.

A fifth, softer issue: the resource names carry no environment or region suffix, so this cannot be deployed twice into the same resource group.

Real-world scenario

Scenario 3 from the brief

“Production and development require different networking configurations.”

Production needs private endpoints and no public access. Development cannot justify the per-endpoint cost, and engineers need to reach the lake from their laptops. Three ways to express that:

  1. Conditional resources in one module. count = var.enable_private_endpoints ? 1 : 0. Keeps everything in one place, but the configuration accumulates conditionals and dev stops resembling prod — so a change validated in dev may still break production networking.
  2. A separate root module per environment calling shared modules. Prod's main.tf calls the private-endpoints module; dev's does not. More files, far more honest — and a reviewer can see at a glance what production has that dev does not.
  3. Same topology, cheaper settings. Dev keeps private endpoints but skips the Databricks workspace, or uses service endpoints plus IP rules instead of private endpoints — free, and structurally similar enough that the DNS and firewall logic is still exercised.

I would take option 2 for the structure and option 3 for the substance: dev uses service endpoints and a firewall allowing the office range, prod uses private endpoints with public access disabled. The important principle is that the difference should be visible and deliberate, not buried in a boolean that nobody re-reads.

Interview questions

What is the difference between a service endpoint and a private endpoint?

A service endpoint keeps traffic on the Azure backbone and lets the service's firewall recognise your subnet, but the service keeps its public IP and public DNS name — you are filtering access to a public endpoint. A private endpoint gives the service a NIC with a private IP inside your VNet, so it can be reached with no public exposure at all and public access can be disabled entirely. Service endpoints are free and need no DNS work; private endpoints are billed per hour and require private DNS zones linked to the VNet, which is where most of the operational complexity lives.

How does DNS resolution work for a private endpoint?

The client keeps using the public hostname. Azure's public DNS returns a CNAME pointing into the privatelink zone for that service — for example account.privatelink.dfs.core.windows.net. If a private DNS zone with that exact name is linked to the client's VNet and contains an A record for the resource, the chain resolves to the private IP; otherwise it falls through to the public IP. So three things must all be true: the zone exists with the documented name, it is linked to the VNet, and the private endpoint has a private_dns_zone_group that registers the A record.

Why does ADLS Gen2 need two private endpoints?

Because a private endpoint targets one subresource, and a storage account exposes separate service endpoints. ADLS Gen2 clients using abfss:// — Databricks, Synapse, Fabric — go through the dfs endpoint, while the portal's data browser and many SDKs use blob. You need a private endpoint and matching private DNS zone for each. Creating only blob produces a lake where portal browsing works and Spark cannot connect, which is a genuinely confusing failure to debug.

What is subnet delegation?

Handing a subnet to a specific Azure service so it may inject its own resources and required network rules into it. Databricks delegates its host and container subnets to Microsoft.Databricks/workspaces; regional VNet integration for a Function App delegates its subnet to Microsoft.Web/serverFarms. A delegated subnet is effectively owned by that service — you cannot put arbitrary resources in it, and the service may manage NSG rules there, which is why you often need ignore_changes on those rules.

How do you decide subnet sizes?

Generously, because private address space is free and resizing a subnet requires it to be empty — which for a Databricks subnet means deleting the workspace. Azure reserves five addresses per subnet, and service minimums apply: /29 is the smallest Azure allows, Databricks host and container subnets must be between /26 and /24, and each cluster node consumes two IPs. I would use a /16 VNet with /24 subnets and leave numbering gaps so one range can grow without renumbering everything.

A Function App cannot reach a storage account behind a private endpoint. What do you check?

Three things in order. Is the app VNet-integrated — does it have virtual_network_subnet_id set to a delegated subnet? Is vnet_route_all_enabled true, so all egress goes through the VNet rather than only private ranges? And is the private DNS zone linked to that VNet, so the app resolves the private IP rather than the public one? A private endpoint governs inbound access to the storage account; making the Function App able to use it is a separate, outbound concern that people often forget.

Key takeaways

  • A private endpoint is a NIC in your subnet. It needs a matching private DNS zone and a VNet link and a private_dns_zone_group — miss any one and it silently does nothing.
  • Applications keep using the public hostname; the CNAME chain lands in the privatelink zone. That is why “it resolves to a public IP” is always a zone problem.
  • ADLS Gen2 needs two endpoints: blob and dfs.
  • Size subnets generously — resizing requires emptying them, and address space is free.
  • Use the separate NSG/route-table association resources, never both inline and separate.
  • Inbound private endpoints and outbound VNet integration are different problems. A Function App needs both.

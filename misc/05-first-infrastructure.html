Resource groups

A resource group is a named container inside a subscription. Three properties matter to you as a Terraform author:

  • It is a lifecycle boundary. Deleting the resource group deletes everything inside it, in the right order, without you specifying anything. This is why ephemeral environments are usually one resource group.
  • It is the most common RBAC scope. “The data engineering team are Contributors on rg-analytics-dev” is the typical unit of permission.
  • Its location is not where its resources live. This surprises everyone. A resource group in westeurope can hold a storage account in northeurope. The RG's location only determines where its own metadata is stored.
main.tf
resource "azurerm_resource_group" "analytics" {
  name     = "rg-analytics-dev-weu-01"
  location = "westeurope"

  tags = {
    workload    = "analytics"
    environment = "dev"
    managed_by  = "terraform"
  }
}
Practical consequence of RG location

In practice you should still put resources in the same region as their resource group — mixing regions within one RG makes the platform harder to reason about and can create cross-region data-transfer charges. But when a service is unavailable in your primary region, it is completely legitimate to place it elsewhere in the same RG. The exception is disaster recovery planning: if the RG's metadata region has an outage, you cannot perform management-plane operations on it, though the resources themselves keep serving traffic.

Azure regions

The location argument accepts either the display name or the internal name, case-insensitively — "West Europe", "westeurope" and "WestEurope" are all accepted and all normalise to the same thing.

Pick one form and use it everywhere

Mixing forms across a codebase produces no functional difference but makes grep unreliable and can create noisy diffs when a provider version changes its normalisation. Standardise on the lowercase, no-space form (westeurope) — it is what the API returns, so it never produces a plan diff.

location.tf — never hardcode it twice
variable "location" {
  type        = string
  description = "Azure region for all resources in this deployment."
  default     = "westeurope"
}

resource "azurerm_resource_group" "analytics" {
  name     = "rg-analytics-dev-weu-01"
  location = var.location
}

resource "azurerm_storage_account" "lake" {
  # Reference the RG's location rather than var.location again.
  # This makes it structurally impossible for them to drift apart.
  location            = azurerm_resource_group.analytics.location
  resource_group_name = azurerm_resource_group.analytics.name
  # ...
}

Naming conventions

Microsoft's Cloud Adoption Framework recommends <resource-type>-<workload>-<environment>-<region>-<instance>. It is not enforced by Azure, but a consistent scheme is what lets you write cost queries, policy assignments and access reviews that actually work.

Three resources are globally unique across all of Azure

Storage accounts, Key Vaults and Function Apps get a DNS name, so their names must be unique across every Azure customer in the world, not just your subscription. stdatalake01 was taken years ago.

This is also why the failure appears only at apply: validate can check the regex, but only the API knows whether the name is available.

Generating names consistently

naming.tf — the pattern used for the rest of this course
locals {
  workload = "analytics"
  env      = "dev"
  region   = "weu"
  instance = "01"

  # Standard pattern for resources that allow hyphens.
  suffix = "${local.workload}-${local.env}-${local.region}-${local.instance}"

  # Storage accounts allow neither hyphens nor uppercase, and cap at 24 chars.
  # substr() guarantees we never exceed the limit as workload names grow.
  sa_name = substr(
    lower(replace("st${local.suffix}", "-", "")),
    0, 24
  )
  # → "stanalyticsdevweu01"

  common_tags = {
    workload    = local.workload
    environment = local.env
    managed_by  = "terraform"
    repository  = "contoso/analytics-platform"
  }
}

resource "azurerm_resource_group" "analytics" {
  name     = "rg-${local.suffix}"      # rg-analytics-dev-weu-01
  location = var.location
  tags     = local.common_tags
}
When global uniqueness needs help

If stanalyticsdevweu01 is taken, add a deterministic suffix rather than a random one where you can — for example the last six characters of the subscription ID, which is stable across applies. A random_string resource also works, but remember its value lives in state: lose the state and the next apply generates a different name and tries to build a whole new storage account.

⚠ v4 → v5: storage_account_id

In v3 and v4 the container took storage_account_name = azurerm_storage_account.lake.name. In v5 that argument is removed and storage_account_id is required. Older tutorials will fail with Unsupported argument. Note also that migrating an existing v4 configuration to the new argument was a known pain point — the provider added a migration path in 4.20, but doing it carelessly on earlier versions forced container replacement, which deletes data.

Code → provider → Azure → state

This is the chain you need to hold in your head for every resource you ever write. Take the storage account above and follow it all the way through.

Three things in that output are worth pausing on:

  • (known after apply) — Terraform cannot know the resource ID or the endpoint URLs until Azure responds. Note that storage_account_id on the container is unknown for exactly this reason: it depends on a resource that does not exist yet. That unknown is the dependency edge, made visible.
  • (sensitive value) — the provider marks primary_access_key sensitive so it is redacted from output. It will still be written to state in plaintext. Lesson 09.
  • resource_group_name = "rg-analytics-dev-weu-01" is known, even though the resource group does not exist yet — because the name is a literal in the configuration, not a computed attribute. Terraform still orders the operations correctly, because the reference creates the edge regardless of whether the value is known.

Note what is in there

primary_access_key — a credential granting full control of the storage account and all its data — is stored in plaintext. Terraform redacts it from console output; it does not encrypt it in state. This is the single strongest argument for a remote backend with encryption and tight access control, and for using managed identities so the key is never needed at all. Lessons 09 and 10.

Reading an Azure resource ID

Resource IDs matter more in Terraform than in the portal: they are what import takes, what role assignment scope takes, and what appears throughout state.

anatomy of a resource ID
/subscriptions/00000000-0000-0000-0000-000000000000
└─┬───────────┘└─┬────────────────────────────────┘
  │              └── subscription GUID
  └── always literal "subscriptions"

                └── resource group name

           └─┬──────────────┘└─┬───────────┘ └─┬───────────────┘

Dependencies

Implicit dependencies — the default and the right one

Any reference to another resource's attribute creates an edge. This is how 95% of ordering should be expressed.

implicit.tf
resource "azurerm_storage_container" "raw" {
  name = "raw"

  # This reference IS the dependency. Terraform reads it, sees the address
  # azurerm_storage_account.lake, and adds the edge. Nothing else is needed.
  storage_account_id = azurerm_storage_account.lake.id
}

Explicit dependencies — depends_on

For genuine ordering requirements that involve no data flow. These exist, but they are rarer than people think.

legitimate depends_on
# A role assignment granting the deployer permission to write data.
resource "azurerm_role_assignment" "deployer_blob_contributor" {
  scope                = azurerm_storage_account.lake.id
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = data.azurerm_client_config.current.object_id
}

# Creating a data-plane object requires that role to already be effective.
# There is no attribute of the role assignment we need — so no reference
# would otherwise exist, and Terraform could create these in parallel.
resource "azurerm_storage_data_lake_gen2_filesystem" "bronze" {
  name               = "bronze"
  storage_account_id = azurerm_storage_account.lake.id

  depends_on = [azurerm_role_assignment.deployer_blob_contributor]
}
Why blanket depends_on is bad practice

Adding it “just to be safe” causes four concrete problems:

  1. It serialises the graph. Terraform's parallelism disappears; applies get slower as the configuration grows.
  2. It is coarser than a reference. A depends_on on a module waits for everything in that module, not the one resource you cared about.
  3. It hides broken references. If ordering works only because of depends_on, someone has probably hardcoded a string where a reference belonged — and that literal will silently go stale.
  4. It can force unnecessary replacement. When a depends_on target is replaced, Terraform may conservatively treat downstream resources as needing replacement too, because it cannot reason about what the dependency provided.

The rule: reach for depends_on only when there is a real ordering requirement with no data flowing between the resources. RBAC propagation before a data-plane operation is the classic legitimate case in Azure.

Which changes destroy your data

Every argument in a provider's schema is marked either updatable or ForceNew. Changing a ForceNew argument means Terraform must delete the resource and create a new one — there is no in-place path.

ChangeResultConsequence
tags~ update in placeHarmless
account_replication_type LRS → GRS~ update in placeHarmless; Azure starts replicating
access_tier Hot → Cool~ update in placeChanges billing; may incur early-deletion charges
name-/+ replaceAll data deleted. Azure has no rename.
location-/+ replaceAll data deleted. Resources cannot move between regions.
is_hns_enabled-/+ replaceAll data deleted. You cannot convert a flat account to ADLS Gen2 in place.
resource_group_name-/+ replaceAll data deleted.
account_kind Storage → StorageV2~ update in placeAn explicit exception the provider documents — an upgrade, not a replacement
what a replacement looks like — read this carefully
  # azurerm_storage_account.lake must be replaced
-/+ resource "azurerm_storage_account" "lake" {
      ~ id             = "/subscriptions/.../stanalyticsdevweu01" -> (known after apply)
      ~ is_hns_enabled = false -> true # forces replacement
        name           = "stanalyticsdevweu01"
    }

Plan: 1 to add, 0 to change, 1 to destroy.
The comment # forces replacement is the most important text in any plan

Terraform tells you exactly which argument triggered it. On a storage account holding your data lake, that plan destroys everything and rebuilds an empty account — and because storage account names are globally unique, the destroy must complete before the create, so there is a window where the name does not exist. Lesson 15 covers prevent_destroy as a guard against applying this by accident.

Exercises

Level 1 · Understand Update or replace?

For a deployed azurerm_storage_account, say whether each change is an in-place update or a replacement, and why:

  1. Adding a tag cost_center = "DATA-01"
  2. Changing min_tls_version from "TLS1_2" to "TLS1_3"
  3. Changing location from "westeurope" to "northeurope"
  4. Setting is_hns_enabled = true on an account created without it
  5. Changing account_replication_type from "LRS" to "GZRS"
Show answer
  1. Update. Tags are metadata; ARM supports a PATCH.
  2. Update. A settable property on the existing account.
  3. Replace. Region is fixed at creation — an Azure constraint, not a Terraform one. All data is lost.
  4. Replace. The hierarchical namespace is a fundamental storage-layer property chosen at creation. All data is lost. This is the one that catches people who start with a plain blob account and later decide they want ADLS Gen2.
  5. Update. Replication can be changed live; Azure begins replicating in the background.

General heuristic: if Azure's own portal offers no way to change a setting after creation, Terraform will need a replacement. When unsure, read the registry documentation — every ForceNew argument says “Changing this forces a new resource to be created.”

Level 2 · Implement Build the medallion skeleton

Extend the configuration in this lesson so that it also creates containers bronze, silver and gold alongside raw. Requirements:

  • All four private.
  • No copy-pasted resource blocks.
  • Removing silver from the list later must not affect gold.
  • Output a map from container name to its abfss:// URI.
Show answer
containers.tf
variable "containers" {
  type        = set(string)
  description = "Medallion layers to create in the data lake."
  default     = ["raw", "bronze", "silver", "gold"]
}

resource "azurerm_storage_container" "layers" {
  for_each = var.containers

  name                  = each.value
  storage_account_id    = azurerm_storage_account.lake.id
  container_access_type = "private"
}

output "abfss_paths" {
  description = "abfss:// URI per medallion layer, for Spark configuration."
  value = {
    for name, c in azurerm_storage_container.layers :
    name => "abfss://${name}@${azurerm_storage_account.lake.name}.dfs.core.windows.net/"
  }
}

Declaring the variable as set(string) rather than list(string) lets it feed for_each directly with no toset(). The resulting state addresses are azurerm_storage_container.layers["raw"] and so on — keyed by name, so removing "silver" destroys exactly one container and leaves gold untouched. With count over a list it would have destroyed and recreated gold as well, because its index would have shifted from 3 to 2.

Note that each.key and each.value are identical when iterating a set of strings.

Level 2 · Implement Write the medallion lake from scratch

With no copying from earlier in the lesson, write a complete configuration that creates:

  • A resource group and an ADLS Gen2 storage account, both consistently named from one place.
  • Containers raw, bronze, silver and gold, driven by a variable, where removing one from the list affects only that container.
  • Tags applied to everything, merged from a common set.
  • Outputs: the DFS endpoint, and a map of container name to its abfss:// URI.
  • The storage account protected against accidental destruction.
Show solution
main.tf
variable "workload"    { type = string }
variable "environment" { type = string }
variable "location" {
  type    = string
  default = "westeurope"
}

variable "medallion_layers" {
  type        = set(string)
  description = "Containers to create in the lake."
  default     = ["raw", "bronze", "silver", "gold"]
}

locals {
  region_short = { westeurope = "weu", northeurope = "neu" }

  suffix = "${var.workload}-${var.environment}-${local.region_short[var.location]}-01"

  # Storage accounts: lowercase alphanumeric only, max 24 characters.
  sa_name = substr(lower(replace("st${local.suffix}", "-", "")), 0, 24)

  common_tags = {
    workload    = var.workload
    environment = var.environment
    managed_by  = "terraform"
  }
}

resource "azurerm_resource_group" "analytics" {
  name     = "rg-${local.suffix}"
  location = var.location
  tags     = local.common_tags
}

resource "azurerm_storage_account" "lake" {
  name                = local.sa_name
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = var.environment == "prod" ? "GZRS" : "LRS"

  is_hns_enabled                  = true    # this is what makes it ADLS Gen2
  https_traffic_only_enabled      = true
  min_tls_version                 = "TLS1_2"
  allow_nested_items_to_be_public = false

  tags = merge(local.common_tags, {
    data_classification = "confidential"
  })

  lifecycle {
    prevent_destroy = true
  }
}

# for_each, not count: the state address becomes ["silver"] rather than [2],
# so removing a layer destroys exactly that layer.
resource "azurerm_storage_container" "layers" {
  for_each = var.medallion_layers

  name                  = each.value
  storage_account_id    = azurerm_storage_account.lake.id
  container_access_type = "private"
}

output "lake_dfs_endpoint" {
  description = "DFS endpoint for abfss:// access from Spark."
  value       = azurerm_storage_account.lake.primary_dfs_endpoint
}

output "layer_paths" {
  description = "abfss:// URI per medallion layer."
  value = {
    for name, c in azurerm_storage_container.layers :
    name => "abfss://${name}@${azurerm_storage_account.lake.name}.dfs.core.windows.net/"
  }
}

The details that separate this from a first attempt: local.suffix defined once so the naming scheme changes in one place; substr(lower(replace(...))) guarding the storage account's character and length rules; set(string) so the variable feeds for_each with no toset(); and merge() so per-resource tags extend the common set rather than replacing it.

Note also that location on the storage account references the resource group rather than var.location again. That makes it structurally impossible for the two to drift apart.

Level 2 · Implement Add a second storage account without duplicating the module

The platform now needs a second, separate account for Function App runtime state — deliberately not the data lake, for the reasons in Lesson 13. It should be plain blob storage (no hierarchical namespace), LRS, and it does not need medallion containers.

Refactor so both accounts come from one for_each-driven resource block rather than two copy-pasted ones, and say when you would not do this.

Show solution
storage.tf
locals {
  storage_accounts = {
    lake = {
      name_prefix  = "st"
      hns          = true
      replication  = var.environment == "prod" ? "GZRS" : "LRS"
      containers   = var.medallion_layers
      classification = "confidential"
    }
    functions = {
      name_prefix  = "stfn"
      hns          = false
      replication  = "LRS"
      containers   = []
      classification = "internal"
    }
  }

  # Flatten (account, container) pairs into a single stably-keyed map.
  containers = {
    for pair in flatten([
      for acct, cfg in local.storage_accounts : [
        for c in cfg.containers : { acct = acct, container = c }
      ]
    ]) : "${pair.acct}-${pair.container}" => pair
  }
}

resource "azurerm_storage_account" "this" {
  for_each = local.storage_accounts

  name                = substr(lower(replace("${each.value.name_prefix}${local.suffix}", "-", "")), 0, 24)
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = each.value.replication

  is_hns_enabled                  = each.value.hns
  https_traffic_only_enabled      = true
  min_tls_version                 = "TLS1_2"
  allow_nested_items_to_be_public = false

  tags = merge(local.common_tags, {
    data_classification = each.value.classification
  })
}

resource "azurerm_storage_container" "layers" {
  for_each = local.containers

  name                  = each.value.container
  storage_account_id    = azurerm_storage_account.this[each.value.acct].id
  container_access_type = "private"
}

When you would not do this. The two accounts serve genuinely different purposes and will diverge: the lake will grow lifecycle policies, private endpoints for blob and dfs, customer-managed keys and prevent_destroy; the runtime account needs none of those and must stay reachable by the Functions host.

Once the differences outnumber the similarities, a shared for_each becomes a block full of conditionals keyed on each.key — harder to read than two explicit resources. The honest answer here is that two separate blocks are better, and the exercise is worth doing to feel where that line sits. Deduplication is not automatically an improvement.

Level 3 · Troubleshoot Intermittent apply failure

This configuration succeeds roughly half the time. When it fails, the error is Error: creating Storage Account: Code="ResourceGroupNotFound".

flaky.tf

  type    = string
  default = "rg-analytics-dev-weu-01"
}

resource "azurerm_resource_group" "analytics" {
  name     = var.resource_group_name
  location = "westeurope"
}

resource "azurerm_storage_account" "lake" {
  name                     = "stanalyticsdevweu01"
  resource_group_name      = var.resource_group_name

Why is it intermittent, and what is the correct fix? Explain why depends_on would be the wrong fix.

Cause. Both resources reference var.resource_group_name, and neither references the other. In the dependency graph they are siblings that both depend on the variable — so there is no edge between them, and Terraform creates them in parallel. Whether it works depends on whether the resource group's creation happens to complete before the storage account request arrives. That is a race, hence the ~50% failure rate.

Correct fix — reference the resource, not the variable:

fixed.tf
resource "azurerm_storage_account" "lake" {
  name                     = "stanalyticsdevweu01"
  resource_group_name      = azurerm_resource_group.analytics.name
  location                 = azurerm_resource_group.analytics.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
}

Why depends_on is the wrong fix. Adding depends_on = [azurerm_resource_group.analytics] would make the symptom go away, which is exactly why it is tempting and exactly why it is dangerous. It papers over a structurally broken configuration: the storage account still does not know where its resource group name comes from. If someone later renames the resource group by changing the azurerm_resource_group block without updating the variable default, the reference-based version fixes itself and the depends_on version breaks in a confusing way.

This is the general principle: a missing reference is a bug, and depends_on hides bugs. Use it only where no data flows at all.

Real-world scenario

Scenario

“Terraform plan wants to destroy and recreate our production storage account. It has 40 TB in it. What do you do?”

A structured investigation:

  1. Do not apply. Obvious, but the first thing to say out loud. If a pipeline might apply automatically, disable it now.
  2. Find the trigger. The plan tells you: look for the line ending # forces replacement. There is always exactly one argument (or more) responsible.
  3. Classify the cause. Three possibilities:
    • Someone changed the configuration — check git log -p on the file. Revert if unintended.
    • Someone changed Azure — drift. The portal change moved a ForceNew attribute; the plan is trying to move it back. Decide which value is correct.
    • The provider changed — a new major version altered how an argument is handled, or a previously optional argument now has a different default. Check git diff .terraform.lock.hcl.
  4. If the new value is genuinely required, a replacement is not the route. Migrating a data lake means creating a new account alongside, copying data (azcopy, AzCopy jobs, or Databricks), repointing consumers, then decommissioning — a project, not a Terraform apply.
  5. Prevent recurrence. Add lifecycle { prevent_destroy = true } to the storage account so any future plan that tries this fails at plan time rather than waiting for someone to read carefully. Add an Azure resource lock as a second layer that works even outside Terraform. Add a CI check that fails when the plan JSON contains a delete action. Lessons 15 and 18.

The answer an interviewer is listening for is that you investigate the cause before touching anything, and that you know a replacement of a stateful resource is a data-migration problem rather than a Terraform problem.

Interview questions

What is an Azure resource group and what does its location mean?

A logical container within a subscription that groups resources sharing a lifecycle and, usually, an RBAC scope. Deleting it deletes everything in it. Its location determines only where the resource group's own metadata is stored — resources inside it can be in different regions. In practice you keep them aligned for clarity and to avoid cross-region charges, but it is not a technical requirement.

What is the difference between an implicit and an explicit dependency?

An implicit dependency is created automatically when one resource references another's attribute — Terraform parses the reference and adds a graph edge. An explicit dependency is declared with depends_on and is needed only when ordering matters but no data flows, for example creating a role assignment before performing a data-plane operation that requires it. Implicit is strongly preferred: it is precise, self-documenting, and cannot go stale. Overusing depends_on serialises the graph and hides places where a hardcoded string should have been a reference.

Why do storage account names have such restrictive rules?

Because the name becomes a DNS hostname — <name>.blob.core.windows.net and .dfs.core.windows.net — so it must be globally unique across every Azure tenant and legal in DNS: 3–24 characters, lowercase letters and digits only. The practical consequence for Terraform is that the failure surfaces only at apply, since validate can check the character rules but not whether another customer already took the name.

What does “forces replacement” mean in a plan?

That the argument you changed cannot be updated in place, because the underlying API has no way to change it on an existing resource — so Terraform must destroy the resource and create a new one, shown as -/+. On stateful resources this destroys the data. Common Azure examples are name, location, resource_group_name and is_hns_enabled on a storage account. The plan output names the specific argument responsible, and a careful reviewer looks for that comment before anything else.

Can you rename a Terraform-managed Azure resource without downtime?

Not the Azure name — Azure has no rename operation, so changing name always means destroy and recreate. You can, however, freely rename the Terraform address — the second label in the resource block — by using a moved block, which tells Terraform the resource in state has a new address without touching Azure at all. Distinguishing these two kinds of “rename” is the point of the question.

What does Terraform store in state for a storage account?

The resource address, the real Azure resource ID, every attribute returned by the API — including computed ones like the endpoint URLs — the provider that manages it, the schema version, and its dependencies. Critically that includes primary_access_key in plaintext. Terraform redacts sensitive values from console output but does not encrypt them in state, which is why state must live in an encrypted remote backend with tight access control.

Key takeaways

  • A resource group's location stores its metadata; it does not constrain where its resources live.
  • Storage accounts, Key Vaults and Function Apps are globally unique because their names become DNS hostnames.
  • Reference other resources' attributes instead of repeating literals — the reference is the dependency.
  • depends_on is for ordering without data flow. Everywhere else it hides a missing reference.
  • (known after apply) in a plan is a dependency edge made visible.
  • Read every plan for # forces replacement. On a data-bearing resource that comment means data loss.

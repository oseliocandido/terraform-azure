Azure Functions

The Azure equivalent of AWS Lambda — but not a drop-in one. A Function App is three resources, not one, it has a mandatory storage account that trips up every private-networking deployment, and its app settings drift by design.

Lambda vs Azure Functions

“Lambda” is AWS terminology. The Azure equivalent is Azure Functions — but the resource model differs in ways that matter to your Terraform.

AWS LambdaAzure Functions
Unit of deployment One function = one resource A Function App containing many functions, sharing one runtime, one identity and one set of app settings
Terraform resources needed aws_lambda_function (+ role) azurerm_service_plan + azurerm_storage_account + azurerm_linux_function_app
Compute model Per-invocation, fully managed Depends on the hosting plan — from truly serverless to a dedicated VM fleet
Storage dependency None A storage account is mandatory — see below
Max execution time 15 minutes 5 min default on Consumption (10 max); unlimited on Premium/Dedicated
Identity IAM execution role Managed identity + Azure RBAC role assignments
Private networking VPC configuration on the function Regional VNet integration (outbound) and private endpoints (inbound) — two separate things
The mental shift

In Lambda you think per function. In Azure you think per app: a Function App is closer to a small service with several entry points. That granularity decision — how many functions per app — matters, because everything inside an app shares scaling, identity, settings and deployment. Group functions that share a lifecycle and a security context.

Anatomy of a Function App

Why the storage account is mandatory

The Functions runtime uses it for things that are not optional:

  • Trigger state — blob trigger receipts, so a blob is not processed twice; timer trigger leases, so only one instance fires a scheduled function.
  • Durable Functions state — orchestration history lives in storage tables and queues.
  • Key storage — function access keys.
  • The code package itself on Consumption and Premium plans, mounted from a file share.
This is the single most common Functions + private networking failure

Lock down the Function App's storage account — public_network_access_enabled = false, or default_action = "Deny" — without giving the app a route to it, and the app silently fails to start. There is often no useful error: the app simply reports no functions. If you restrict that storage account you must also configure VNet integration, private endpoints for blob, file, queue and table, and the matching private DNS zones. Many teams keep the runtime storage account separate from the data lake and accept a more permissive posture on it precisely to avoid this.

Hosting plans

Plansku_nameCold startVNet integrationUse for

The choice that decides your architecture

Classic Consumption (Y1) cannot do VNet integration. If your lake and vault have public access disabled, a Y1 function cannot reach them — full stop. That single fact usually forces Premium (EP1) or Flex Consumption for a private data platform, and it is a meaningful cost step: Premium bills for a warm instance continuously rather than per execution. Decide this before designing the network, not after.

Identity-based storage connections

The default pattern puts a connection string containing an account key into AzureWebJobsStorage. That key is then in app settings, in Terraform state, and readable by anyone with Contributor on the app. storage_uses_managed_identity = true removes it.

Connection stringManaged identity
SettingAzureWebJobsStorage = a key-bearing stringstorage_uses_managed_identity = true
Key in stateYesNo
RotationRotating the key breaks the app until reappliedNothing to rotate
Works with shared_access_key_enabled = falseNoYes
Extra setupNoneThe identity needs Storage Blob Data Owner, Queue Data Contributor, and Account Contributor for the Premium file share
Under-granting the runtime roles

Identity-based connections need broader roles on the runtime storage account than people expect — the runtime writes blobs, queues and, on Premium, mounts a file share. Storage Blob Data Contributor alone produces an app that deploys successfully and then does not run, with unhelpful diagnostics. Grant the roles above on the runtime account, and keep that account separate from your data lake so this generosity does not extend to your data.

Infrastructure vs code deployment

Terraform should not deploy your function code

It is possible — zip_deploy_file, or WEBSITE_RUN_FROM_PACKAGE pointing at a blob. It is a bad idea. Application code changes many times a day; infrastructure changes weekly. Coupling them means every code change runs a plan against production infrastructure state, and a code rollback becomes a Terraform operation.

Terraform creates the app, its identity, its settings and its permissions. A separate pipeline — func azure functionapp publish, the Azure Functions GitHub Action, or an Azure DevOps task — deploys the code. The two pipelines have different triggers, different approvers and different rollback stories.

App settings drift

app_settings is a map that Terraform manages as a whole. Azure and the deployment tooling add their own keys — WEBSITE_RUN_FROM_PACKAGE, App Insights instrumentation keys, function keys. Each plan then proposes to remove them.

the permanent diff
  ~ resource "azurerm_linux_function_app" "ingest" {
      ~ app_settings = {
          - "WEBSITE_RUN_FROM_PACKAGE" = "https://stfunc.../releases/v1.4.2.zip" -> null
            # (5 unchanged elements hidden)
        }
    }

Applying that would unset the setting pointing at the deployed package — breaking the running app. The fix is ignore_changes on the specific keys, as in the configuration above.

Ignore specific keys, not the whole map

ignore_changes = [app_settings] makes Terraform stop managing app settings entirely — after which adding a new setting in code does nothing, silently. Always target individual keys: ignore_changes = [app_settings["WEBSITE_RUN_FROM_PACKAGE"]]. Lesson 15 covers ignore_changes properly.

DirectionMechanismTerraform

Locking inbound access and then breaking deployment

Setting public_network_access_enabled = false also blocks the SCM/Kudu endpoint that deployment tooling uses. A CI runner on the public internet can then no longer publish code. Solutions: a self-hosted agent inside the VNet, an IP restriction allowing the runner's egress range on the SCM site specifically, or deploying via WEBSITE_RUN_FROM_PACKAGE pointing at a blob the app pulls itself. Decide this at design time — discovering it during an incident is unpleasant.

Exercises

Level 1 · Understand Why does the app show no functions?

A Premium Function App is deployed with private networking. Terraform applies cleanly. Code deploys successfully. The portal shows the app as Running but lists no functions, and Application Insights shows no traces at all.

List the likely causes in order.

Show answer

Almost always: the runtime cannot reach its own storage account. The Functions host reads the function metadata from storage at startup. If it cannot, it starts with zero functions and reports no error to the portal.

Check in this order:

  1. Does the runtime storage account have public_network_access_enabled = false or a Deny firewall, without private endpoints the app can reach?
  2. Does it have private endpoints for all four services the runtime uses — blob, file, queue and table — with matching private DNS zones linked to the VNet?
  3. Is the app VNet-integrated, and is vnet_route_all_enabled = true? Without route-all, DNS and storage traffic may still go out publicly.
  4. With storage_uses_managed_identity = true, does the identity have Storage Blob Data Owner, Storage Queue Data Contributor and Storage Account Contributor on the runtime account?
  5. Is AZURE_CLIENT_ID set? With a user-assigned identity the runtime must be told which one to use.

This is why many teams keep the runtime storage account outside the private-networking perimeter and reserve the lockdown for the data lake — the security benefit on a metadata-only account is modest compared with the operational cost.

Level 2 · Implement Zero-credential ingestion function

Write the Terraform for a Python Function App that:

  • Writes to the raw container in the data lake.
  • Reads one secret from Key Vault.
  • Sends telemetry to Application Insights.
  • Contains no connection strings or keys anywhere — not in app settings, not in state.
  • Uses Premium hosting in prod and Consumption in dev.
Show answer

The full configuration is the one in the Building it section above. The four credential-free choices are:

  1. Runtime storage: storage_uses_managed_identity = true instead of storage_account_access_key. No key in app settings or state.
  2. Lake access: app settings carry only LAKE_ACCOUNT_NAME; the code uses DefaultAzureCredential. Permission comes from a role assignment scoped to the raw container.
  3. Key Vault: the app setting is a @Microsoft.KeyVault(...) reference, resolved by the App Service runtime with the app's identity. Terraform stores a pointer.
  4. App Insights: application_insights_connection_string is unavoidable — it contains an instrumentation key. It is low-sensitivity (write-only telemetry ingestion), and the modern alternative is Entra ID-based ingestion where your tier supports it.

Environment differences via a single local:

environment switching
locals { is_prod = var.environment == "prod" }

# EP1 supports VNet integration and always-on; Y1 supports neither.
sku_name                  = local.is_prod ? "EP1" : "Y1"
virtual_network_subnet_id = local.is_prod ? azurerm_subnet.this["functions"].id : null
always_on                 = local.is_prod
vnet_route_all_enabled    = local.is_prod

Note that these must move together: always_on = true on a Y1 plan is rejected by Azure, and virtual_network_subnet_id on Y1 is unsupported. Deriving all of them from one is_prod local keeps the combination valid — the more general lesson being that environment differences should hang off a single decision rather than several independent booleans that can be set to an impossible combination.

# OUTBOUND: the app reaches private endpoints through a delegated subnet.
resource "azurerm_subnet" "functions" {

The problem this creates: public_network_access_enabled = false also blocks the SCM/Kudu endpoint that deployment tooling uses. A GitHub-hosted runner on the public internet can no longer publish code — and you usually discover this the first time you try to deploy after the hardening lands.

Two solutions. Either run the deploy from inside the network — a self-hosted agent in the VNet, or a private build pool — or invert the direction: publish the package to a storage blob and set WEBSITE_RUN_FROM_PACKAGE to a URL the app pulls itself, so nothing needs inbound access. A third, weaker option is an IP restriction allowing the runner's egress range on the SCM site specifically. Decide at design time, not during an incident.

Find four problems.

Show answer

1 · Y1 with always_on and VNet integration.

Consumption plans do not support always_on — Azure rejects it — and classic Y1 does not support regional VNet integration at all. Use EP1 (Premium) or FC1 (Flex Consumption) if you need either.

2 · Using the data lake as the runtime storage account.

The Functions runtime writes its own metadata, queues and file share into whatever account you give it. Pointing it at the data lake mixes runtime plumbing with your data, forces broad runtime roles on the lake, and means locking down the lake breaks the app. Use a separate, small storage account.

3 · Two credentials in plaintext.

storage_account_access_key and primary_connection_string both put the account key into app settings and into Terraform state. Replace with storage_uses_managed_identity = true for the runtime, and an account name plus a role assignment for the lake.

4 · The name is too long and not globally unique-safe.

func-ingest-analytics-production-westeurope-01 is 45 characters. Function App names become DNS hostnames and Microsoft recommends staying under 32 characters to avoid host ID collisions — two apps whose first 32 characters match can collide on their host ID and corrupt each other's trigger state, which is an extremely confusing bug. Use the short region form and the short environment form: func-ingest-prod-weu-01.

Interview questions

What is the Azure equivalent of AWS Lambda, and how does it differ?

Azure Functions. The main structural difference is granularity: a Lambda function is one resource, whereas Azure groups many functions into a Function App that shares a runtime, identity, app settings and scaling. An Azure Function App also requires an explicit hosting plan and a mandatory storage account for trigger state, keys and often the code package — so a minimal deployment is three or four Terraform resources rather than one. Permissions come from a managed identity and Azure RBAC rather than an IAM execution role.

Why does a Function App need a storage account?

The runtime uses it for trigger state — blob receipts so a blob is not processed twice, timer leases so only one instance fires a schedule — for function access keys, for Durable Functions orchestration history, and on Consumption and Premium plans for the code package mounted from a file share. The practical consequence is that locking that storage account down behind private networking will silently break the app unless you also add private endpoints for blob, file, queue and table with matching DNS zones. Which is why the runtime account should be separate from the data lake.

How do you avoid connection strings in a Function App?

Three moves. For the runtime storage, storage_uses_managed_identity = true instead of an access key, with the identity granted Storage Blob Data Owner, Storage Queue Data Contributor and Storage Account Contributor on that account. For data access, put only the account name in app settings and let the code use DefaultAzureCredential, with a role assignment scoped to the container. For third-party secrets, use a @Microsoft.KeyVault(...) reference so the App Service runtime resolves it with the app's identity and Terraform stores only a pointer.

Should Terraform deploy function code?

No. Application code changes many times a day and infrastructure changes weekly; coupling them means every code change runs a plan against production infrastructure state and every rollback becomes a Terraform operation. Terraform should create the app, its identity, settings, networking and RBAC. A separate pipeline publishes the code. The one Terraform concession is ignore_changes on the settings the deploy tooling writes, such as WEBSITE_RUN_FROM_PACKAGE, so the two pipelines do not fight.

Which hosting plan would you choose for a data ingestion function?

It depends almost entirely on networking. If the lake and vault have public access disabled, classic Consumption (Y1) is out — it cannot do VNet integration — so Premium (EP1) or Flex Consumption (FC1). Premium also removes cold starts and lifts the execution timeout, which matters for ingestion runs. In dev, where public access is usually allowed, Y1 is fine and much cheaper. I would drive that from a single environment variable so the plan SKU, always_on and VNet integration all move together — they are only valid in certain combinations.

Why do app settings cause permanent plan diffs?

Because app_settings is a map Terraform manages as a whole, while Azure and the deployment tooling add keys of their own — WEBSITE_RUN_FROM_PACKAGE, instrumentation keys, function keys. Terraform sees keys it did not declare and proposes to remove them, which would break the running app. The fix is ignore_changes targeting those specific keys. Ignoring the whole app_settings map is the wrong fix, because then adding a new setting in code silently does nothing.

Key takeaways

  • A Function App is a service plan + a storage account + the app. Plan for all three.
  • The runtime storage account is mandatory and is where private-networking deployments break. Keep it separate from your data lake.
  • Classic Consumption (Y1) cannot do VNet integration — that decision drives your whole architecture.
  • storage_uses_managed_identity = true plus per-container role assignments removes every credential.
  • Terraform owns the app; a separate pipeline owns the code.
  • ignore_changes on individual app-setting keys, never the whole map.

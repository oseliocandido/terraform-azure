Variables, locals, outputs & environments

A Terraform variable is not a programming variable — it is a parameter of a module's public interface, bound once before evaluation begins and immutable thereafter. Getting that distinction right is what makes one codebase deploy dev, test and prod without branching.

By the end of this lesson you can

  • Explain how Terraform variables differ from variables in a programming language
  • Write precise type constraints, including optional() with defaults
  • Recite the variable precedence order and predict which value wins
  • Use validation blocks to fail at plan time instead of mid-apply
  • Explain what sensitive = true does and — crucially — what it does not
  • Structure a repository so dev/test/prod share code but not state

How Terraform variables differ

You already know what a variable is. What matters here is the four ways Terraform's differ, because each one changes how you design configuration.

PropertyA Python variableA Terraform variable
Assignment Any time, any number of times Once, before evaluation begins, from outside the configuration. Nothing inside the configuration can set one.
Scope Function or module scope The module it is declared in. A root variable is not visible inside a child module unless explicitly passed.
Purpose Holding intermediate values The module's public API. If a value is computed inside the configuration, it should be a local, not a variable.
Effect on the graph None — it's just a value Variables are resolved before the graph is walked, so a variable value can determine how many resources exist. Their values must be knowable at plan time.
The design rule that follows

Variables are inputs, locals are computation, outputs are exports. If you find yourself giving a variable a default that no caller ever overrides, it should be a local. If you find yourself writing the same expression in three resources, it should be a local. Variables should be the things a caller genuinely needs to decide.

Declaring variables

variables.tf
variable "environment" {
  type        = string
  description = "Deployment environment. Drives sizing, replication and network posture."

  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be one of: dev, test, prod."
  }
}

variable "location" {
  type        = string
  description = "Azure region, lowercase with no spaces (e.g. westeurope)."
  default     = "westeurope"

  validation {
    condition     = can(regex("^[a-z]+[a-z0-9]*$", var.location))
    error_message = "Use the lowercase no-space form, e.g. westeurope, not \"West Europe\"."
  }
}

variable "medallion_layers" {
  type        = set(string)
  description = "Containers to create in the data lake."
  default     = ["raw", "bronze", "silver", "gold"]

  validation {
    condition     = length(var.medallion_layers) > 0
    error_message = "At least one layer must be defined."
  }

  validation {
    # Container names: 3-63 chars, lowercase alphanumeric and hyphens.
    condition = alltrue([
      for l in var.medallion_layers : can(regex("^[a-z0-9][a-z0-9-]{2,62}$", l))
    ])
    error_message = "Layer names must be 3-63 lowercase alphanumeric characters or hyphens."
  }
}

variable "admin_group_object_id" {
  type        = string
  description = "Entra ID group granted Storage Blob Data Owner on the lake."
  nullable    = false
}

variable "databricks_token" {
  type        = string
  description = "Databricks PAT. Prefer OAuth — see Lesson 12."
  sensitive   = true
  default     = null
}
ArgumentMeaning
typeType constraint. Always set one — without it the variable is any and errors surface late and cryptically.
descriptionShown in errors, in terraform console, and in generated module documentation. For a shared module this is the API documentation.
defaultMakes the variable optional. No default = required; Terraform prompts interactively or fails in CI.
sensitiveRedacts the value from plan and apply output. Does not encrypt it in state. See below.
nullableDefaults to true. Setting false means an explicit null is rejected rather than falling back to the default.
validationZero or more blocks. Each has a condition and an error_message. All are evaluated, so a caller sees every problem at once.
ephemeralTerraform 1.10+. The value may be used during an operation but is never persisted to state or plan files. The right choice for genuinely transient secrets.

Complex type constraints

This is where Terraform's type system earns its keep — a well-typed object variable documents itself and fails fast.

variables.tf — a typed configuration object
variable "lake" {
  description = "Data lake storage account configuration."

  type = object({
    replication       = string
    access_tier       = optional(string, "Hot")
    versioning        = optional(bool, false)
    soft_delete_days  = optional(number, 7)
    allow_public      = optional(bool, false)

    layers = map(object({
      tier_after_days   = optional(number)
      delete_after_days = optional(number)
    }))
  })

  validation {
    condition     = contains(["LRS", "ZRS", "GRS", "GZRS", "RAGZRS"], var.lake.replication)
    error_message = "replication must be one of: LRS, ZRS, GRS, GZRS, RAGZRS."
  }

  validation {
    condition     = var.lake.soft_delete_days >= 1 && var.lake.soft_delete_days <= 365
    error_message = "soft_delete_days must be between 1 and 365."
  }
}
optional(type, default) is the modern idiom

Before it existed, callers had to supply every attribute of an object variable, or you used any and lost all type checking. Now a caller can pass { replication = "LRS", layers = {} } and Terraform fills the rest in. Use it liberally — it is what makes a typed module variable pleasant rather than punishing.

Where values come from, and which wins

Common mistake · the invisible terraform.tfvars

A file literally named terraform.tfvars, or anything ending .auto.tfvars, is loaded automatically with no flag. A leftover terraform.tfvars from someone's local experiment silently overrides defaults for everyone who clones the repo. Either commit it deliberately as the shared default, or gitignore it and use explicit -var-file for everything.

Validation — failing early on purpose

Every validation rule you write converts a confusing mid-apply Azure error into a clear message at plan time, before anything is created. On a configuration that takes fifteen minutes to apply, this is the difference between a five-second correction and a partial deployment.

validation patterns worth stealing
variable "storage_account_name" {
  type = string

  validation {
    condition     = can(regex("^[a-z0-9]{3,24}$", var.storage_account_name))
    error_message = "Storage account names must be 3-24 lowercase letters and digits only, with no hyphens."
  }
}

variable "subnet_cidrs" {
  type = map(string)

  validation {
    # can() turns an error into false — the standard way to test "is this parseable"
    condition     = alltrue([for c in values(var.subnet_cidrs) : can(cidrnetmask(c))])
    error_message = "Every value must be a valid CIDR block, e.g. 10.10.1.0/24."
  }
}

variable "retention_days" {
  type    = number
  default = 30

  validation {
    condition     = var.retention_days >= 1 && var.retention_days <= 365
    error_message = "retention_days must be between 1 and 365. Got ${var.retention_days}."
  }
}
what a failed validation looks like
$ terraform plan -var 'environment=production'

Error: Invalid value for variable

  on variables.tf line 1:
   1: variable "environment" {
    ├────────────────
    │ var.environment is "production"

environment must be one of: dev, test, prod.

This was checked by the validation rule at variables.tf:6,3-13.
Related checks: preconditions and postconditions

validation can only inspect that one variable. For rules spanning several values — “if public_network_access_enabled is false then private_endpoint_subnet_id must be set” — use a lifecycle { precondition { ... } } block on the resource, or a check block for non-blocking assertions. Those run at plan time and can reference anything.

Sensitive variables — what the flag really does

sensitive.tf
variable "sql_admin_password" {
  type      = string
  sensitive = true
}

output "connection_string" {
  value     = "Server=...;Password=${var.sql_admin_password}"
  sensitive = true   # required — sensitivity propagates, and Terraform enforces it
}

✓ sensitive = true does

  • Redact the value in plan and apply output as (sensitive value)
  • Propagate: anything derived from it becomes sensitive too
  • Force you to mark derived outputs sensitive, or error
  • Redact it in the JSON plan's human-facing rendering

✗ It does not

  • Encrypt anything in the state file
  • Keep it out of state — it is written in plaintext
  • Keep it out of a saved plan file
  • Prevent terraform output -raw from printing it
  • Stop provider debug logs (TF_LOG=DEBUG) from containing it
This is the most misunderstood feature in Terraform

sensitive is a display control, not a security control. Its purpose is stopping a password appearing in a CI log that fifty people can read. It does nothing about the state file.

For values that genuinely must not persist, Terraform 1.10 added ephemeral values — variables, outputs and resources whose values are never written to state or plan files — and 1.11 added write-only arguments, which let a managed resource accept one. That is a real security control. Lesson 09 covers the whole secrets problem properly.

Locals

A local names an expression. It cannot be overridden from outside, takes no type constraint, and exists purely to avoid repetition and to give intermediate values a meaningful name.

locals.tf
locals {
  # 1 · derived naming — one place to change the scheme
  suffix  = "${var.workload}-${var.environment}-${var.region_short}-${var.instance}"
  rg_name = "rg-${local.suffix}"
  kv_name = "kv-${local.suffix}"
  sa_name = substr(lower(replace("st${local.suffix}", "-", "")), 0, 24)

  # 2 · environment-driven behaviour, decided once
  is_prod = var.environment == "prod"

  # 3 · a sizing table beats a chain of conditionals
  sizing = {
    dev  = { replication = "LRS",    soft_delete = 7,  sku = "standard" }
    test = { replication = "ZRS",    soft_delete = 14, sku = "standard" }
    prod = { replication = "GZRS",   soft_delete = 30, sku = "premium"  }
  }
  env_config = local.sizing[var.environment]

  # 4 · tags built once, merged everywhere
  common_tags = {
    workload    = var.workload
    environment = var.environment
    managed_by  = "terraform"
    repository  = var.repository_url
    # A deploy timestamp would cause a diff on every plan — don't.
  }

  # locals CAN reference other locals, but not themselves
  lake_url = "https://${local.sa_name}.dfs.core.windows.net"
}
Common mistake · a timestamp in tags

deployed_at = timestamp() looks helpful and is a trap: timestamp() returns a new value on every evaluation, so every plan shows a change on every tagged resource, forever. If you need deployment metadata, use a value that only changes when something real changes — the git commit SHA, passed in as a variable from CI.

Outputs

Outputs serve three distinct audiences, and it is worth knowing which you are writing for:

  1. Humans — printed after apply, and readable with terraform output.
  2. Parent modules — module.storage.lake_id is how one module feeds another.
  3. Other configurations — read across state boundaries via terraform_remote_state, or by a pipeline consuming terraform output -json.
outputs.tf
output "lake_id" {
  description = "Resource ID of the data lake storage account. Used as an RBAC scope."
  value       = azurerm_storage_account.lake.id
}

output "lake_dfs_endpoint" {
  description = "DFS endpoint for abfss:// access from Spark."
  value       = azurerm_storage_account.lake.primary_dfs_endpoint
}

output "layer_paths" {
  description = "Map of medallion layer name to its abfss:// URI."
  value = {
    for name, fs in azurerm_storage_data_lake_gen2_filesystem.layers :
    name => "abfss://${name}@${azurerm_storage_account.lake.name}.dfs.core.windows.net/"
  }
}

output "lake_primary_access_key" {
  description = "Do not use. Present only to demonstrate sensitivity propagation."
  value       = azurerm_storage_account.lake.primary_access_key
  sensitive   = true
}

# An output can carry a postcondition — a self-check that runs at plan time.
output "lake_is_hns" {
  value = azurerm_storage_account.lake.is_hns_enabled

  precondition {
    condition     = azurerm_storage_account.lake.is_hns_enabled
    error_message = "The lake storage account must have the hierarchical namespace enabled."
  }
}
consuming outputs
terraform output                       # all outputs, human-readable
terraform output lake_id               # one, quoted
terraform output -raw lake_id          # one, unquoted — for shell scripts
terraform output -json layer_paths     # structured — for pipelines

# feeding the next pipeline stage
LAKE_URL=$(terraform output -raw lake_dfs_endpoint)
Outputs are stored in state, in plaintext

Marking an output sensitive hides it from the console. It is still written to state, and terraform output -raw will print it on demand. Never output a secret unless a consumer genuinely needs it — and if one does, prefer outputting a Key Vault secret ID that the consumer resolves itself, rather than the secret value.

Running dev, test and prod from one codebase

There are two workable patterns and one that people reach for and regret. Lesson 17 covers the trade-offs in full; here is enough to structure your practice work.

Pattern A — one root module, one tfvars and one backend key per environment

layout
terraform/
├── main.tf
├── variables.tf
├── outputs.tf
├── versions.tf
└── env/
    ├── dev.tfvars          ├── dev.backend.hcl
    ├── test.tfvars         ├── test.backend.hcl
    └── prod.tfvars         └── prod.backend.hcl
deploying
terraform init -reconfigure -backend-config=env/dev.backend.hcl
terraform plan -var-file=env/dev.tfvars -out=tfplan
terraform apply tfplan

Pro: zero code duplication; a change reaches every environment. Con: the same code path serves prod, so a mistake can reach prod as easily as dev, and -reconfigure between environments is easy to forget — which is how someone applies dev's plan to prod's state.

Pattern B — a directory per environment

layout
terraform/
├── modules/
│   ├── storage/
│   ├── networking/
│   └── databricks/
└── environments/
    ├── dev/     main.tf  backend.tf  terraform.tfvars
    ├── test/    main.tf  backend.tf  terraform.tfvars
    └── prod/    main.tf  backend.tf  terraform.tfvars

Each environment is its own root module calling shared modules with different inputs. Backend configuration is committed per directory, so cd environments/prod && terraform apply cannot possibly touch dev's state.

Pro: explicit, safe, and environments can legitimately differ (prod has private endpoints, dev does not) without conditionals everywhere. Con: the main.tf files are similar, and a change must be applied in each — which many teams consider a feature, since it forces promotion through environments.

Do not use workspaces for environments

terraform workspace gives you multiple states from one configuration and one backend. It is tempting and it is the wrong tool here: every workspace shares one backend and therefore one set of access controls, so anyone who can apply to dev can apply to prod; environments cannot differ structurally without count hacks keyed on terraform.workspace; and it is easy to be in the wrong workspace without noticing. HashiCorp's own guidance points to separate configurations for environments. Workspaces are good for short-lived parallel copies — a per-pull-request preview environment.

Exercises

Level 1 · Understand Which value wins?

Given all of the following, what is the final value of var.environment?

  • variables.tf declares default = "dev"
  • terraform.tfvars contains environment = "test"
  • zz.auto.tfvars contains environment = "staging"
  • The shell has TF_VAR_environment=qa exported
  • The command is terraform plan -var-file=env/prod.tfvars, and that file contains environment = "prod"
Show answer

"prod", from the explicit -var-file.

Applying the precedence order lowest to highest:

  1. default = "dev" — the floor
  2. TF_VAR_environment=qa → "qa"
  3. terraform.tfvars → "test"
  4. zz.auto.tfvars → "staging"
  5. -var-file=env/prod.tfvars → "prod"

The real lesson is that a repository in this state is a hazard. Four sources silently competing means nobody can predict what a plan will do. Pick one mechanism — explicit -var-file — and gitignore terraform.tfvars and *.auto.tfvars.

Level 2 · Implement A validated network variable

Write a variable subnets that:

  • Is a map from subnet name to an object with address_prefix (required), service_endpoints (optional, defaults to empty list) and delegation (optional, defaults to null).
  • Rejects any address prefix that is not a valid CIDR.
  • Requires at least one subnet named exactly privatelink.
  • Rejects subnets smaller than /28 (Azure's minimum).
Show answer
solution
variable "subnets" {
  description = "Subnets to create in the platform VNet, keyed by short name."

  type = map(object({
    address_prefix    = string
    service_endpoints = optional(list(string), [])
    delegation        = optional(string, null)
  }))

  validation {
    condition = alltrue([
      for s in values(var.subnets) : can(cidrnetmask(s.address_prefix))
    ])
    error_message = "Every address_prefix must be a valid CIDR block, e.g. 10.10.1.0/24."
  }

  validation {
    condition     = contains(keys(var.subnets), "privatelink")
    error_message = "A subnet named \"privatelink\" is required for private endpoints."
  }

  validation {
    condition = alltrue([
      for s in values(var.subnets) :
      tonumber(split("/", s.address_prefix)[1]) <= 28
    ])
    error_message = "Azure subnets must be /28 or larger (a smaller prefix number)."
  }
}

Each rule is a separate validation block so a caller with three mistakes sees all three at once. Note the third rule would crash on a malformed prefix — but it never runs on one, because validation blocks all evaluate and the first rule reports the malformed input. If you want to be strict, wrap it in can() too.

Level 2 · Implement Design a typed, validated module input

Write a single variable "lake" that fully describes a data lake, so a caller can pass one object instead of eleven separate variables. It must:

  • Require replication and layers; default everything else sensibly and securely.
  • Reject an invalid replication type, a soft-delete window outside 1–365, and any layer name that breaks Azure's container naming rules.
  • Let a caller write { replication = "LRS", layers = { raw = {} } } and have it work.

Then show the two-line caller.

Show solution
variables.tf
variable "lake" {
  description = "Data lake storage account configuration."

  type = object({
    replication      = string
    access_tier      = optional(string, "Hot")
    versioning       = optional(bool, true)
    soft_delete_days = optional(number, 30)
    public_access    = optional(bool, false)
    shared_keys      = optional(bool, false)

    layers = map(object({
      cool_after_days   = optional(number)
      delete_after_days = optional(number)
    }))
  })

  validation {
    condition     = contains(["LRS", "ZRS", "GRS", "GZRS", "RAGZRS"], var.lake.replication)
    error_message = "lake.replication must be one of: LRS, ZRS, GRS, GZRS, RAGZRS."
  }

  validation {
    condition     = var.lake.soft_delete_days >= 1 && var.lake.soft_delete_days <= 365
    error_message = "lake.soft_delete_days must be between 1 and 365."
  }

  validation {
    # Container names: 3-63 chars, lowercase alphanumeric and hyphens,
    # must start with a letter or digit.
    condition = alltrue([
      for name in keys(var.lake.layers) :
      can(regex("^[a-z0-9][a-z0-9-]{2,62}$", name))
    ])
    error_message = "Every layer name must be 3-63 lowercase alphanumeric characters or hyphens."
  }

  validation {
    condition     = contains(["Hot", "Cool", "Cold"], var.lake.access_tier)
    error_message = "lake.access_tier must be Hot, Cool or Cold."
  }
}
env/dev.tfvars
# Everything else falls back to the optional() defaults, which are the
# SECURE values - a caller must deliberately opt out of them.
lake = {
  replication = "LRS"
  layers = {
    raw    = { cool_after_days = 7 }
    bronze = {}
    silver = {}
    gold   = {}
  }
}

optional(type, default) is what makes a typed object variable pleasant rather than punishing — before it existed, a caller had to supply every attribute or you fell back to any and lost type checking entirely.

Note that the defaults are chosen so the secure configuration is the one you get by saying nothing: no public access, no shared keys, versioning on. A caller weakening any of those has to write it down, which means it shows up in the diff and in code review.

Level 2 · Implement Replace a conditional chain with a lookup table

This works and does not scale. Refactor it.

bad.tf
locals {
  replication = var.environment == "prod" ? "GZRS" : (var.environment == "test" ? "ZRS" : "LRS")
  sku         = var.environment == "prod" ? "premium" : "standard"
  retention   = var.environment == "prod" ? 90 : (var.environment == "test" ? 30 : 7)
  func_sku    = var.environment == "prod" ? "EP1" : (var.environment == "test" ? "EP1" : "Y1")
  private_pe  = var.environment == "prod" ? true : false
  node_count  = var.environment == "prod" ? 8 : (var.environment == "test" ? 4 : 2)
}

Requirements: adding a staging environment must be a single localised edit, and an unknown environment must fail with a clear message rather than silently falling through to the dev values.

Show solution
locals.tf
variable "environment" {
  type = string

  validation {
    # A validation block can only reference its OWN variable - not a local,
    # not another variable. So the list is repeated here deliberately.
    condition     = contains(["dev", "test", "staging", "prod"], var.environment)
    error_message = "environment must be one of: dev, test, staging, prod."
  }
}

locals {
  # One row per environment. Adding "staging" is one block, not six edits.
  sizing = {
    dev = {
      replication = "LRS"
      sku         = "standard"
      retention   = 7
      func_sku    = "Y1"
      private_pe  = false
      node_count  = 2
    }
    test = {
      replication = "ZRS"
      sku         = "standard"
      retention   = 30
      func_sku    = "EP1"
      private_pe  = false
      node_count  = 4
    }
    staging = {
      replication = "ZRS"
      sku         = "premium"
      retention   = 30
      func_sku    = "EP1"
      private_pe  = true
      node_count  = 4
    }
    prod = {
      replication = "GZRS"
      sku         = "premium"
      retention   = 90
      func_sku    = "EP1"
      private_pe  = true
      node_count  = 8
    }
  }

  # A missing key errors loudly here rather than silently defaulting.
  env = local.sizing[var.environment]
}

resource "azurerm_storage_account" "lake" {
  account_replication_type = local.env.replication
  # ...
  blob_properties {
    delete_retention_policy {
      days = local.env.retention
    }
  }
}

The table makes the differences between environments the readable artefact. With the conditional chain you have to trace six separate expressions to answer “what is different about staging?”; with the table you read one block.

It also removes a real class of bug. In the original, nothing stops someone setting func_sku = "Y1" alongside private_pe = true — an impossible combination, because Consumption plans cannot do VNet integration. Grouping the values per environment makes valid combinations the default and invalid ones visibly wrong.

Level 3 · Troubleshoot The secret that leaked anyway

A team is confident their SQL password is protected. A security review disagrees. Find every leak:

broken.tf
variable "sql_admin_password" {
  type      = string
  sensitive = true
}

resource "azurerm_key_vault_secret" "sql" {
  name         = "sql-admin-password"
  value        = var.sql_admin_password
  key_vault_id = azurerm_key_vault.main.id
}

output "sql_connection" {
  value     = "Server=tcp:${azurerm_mssql_server.main.fqdn};User ID=sqladmin;Password=${var.sql_admin_password}"
  sensitive = true
}

Their CI runs terraform plan -out=tfplan, uploads tfplan as a build artefact, and stores state in an Azure Storage backend.

Show answer

Four separate exposures, none prevented by sensitive = true:

  1. State. azurerm_key_vault_secret.sql.value is stored in state in plaintext. Anyone who can read the state blob has the password — regardless of their Key Vault permissions. This is the central irony: putting a secret into Key Vault via Terraform copies it somewhere less protected.
  2. The plan artefact. tfplan contains the full planned attribute values, including the secret. Uploading it as a build artefact makes it readable by everyone with access to the build — often the whole engineering organisation.
  3. The output. Stored in state, and printable at any time with terraform output -raw sql_connection by anyone who can read the state.
  4. Debug logs. If anyone ever runs with TF_LOG=DEBUG or TF_LOG=TRACE, the provider logs request bodies — including the secret — and those logs usually end up in the CI log store.

What to do instead:

  • Do not create the secret with Terraform. Have Terraform create the vault and the RBAC, and let a human or a dedicated rotation job populate the value out of band.
  • If Terraform must generate one, use an ephemeral variable (Terraform 1.10+) together with a write-only argument such as value_wo (Terraform 1.11+, supported by azurerm_key_vault_secret) so the value never reaches state or the plan file.
  • Output the secret's Key Vault ID, not its value: consumers resolve it themselves with their own identity, which is also auditable.
  • Restrict plan artefacts to a short retention with tight access, and treat them as secrets.
  • Best of all: use a managed identity so there is no password. Lesson 08.

Lesson 09 works through this whole problem.

Interview questions

How do Terraform variables differ from variables in a normal programming language?

They are inputs to a module, not mutable storage. They are bound once from outside the configuration before evaluation begins, cannot be reassigned, and nothing inside the configuration can set one — that is what locals are for. They are scoped to the module that declares them, so a root variable is invisible to a child module unless passed explicitly. And because they are resolved before the dependency graph is walked, their values can determine how many resources exist, which is why they must be knowable at plan time.

What is the variable precedence order?

Lowest to highest: the declared default; TF_VAR_ environment variables; terraform.tfvars; terraform.tfvars.json; *.auto.tfvars files in alphabetical order; then -var-file and -var on the command line, applied in the order given. The practical point is that terraform.tfvars and *.auto.tfvars are loaded with no flag, so a stray file can silently change a plan.

What does sensitive = true actually protect against?

Accidental display. It redacts the value in plan and apply output and propagates that marking to anything derived from it. It does not encrypt or omit the value from state or from a saved plan file, does not stop terraform output -raw, and does not affect provider debug logs. It is a display control, not a security control. For values that must never persist, Terraform 1.10 added ephemeral values and 1.11 added write-only arguments, which genuinely are never written to state.

When would you use a local instead of a variable?

When the value is computed inside the configuration rather than decided by the caller. Derived names, merged tag maps, an is_prod boolean, a lookup into an environment sizing table — all locals. A variable whose default nobody ever overrides is a smell: it is advertising a decision point that does not exist. Locals also keep the module's public API small, which matters a lot for shared modules.

How would you manage multiple Azure environments with Terraform?

Two viable patterns. One root module with a tfvars file and a separate backend key per environment keeps code duplication at zero but runs prod through the same code path as dev and depends on nobody forgetting -reconfigure. A directory per environment, each a thin root module calling shared modules with different inputs and its own committed backend configuration, is more verbose but makes it structurally impossible to apply the wrong state, and lets environments differ genuinely — prod with private endpoints, dev without.

I would use directories for anything with a production environment, and ideally separate subscriptions per environment so the blast radius is bounded by Azure RBAC too. I would not use workspaces: they share one backend and therefore one set of permissions, so they give isolation of state without isolation of access.

Why should you add validation blocks to variables?

To convert a confusing failure deep in an apply into a clear message at plan time, before anything is created. A storage account name with a hyphen, a region typed as “West Europe” instead of westeurope, a retention value out of range — each of those otherwise fails minutes in, after other resources already exist. Validations also document the contract for anyone calling a shared module. For rules spanning multiple values I would use precondition blocks instead, since validation can only see the one variable.

Key takeaways

  • Variables are a module's API, bound once from outside. Locals are computation. Outputs are exports.
  • Always set type and description. Use optional(type, default) to make object variables usable.
  • Command line beats files beats environment. terraform.tfvars and *.auto.tfvars load with no flag — a real hazard.
  • Every validation block turns a mid-apply failure into a plan-time message.
  • sensitive = true hides values from output. It does nothing to state. Ephemeral values are the real control.
  • Environments: tfvars-per-env or directory-per-env. Not workspaces.

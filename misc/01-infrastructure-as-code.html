Infrastructure as Code & Terraform's architecture

Before any syntax: what problem Terraform solves, what it actually is (four separate things people all call “Terraform”), and how it compares to the alternatives you will be asked about — Bicep, Ansible and Pulumi.

By the end of this lesson you can

  • Explain declarative infrastructure in terms of desired state reconciliation, not “config files”
  • Distinguish the Terraform language, CLI, provider and state — and say which one a given error comes from
  • Draw the path from a .tf file to a real Azure resource
  • Justify choosing Terraform over Bicep, Ansible or Pulumi in an interview — and say when you would not
  • Name the five core configuration constructs and what each is for
Concepts only No Azure subscription needed Terraform 1.16 · azurerm 5.x

The problem, in data engineering terms

You have built a data platform in the Azure portal. It works. It contains, roughly: a resource group, an ADLS Gen2 storage account with four containers, a Key Vault holding six secrets, a Databricks workspace injected into a VNet with three subnets, two network security groups, four private endpoints, four private DNS zones with their virtual network links, a function app with its own storage account and service plan, and eleven role assignments gluing those identities to those resources.

Now answer these questions:

  • Reproduce it exactly in a second subscription for staging. How long, and how confident are you that it is identical?
  • Somebody changed a firewall rule on the storage account three weeks ago. Who, when, and why?
  • A role assignment is missing in prod but present in dev. Which one?
  • Delete the whole thing cleanly, in dependency order, leaving nothing orphaned.
  • Onboard a new engineer. Where is the platform described?

Click-ops answers all of these badly. Infrastructure as Code answers all of them with the same primitive: the infrastructure has a source-controlled definition, and a tool makes reality match that definition. Reproduction is apply in another subscription. History is git log. Drift is a diff. Teardown is destroy. Onboarding is “read the repo”.

The real payoff

The value of IaC is not that you type instead of click. It is that infrastructure becomes reviewable. A change to production networking becomes a pull request that a colleague can read, question and approve before it exists — which is the only control that actually scales.

Declarative vs imperative

This distinction is the one interviewers ask about and the one most people explain shallowly. The shallow version is “imperative says how, declarative says what”. True, but it misses the mechanism.

An imperative script describes a sequence of actions:

imperative.sh
az group create --name rg-analytics-dev-weu-01 --location westeurope
az storage account create \
  --name stanalyticsdevweu01 \
  --resource-group rg-analytics-dev-weu-01 \
  --sku Standard_LRS \
  --enable-hierarchical-namespace true

Run it once: you get a resource group and a storage account. Run it twice: the second run errors, because the resource group already exists. The script encodes actions, and actions are not repeatable. To make it repeatable you must write the checks yourself — “does it exist? if not, create; if yes, does it match? if not, update which properties?” — and that conditional logic is the part that grows without limit.

A declarative configuration describes an end state:

declarative.tf
resource "azurerm_resource_group" "analytics" {
  name     = "rg-analytics-dev-weu-01"
  location = "westeurope"
}

resource "azurerm_storage_account" "lake" {
  name                     = "stanalyticsdevweu01"
  resource_group_name      = azurerm_resource_group.analytics.name
  location                 = azurerm_resource_group.analytics.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  is_hns_enabled           = true
}

This says nothing about creating anything. It says: when Terraform is finished, a resource group with this name and a storage account with these properties should exist. Terraform is responsible for working out the actions.

The mechanism: three-way reconciliation

Here is the part that matters. Terraform does not compare two things, it compares three:

The three inputs give three different meanings to a difference:

Difference between…MeansTerraform's response
Configuration and state You changed the code Plan an update, replacement, creation or destruction
State and reality Drift — somebody changed Azure outside Terraform Refresh state, then plan to push reality back toward the configuration
Configuration and reality, with nothing in state The resource exists but Terraform does not know about it Plan to create it — and fail with “already exists”. This is the classic brownfield problem, solved by import (Lesson 16).

Because the configuration describes an end state rather than actions, applying it twice with no code change produces no change at all. That property is idempotence, and it is what makes it safe to run the same pipeline on every merge.

Mental model to carry through the whole course

Terraform is a reconciliation engine over a dependency graph. Your .tf files are not a program that runs top to bottom — they are a set of nodes and the references between them are the edges. Terraform builds the graph, walks it in dependency order, and calls provider APIs to close the gap between state and configuration. Every confusing Terraform behaviour you will hit makes sense once you ask “what does the graph look like, and what is in state?”

What “Terraform” actually is — four separate things

People say “Terraform” for four different components. Being precise about which one you mean is genuinely useful, because it tells you where a problem lives and which documentation to read.

ComponentWhat it isAn error from it looks like
Language HCL — the syntax and semantics of .tf files. Blocks, expressions, functions, the type system. Invalid expression, Unsupported argument, Invalid function argument
CLI / core The terraform binary. Graph construction, diffing, state management, concurrency. Cloud-agnostic. Cycle: ..., Error acquiring the state lock, Error: Invalid count argument
Provider A plugin binary (here terraform-provider-azurerm). Defines resource types and translates them into API calls. Error: creating Storage Account: unexpected status 409, Error: Insufficient features blocks
State A JSON document recording which real resource each configuration address corresponds to, plus a cached copy of its attributes. Resource already managed by Terraform, Instance ... does not exist in state
Why this split exists at all

HashiCorp does not maintain most providers. The plugin boundary means AWS, Azure, Databricks, Snowflake, Datadog, GitHub and several thousand others can each ship their own binary on their own release schedule, while Terraform core stays the same. It is also why providers version independently of the CLI — and why you pin them separately, as Lesson 04 covers.

The five core constructs

You will meet all of these properly over the next few lessons. Here they are together so the vocabulary is in place — this is the whole configuration language in one table.

ConstructPurposeGoes in state?Azure example
resource Something Terraform creates and owns. The only construct that changes your cloud. Yes An ADLS Gen2 storage account this configuration is responsible for
data Something Terraform reads but does not own. Read-only lookup at plan time. Yes (cached), but never created or destroyed A pre-existing VNet managed by the platform team, or your own tenant ID
variable An input to the configuration. Set per environment. No (but values can leak into state via the resources that use them) environment = "prod", location = "westeurope"
output A return value — exposed to the CLI, to CI, and to a parent module. Yes The storage account ID that the Databricks module needs
locals A named intermediate expression. Not an input, not an output — just naming a value so you don't repeat it. No A computed name prefix, or a merged tag map

Two more block types complete the picture: provider (configure a plugin — Lesson 04) and module (call another directory of configuration — Lesson 14). Plus terraform itself, the settings block where you pin versions and declare a backend.

Common mistake · resource vs data source

A very common beginner error is using a resource block for something that already exists and is owned by another team. If you write resource "azurerm_resource_group" "shared" for a resource group the platform team created, Terraform will try to create it, fail on the name conflict — and worse, if you do get it into state and later remove the block, Terraform will happily destroy someone else's resource group.

Rule: resource means “this configuration owns the lifecycle of this thing”. data means “this thing exists; tell me about it”.

A first look at a complete configuration

You are not expected to understand every line yet — Lessons 03 to 05 build this up properly. Read it for shape, and notice that nothing in it describes an order of operations.

main.tf — a minimal but complete configuration
# Settings block: which Terraform version, which providers, where state lives.
terraform {
  required_version = ">= 1.9.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 5.0"
    }
  }
}

# Provider block: configure the azurerm plugin.
provider "azurerm" {
  features {}
  subscription_id = var.subscription_id
}

# An input.
variable "subscription_id" {
  type        = string
  description = "Target Azure subscription ID."
}

# A named intermediate value.
locals {
  workload = "analytics"
  env      = "dev"
  tags = {
    workload    = local.workload
    environment = local.env
    managed_by  = "terraform"
  }
}

# A data source: read something that already exists.
data "azurerm_client_config" "current" {}

# Resources: things this configuration owns.
resource "azurerm_resource_group" "analytics" {
  name     = "rg-${local.workload}-${local.env}-weu-01"
  location = "westeurope"
  tags     = local.tags
}

resource "azurerm_storage_account" "lake" {
  name                     = "st${local.workload}${local.env}weu01"
  resource_group_name      = azurerm_resource_group.analytics.name
  location                 = azurerm_resource_group.analytics.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
  is_hns_enabled           = true       # this is what makes it ADLS Gen2
  tags                     = local.tags
}

# An output: a value other configurations or humans need.
output "lake_id" {
  description = "Resource ID of the data lake storage account."
  value       = azurerm_storage_account.lake.id
}

What Terraform makes of that

Terraform reads the whole directory, notices that azurerm_storage_account.lake mentions azurerm_resource_group.analytics.name, and derives an edge. It never needed to be told the order:

This is also why Terraform can parallelise: data.azurerm_client_config.current has no edges to the others, so it is resolved concurrently. By default Terraform walks the graph with ten concurrent operations.

Terraform vs the alternatives

You will be asked to justify this choice. Answering “Terraform is multi-cloud” is a weak answer — most companies are not meaningfully multi-cloud, and interviewers know it. Here are the honest comparisons.

Terraform vs ARM templates and Bicep

ARM templates are Azure's native JSON deployment format. Bicep is a friendlier language that transpiles to ARM. Both are executed by Azure Resource Manager itself.

TerraformBicep / ARM
Who executes the deployment The Terraform CLI on your machine or runner, calling ARM resource by resource ARM itself — you submit a template and Azure orchestrates it
State Explicit state file you must store and protect No state file. ARM reads live resource state at deployment time
Preview of changes terraform plan — mature, precise, shows replacements what-if — good, but historically less reliable on some resource types
Deleting resources Remove the block → Terraform destroys it Removing from a template does nothing unless you use complete mode deployment, which is blunt and risky
New Azure features Lag of days to months while the provider adds support Available immediately — it is the native API surface
Non-Azure resources Same tool and same graph for Databricks objects, Snowflake, GitHub, Datadog… Azure only
The honest data-engineering answer

For a pure-Azure data platform, the strongest argument for Terraform is not multi-cloud — it is that a data platform is never only Azure resources. You also need Databricks workspace objects (clusters, jobs, Unity Catalog grants), maybe Snowflake, maybe Kafka topics, maybe GitHub repos and service connections. Terraform expresses all of those in one dependency graph, so “create the storage account, then grant the access connector on it, then register it as a Unity Catalog external location” is a single plan. Bicep stops at the Azure boundary and you glue the rest together with scripts.

When Bicep is the better choice

If your team is Azure-only, already fluent in ARM, deploys nothing outside Azure, and does not want to operate a state backend, Bicep is a perfectly sound choice — and it will support brand-new Azure features before azurerm does. Saying this in an interview signals judgement rather than tool loyalty.

Terraform vs Ansible

These are often presented as competitors. They mostly are not — they operate at different layers.

  • Terraform is declarative and stateful. It knows what it created and can destroy it precisely.
  • Ansible is procedural with idempotent modules, and stateless. It describes tasks to run against hosts. It has Azure modules and can create a storage account, but it has no record of what it made, so it cannot tell you “these 40 resources are mine” or reliably tear them down.

For a modern Azure data platform the Ansible layer is often absent entirely — Databricks compute is managed by Databricks, Functions are PaaS, and there are no VMs to configure. In that world you use Terraform and stop.

Terraform vs Pulumi

Pulumi lets you define infrastructure in TypeScript, Python, Go or C#. It has a state file, a preview step and a resource graph, so the model is genuinely similar — many Pulumi providers are generated from the Terraform ones.

TerraformPulumi
Language HCL — a purpose-built configuration DSL General-purpose languages with a real type system, IDE support, unit-testing frameworks
Ceiling on complexity Deliberately low. No arbitrary loops, no I/O, no classes. HCL pushes back when configuration gets clever. Unbounded. You can write a class hierarchy that generates your infrastructure — for better and for worse.
Readability by non-authors High. There is one obvious way to express a resource; a plan is easy to correlate to code. Depends entirely on discipline. Abstractions can make it hard to see what will actually be created.
Hiring and ecosystem Very large. Most Azure/data engineering job specs say “Terraform”. Smaller, though growing.

HCL's limitations are the feature. Infrastructure code is read far more often than it is written, usually under time pressure during an incident, and often by someone who did not write it.

Where Terraform is a poor fit

Rule 4 of good engineering judgement: do not pretend the tool manages everything equally well. Terraform is weakest at:

  • Data-plane operations. Terraform is a control-plane tool. Creating a storage container is natural; uploading a thousand files into it, or running a Spark job, is not. Note that some things straddle this line awkwardly — Lesson 06 covers why creating a container can fail with a firewall error even though creating the storage account succeeded.
  • Anything that changes on its own. Autoscaling node counts, tokens that rotate, tags applied by Azure Policy. Terraform will see them as drift on every plan unless you use ignore_changes (Lesson 15).
  • Imperative sequences with side effects. Database migrations, one-off backfills, “run this, check the output, then run that”. Terraform has provisioners for this and the documentation itself calls them a last resort.
  • Brand-new Azure features. The provider must add support first. Escape hatches exist (the azapi provider talks to the raw ARM API), but they are escape hatches.
  • Secret material. Terraform can create a Key Vault secret, but the value passes through and is stored in state in plaintext. Lesson 09 is entirely about this problem.

Common mistakes at this stage

Mistake 1 · “Terraform files run top to bottom”

They do not. Order within a file is irrelevant; ordering comes only from references. Splitting a configuration across main.tf, variables.tf and outputs.tf is purely a human convention — Terraform concatenates every .tf file in the directory and treats them as one configuration.

Mistake 2 · Treating state as a cache you can delete

State is not a cache. It is the only record connecting your code to real resource IDs. Delete it and Terraform believes it has created nothing, so the next apply tries to create everything again — and where names are globally unique (storage accounts, key vaults) it will fail halfway, leaving you with a partial deployment and no state. Lesson 10.

Mistake 3 · Editing in the portal “just this once”

A portal change that Terraform does not know about is drift. Depending on the resource, the next apply will silently revert it — or, if the property forces replacement, destroy and recreate the resource. Doing this to a storage account with data in it is how people learn this lesson permanently.

Exercises

Level 1 · Understand Classify the failure

For each error, say which of the four components it comes from — language, CLI/core, provider, or state:

  1. Error: Cycle: azurerm_subnet.a, azurerm_network_security_group.b
  2. Error: creating Storage Account: StorageAccountAlreadyTaken
  3. Error: Unsupported argument — An argument named "enable_rbac_authorization" is not expected here.
  4. Error: Resource already managed by Terraform
  5. Error: Invalid function argument — call to function "cidrsubnet" failed
Show answer
  1. CLI / core. Cycle detection happens in graph construction, before any provider is called. Azure knows nothing about it.
  2. Provider. The provider made a real API call and Azure rejected it — storage account names are globally unique across all of Azure.
  3. Language + provider schema. The parser checks your arguments against the schema the provider advertises. This specific one is the v4→v5 rename: it is now rbac_authorization_enabled.
  4. State. Nothing was sent to Azure; core found an existing entry at that address.
  5. Language. A built-in function evaluated during expression evaluation, entirely inside core.
Level 1 · Understand Three-way diff

A storage account exists in Azure. It is in Terraform state. Its configuration says account_replication_type = "LRS", state records "LRS", but a colleague changed it to "GRS" in the portal this morning.

What will terraform plan show, and what will terraform apply do?

Show answer

During the refresh phase Terraform reads the real resource and updates its in-memory state to "GRS". It then compares that against the configuration, which still says "LRS", and reports an in-place update:

plan output
  ~ resource "azurerm_storage_account" "lake" {
      ~ account_replication_type = "GRS" -> "LRS"
    }

Plan: 0 to add, 1 to change, 0 to destroy.

apply reverts the colleague's change. This is the intended behaviour — the configuration is the source of truth — but it is also why manual portal edits are dangerous: nobody is warned unless somebody looks at a plan.

Level 2 · Implement Choose the construct

Your team owns a data lake. The VNet it must connect to is owned by the central platform team and is created by a different Terraform repository. Your configuration needs the VNet's ID to place a private endpoint's subnet reference.

Which construct do you use for the VNet, and what would go wrong with the other one? Write the block type and explain the failure mode in two sentences.

Show answer

Use a data source: data "azurerm_virtual_network" "platform" { ... }. You need to read the VNet, not own it.

If you used resource "azurerm_virtual_network" instead, the first apply would fail because the VNet already exists. And if you resolved that by importing it into your state, you would now have two Terraform configurations that each believe they own the same VNet — their applies would fight, and deleting the block from yours would destroy the platform team's network.

A third option, better still at scale, is a terraform_remote_state data source or a published output — covered in Lesson 10.

Level 2 · Implement Translate the imperative script into HCL

A colleague stands up their dev lake with this shell script. Rewrite it as a complete, runnable Terraform configuration.

setup.sh
az group create --name rg-analytics-dev-weu-01 --location westeurope

az storage account create \
  --name stanalyticsdevweu01 \
  --resource-group rg-analytics-dev-weu-01 \
  --location westeurope \
  --sku Standard_LRS --kind StorageV2 \
  --enable-hierarchical-namespace true \
  --min-tls-version TLS1_2

az storage container create --name raw \
  --account-name stanalyticsdevweu01 --auth-mode login

Two constraints: no literal string may appear twice, and the result must be safely re-runnable.

Show solution
main.tf
terraform {
  required_version = ">= 1.9.0"

  required_providers {
    azurerm = {
      source  = "hashicorp/azurerm"
      version = "~> 5.0"
    }
  }
}

provider "azurerm" {
  features {}
}

locals {
  suffix   = "analytics-dev-weu-01"
  location = "westeurope"
}

resource "azurerm_resource_group" "analytics" {
  name     = "rg-${local.suffix}"
  location = local.location
}

resource "azurerm_storage_account" "lake" {
  name = "stanalyticsdevweu01"

  # References, not repeated literals. These ARE the dependency edges.
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  account_tier             = "Standard"
  account_kind             = "StorageV2"
  account_replication_type = "LRS"
  is_hns_enabled           = true
  min_tls_version          = "TLS1_2"
}

resource "azurerm_storage_container" "raw" {
  name               = "raw"
  storage_account_id = azurerm_storage_account.lake.id
}

Three things the translation buys you that the script did not have. It is idempotent — running it twice is a no-op rather than an error. It has a real dependency graph, because the storage account references the resource group instead of repeating its name, so Terraform works out the ordering itself. And it is reversible: terraform destroy removes all three in the correct order, which the script has no equivalent of.

Incidentally, --auth-mode login on the last line is the control-plane/data-plane split showing through — creating a container is a data-plane call needing different authentication from the two commands above it. Lesson 06.

Level 2 · Implement Model a resource another team owns

Extend that configuration so the storage account restricts access to a subnet the platform team owns: snet-shared-dev-weu-01, in VNet vnet-shared-dev-weu-01, resource group rg-network-dev-weu-01.

You must not be able to modify or destroy their subnet. Write the blocks, then say in one sentence what would go wrong with the alternative.

Show solution
network.tf
# A DATA source: read it, never own it. Deleting this block from the
# configuration cannot delete the platform team's subnet.
data "azurerm_subnet" "shared" {
  name                 = "snet-shared-dev-weu-01"
  virtual_network_name = "vnet-shared-dev-weu-01"
  resource_group_name  = "rg-network-dev-weu-01"
}

resource "azurerm_storage_account" "lake" {
  # ... as before ...

  network_rules {
    default_action             = "Deny"
    bypass                     = ["AzureServices"]
    virtual_network_subnet_ids = [data.azurerm_subnet.shared.id]
  }
}

What goes wrong with a resource block instead: the first apply fails because the subnet already exists — and if you resolved that by importing it, your configuration would now claim ownership of another team's subnet, so removing the block later would destroy it and break every workload attached to it.

Worth noticing: adding default_action = "Deny" in the same apply that creates a container is exactly what produces the 403 in Lesson 06 — your own runner is now outside the firewall it just built.

Level 3 · Troubleshoot Why does this not do what its author expected?

An engineer writes this and complains that Terraform “ignores the order”:

broken.tf
resource "azurerm_storage_account" "lake" {
  name                     = "stanalyticsdevweu01"
  resource_group_name      = "rg-analytics-dev-weu-01"
  location                 = "westeurope"
  account_tier             = "Standard"
  account_replication_type = "LRS"
}

resource "azurerm_resource_group" "analytics" {
  name     = "rg-analytics-dev-weu-01"
  location = "westeurope"
}

They report: “Terraform tried to create the storage account first and failed with Resource group 'rg-analytics-dev-weu-01' could not be found. But the resource group is right there in the file.”

Explain the cause and give the one-line fix.

Show answer

resource_group_name is a hardcoded string literal, not a reference. Terraform builds its dependency graph from references between addresses. Because nothing in the storage account block mentions azurerm_resource_group.analytics, the graph has two independent nodes and Terraform is free to create them in parallel — which it does, ten at a time.

The string happening to match the resource group's name is invisible to Terraform. The fix:

fixed.tf
resource "azurerm_storage_account" "lake" {
  name                     = "stanalyticsdevweu01"
  resource_group_name      = azurerm_resource_group.analytics.name   # reference, not literal
  location                 = azurerm_resource_group.analytics.location
  account_tier             = "Standard"
  account_replication_type = "LRS"
}

This is the single most important habit in Terraform: reference, don't repeat. Every literal you replace with a reference adds a correct edge to the graph. Lesson 05 covers this as implicit vs explicit dependencies.

Interview questions

What is Infrastructure as Code, and what does it actually buy you?

Defining infrastructure in machine-readable files kept under version control, with a tool responsible for making the real environment match. The benefits are reproducibility (the same definition deploys to dev, staging and prod), auditability (git history answers “who changed the firewall and why”), reviewability (infrastructure changes go through pull request before they exist), disaster recovery, and drift detection.

The one I would lead with is reviewability — it is the benefit that changes how a team works, not just how fast an individual is.

Explain declarative vs imperative infrastructure.

Imperative code specifies a sequence of actions; the author owns the ordering and the “does it already exist?” logic, and re-running is generally not safe. Declarative code specifies a desired end state; the engine computes the actions by diffing desired state against current state, which makes it idempotent.

The detail worth adding: Terraform's diff is three-way — configuration, state, and real infrastructure. That third input is what lets it distinguish “you changed the code” from “someone changed the cloud”.

Terraform or Bicep for an Azure-only platform?

Both are defensible. Bicep is native, needs no state file, and supports new Azure features on day one. Terraform gives a stronger plan/destroy story, and — the argument I would actually make for a data platform — it puts non-Azure resources in the same dependency graph. Databricks Unity Catalog objects, Snowflake, Kafka and GitHub can be provisioned in the same plan as the storage account they depend on.

I would choose Bicep for an Azure-only team that does not want to operate a state backend, and Terraform as soon as the platform crosses a provider boundary or the team already has Terraform skills.

Is Terraform a replacement for Ansible?

No — different layers. Terraform provisions infrastructure declaratively and keeps state, so it knows exactly what it owns and can destroy it. Ansible configures software on hosts procedurally with idempotent modules and keeps no state. They are commonly used together, though for a PaaS-based Azure data platform there is often no Ansible layer at all, since there are no VMs to configure.

What are the main components of Terraform's architecture?

Four. The configuration language (HCL). Terraform core, which parses configuration, builds a dependency graph, computes the diff and manages state — and is entirely cloud-agnostic. Provider plugins, separate binaries downloaded during init, which translate resource types into API calls and communicate with core over gRPC. And state, the JSON record mapping configuration addresses to real resource IDs.

What is the difference between a resource and a data source?

A resource is something Terraform creates, updates and destroys — it owns the lifecycle. A data source is a read-only lookup of something that already exists, resolved during plan and used to feed values into resources. Data sources never create or destroy anything. Practically: use a data source for anything another team owns, so that removing it from your configuration cannot delete it.

Give an example of something Terraform handles badly.

Anything with a life of its own or living on the data plane. Autoscaled node counts and rotated tokens show up as drift on every plan. Uploading data, running jobs, or performing ordered operations with side effects fits provisioners badly — HashiCorp themselves call those a last resort. And secrets pass through state in plaintext, so creating a Key Vault secret with a real value in Terraform means that value now lives in your state file.

Key takeaways

  • Terraform reconciles three things: configuration, state and reality. Almost every surprising behaviour is explained by asking which of the three is out of step.
  • “Terraform” means four separable components — language, core, provider, state. Knowing which one an error came from tells you where to look.
  • Order comes from references, not from file layout. Hardcoded strings create silent, missing edges.
  • resource = you own it. data = you read it. Getting this wrong can destroy another team's infrastructure.
  • Terraform's advantage for a data platform is one graph across Azure and Databricks and everything else — not “multi-cloud”.

HCL: types, expressions and functions

You already know what a variable and a loop are. What you need is the shape of HCL's type system — especially the list/set distinction that decides whether for_each works — and the ways HCL deliberately refuses to behave like a programming language.

By the end of this lesson you can

  • Read any block and name its parts: block type, labels, arguments, nested blocks
  • Choose correctly between list, set, map, object and tuple — and explain why it matters for for_each
  • Write for expressions that produce maps, filter, and flatten nested structures
  • Use try, coalesce, merge and lookup the way real Azure configurations do
  • Explain why a dynamic block exists and when not to use one
  • Explore any expression interactively with terraform console

HCL is not a programming language, on purpose

Coming from Python or TypeScript, four constraints will surprise you. Each is a deliberate design decision, and understanding why stops you fighting the language.

What you expectWhat HCL doesWhy
Statements execute in order Blocks are declarations. Order in the file is irrelevant; evaluation order comes from the reference graph. Terraform needs a graph to parallelise and to compute a diff. A sequence cannot be diffed.
Reassign a variable Everything is immutable. A local is bound once; there is no x = x + 1. Mutable values would make evaluation order significant, which would break the graph model.
Write a loop or a function No for statement, no user-defined functions in the classic sense. You get for expressions, for_each/count meta-arguments, and (since 1.8) provider-defined and local function blocks for pure value transforms. Arbitrary control flow would let configuration produce a different resource set on each run — the opposite of reproducible.
Print, read files, call an API No side effects. Expressions are pure. I/O happens only through providers and data sources. Plan must be able to evaluate everything without changing anything.
The one sentence to internalise

HCL expressions compute values; the resource blocks those values feed decide infrastructure. Anything clever you do in HCL is clever value-shuffling — it never changes the fact that Terraform must be able to enumerate every resource before it does anything.

Common mistake · argument vs block syntax

Writing an = where the schema expects a block, or omitting it where it expects an argument:

wrong
blob_properties = {          # ✗ blob_properties is a block, not an argument
  versioning_enabled = true
}

tags {                       # ✗ tags is a map argument, not a block
  environment = "dev"
}

The provider schema decides which is which. The error is Unexpected "=" — An argument or block definition is required or Blocks of type "tags" are not expected here. When in doubt, check the registry docs for that resource — arguments described as “a foo block as defined below” take no =.

The type system

types.tf — every type, with Azure-flavoured values
locals {
  # ---- primitives ----
  location    = "westeurope"          # string
  retention   = 30                    # number (no int/float distinction)
  hns_enabled = true                  # bool

  # ---- collections: homogeneous ----
  # list: ordered, duplicates allowed, addressed by index
  regions = ["westeurope", "northeurope", "westeurope"]

  # set: unordered, deduplicated, NOT addressable by index
  containers = toset(["raw", "bronze", "silver", "gold"])

  # map: string keys, values all the same type
  tags = {
    environment = "dev"
    workload    = "analytics"
  }

  # ---- structural: heterogeneous ----
  # object: named attributes, each with its own type
  lake_config = {
    name          = "stanalyticsdevweu01"
    tier          = "Standard"
    replication   = "LRS"
    hns           = true
    retention_days = 7
  }

  # tuple: positional, each position its own type
  pair = ["westeurope", 3, true]

  # nested: a map of objects — the single most useful shape in Terraform
  subnets = {
    privatelink = { prefix = "10.10.1.0/24", delegate = null }
    databricks_host = { prefix = "10.10.2.0/24", delegate = "Microsoft.Databricks/workspaces" }
    functions   = { prefix = "10.10.3.0/26", delegate = "Microsoft.App/environments" }
  }
}

list vs set — the distinction that actually bites

They look identical in HCL syntax (both written with [...]), and Terraform will convert between them silently in many places. But they behave differently in the one place it counts.

list(string)set(string)
Order preservedYesNo — Terraform stores it sorted
DuplicatesAllowedSilently removed
Index accesslocal.regions[0]Not possible — convert with tolist() first
Usable with for_eachNo — wrap in toset()Yes
Resource instance keysWith count: [0], [1]…With for_each: ["raw"], ["bronze"]…
Why this matters more than it looks

Instance keys end up in state addresses. With a list and count, removing "bronze" from the middle of ["raw","bronze","silver","gold"] shifts every subsequent index — so Terraform plans to destroy and recreate silver and gold, because [2] used to be silver and is now gold.

With a set and for_each, the key is the value itself. Removing "bronze" destroys exactly one container. This is why the course, like every production codebase, prefers for_each. Full treatment in Lesson 15.

Type conversion

HCL converts automatically when it is unambiguous, and errors when it is not. Terraform will happily accept the string "30" where a number is required, and true where a string is required.

conversion functions you will use
toset(["raw", "bronze", "raw"])   # → set: ["bronze", "raw"]  (deduped, sorted)
tolist(toset(["b", "a"]))         # → list: ["a", "b"]        (sorted, now indexable)
tomap({ a = 1, b = 2 })           # → map(number)
tostring(30)                      # → "30"
tonumber("30")                    # → 30

Strings and interpolation

strings.tf
locals {
  workload = "analytics"
  env      = "dev"
  region   = "weu"

  # interpolation — ${ } inside a quoted string
  rg_name = "rg-${local.workload}-${local.env}-${local.region}-01"

  # storage accounts allow only lowercase letters and digits, max 24 chars
  sa_name = lower("st${local.workload}${local.env}${local.region}01")

  # you can call functions and use conditionals inside interpolation
  sku = "Standard_${local.env == "prod" ? "GZRS" : "LRS"}"

  # a bare expression needs no interpolation at all — this is redundant:
  bad  = "${var.location}"
  good = var.location
}
Common mistake · wrapping a whole expression in "${ }"

count = "${length(var.regions)}" works but is legacy style from Terraform 0.11. terraform fmt will not remove it; linters will flag it. Use interpolation only when you are genuinely embedding a value inside a larger string.

Heredoc strings

Used for JSON policies, scripts and anything multi-line. The <<- form strips leading indentation.

heredoc.tf
locals {
  # For real JSON, prefer jsonencode() over a heredoc — it guarantees valid
  # JSON and lets you interpolate values without quoting bugs.
  lifecycle_rule = jsonencode({
    rules = [{
      name    = "archive-raw-after-90d"
      enabled = true
      filters = { prefixMatch = ["raw/"] }
    }]
  })

  init_script = <<-EOT
    #!/bin/bash
    set -euo pipefail
    echo "Mounting ${local.sa_name}"
  EOT
}

Operators and conditionals

operators.tf
locals {
  a = 10 + 5          # arithmetic: + - * / %
  b = 10 > 5          # comparison: == != < <= > >=
  c = true && false   # logical: && || !

  # conditional expression:  condition ? true_value : false_value
  replication = var.environment == "prod" ? "GZRS" : "LRS"
  retention   = var.environment == "prod" ? 90 : 7

  # both branches must be the same type — this errors:
  # bad = var.enabled ? "yes" : 0
}
Both branches are evaluated

HCL's conditional is not short-circuiting in the way you might assume. This fails when the list is empty, even though the condition guards against it:

fails on an empty list
first_subnet = length(var.subnets) > 0 ? var.subnets[0] : "none"

Use try() or one() instead: try(var.subnets[0], "none"). try() evaluates its arguments in order and returns the first that does not produce an error.

for expressions

A for expression transforms one collection into another. It is an expression, not a statement — it produces a value. Brackets decide the output type: [ ] gives a tuple/list, { } gives an object/map.

for_expressions.tf
locals {
  containers = ["raw", "bronze", "silver", "gold"]

  # 1 · list → list
  upper = [for c in local.containers : upper(c)]
  # ["RAW", "BRONZE", "SILVER", "GOLD"]

  # 2 · list → map   (key => value)
  paths = { for c in local.containers : c => "abfss://${c}@${local.sa_name}.dfs.core.windows.net/" }
  # { raw = "abfss://raw@...", bronze = "abfss://bronze@...", ... }

  # 3 · with a filter (the "if" clause)
  curated = [for c in local.containers : c if c != "raw"]
  # ["bronze", "silver", "gold"]

  # 4 · iterating a map yields key AND value
  tag_strings = [for k, v in local.tags : "${k}=${v}"]
  # ["environment=dev", "workload=analytics"]

  # 5 · the single most useful pattern in Terraform:
  #     turn a list of objects into a map keyed by something stable,
  #     so it can be used with for_each
  subnet_defs = [
    { name = "privatelink", prefix = "10.10.1.0/24" },
    { name = "functions",   prefix = "10.10.3.0/26" },
  ]
  subnets_by_name = { for s in local.subnet_defs : s.name => s }
  # { privatelink = {name=..., prefix=...}, functions = {...} }

  # 6 · grouping mode — note the ellipsis, which collects duplicates
  #     into a list instead of erroring on a repeated key
  by_tier = { for c in local.container_defs : c.tier => c.name... }
}

Flattening nested loops

HCL has no nested for_each. The standard idiom for “every combination of X and Y” is a nested for inside flatten(), producing a flat map. You will use this for things like “assign three roles to two identities”.

flatten.tf — cross-product of identities × roles
locals {
  access = {
    databricks = ["Storage Blob Data Contributor", "Key Vault Secrets User"]
    functions  = ["Storage Blob Data Reader"]
  }

  # produce one entry per (identity, role) pair
  assignments = {
    for pair in flatten([
      for identity, roles in local.access : [
        for role in roles : {
          identity = identity
          role     = role
        }
      ]
    ]) : "${pair.identity}-${pair.role}" => pair
  }
}

# → {
#     "databricks-Storage Blob Data Contributor" = { identity = "databricks", role = "..." }
#     "databricks-Key Vault Secrets User"        = { ... }
#     "functions-Storage Blob Data Reader"       = { ... }
#   }
#
# which is now directly usable:  for_each = local.assignments
Why the key must be stable

That composite key becomes part of the resource address in state: azurerm_role_assignment.this["databricks-Storage Blob Data Contributor"]. If you generate keys from something that changes — an index, a timestamp, a resource ID that is unknown until apply — Terraform cannot match old instances to new ones and will plan to destroy and recreate them. Keys must be derivable at plan time from static input.

Splat expressions

splat.tf
# shorthand for [for s in azurerm_subnet.this : s.id]
subnet_ids = azurerm_subnet.this[*].id

# with for_each (a map), values() first
subnet_ids = values(azurerm_subnet.this)[*].id

# splat on a possibly-null single value returns [] or [value] — handy
principal_ids = azurerm_linux_function_app.this.identity[*].principal_id

dynamic blocks

for_each on a resource creates multiple resources. dynamic creates multiple nested blocks inside one resource. Use it when the provider schema wants repeated blocks and the number is data-driven.

dynamic.tf — NSG rules from a variable
variable "nsg_rules" {
  type = map(object({
    priority                   = number
    direction                  = string
    access                     = string
    protocol                   = string
    source_port_range          = string
    destination_port_range     = string
    source_address_prefix      = string
    destination_address_prefix = string
  }))
  default = {}
}

resource "azurerm_network_security_group" "this" {
  name                = "nsg-databricks-dev-weu-01"
  location            = var.location
  resource_group_name = var.resource_group_name

  dynamic "security_rule" {
    for_each = var.nsg_rules

    content {
      name                       = security_rule.key
      priority                   = security_rule.value.priority
      direction                  = security_rule.value.direction
      access                     = security_rule.value.access
      protocol                   = security_rule.value.protocol
      source_port_range          = security_rule.value.source_port_range
      destination_port_range     = security_rule.value.destination_port_range
      source_address_prefix      = security_rule.value.source_address_prefix
      destination_address_prefix = security_rule.value.destination_address_prefix
    }
  }
}

Inside the content block, the iterator is named after the block (security_rule) and exposes .key and .value. Override the name with iterator = r when nesting dynamics.

Use dynamic sparingly

HashiCorp's own documentation warns that overuse makes configuration hard to read. A conditional single block is the most common legitimate use — for_each over a zero-or-one collection:

conditional block idiom
dynamic "identity" {
  for_each = var.enable_managed_identity ? [1] : []
  content {
    type = "SystemAssigned"
  }
}

If you can write three literal blocks instead of a dynamic over three items, write the three blocks. A reviewer can see them.

Common mistakes

Trying to build a resource name from a value that is unknown at plan time

name = "st${random_id.suffix.hex}" is fine. for_each keyed on azurerm_storage_account.lake.id is not — that ID does not exist until apply, so Terraform cannot enumerate the instances during plan and errors with The "for_each" value depends on resource attributes that cannot be determined until apply.

Rule: for_each and count keys must be computable from static input at plan time.

Using lookup() on an object

lookup() is for maps. On an object with known attributes, use try(obj.attr, default) or declare the attribute as optional() in the variable type (Lesson 07). Using lookup() with a default on a map is also increasingly discouraged in favour of try().

Assuming set ordering

tolist(toset(["gold","raw"]))[0] is "gold", not "raw" — sets are stored sorted. If order matters, keep a list and never round-trip through a set.

Exercises

Level 1 · Understand Name the type

Give the most specific type of each value:

  1. ["raw", "bronze"]
  2. { name = "lake", tier = "Standard" }
  3. { dev = 7, prod = 90 }
  4. ["westeurope", 3, true]
  5. toset([1, 2, 2, 3])
Show answer
  1. tuple([string, string]), which converts to list(string) wherever one is expected.
  2. object({ name = string, tier = string }) — converts to map(string) because both values happen to be strings.
  3. object({ dev = number, prod = number }) → map(number).
  4. tuple([string, number, bool]). It cannot become a list, because a list requires one element type.
  5. set(number) containing [1, 2, 3] — the duplicate is dropped.

The practical takeaway: literal [ ] and { } produce tuples and objects, which Terraform converts to lists and maps when the target type requires it. Mixed-type values can only stay tuples/objects.

Level 2 · Implement Build a container map

Given:

input
locals {
  storage_account = "stanalyticsdevweu01"
  layers = [
    { name = "raw",    tier = "Cool", retention_days = 365 },
    { name = "bronze", tier = "Hot",  retention_days = 90  },
    { name = "silver", tier = "Hot",  retention_days = 90  },
    { name = "gold",   tier = "Hot",  retention_days = null },
  ]
}

Write locals that produce:

  1. layers_by_name — a map keyed by layer name, ready for for_each.
  2. hot_layers — a list of just the names whose tier is "Hot".
  3. abfss_paths — a map from layer name to its abfss:// URI.
  4. retention — a map from layer name to retention days, defaulting to 30 where null.
Show answer
solution
locals {
  # 1 · keyed map — the shape for_each needs
  layers_by_name = { for l in local.layers : l.name => l }

  # 2 · filtered list of names
  hot_layers = [for l in local.layers : l.name if l.tier == "Hot"]

  # 3 · derived URIs
  abfss_paths = {
    for l in local.layers :
    l.name => "abfss://${l.name}@${local.storage_account}.dfs.core.windows.net/"
  }

  # 4 · coalesce handles the null
  retention = {
    for l in local.layers :
    l.name => coalesce(l.retention_days, 30)
  }
}

Verify any of these with terraform console before wiring them into a resource. Note that coalesce returns the first non-null and non-empty argument, which is what you want here; try would not help, since null is a valid value rather than an error.

Level 2 · Implement Build a subnet plan using expressions only

From the input below, write locals producing the four values listed. No literal CIDR string may appear anywhere in your answer.

input.tf
variable "vnet_cidr" {
  type    = string
  default = "10.10.0.0/16"
}

variable "subnets" {
  type = map(object({
    newbits    = number
    netnum     = number
    delegation = optional(string)
  }))
  default = {
    privatelink = { newbits = 8,  netnum = 1 }
    databricks  = { newbits = 8,  netnum = 2,  delegation = "Microsoft.Databricks/workspaces" }
    functions   = { newbits = 10, netnum = 16, delegation = "Microsoft.Web/serverFarms" }
  }
}
  1. prefixes — map of subnet name to its CIDR.
  2. delegated — a set of the names that have a delegation.
  3. usable_ips — map of name to usable address count (Azure reserves 5 per subnet).
  4. summary — strings like "privatelink: 10.10.1.0/24 (251 usable)".
Show solution
locals.tf
locals {
  # 1 - cidrsubnet(prefix, newbits, netnum)
  prefixes = {
    for k, v in var.subnets : k => cidrsubnet(var.vnet_cidr, v.newbits, v.netnum)
  }

  # 2 - a filtered "for" over a map, projected into a set of keys
  delegated = toset([
    for k, v in var.subnets : k if v.delegation != null
  ])

  # 3 - host bits = 32 - prefix length;  usable = 2^hostbits - 5
  usable_ips = {
    for k, prefix in local.prefixes :
    k => pow(2, 32 - tonumber(split("/", prefix)[1])) - 5
  }

  # 4 - iterating a MAP yields keys in sorted order, so no sort() is needed
  summary = [
    for k, prefix in local.prefixes :
    format("%s: %s (%d usable)", k, prefix, local.usable_ips[k])
  ]
}

# summary = [
#   "databricks: 10.10.2.0/24 (251 usable)",
#   "functions: 10.10.4.0/26 (59 usable)",
#   "privatelink: 10.10.1.0/24 (251 usable)",
# ]

Verify each of these in terraform console before wiring them into resources. CIDR arithmetic is easy to get subtly wrong and expensive to correct later, because resizing a subnet requires emptying it first.

Two details: format("%d", ...) renders the number from pow() without a decimal point, and iterating a map gives sorted keys — a for over a list would instead preserve the list's own order.

Level 2 · Implement Reshape a flat list into an access matrix

A team hands you their access requirements as a flat list. Derive two values from it.

input.tf
locals {
  grants = [
    { team = "engineering", layer = "raw",    access = "read"  },
    { team = "engineering", layer = "silver", access = "write" },
    { team = "engineering", layer = "gold",   access = "write" },
    { team = "analysts",    layer = "gold",   access = "read"  },
    { team = "ml",          layer = "silver", access = "read"  },
    { team = "ml",          layer = "gold",   access = "read"  },
  ]
}
  1. assignments — a map keyed "<team>-<layer>" whose value carries the team, the layer and the Azure role name (read becomes Storage Blob Data Reader, write becomes Storage Blob Data Contributor). It must be usable directly as a for_each.
  2. layers_by_team — a map of team name to the list of layers it touches.
Show solution
locals.tf
locals {
  role_for = {
    read  = "Storage Blob Data Reader"
    write = "Storage Blob Data Contributor"
  }

  # 1 - project the list into a map with a stable composite key
  assignments = {
    for g in local.grants :
    "${g.team}-${g.layer}" => {
      team  = g.team
      layer = g.layer
      role  = local.role_for[g.access]
    }
  }

  # 2 - GROUPING mode. The ellipsis collects duplicate keys into a list
  #     instead of failing on the repeated "engineering" key.
  layers_by_team = {
    for g in local.grants : g.team => g.layer...
  }
}

# layers_by_team = {
#   analysts    = ["gold"]
#   engineering = ["raw", "silver", "gold"]
#   ml          = ["silver", "gold"]
# }

resource "azurerm_role_assignment" "lake" {
  for_each = local.assignments

  scope                = azurerm_storage_container.layers[each.value.layer].id
  role_definition_name = each.value.role
  principal_id         = local.team_principals[each.value.team]
  principal_type       = "Group"
}

The ... grouping suffix is the part most people do not know exists. Without it, { for g in local.grants : g.team => g.layer } fails with Duplicate object key, because three entries share the key "engineering".

The composite key matters too. "engineering-silver" is derived entirely from static input, so it is known at plan time and stable between runs. Keying on anything computed — a container ID, a principal ID — fails with the for_each value depends on resource attributes that cannot be determined until apply. Lesson 15.

Find four separate problems. Two are HCL-level, two are Azure-level.

Show answer

1 · for_each on a list (HCL).

for_each accepts a set or a map, never a list. Error: Invalid for_each argument … must be a map, or set of strings. Fix: for_each = toset(var.containers), or change the variable type to set(string).

2 · tags written as a block (HCL).

tags is a map argument, so it needs =: tags = { environment = "dev" }.

3 · Invalid storage account name (Azure).

"st-analytics-dev-weu-01" contains hyphens and is 23 characters. Storage account names must be 3–24 characters, lowercase letters and digits only, and globally unique across all of Azure. Fix: "stanalyticsdevweu01". This is caught at plan time by the provider's validation, not by terraform validate… actually it is caught by validate here, because the provider declares a regex — but the global uniqueness failure only appears at apply.

4 · Missing is_hns_enabled for a data lake (Azure, design-level).

Not a syntax error, but this creates a flat blob storage account, not ADLS Gen2. Without is_hns_enabled = true there is no hierarchical namespace, so no real directories, no POSIX-style ACLs, and worse performance for analytics engines. And because that argument forces replacement, discovering this after loading data means destroying the account. Lesson 06.

Interview questions

What is the difference between a list and a set in Terraform, and why does it matter?

A list is ordered and allows duplicates, addressable by index. A set is unordered and deduplicated, and cannot be indexed. It matters because for_each accepts only sets and maps, and because the instance key ends up in the state address. With count over a list, removing an element shifts every later index and causes unrelated resources to be destroyed and recreated. With for_each over a set, the key is the value itself, so removing one element affects exactly one resource.

What is the difference between an argument and an attribute?

An argument is an input you set inside a block — name = "...". An attribute is a value the resource exports for you to read — azurerm_storage_account.lake.id. Many are both. The important category is attributes that are only known after apply, such as a resource ID or a managed identity's principal ID; those cannot be used where Terraform needs a value at plan time, like a for_each key.

When would you use a dynamic block?

When a resource schema takes repeated nested blocks and the number of them is driven by data — NSG security rules from a variable, or IP restrictions on a function app. Also for conditionally including a single block, using for_each = condition ? [1] : []. I would avoid it when the blocks are few and known, since literal blocks are far easier to review. Note it produces nested blocks within one resource, not multiple resources — that is for_each on the resource itself.

How do you handle an optional value that may not exist?

try(expr, fallback) returns the first argument that evaluates without error — good for possibly-absent object attributes or out-of-range indexes. coalesce(a, b) returns the first non-null, non-empty value — good when the value exists but may be null. For variable types, declaring an attribute optional(string, "default") is cleaner than either. And one() safely reduces a zero-or-one list to a value or null, which is the idiom for reading an optional identity block.

Why does Terraform not let you write arbitrary loops or functions?

Because Terraform must be able to enumerate the complete set of resources and their dependencies before it does anything — that is what makes a plan possible. Arbitrary control flow or side effects would mean the resource set could differ between the plan and the apply, and the configuration would no longer be reviewable. The constraint pushes complexity into modules and data structures, where it stays visible.

How would you create a resource for every combination of two lists?

There is no nested for_each, so you build the cross-product as a value first: a nested for expression wrapped in flatten(), then projected into a map with a composite key, and use that map as the for_each. The key must be stable and derivable at plan time — typically a string joining the two source values — because it becomes part of the resource's address in state.

Key takeaways

  • Blocks take no =; arguments always do. The provider schema decides which a given name is.
  • Collections are homogeneous (list, set, map); structural types are not (object, tuple).
  • for_each takes a set or map only, and its keys must be known at plan time.
  • for expressions with { } produce maps — the shape almost everything downstream wants. Combine with flatten() for cross-products.
  • Conditionals evaluate both branches; use try() for anything that might error.
  • terraform console is the correct way to learn every one of these. Use it constantly.

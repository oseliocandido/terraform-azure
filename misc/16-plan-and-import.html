Reading plans, state surgery, import & brownfield

Reading a plan carefully is the highest-value skill in this course — it is the last checkpoint before production changes. This lesson goes through plan output line by line, then covers the state operations you reach for when reality and state disagree, including adopting infrastructure that already exists.

By the end of this lesson you can

  • Read every symbol and annotation in plan output and say what it means
  • Parse plan JSON to enforce policy automatically
  • Use state list / show / mv / rm and know the risk of each
  • Choose correctly between moved, import and removed blocks
  • Adopt an existing Azure resource into Terraform without recreating it
  • Investigate drift methodically instead of guessing

What you seeWhat it means
# … will be createdNew resource. Nothing exists yet, so every attribute shows +.
(known after apply)Terraform cannot compute this until Azure responds. Usually IDs and endpoints. Also a visible dependency edge.
~ old -> newAn in-place update. The resource keeps its identity and data.
- "temp" = "true" -> nullAn element removed from a map — here a tag being deleted.
# (28 unchanged attributes hidden)Noise suppression. Use terraform show on a saved plan when you want everything.
# forces replacementRead every plan for this. It names the exact argument that made an in-place update impossible.
(because … is not in configuration)Terraform explains why a destroy is planned. Extremely useful — most destroys are a removed block or an index shift.
Changes to OutputsOutputs changing. Harmless in itself, but a signal that something downstream may be affected.
How to read a plan in thirty seconds
  1. Read the summary line first. Does the destroy count match what you intended?
  2. Search for forces replacement. Every occurrence is a potential data-loss event.
  3. Read every - resource block and the “because” explanation next to it.
  4. Only then read the ~ updates — they are almost always the safe part.

Parsing plans as JSON

machine-readable plan analysis
terraform plan -out=tfplan
terraform show -json tfplan > plan.json

# everything being destroyed or replaced
jq -r '.resource_changes[]
       | select(.change.actions | index("delete"))
       | "\(.change.actions | join(",")): \(.address)"' plan.json

# just replacements, with the reason
jq -r '.resource_changes[]
       | select(.change.actions == ["delete","create"] or .change.actions == ["create","delete"])
       | "\(.address) — replaced because: \(.change.replace_paths // [] | flatten | join(", "))"' plan.json

# a counts summary
jq -r '[.resource_changes[].change.actions | join(",")] | group_by(.)
       | map({action: .[0], count: length}) | .[] | "\(.count)\t\(.action)"' plan.json
the CI gate this enables
#!/usr/bin/env bash
set -euo pipefail

terraform show -json tfplan > plan.json

DESTROYS=$(jq '[.resource_changes[] | select(.change.actions | index("delete"))] | length' plan.json)

if [ "$DESTROYS" -gt 0 ] && [ "${ALLOW_DESTROY:-false}" != "true" ]; then
  echo "::error::Plan destroys $DESTROYS resource(s). Set ALLOW_DESTROY=true to override."
  jq -r '.resource_changes[] | select(.change.actions | index("delete")) | "  - " + .address' plan.json
  exit 1
fi

State surgery

CommandEffectRiskPrefer instead
state list [filter]List addressesNone—
state show ADDRPrint one resource's attributesPrints sensitive values to your terminal and shell history—
state pullPrint raw state JSONThe output is a secret—
state mv OLD NEWRename an addressImmediate, unreviewed state mutationA moved block
state rm ADDRForget a resource; Azure keeps itCreates an orphan that nothing managesA removed block
import ADDR IDAdopt an existing resourceWrong ID silently binds the wrong thingAn import block
state pushOverwrite remote stateExtreme. Can destroy the record of your entire platformRestore a blob version

Prefer configuration blocks over CLI state commands

moved, import and removed blocks all do in a reviewable, planned, version-controlled way what state mv, state import and state rm do immediately and invisibly. A colleague can see a moved block in a pull request; nobody can see that you ran terraform state mv on your laptop last Tuesday. Reach for the CLI only when recovering from something the blocks cannot express.

The three refactoring blocks

moved — rename an address, change nothing in Azure
moved {
  from = azurerm_storage_account.lake
  to   = module.lake.azurerm_storage_account.this
}

moved {
  from = azurerm_storage_container.layers[0]
  to   = azurerm_storage_container.layers["raw"]
}
import — adopt an existing resource
import {
  to = azurerm_storage_account.lake
  id = "/subscriptions/0000.../resourceGroups/rg-analytics-prod-weu-01/providers/Microsoft.Storage/storageAccounts/stanalyticsprodweu01"
}
removed — stop managing WITHOUT destroying
# Delete the resource block, then add this. Terraform 1.7+
removed {
  from = azurerm_storage_account.legacy

  lifecycle {
    destroy = false      # forget it, do not delete it
  }
}
Why removed matters

Before it existed, handing a resource to another team meant running terraform state rm — unreviewable, and easy to forget to do before merging the deletion, at which point the next apply destroys it. A removed block with destroy = false makes “stop managing this” an explicit, reviewed change that shows up in the plan.

“An Azure Storage Account already exists and the company wants to start managing it with Terraform.”

Generated configuration is a starting point, not an answer

It is exhaustive, entirely literal (no variables or references), and it faithfully reproduces bad settings — note allow_nested_items_to_be_public = true and shared_access_key_enabled = true above. Your job is to review it, decide which settings should change, and change them deliberately in a later commit. Do not mix the import with the improvements.

Importing child resources

The account is only the beginning — its containers, lifecycle policy and role assignments each need importing too, each with its own ID format.

imports.tf
locals {
  sa_id = "/subscriptions/0000.../resourceGroups/rg-legacy-data/providers/Microsoft.Storage/storageAccounts/stlegacydata001"
}

import {
  to = azurerm_storage_account.legacy
  id = local.sa_id
}

# Containers use the resource-manager ID form.
import {
  for_each = toset(["raw", "curated", "archive"])

  to = azurerm_storage_container.legacy[each.value]
  id = "${local.sa_id}/blobServices/default/containers/${each.value}"
}

# The management policy's ID is the account ID plus a fixed suffix.
import {
  to = azurerm_storage_management_policy.legacy
  id = "${local.sa_id}/managementPolicies/default"
}
Finding an ID format

Every resource's registry documentation page ends with an Import section showing the exact ID format. Read it — the formats are not always guessable, and role assignments in particular use a form with the scope followed by the assignment GUID. When stuck, create one example of the resource with Terraform in a sandbox and read its id from state.

Investigating drift methodically

a diagnostic sequence
# 1 · What changed outside Terraform, without proposing to revert it?
terraform plan -refresh-only

# 2 · What does state currently believe?
terraform state show azurerm_storage_account.lake

# 3 · What does Azure actually say?
az storage account show --name stanalyticsprodweu01 \
  --resource-group rg-analytics-prod-weu-01

# 4 · WHO changed it and when? The activity log is the answer.
az monitor activity-log list \
  --resource-group rg-analytics-prod-weu-01 \
  --start-time 2026-09-01T00:00:00Z \
  --query "[?contains(resourceId, 'stanalyticsprodweu01')].
           {time:eventTimestamp, op:operationName.value, who:caller, status:status.value}" \
  -o table

# 5 · Did OUR configuration change? Check git, not just the plan.
git log -p --since="2 weeks ago" -- lake.tf

# 6 · Did the PROVIDER change?
git log -p -- .terraform.lock.hcl
Step 4 is the one people skip

The Azure activity log records who made every control-plane change and when. Most “mysterious drift” turns out to be a named person doing something reasonable during an incident, or an Azure Policy remediation task. Knowing which changes the fix: revert it, adopt it into configuration, or add ignore_changes if a system legitimately owns that attribute.

Deciding what to do about drift

CauseRight response
An emergency portal fix that should persistUpdate the configuration to match, then terraform apply -refresh-only so state agrees. The change is now reviewed and reproducible.
An unauthorised changeLet the next apply revert it — but check first that reverting is not itself destructive, and talk to whoever made it.
Azure Policy appending tagsignore_changes on those specific tags. Fighting policy from Terraform is a losing game.
Autoscaling changing a countignore_changes on that attribute.
Another Terraform configuration managing the same resourceA design bug. Decide who owns it; the other side uses a data source or a removed block.
The resource was deletedDecide whether recreating is safe. For anything stateful it usually is not — see Lesson 10.

Exercises

Level 1 · Understand Read this plan
plan excerpt
  # azurerm_key_vault.main must be replaced
-/+ resource "azurerm_key_vault" "main" {
      ~ id                         = "/subscriptions/.../kv-analytics-prod-weu-01" -> (known after apply)
        name                       = "kv-analytics-prod-weu-01"
      ~ soft_delete_retention_days = 7 -> 90
      ~ sku_name                   = "standard" -> "premium" # forces replacement
      ~ vault_uri                  = "https://kv-analytics-prod-weu-01.vault.azure.net/" -> (known after apply)
    }

  # azurerm_key_vault_secret.api will be destroyed
  # (because azurerm_key_vault.main is being replaced)
  - resource "azurerm_key_vault_secret" "api" { ... }

Plan: 2 to add, 0 to change, 2 to destroy.

Answer: what triggered this, what happens if you apply it, and what should you do?

Show answer

Trigger: sku_name changing from standard to premium, marked # forces replacement. The retention change is incidental — it would have been an in-place update on its own.

If applied:

  • The vault and every secret, key and certificate in it are destroyed.
  • The secret is destroyed too, and Terraform tells you why: it depends on a resource being replaced.
  • Because Key Vault soft-deletes, the name stays reserved — so the create step may fail with a conflict, leaving you with no vault at all.
  • If purge_protection_enabled is on, that failure cannot be resolved for up to 90 days.
  • Every application reading from this vault breaks immediately.

What to do:

  1. Do not apply. Check whether the SKU change was intended — git log -p on the file.
  2. If unintended, revert it. The retention change can go ahead on its own.
  3. If genuinely needed, it is a migration: create a new premium vault alongside, copy secrets, repoint consumers, then decommission. Azure cannot change a vault's SKU in place.
  4. Add lifecycle { prevent_destroy = true } so this plan fails at plan time in future rather than relying on someone reading carefully.

The general point: the destroy of azurerm_key_vault_secret.api is collateral. Replacements cascade to dependents, so a two-line diff can produce a plan that destroys a dozen things.

Level 2 · Implement Hand a resource to another team without deleting it

The shared VNet is in two state files — yours and the platform team's — and they revert each other nightly. You are giving it up. Write the change.

There is one flag here that, if omitted, destroys the platform team's network. Write the verification that catches that before it happens.

Show solution
handover.tf
# STEP 1: delete the resource block.
#
#   resource "azurerm_virtual_network" "shared" { ... }   <- removed
#
# Deleting it alone would make the next apply DESTROY the VNet. The removed
# block below is what turns "delete" into "forget".

removed {
  from = azurerm_virtual_network.shared

  lifecycle {
    # THE CRITICAL FLAG. Without it, this destroys the shared VNet and
    # everything attached to it.
    destroy = false
  }
}

# STEP 2: read it instead of owning it.
data "azurerm_virtual_network" "shared" {
  name                = "vnet-shared-prod-weu-01"
  resource_group_name = "rg-shared-prod-weu-01"
}

# STEP 3: repoint every reference.
#   azurerm_virtual_network.shared.id
#     ->  data.azurerm_virtual_network.shared.id
data "azurerm_subnet" "privatelink" {
  name                 = "snet-privatelink-prod-weu-01"
  virtual_network_name = data.azurerm_virtual_network.shared.name
  resource_group_name  = data.azurerm_virtual_network.shared.resource_group_name
}

terraform plan -out=tfplan

  | select(.change.actions | index("delete"))

Before removed blocks existed (Terraform 1.7) this required running terraform state rm and remembering to do it before merging the deletion — precisely the kind of ordering people get wrong under time pressure. The block makes the intent explicit, reviewable and visible in the plan.

The prevention is a rule rather than a tool: one resource, one owner. Where a boundary is genuinely shared, the non-owner uses a data source. A scheduled drift-detection job would have surfaced this on day one instead of week six.

Level 3 · Troubleshoot Two configurations, one resource

Symptoms:

  • The platform team's pipeline runs at 02:00. The analytics team's runs at 03:00.
  • Every morning, one of them shows a change to vnet-shared-prod-weu-01's DNS servers and applies it.
  • The next night the other reverts it.
  • Both pipelines are green. Nobody has changed any code in weeks.

Diagnose and fix.

Show answer

Diagnosis: the VNet is in both state files. Each configuration considers itself the owner, so each sees the other's value as drift and reverts it — a stable oscillation. Both pipelines are green because from each side's perspective it is doing exactly its job.

confirm
cd platform  && terraform state list | grep virtual_network
cd analytics && terraform state list | grep virtual_network
# both list azurerm_virtual_network.shared → confirmed

# and the activity log shows two different service principals alternating
az monitor activity-log list -g rg-shared-prod-weu-01 \
  --query "[?contains(resourceId,'vnet-shared-prod-weu-01')].{t:eventTimestamp,who:caller}" -o table

Fix — pick one owner. The platform team owns networking, so analytics should stop managing it.

analytics: stop managing, do NOT destroy
# Delete the resource "azurerm_virtual_network" "shared" block, then:
removed {
  from = azurerm_virtual_network.shared

  lifecycle {
    destroy = false     # critical — without this, the VNet is DELETED

The dangerous shortcut

Simply deleting the resource block and running apply would destroy the shared VNet and everything attached to it. The removed block with destroy = false is the entire point. Before it existed you had to run terraform state rm first and remember to do it before merging — which is precisely the kind of ordering people get wrong.

Prevention: one resource, one owner, always. Where a boundary is shared, the non-owner uses a data source. And a scheduled drift-detection job comparing consecutive plans would have caught this on day one instead of week six.

Interview questions

Explain the symbols in Terraform plan output.

+ create, ~ update in place, - destroy, -/+ destroy then create (replacement), and +/- create then destroy when create_before_destroy is set. The annotations matter as much as the symbols: (known after apply) marks values Terraform cannot compute until the API responds — which is also a visible dependency edge — and # forces replacement names the specific argument that made an in-place update impossible. That comment is the one I look for first, because on a stateful resource it means data loss.

How do you bring existing Azure infrastructure under Terraform management?

With import blocks. I find the resource ID, write an import block naming the target address, and run terraform plan -generate-config-out to produce a starting configuration. Then I iterate until the plan shows the import and zero other changes — that is the safety property, because any change at that point would modify a resource people are using. Only after applying the import do I improve the settings, in a separate commit. I prefer import blocks to the terraform import CLI because they are previewable in a plan, reviewable in a pull request, work in CI and support for_each.

What is the difference between terraform state rm and a removed block?

Both stop Terraform managing a resource without deleting it in Azure. state rm mutates state immediately, with no plan, no review and no record in version control. A removed block with lifecycle { destroy = false } declares the intent in code, shows up in the plan, and is reviewed like any other change. Critically, it also solves an ordering hazard: deleting a resource block and applying would destroy the resource, and before removed blocks existed you had to remember to run state rm first.

Two Terraform configurations manage the same resource. What happens and how do you fix it?

Each considers itself the owner, so each sees the other's changes as drift and reverts them — the resource oscillates on whatever cadence the two pipelines run, and both pipelines report success. I would confirm with terraform state list on both and the Azure activity log showing two principals alternating. The fix is to pick one owner: the other removes it from state with a removed block using destroy = false and replaces the references with a data source. The prevention is a clear ownership boundary per resource and scheduled drift detection, which would surface this immediately rather than after weeks.

A plan wants to destroy and recreate a production resource. Walk me through your response.

Do not apply, and stop any pipeline that might. Find the # forces replacement line — the plan names the argument responsible. Then determine the cause: git log -p on the file for a configuration change, terraform plan -refresh-only plus the Azure activity log for drift, and git diff on the lock file for a provider change. If it was unintended, revert. If the new value is genuinely required, a replacement is not the mechanism — for a stateful resource that is a data migration project. Finally, add prevent_destroy and a CI gate on delete actions so the next occurrence fails at plan time rather than depending on someone reading carefully.

What is drift and how do you decide what to do about it?

A difference between state and reality caused by something other than Terraform. I investigate with plan -refresh-only to see it without proposing a revert, then the Azure activity log to find who changed it and when — that step is what most people skip, and it usually turns a mystery into an obvious explanation. The response depends on the cause: an emergency fix that should persist gets adopted into configuration; an unauthorised change gets reverted after checking that reverting is not itself destructive; a system that legitimately owns the attribute, like Azure Policy or an autoscaler, gets ignore_changes; and two configurations fighting is a design bug to resolve, not to ignore.

Key takeaways

  • Read the summary line, then search for forces replacement, then read every destroy and its “because”.
  • Plan JSON turns careful reading into an automated gate. Fail CI on unexpected deletes.
  • Prefer moved, import and removed blocks over CLI state commands — they are reviewable.
  • Brownfield import succeeds when the plan is empty. Adopt first, improve second.
  • removed without destroy = false deletes the resource. That flag is the whole point.
  • Investigate drift with the activity log before deciding. Most drift has a person and a reason behind it.

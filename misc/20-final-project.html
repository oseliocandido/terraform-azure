The full production architecture is not free. The significant costs are private endpoints (billed per endpoint-hour, and there are five or six of them), the Premium function plan, the Databricks workspace's compute, and Log Analytics ingestion.

The brief

Requirements

Contoso Analytics needs a data platform on Azure. Source systems land files and CDC feeds; Databricks processes them through a medallion architecture; Power BI reads the gold layer.

  • Storage: ADLS Gen2 with raw, bronze, silver and gold, each with its own retention policy.
  • Ingestion: an Azure Function writing to raw, calling a third-party API that needs a static key.
  • Processing: a Databricks workspace with Unity Catalog access to the lake.
  • Security: no credentials anywhere. Managed identities and RBAC only. No shared storage keys in production.
  • Network: production has no public data-plane exposure. Dev may be public for cost reasons.
  • Governance: everything tagged, everything in code, everything reviewed before it reaches production.
  • Operations: remote state, environment isolation, drift detection.

Why this structure

Structure C from Lesson 17 — directory per environment with shared modules. It is the right size for this project: the backend is committed per environment so you cannot apply to the wrong state, environments can legitimately differ (prod has private endpoints, dev does not), and there is no layering machinery to maintain for a platform one person operates. If Contoso grew to eight product teams, you would split into layers.

Phase 0 — bootstrap

bootstrap/bootstrap.sh
#!/usr/bin/env bash
set -euo pipefail

LOCATION="westeurope"
ENV="${1:?usage: bootstrap.sh <dev|test|prod>}"
RG="rg-tfstate-${ENV}-weu-01"
SA="sttfstate${ENV}weu01"

az group create --name "$RG" --location "$LOCATION"

az storage account create \
  --name "$SA" --resource-group "$RG" --location "$LOCATION" \
  --sku Standard_GZRS --kind StorageV2 \
  --min-tls-version TLS1_2 --https-only true \
  --allow-blob-public-access false \
  --allow-shared-key-access false

az storage account blob-service-properties update \
  --account-name "$SA" --resource-group "$RG" \
  --enable-versioning true \
  --enable-delete-retention true --delete-retention-days 30

az storage container create --name tfstate --account-name "$SA" --auth-mode login

az lock create --name no-delete-tfstate --lock-type CanNotDelete --resource-group "$RG"

echo "Backend ready: $SA / tfstate"

Catches: an unversioned or key-accessible state backend, discovered only when Phase 7's apply already depends on it.
verify-bootstrap.sh
ENV=dev   # repeat for test, prod
RG="rg-tfstate-${ENV}-weu-01"
SA="sttfstate${ENV}weu01"

az storage account show --name "$SA" --resource-group "$RG" \
  --query "allowSharedKeyAccess" -o tsv
# expect: false

az storage account blob-service-properties show \
  --account-name "$SA" --resource-group "$RG" \
  --query "{versioning:isVersioningEnabled, retentionDays:deleteRetentionPolicy.days}" -o json
# expect: {"versioning": true, "retentionDays": 30}

az lock list --resource-group "$RG" --query "[].{name:name, level:level}" -o table
# expect: no-delete-tfstate   CanNotDelete

Pass: all four checks return the expected value, and init completes with no key-based fallback warning.

If allowSharedKeyAccess is true: the state backend has an access key floating around, and use_azuread_auth in the backend block is doing nothing to enforce RBAC-only access. Fix the bootstrap script, not the symptom.

Phase 1 — the naming module

modules/naming/main.tf
variable "workload"    { type = string }
variable "environment" { type = string }
variable "location"    { type = string }
variable "instance" {
  type    = number
  default = 1
}
variable "extra_tags" {
  type    = map(string)
  default = {}
}

locals {
  region_short = {
    westeurope  = "weu"
    northeurope = "neu"
    uksouth     = "uks"
  }

  suffix = join("-", [
    var.workload,
    var.environment,
    local.region_short[var.location],
    format("%02d", var.instance),
  ])

  # Globally unique names cannot contain hyphens and cap at 24 characters.
  compact = substr(replace(local.suffix, "-", ""), 0, 20)
}

output "suffix" { value = local.suffix }

output "names" {
  value = {
    resource_group_network   = "rg-network-${var.environment}-${local.region_short[var.location]}-01"
    resource_group_analytics = "rg-analytics-${var.environment}-${local.region_short[var.location]}-01"
    resource_group_workloads = "rg-workloads-${var.environment}-${local.region_short[var.location]}-01"
    virtual_network          = "vnet-${local.suffix}"
    key_vault                = substr("kv-${local.suffix}", 0, 24)
    storage_lake             = substr("st${local.compact}", 0, 24)
    storage_functions        = substr("stfn${local.compact}", 0, 24)
    databricks_workspace     = "dbw-${local.suffix}"
    databricks_connector     = "dbac-${local.suffix}"
    function_app             = substr("func-ingest-${var.environment}-${local.region_short[var.location]}-01", 0, 32)
    service_plan             = "asp-${local.suffix}"
    identity_ingest          = "id-ingest-${local.suffix}"
    log_analytics            = "log-${local.suffix}"
  }
}

output "tags" {
  value = merge({
    workload    = var.workload
    environment = var.environment
    managed_by  = "terraform"
    repository  = "contoso/analytics-platform"
  }, var.extra_tags)
}
Is a naming module a thin wrapper?

Lesson 14 warned against modules that only compute values. This one is borderline, and the justification is that it is used by three root modules and encodes rules that are genuinely easy to get wrong — the 24- and 32-character caps, the hyphen stripping, the region abbreviations. If it were used once, it would be a locals block. Be able to defend the choice either way; that is the actual skill.

CP2 Generated names respect Azure's limits
Catches: a workload or environment name combination that produces a storage account name over 24 characters, or a function app name over 32 — both fail only at apply, deep into the run.
modules/naming/tests/checkpoint.tftest.hcl
variables {
  workload    = "analyticsplatform"   # deliberately long, to stress the caps
  environment = "staging"
  location    = "westeurope"
}

run "names_respect_azure_limits" {
  command = plan

  assert {
    condition     = length(output.names.storage_lake) <= 24
    error_message = "Storage account names must not exceed 24 characters."
  }

  assert {
    condition     = length(output.names.function_app) <= 32
    error_message = "Function app names should stay at or under 32 characters."
  }

  assert {
    condition     = can(regex("^[a-z0-9]+$", output.names.storage_lake))
    error_message = "Storage account names must be lowercase alphanumeric only."
  }

  assert {
    condition     = can(regex("^[a-zA-Z][a-zA-Z0-9-]{1,22}[a-zA-Z0-9]$", output.names.key_vault))
    error_message = "Key Vault names must be 3-24 chars, alphanumerics and hyphens, starting with a letter."
  }
}

Phase 2 — networking

modules/networking/main.tf
variable "name"                { type = string }
variable "resource_group_name" { type = string }
variable "location"            { type = string }
variable "tags" {
  type    = map(string)
  default = {}
}

variable "address_space" {
  type = string

  validation {
    condition     = can(cidrnetmask(var.address_space))
    error_message = "address_space must be a valid CIDR block, e.g. 10.10.0.0/16."
  }
}

variable "subnets" {
  description = "Subnets carved from address_space with cidrsubnet(newbits, netnum)."

  type = map(object({
    newbits           = number
    netnum            = number
    delegation        = optional(string)
    service_endpoints = optional(list(string), [])
  }))
}

locals {
  prefixes = {
    for k, v in var.subnets : k => cidrsubnet(var.address_space, v.newbits, v.netnum)
  }
}

resource "azurerm_virtual_network" "this" {
  name                = var.name
  resource_group_name = var.resource_group_name
  location            = var.location
  address_space       = [var.address_space]
  tags                = var.tags
}

resource "azurerm_subnet" "this" {
  for_each = var.subnets

  name                 = "snet-${replace(each.key, "_", "-")}"
  resource_group_name  = var.resource_group_name
  virtual_network_name = azurerm_virtual_network.this.name
  address_prefixes     = [local.prefixes[each.key]]
  service_endpoints    = each.value.service_endpoints

  dynamic "delegation" {
    for_each = each.value.delegation == null ? [] : [each.value.delegation]

    content {
      name = "delegation"
      service_delegation {
        name = delegation.value
        actions = [
          "Microsoft.Network/virtualNetworks/subnets/join/action",
          "Microsoft.Network/virtualNetworks/subnets/action",
        ]
      }
    }
  }
}

# Databricks injects its own rules — keep this NSG bare and ignore them.
resource "azurerm_network_security_group" "databricks" {
  name                = "nsg-databricks-${var.name}"
  resource_group_name = var.resource_group_name
  location            = var.location
  tags                = var.tags

  lifecycle {
    ignore_changes = [security_rule]
  }
}

resource "azurerm_subnet_network_security_group_association" "databricks" {
  for_each = toset([
    for k, v in var.subnets : k
    if v.delegation == "Microsoft.Databricks/workspaces"
  ])

  subnet_id                 = azurerm_subnet.this[each.value].id
  network_security_group_id = azurerm_network_security_group.databricks.id
}

output "vnet_id"     { value = azurerm_virtual_network.this.id }
output "subnet_ids"  { value = { for k, s in azurerm_subnet.this : k => s.id } }
output "subnet_names" { value = { for k, s in azurerm_subnet.this : k => s.name } }

# The workspace needs the ASSOCIATION ids, not the subnet ids (Lesson 12).
output "databricks_nsg_association_ids" {
  value = { for k, a in azurerm_subnet_network_security_group_association.databricks : k => a.id }
}

Catches: CIDR arithmetic errors, Databricks subnets outside the /26-/24 range Azure requires, and address spaces that overlap between environments — all invisible until a peering or a workspace creation fails.

CP5 The lake resolves privately, from inside the network
Catches: the single most common private-endpoint failure: everything shows Approved in the portal, and clients still resolve the public IP because a DNS zone is missing, misnamed, or never linked.
verify-private-dns.sh
# From a VM or Cloud Shell attached to the platform VNet - NOT your laptop.

for svc in blob dfs; do
  echo "-- $svc --"
  nslookup "stanalyticsprodweu01.${svc}.core.windows.net"
done
# expect BOTH: a CNAME into privatelink.SVC.core.windows.net,
#              resolving to an address in 10.10.1.0/24.
# A public IP here (20.x, 40.x, ...) means the zone for that service is
# missing, misnamed, or not linked to this VNet.

# Confirm the A record actually exists in the dfs zone - this is what
# private_dns_zone_group writes, and it's the block people forget.
az network private-dns record-set a list \
  --zone-name privatelink.dfs.core.windows.net \
  --resource-group rg-network-prod-weu-01 -o table

az network private-dns record-set a list \
  --zone-name privatelink.blob.core.windows.net \
  --resource-group rg-network-prod-weu-01 -o table

Pass: both hostnames resolve to 10.10.1.x addresses, and both zones list an A record.

If dfs resolves publicly but blob resolves privately: only the blob endpoint was built. Databricks and Spark use abfss://, which goes through dfs — this exact asymmetry is the Lesson 11 scenario where the portal works and every Spark job fails.

Straightforward

Self-assessment

The course opened with a sentence and a promise that every part of it would become transparent. Read it again and check yourself — if any clause is still fuzzy, the lesson to revisit is named beside it.

“…creates an ADLS Gen2 storage account…”

A storage account with is_hns_enabled = true, which replaces the flat blob namespace with a real directory tree — giving atomic directory renames (what Spark's commit protocol depends on), POSIX-style ACLs, and cheap recursive deletes. It is ForceNew, so it must be right at creation. Lesson 06.

“…configures its networking…”

public_network_access_enabled = false, plus private endpoints for both blob and dfs, each with a private DNS zone of the exact documented name, linked to the VNet, and a private_dns_zone_group that registers the A record. Miss any one of those three and the endpoint exists but resolves publicly. Lesson 11.

“…creates the required containers…”

for_each over a map of medallion layers, so the state address is ["silver"] rather than [2] — meaning removing a layer destroys exactly that layer instead of cascading through every later index. The map's values also carry each layer's lifecycle policy. Lessons 06 and 15.

“…assigns a managed identity the appropriate RBAC roles…”

A user-assigned identity (or a Databricks access connector), granted a data-plane role such as Storage Blob Data Contributor — because control-plane roles like Contributor grant no data access — scoped to an individual container rather than the account. Azure manages the credential, so nothing exists to leak or rotate. Lesson 08.

“…stores configuration in Key Vault…”

Terraform creates the vault in RBAC mode with purge protection and grants the workload identity Key Vault Secrets User on a single secret. It does not write the secret's value — that would put it in state in plaintext, and so would reading it with a data source. The app setting holds a @Microsoft.KeyVault(...) reference the runtime resolves with its own identity. Lesson 09.

“…exposes outputs consumed by the Databricks module.”

The storage module outputs id, name, dfs_endpoint and container_scopes — never an access key. Those outputs are a public API: renaming one breaks every caller. The root module wires them into role assignments and into the Databricks configuration. Lesson 14.

“…Terraform tracks those resources in remote state…”

An Azure Storage backend with use_azuread_auth = true, so access is Entra ID RBAC rather than a shared account key, with blob versioning for recovery and a blob lease for locking. State maps each configuration address to a real resource ID and caches every attribute — in plaintext — which is why read access to state is equivalent to read access to every secret. Lesson 10.

“…the CI/CD pipeline generates a plan before applying changes.”

A pull-request pipeline authenticating via OIDC federated credentials — no stored secret — that runs fmt, validate, lint, scan and plan, checks the plan JSON against policy, and posts the plan as a comment so a human reviews consequences rather than only the diff. Merging triggers an apply to dev, then to production behind an approval gate bound to a protected environment, with a separate higher-privileged identity. Lesson 18.

Defend your design

The checkpoints prove the platform works. These five are the questions an interviewer asks after you have already described it — each one has a real trade-off behind it, not a single correct answer, and you should be able to argue your own choice even where it differs from what is built here.

Lesson 13Why is the Function App's runtime storage a separate account from the data lake?

Because the Functions host writes its own trigger receipts, timer leases and, on Premium, a mounted file share into whatever account it is given — and it needs broad roles there (Storage Blob Data Owner, Storage Queue Data Contributor, Storage Account Contributor) to do it. Pointing that at the lake would mean granting the ingest identity far more than it needs on the data itself, and locking the lake down behind private endpoints would simultaneously risk breaking the runtime in ways that have nothing to do with data access.

The honest counter-argument: it is one more resource to manage and one more thing to name. For a single-function proof of concept, sharing an account is a defensible simplification — the separation earns its cost once the lake's security posture and the runtime's operational needs start pulling in different directions, which in this platform happens by Phase 4.

Lesson 12Why does Unity Catalog configuration live in a second root module instead of the main one?

Because the databricks provider must be configured from the workspace's URL, which does not exist until the workspace is created. Put both in one configuration and destroy can leave the provider unable to configure itself — the workspace gets deleted before the objects inside it, and Terraform has no way left to reach the API that would delete them, leaving orphaned state entries only terraform state rm can clear.

This is not really a Databricks rule; it is a rule about any provider configured from a resource you also create in the same apply — the same shape shows up with Kubernetes, PostgreSQL and Vault. The cost is two applies and two pipelines instead of one, which is worth naming explicitly if an interviewer asks why the repository has a dev-databricks directory that looks, at a glance, like duplication.

Lesson 11Why does dev use service endpoints and public access instead of private endpoints?

Cost, stated plainly. Private endpoints bill per endpoint-hour, and this platform alone needs five or six of them; multiplied across every developer's disposable environment, that adds up fast for a control that dev does not strictly need. Service endpoints plus a firewall allow-list exercise almost the same code path — the storage account still has network_rules, the container creation still depends on the deployer being let through it — without the recurring charge.

The risk this accepts: dev's network posture is not what will actually run in production, so a networking bug that only manifests behind a private endpoint (a missing DNS zone, say) will not be caught until the first prod deploy. That is a real gap, not a free lunch, and it is why Lesson 17's structure keeps the difference to a small, visible set of tfvars rather than letting environments diverge silently.

Lesson 08Why is RBAC assigned per container instead of per storage account?

Because the alternative — one role assignment covering the whole account — gives Databricks write access to raw as a side effect of needing write access to silver. Scoping to .../blobServices/default/containers/<layer> costs exactly as many lines of Terraform, since it is generated from the same for_each cross product, and it is what lets the platform actually enforce “raw is immutable” rather than merely document it.

The trade-off is legibility at scale: with a dozen containers and a dozen identities, the access matrix local becomes the single place a reviewer must read to understand the entire security posture — which is a feature until that table itself gets long enough to need its own review discipline.

Lesson 14Is the naming module in Phase 1 justified, or is it the thin wrapper Lesson 14 warns against?

Genuinely borderline, and worth arguing both ways rather than reciting one answer. In favour: three root modules consume it, and it encodes rules that are easy to get subtly wrong — the 24- and 32-character caps, the hyphen-stripping for globally-unique names, the region abbreviation table — so centralising them means a naming-scheme change happens in one place instead of three.

Against: its inputs map almost one-to-one onto a handful of string operations, it creates no Azure resources, and a caller could inline the same locals block with about the same line count. A module that only computes values is close to the thin-wrapper anti-pattern by definition.

The tie-breaker used here is reuse count plus error surface: at three call sites and with real character-limit bugs to avoid, it earns its place. At one call site, it would not, and the right answer would be a plain locals block in the root module. Being able to make that argument — rather than a blanket “modules are good practice” — is the actual skill Lesson 14 is testing for.

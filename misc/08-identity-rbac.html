Identity, Entra ID & Azure RBAC

The goal of this lesson is a data platform with no credentials anywhere — no account keys, no connection strings, no passwords in app settings. That is entirely achievable with managed identities and role assignments, and it is the single biggest security improvement available to you.

By the end of this lesson you can

  • Distinguish authentication from authorization, and app registration from service principal
  • Choose between a user, a service principal, and a system- or user-assigned managed identity
  • Explain why Contributor does not let you read a blob
  • Write role assignments at the right scope, using the right ID
  • Give Databricks and Functions access to ADLS with no secrets at all
  • Handle RBAC propagation delay and the errors it causes

Authentication vs authorization

Authentication — who are you?

Handled by Microsoft Entra ID (formerly Azure AD). Produces a signed JWT access token containing the principal's object ID, tenant, and what it is allowed to request tokens for.

Failure looks like: 401 Unauthorized, AADSTS700016, invalid_client.

Authorization — what may you do?

Handled by Azure RBAC, evaluated by Azure Resource Manager (or by the data-plane service) on every request. Looks up role assignments matching the token's principal and the target's scope.

Failure looks like: 403 Forbidden, AuthorizationFailed, AuthorizationPermissionMismatch.

Reading the error tells you which system rejected you

A 401 means Entra ID would not issue or accept a token — check credentials, tenant, expiry. A 403 means the token was fine but the principal lacks a role at that scope — check role assignments. Confusing the two sends people rotating credentials when they needed a role assignment, and vice versa.

App registration vs service principal

A distinction that confuses almost everyone, and it appears in Terraform as two separate resources.

  • The application object (app registration) is the global definition: name, redirect URIs, API permissions, federated credentials. It lives in the tenant where it was registered.
  • The service principal is the local instance of that application in a tenant — the thing that actually holds role assignments and can sign in.

For a single-tenant app they are one-to-one, so people use the terms interchangeably. The reason it matters in Terraform: azurerm_role_assignment.principal_id needs the service principal's object ID, not the application's object ID and not the client ID.

the three IDs, and which one you need
resource "azuread_application" "ci" {
  display_name = "sp-terraform-ci-analytics"
}

resource "azuread_service_principal" "ci" {
  client_id = azuread_application.ci.client_id
}

# ✗ WRONG — this is the application object's ID
# principal_id = azuread_application.ci.object_id

# ✗ WRONG — this is the client ID, used for authentication, not authorization
# principal_id = azuread_application.ci.client_id

# ✓ RIGHT — the service principal's object ID
resource "azurerm_role_assignment" "ci_contributor" {
  scope                = azurerm_resource_group.analytics.id
  role_definition_name = "Contributor"
  principal_id         = azuread_service_principal.ci.object_id
  principal_type       = "ServicePrincipal"
}

The Azure RBAC model

Three inputs produce one role assignment. All Azure authorization is this one sentence:

Scope, and why it is your main lever

scopes, widest to narrowest
locals {
  # Management group — affects every subscription beneath it
  scope_mg = "/providers/Microsoft.Management/managementGroups/mg-analytics"

  # Subscription
  scope_sub = "/subscriptions/${var.subscription_id}"

  # Resource group — the most common scope
  scope_rg = azurerm_resource_group.analytics.id

  # Single resource
  scope_sa = azurerm_storage_account.lake.id

  # Sub-resource: ONE container. This is the scope you want for data access.
  scope_container = "${azurerm_storage_account.lake.id}/blobServices/default/containers/silver"
}
Container-level scoping is the least-privilege win most teams miss

Granting Storage Blob Data Contributor on the storage account gives read/write to every layer including raw. Scoping the same role to .../containers/silver gives access to exactly that layer. It is the same amount of Terraform and dramatically less blast radius. Do this by default.

Control-plane roles vs data-plane roles

This is the single most important RBAC concept for a data engineer, and Lesson 06 already showed the error it produces. Here is why it exists.

Why Owner can still read your data — and why that is not a defence

An Owner or Contributor cannot read blobs directly, but they can read the storage account keys (listKeys is a control-plane action) and use those to access everything. That is the loophole. Setting shared_access_key_enabled = false closes it: with no keys, control-plane roles genuinely cannot reach the data, and access becomes governed purely by data roles. This is the real argument for disabling shared keys.

Common mistake · Owner for the deployment principal

Terraform needs Contributor to create resources, and it needs Microsoft.Authorization/roleAssignments/write to create role assignments — which Contributor deliberately excludes. The lazy fix is granting Owner, which also lets the pipeline grant anything to anyone, including privilege escalation to itself. The correct fix is Contributor plus User Access Administrator (or better, Role Based Access Control Administrator, which is narrower), both scoped to the specific resource groups, and ideally with an ABAC condition limiting which roles it may assign.

Managed identities in Terraform

System-assigned

system-assigned identity
resource "azurerm_linux_function_app" "ingest" {
  name                = "func-ingest-dev-weu-01"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location
  service_plan_id     = azurerm_service_plan.functions.id

  # Azure creates a service principal bound to this function app.
  identity {
    type = "SystemAssigned"
  }

  site_config {}
}

# The principal ID is only known AFTER the app is created.
resource "azurerm_role_assignment" "ingest_to_lake" {
  scope                = "${azurerm_storage_account.lake.id}/blobServices/default/containers/raw"
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = azurerm_linux_function_app.ingest.identity[0].principal_id
  principal_type       = "ServicePrincipal"
}
Why identity[0]

identity is a repeatable block in the schema, so Terraform exposes it as a list even when at most one is allowed. identity[0].principal_id errors if no identity block is configured; use one(azurerm_linux_function_app.ingest.identity) or a splat if it might be absent.

User-assigned — usually the better choice

Recommendation

Use user-assigned for anything in a data platform. The decisive reasons are that role assignments survive replacing the compute — a Function App replacement does not silently drop all its permissions — and that you can create identities and grant roles in a separate, earlier apply, which sidesteps propagation-delay failures. Use system-assigned only for single-purpose resources where the identity genuinely has no meaning outside that resource, such as a storage account reaching its own customer-managed key.

RBAC propagation delay

the intermittent failure
azurerm_role_assignment.ingest_to_raw: Creation complete after 8s
azurerm_storage_data_lake_gen2_filesystem.raw: Creating...

Error: creating File System "raw": unexpected status 403 with
AuthorizationPermissionMismatch: This request is not authorized to perform
this operation using this permission.

The role assignment exists. Azure has simply not finished replicating it to the endpoint enforcing it. This is normal and documented — assignments generally take effect within a couple of minutes but can take longer. Options, best first:

  1. Grant the deployment identity its data roles out of band, once, before the pipeline ever runs. The pipeline then never creates a role it immediately depends on.
  2. Split the apply: one configuration creates identities and role assignments; a later one creates the resources that use them. Natural when environments are split into layers (Lesson 17).
  3. Use user-assigned identities, so the assignment usually pre-dates the compute by a long way.
  4. Insert a wait — pragmatic, ugly, and sometimes the right answer:
the pragmatic wait
resource "time_sleep" "wait_for_rbac" {
  depends_on      = [azurerm_role_assignment.deployer_data]
  create_duration = "60s"
}

resource "azurerm_storage_data_lake_gen2_filesystem" "raw" {
  name               = "raw"
  storage_account_id = azurerm_storage_account.lake.id
  depends_on         = [time_sleep.wait_for_rbac]
}
Why time_sleep is a smell, not a solution

It adds a fixed minute to every apply forever, and 60 seconds is a guess that will occasionally be wrong. It is acceptable as a stopgap in a dev environment. If it is in your production pipeline, the underlying problem — the deployment identity bootstrapping its own permissions — should be fixed instead.

Custom roles

When no built-in role fits, define one. Keep them rare: built-in roles are maintained by Microsoft as APIs evolve, custom ones are maintained by you.

custom-role.tf
resource "azurerm_role_definition" "lake_layer_reader" {
  name        = "Data Lake Layer Reader"
  scope       = azurerm_resource_group.analytics.id
  description = "Read blobs in the lake and read the account's configuration, but never list keys."

  permissions {
    actions = [
      "Microsoft.Storage/storageAccounts/read",
      "Microsoft.Storage/storageAccounts/blobServices/containers/read",
    ]

    data_actions = [
      "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read",
    ]

    # Explicitly deny key access even if a wildcard action were added later.
    not_actions = [
      "Microsoft.Storage/storageAccounts/listkeys/action",
    ]

    not_data_actions = []
  }

  assignable_scopes = [azurerm_resource_group.analytics.id]
}

resource "azurerm_role_assignment" "analyst_gold" {
  scope              = "${azurerm_storage_account.lake.id}/blobServices/default/containers/gold"
  role_definition_id = azurerm_role_definition.lake_layer_reader.role_definition_resource_id
  principal_id       = data.azuread_group.analysts.object_id
  principal_type     = "Group"
}

Assign roles to groups, not to people

groups.tf
data "azuread_group" "data_engineers" {
  display_name     = "sg-data-engineers"
  security_enabled = true
}

resource "azurerm_role_assignment" "engineers_silver_write" {
  scope                = "${azurerm_storage_account.lake.id}/blobServices/default/containers/silver"
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = data.azuread_group.data_engineers.object_id
  principal_type       = "Group"
}

Membership changes then happen in Entra ID — through joiner/mover/leaver processes and access reviews — without a Terraform apply. Assigning roles directly to individual users means every hire and departure is an infrastructure pull request, which is both slow and a guarantee that leavers keep access.

Scenario: Databricks reads and writes ADLS with no credentials

Scenario 2 from the brief

“Databricks needs read/write access to a storage account without storing credentials.”

The modern answer is a Databricks Access Connector — an Azure resource that carries a managed identity, which Unity Catalog uses to reach storage. No keys, no service principal secrets, no mount points with embedded credentials.

databricks-access.tf
resource "azurerm_databricks_access_connector" "unity" {
  name                = "dbac-analytics-dev-weu-01"
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location

  identity {
    type = "SystemAssigned"
  }

  tags = local.common_tags
}

# One assignment per layer, scoped to that container only.
locals {
  databricks_access = {
    raw    = "Storage Blob Data Reader"
    bronze = "Storage Blob Data Contributor"
    silver = "Storage Blob Data Contributor"
    gold   = "Storage Blob Data Contributor"
  }
}

resource "azurerm_role_assignment" "databricks_layers" {
  for_each = local.databricks_access

  scope                = "${azurerm_storage_account.lake.id}/blobServices/default/containers/${each.key}"
  role_definition_name = each.value
  principal_id         = azurerm_databricks_access_connector.unity.identity[0].principal_id
  principal_type       = "ServicePrincipal"
}

Note what this expresses: Databricks may read the raw landing zone but not modify it — raw is immutable by design — while it has full read/write on the curated layers. That policy is now infrastructure, reviewable in a pull request, rather than a convention people remember. Lesson 12 connects this to Unity Catalog external locations.

Common mistakes

Using Contributor and expecting data access

Covered above, but it is worth repeating because it accounts for a large share of Azure Terraform support questions. Management roles and data roles are disjoint.

Forgetting principal_type for freshly created principals

When you create a service principal and assign it a role in the same apply, Entra ID replication can lag and Azure rejects the assignment with PrincipalNotFound. Set principal_type = "ServicePrincipal" and, if needed, skip_service_principal_aad_check = true — that argument exists specifically for this race.

Non-deterministic role assignment names

Role assignments have a GUID name that Terraform generates if you do not supply one. Combined with for_each over an unstable key, this produces churn — assignments destroyed and recreated on every apply, each time causing a brief window with no access. Keep for_each keys stable and derived from static input.

Exercises

Level 1 · Understand Which role, which scope?

Choose the narrowest role and scope for each:

  1. A Power BI service principal reading curated tables from the gold container.
  2. An ingestion Function App writing to raw and reading one Key Vault secret.
  3. The Terraform CI principal deploying the whole platform, including role assignments.
  4. A data science team needing to read silver and read/write gold.
Show answer
  1. Storage Blob Data Reader scoped to .../containers/gold. Not the storage account — there is no reason for BI to see raw.
  2. Storage Blob Data Contributor on .../containers/raw, plus Key Vault Secrets User. Scope the vault role to the individual secret if the vault holds secrets for several applications; otherwise the vault is acceptable.
  3. Contributor on each target resource group, plus Role Based Access Control Administrator (narrower than User Access Administrator) for the role assignments. Never Owner, and never at subscription scope if resource-group scope will do.
  4. Assign to an Entra ID group, not to individuals: Storage Blob Data Reader on silver and Storage Blob Data Contributor on gold.

The pattern in all four: pick the narrowest scope that works, prefer data roles over control roles for data access, and assign to groups wherever humans are involved.

    databricks = azurerm_databricks_access_connector.unity.identity[0].principal_id

Level 2 · Implement Write a least-privilege custom role

The BI team needs to read blobs in gold and see the storage account's configuration — but must never be able to read the account keys, which would bypass every data-plane control you have.

No built-in role fits: Reader grants no data access, and Storage Blob Data Reader grants no configuration visibility. Write the custom role and assign it to a group.

Show solution
custom-role.tf
resource "azurerm_role_definition" "lake_layer_reader" {
  name        = "Data Lake Layer Reader"
  scope       = azurerm_resource_group.analytics.id
  description = "Read blobs and account configuration. Cannot list account keys."

  permissions {
    # Control plane: see the account, not its secrets.
    actions = [
      "Microsoft.Storage/storageAccounts/read",
      "Microsoft.Storage/storageAccounts/blobServices/read",
      "Microsoft.Storage/storageAccounts/blobServices/containers/read",
    ]

    # Data plane: read blob content.
    data_actions = [
      "Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read",
    ]

    # Belt and braces: even if a wildcard action is added above later,
    # key access stays denied. not_actions always wins.
    not_actions = [
      "Microsoft.Storage/storageAccounts/listkeys/action",
      "Microsoft.Storage/storageAccounts/listAccountSas/action",
      "Microsoft.Storage/storageAccounts/listServiceSas/action",
    ]

    not_data_actions = []
  }

  assignable_scopes = [azurerm_resource_group.analytics.id]
}

data "azuread_group" "bi" {
  display_name     = "sg-bi-analysts"
  security_enabled = true
}

resource "azurerm_role_assignment" "bi_gold" {
  # Scoped to ONE container, not the account.
  scope = "${azurerm_storage_account.lake.id}/blobServices/default/containers/gold"

  # Custom roles are referenced by role_definition_id, not by name.
  role_definition_id = azurerm_role_definition.lake_layer_reader.role_definition_resource_id

  principal_id   = data.azuread_group.bi.object_id
  principal_type = "Group"
}

Three specifics. Custom roles use role_definition_id with the resource's role_definition_resource_id attribute, not role_definition_name. not_actions is a subtraction that always wins over actions, so the key-listing denial survives future edits. And the assignment targets a group, so joiners and leavers are handled in Entra ID rather than by a Terraform apply.

Keep custom roles rare, though. Built-in roles are maintained by Microsoft as APIs evolve; a custom one is yours to update when Azure adds a new data action you should have included.

Level 3 · Troubleshoot Three RBAC bugs
broken.tf
resource "azuread_application" "etl" {
  display_name = "sp-etl-pipeline"
}

resource "azuread_service_principal" "etl" {
  client_id = azuread_application.etl.client_id
}

resource "azurerm_role_assignment" "etl_lake" {
  scope                = azurerm_storage_account.lake.id
  role_definition_name = "Contributor"
  principal_id         = azuread_application.etl.object_id
}

resource "azurerm_storage_data_lake_gen2_filesystem" "bronze" {
  name               = "bronze"
  storage_account_id = azurerm_storage_account.lake.id
}

The pipeline reports 403 AuthorizationPermissionMismatch when it tries to write data. Find three problems.

Show answer

1 · Wrong principal ID.

azuread_application.etl.object_id is the application object's ID. Role assignments need the service principal's object ID: principal_id = azuread_service_principal.etl.object_id. Depending on timing this either fails with PrincipalNotFound or silently creates an assignment against an object that never authenticates — which is worse, because it looks correct in the portal.

2 · Wrong role for the job.

Contributor is a control-plane role. It lets the principal manage the storage account but grants no dataActions, so writing blobs is denied — exactly the reported error. It needs Storage Blob Data Contributor. And it should be scoped to the specific container rather than the whole account.

3 · Missing ordering, and a missing principal_type.

The filesystem is a data-plane object, so it requires the role assignment to be effective first — but nothing connects the two resources, so Terraform may create them in parallel. Add depends_on. Separately, because the service principal is created in the same apply, add principal_type = "ServicePrincipal" and consider skip_service_principal_aad_check = true to survive Entra ID replication lag.

fixed.tf
resource "azurerm_role_assignment" "etl_lake" {
  scope                            = "${azurerm_storage_account.lake.id}/blobServices/default/containers/bronze"
  role_definition_name             = "Storage Blob Data Contributor"
  principal_id                     = azuread_service_principal.etl.object_id
  principal_type                   = "ServicePrincipal"
  skip_service_principal_aad_check = true
}

resource "azurerm_storage_data_lake_gen2_filesystem" "bronze" {
  name               = "bronze"
  storage_account_id = azurerm_storage_account.lake.id
  depends_on         = [azurerm_role_assignment.etl_lake]
}

There is a chicken-and-egg wrinkle worth noticing: the role is scoped to a container that this apply is about to create. In practice you would scope the deployer's role to the storage account, and scope the workload identities to individual containers.

Interview questions

What is the difference between authentication and authorization in Azure?

Authentication is Entra ID establishing who a principal is and issuing a token. Authorization is Azure RBAC deciding whether that principal may perform a given action on a given resource, evaluated per request. Practically, a 401 means the token was rejected — a credential or tenant problem. A 403 means the token was fine but no role assignment grants that action at that scope.

What is a managed identity, and when would you use user-assigned over system-assigned?

A managed identity is a service principal whose credentials Azure creates, stores and rotates — the resource fetches tokens from the instance metadata endpoint, so no secret exists for anyone to leak. System-assigned is bound 1:1 to a resource and deleted with it. User-assigned is a standalone Azure resource. I default to user-assigned in a data platform for two reasons: role assignments survive replacing the compute, so a Function App recreation does not silently drop every permission; and roles can be granted before the compute exists, which avoids the RBAC propagation race you otherwise hit when creating a resource and immediately using its identity.

Why does a Contributor get 403 when reading a blob?

Because Azure separates control-plane and data-plane permissions. Contributor grants actions — managing the storage account — but no dataActions, so blob reads are denied. Reading blobs needs a data role such as Storage Blob Data Reader. The subtlety is that Contributor can call listKeys and use an account key to reach the data anyway, which is why disabling shared access keys is what actually makes the separation meaningful.

How would you give Databricks access to ADLS Gen2?

With a Databricks Access Connector carrying a managed identity, granted Storage Blob Data Contributor on the relevant containers, and referenced from a Unity Catalog storage credential and external location. No secrets exist anywhere. I would scope per container rather than per account, so for example Databricks reads the raw landing zone but cannot modify it, while having read/write on bronze, silver and gold. The legacy alternatives — account keys in a secret scope, or a service principal with a client secret and DBFS mounts — both put a durable credential somewhere and should be avoided in new work.

What permissions does a Terraform deployment principal need?

Contributor scoped to the resource groups it manages, which covers creating and configuring resources. If it must also manage role assignments it needs Microsoft.Authorization/roleAssignments/write, which Contributor deliberately excludes — so add Role Based Access Control Administrator rather than granting Owner, since Owner also allows the pipeline to escalate its own privileges. If it creates data-plane objects such as containers, it also needs the corresponding data role — and I would grant that once, out of band, rather than having the pipeline bootstrap its own permissions and hit propagation delays.

Should role assignments go to users or groups?

Groups, essentially always, for anything involving humans. Membership then changes through the identity lifecycle — joiner/mover/leaver, access reviews — without a Terraform apply. Assigning to individuals means every hire and departure becomes an infrastructure pull request, which is slow and, more importantly, reliably forgotten when people leave. Service principals and managed identities are assigned directly, since they represent one workload each.

Your apply fails with 403 immediately after creating a role assignment. What is happening?

Azure RBAC propagation delay — the assignment exists but has not replicated to the endpoint enforcing it, which normally takes up to a couple of minutes. Re-running usually succeeds with no code change. The durable fixes are to grant the deployment identity its data roles out of band before the pipeline runs, to split identity and role creation into an earlier apply, or to use user-assigned identities so assignments long pre-date the compute. A time_sleep resource works but adds fixed latency to every run and is a guess about the delay, so I treat it as a stopgap.

Key takeaways

  • Role assignment = principal + role definition + scope. Assignments are additive and inherit downward.
  • Control-plane roles and data-plane roles are disjoint. Contributor does not read blobs.
  • Setting shared_access_key_enabled = false is what makes that separation real, by closing the listKeys loophole.
  • Scope data roles to containers, not accounts. Same effort, far less blast radius.
  • Prefer user-assigned managed identities: roles survive resource replacement and can be granted in advance.
  • Use the service principal's object ID — not the application object ID, not the client ID.
  • Assign roles to groups for humans; directly for workload identities.

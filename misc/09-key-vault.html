Key Vault & the secrets-in-state problem

Key Vault is easy. The hard part is the uncomfortable fact underneath it: any secret that flows through Terraform is written to state in plaintext — including secrets you merely read with a data source. This lesson is mostly about designing so that does not happen.

By the end of this lesson you can

  • Provision a Key Vault with RBAC authorization, soft delete and purge protection
  • Explain exactly why sensitive = true does not solve the state problem
  • Rank the five patterns for handling secrets, and pick the right one
  • Use ephemeral resources and write-only arguments to keep values out of state entirely
  • Explain why destroying and recreating a Key Vault often fails

The problem, stated plainly

this looks responsible and is not
variable "api_key" {
  type      = string
  sensitive = true          # redacted from output…
}

resource "azurerm_key_vault_secret" "api" {
  name         = "third-party-api-key"
  value        = var.api_key   # …and now written to state in plaintext
  key_vault_id = azurerm_key_vault.main.id
}
what is actually in the state file
{
  "type": "azurerm_key_vault_secret",
  "name": "api",
  "instances": [{
    "attributes": {
      "id": "https://kv-analytics-prod-weu-01.vault.azure.net/secrets/third-party-api-key/a1b2c3",
      "name": "third-party-api-key",
      "value": "",
      "content_type": "",
      "...": "..."
    }
  }]
}
The consequence, spelled out

You have carefully placed a secret in Key Vault, protected by RBAC, audit logging, soft delete and network restrictions. And you have simultaneously placed a plaintext copy in a storage blob whose access controls are almost certainly broader than the vault's — everyone who can run terraform plan can read it.

Worse: reading is just as bad as writing. A data "azurerm_key_vault_secret" block caches the retrieved value in state too. There is no way for a secret to pass through Terraform without being persisted, unless you use ephemeral values.

Provisioning a Key Vault

keyvault.tf
data "azurerm_client_config" "current" {}

resource "azurerm_key_vault" "main" {
  name                = "kv-${local.suffix}"   # globally unique, 3-24 chars
  resource_group_name = azurerm_resource_group.analytics.name
  location            = azurerm_resource_group.analytics.location
  tenant_id           = data.azurerm_client_config.current.tenant_id

  sku_name = "standard"   # "premium" adds HSM-backed keys

  # --- authorization model: RBAC, not access policies ---
  rbac_authorization_enabled = true

  # --- deletion protection ---
  soft_delete_retention_days = 90     # 7-90; deleted vaults are recoverable this long
  purge_protection_enabled   = true   # cannot be disabled once enabled

  # --- network ---
  public_network_access_enabled = false

  network_acls {
    default_action = "Deny"
    bypass         = "AzureServices"
    ip_rules       = var.deployment_agent_ip_ranges
  }

  tags = local.common_tags
}
⚠ v4 → v5: rbac_authorization_enabled

In v3 and v4 this argument was enable_rbac_authorization. Every older tutorial uses the old name and fails on v5 with An argument named "enable_rbac_authorization" is not expected here. The behaviour is identical; only the name changed.

Use RBAC for new vaults

Microsoft's own guidance recommends the RBAC model. The one thing to know about migration: switching an existing vault from access policies to RBAC means every consumer must have an equivalent role assignment before you flip the flag, or they break instantly. Flipping it is a one-line change with an outage-shaped blast radius.

key-vault-rbac.tf
# Platform team manages secrets
resource "azurerm_role_assignment" "kv_officer" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Secrets Officer"
  principal_id         = data.azuread_group.platform_team.object_id
  principal_type       = "Group"
}

# The ingest function reads ONE secret, not the whole vault
resource "azurerm_role_assignment" "ingest_reads_one_secret" {
  scope                = "${azurerm_key_vault.main.id}/secrets/source-api-key"
  role_definition_name = "Key Vault Secrets User"
  principal_id         = azurerm_user_assigned_identity.ingest.principal_id
  principal_type       = "ServicePrincipal"
}

# The storage account's identity, for customer-managed key encryption
resource "azurerm_role_assignment" "lake_cmk" {
  scope                = azurerm_key_vault.main.id
  role_definition_name = "Key Vault Crypto Service Encryption User"
  principal_id         = azurerm_storage_account.lake.identity[0].principal_id
  principal_type       = "ServicePrincipal"
}

Soft delete and purge protection

the error
Error: creating Key Vault "kv-analytics-dev-weu-01": ConflictError:
Exist soft deleted vault with the same name. You must recover or purge the
vault before reusing the name.
provider features that control this
provider "azurerm" {
  features {
    key_vault {
      # Recover an existing soft-deleted vault instead of failing.
      recover_soft_deleted_key_vaults = true

      # Permanently purge on destroy. Convenient in throwaway dev,
      # DANGEROUS anywhere else — it bypasses Azure's safety net entirely.
      purge_soft_delete_on_destroy = var.environment == "dev"

      purge_soft_deleted_secrets_on_destroy = var.environment == "dev"
    }
  }
}
purge_protection_enabled cannot be turned off

Once enabled on a vault, it is permanent — Azure will not let you disable it, and neither will Terraform. That means a vault with purge protection cannot be fully removed until its soft-delete retention expires, up to 90 days. Enable it in production, where that is exactly what you want. Think carefully before enabling it in an ephemeral dev environment that is destroyed and rebuilt daily under the same name.

Five patterns for secrets, best to worst

1 · Have no secret at all — managed identity

the best pattern is the absent one
# ✗ The old way: a connection string in app settings
# app_settings = {
#   "LakeConnection" = azurerm_storage_account.lake.primary_connection_string
# }

# ✓ The good way: no credential exists to protect
resource "azurerm_role_assignment" "func_to_lake" {
  scope                = "${azurerm_storage_account.lake.id}/blobServices/default/containers/raw"
  role_definition_name = "Storage Blob Data Contributor"
  principal_id         = azurerm_user_assigned_identity.ingest.principal_id
  principal_type       = "ServicePrincipal"
}

resource "azurerm_linux_function_app" "ingest" {
  # ...
  identity {
    type         = "UserAssigned"
    identity_ids = [azurerm_user_assigned_identity.ingest.id]
  }

  app_settings = {
    # The app uses DefaultAzureCredential with just an account name.
    "LAKE_ACCOUNT_NAME"    = azurerm_storage_account.lake.name
    "AZURE_CLIENT_ID"      = azurerm_user_assigned_identity.ingest.client_id
  }
}

Nothing sensitive is in the configuration, in state, or in app settings. For everything inside Azure — storage, SQL, Service Bus, Event Hubs, Cosmos DB — this is achievable, and it should be your default. The only remaining secrets are third-party credentials that genuinely have no Entra ID equivalent.

2 · Key Vault references — the value never touches Terraform

key vault reference in app settings
# Terraform creates the vault and the RBAC, but never sees the secret value.
# A human or a rotation job populates it out of band.

data "azurerm_key_vault_secret" "third_party" {
  # NOTE: this data source WOULD read the value into state.
  # Shown here only to contrast with the approach below.
  name         = "third-party-api-key"
  key_vault_id = azurerm_key_vault.main.id
}

resource "azurerm_linux_function_app" "ingest" {
  # ...
  app_settings = {
    # A Key Vault reference. The App Service runtime resolves this at
    # startup using the app's managed identity. Terraform stores only
    # this URI string — never the secret.
    "THIRD_PARTY_API_KEY" = "@Microsoft.KeyVault(VaultName=${azurerm_key_vault.main.name};SecretName=third-party-api-key)"
  }
}
Why this is strong

The app setting's value is a pointer, not a secret. Terraform state contains the string @Microsoft.KeyVault(...). Rotating the secret in Key Vault takes effect without a Terraform apply, and every resolution is logged against the app's identity in the vault's audit log. Build the reference string yourself rather than using the data source — the moment you use data.azurerm_key_vault_secret, the value is in state.

3 · Ephemeral resources and write-only arguments

When Terraform genuinely must handle a value, Terraform 1.10 introduced ephemeral values and 1.11 added write-only arguments. The azurerm provider supports both for Key Vault secrets.

ephemeral.tf — nothing reaches state
terraform {
  required_version = ">= 1.11.0"
}

# 1 · An ephemeral resource READS a secret without persisting it.
#     Its value can only be used in other ephemeral contexts or
#     write-only arguments.
ephemeral "azurerm_key_vault_secret" "source_api_key" {
  name         = "source-api-key"
  key_vault_id = azurerm_key_vault.main.id
}

# 2 · A write-only argument WRITES a value without persisting it.
#     value_wo is never stored in state or in the plan file.
#     value_wo_version is the trigger: bump it to push a new value.
resource "azurerm_key_vault_secret" "replica" {
  name             = "source-api-key-replica"
  key_vault_id     = azurerm_key_vault.replica.id
  value_wo         = ephemeral.azurerm_key_vault_secret.source_api_key.value
  value_wo_version = 1
}
valuevalue_wo
Stored in stateYes, plaintextNo
Stored in the plan fileYesNo
Drift detection on the valueYes — Terraform notices if it changed in AzureNo — Terraform cannot compare what it does not store
How you push a new valueChange valueChange the value and increment value_wo_version
The trade-off is real

Because Terraform does not store the value, it cannot detect drift in it — if somebody changes the secret in the portal, no plan will notice. That is usually exactly what you want for a secret (rotation should not look like drift), but it is a genuine behaviour change and the reason value_wo_version exists: it gives you an explicit, reviewable trigger for an update.

4 · Create the vault in Terraform, populate it elsewhere

Terraform provisions the vault, its network configuration and its RBAC. A separate, tightly controlled process — a rotation function, a privileged pipeline, or a documented manual step — writes the values. Terraform outputs the secret ID, never the value.

outputs.tf
output "api_key_secret_id" {
  description = "Key Vault secret identifier. Consumers resolve the value themselves."
  value       = "${azurerm_key_vault.main.id}/secrets/third-party-api-key"
  # not sensitive — it is a URI, not a secret
}

5 · Accept the risk, and mitigate it

Sometimes there is no alternative: a provider needs a literal value, or you are generating a password for a resource that has no identity-based option. If you end up here, do all of the following:

  • Remote backend with encryption at rest and customer-managed keys if your policy requires them (Lesson 10).
  • State container RBAC restricted to the deployment identity and a small break-glass group — not the whole engineering team.
  • shared_access_key_enabled = false on the state storage account, so state cannot be read with a leaked key.
  • Plan artefacts treated as secrets: short retention, restricted access, never a public artefact store.
  • TF_LOG never set to DEBUG or TRACE in a pipeline that logs publicly.
  • Split the sensitive resources into their own state, so the blast radius of that one state file is small.
  • Generate rather than hardcode, so at least no human ever knew the value:
generating a password
resource "random_password" "sql_admin" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}<>:?"
}

# Still in state — random_password persists its result by design,
# because it must produce the same value on the next plan.
resource "azurerm_key_vault_secret" "sql_admin" {
  name         = "sql-admin-password"
  value        = random_password.sql_admin.result
  key_vault_id = azurerm_key_vault.main.id
}
random_password does not solve the problem

It is often presented as the secure option. It is not — the generated value is stored in state exactly like any other, because Terraform must reproduce it on the next plan rather than generating a new one. The only thing it improves is that the value was never in a human's clipboard or a git commit. That is worth something, but it is not encryption.

The chicken-and-egg with public_network_access_enabled = false

Disabling public access on a vault means Terraform itself can no longer reach the vault's data plane from a public runner — so creating or reading secrets fails, even though creating the vault succeeded. This is the same control-plane/data-plane split as storage in Lesson 06. Options: run Terraform from a private-network agent, keep the runner's IP in network_acls.ip_rules, or — best — do not have Terraform touch secret values at all.

Level 1 · Understand Where does the secret end up?

For each, say whether the secret's plaintext value ends up in Terraform state:

  1. resource "azurerm_key_vault_secret" with value = var.api_key
  2. data "azurerm_key_vault_secret" reading an existing secret
  3. An app setting containing "@Microsoft.KeyVault(VaultName=kv-x;SecretName=y)"
  4. resource "random_password"
  5. ephemeral "azurerm_key_vault_secret"
  6. resource "azurerm_key_vault_secret" using value_wo
  7. A variable declared sensitive = true but never used in any resource
Show answer
  1. Yes. Written to state in plaintext.
  2. Yes. Reading is as bad as writing — the data source caches the value in state. This surprises most people.
  3. No. State holds the reference string, which is a pointer. The App Service runtime resolves it with the app's managed identity.
  4. Yes. By design — Terraform must reproduce the same value on the next plan rather than generating a new one.
  5. No. Ephemeral resources are never persisted to state or the plan file.
  6. No. Write-only arguments are not stored. The trade-off is that Terraform cannot detect drift on the value.
  7. No — variables are not themselves stored in state. But the moment it feeds any resource argument, that resource's state entry contains it. Sensitivity is about display, not persistence.

Level 2 · Implement Keep a generated secret out of state entirely

A legacy system needs a database password Terraform must generate. Write the configuration so the generated value never appears in state or in a saved plan file.

State the Terraform version this requires, and the one real behavioural trade-off you accept.

Show solution
secret.tf
terraform {
  # ephemeral values: 1.10   write-only arguments: 1.11
  required_version = ">= 1.11.0"
}

# An EPHEMERAL resource. Its value exists only during the operation and is
# never written to state or to the plan file.
ephemeral "random_password" "sql_admin" {
  length           = 32
  special          = true
  override_special = "!#$%&*()-_=+[]{}"
}

resource "azurerm_key_vault_secret" "sql_admin" {
  name         = "sql-admin-password"
  key_vault_id = azurerm_key_vault.main.id

  # value_wo is WRITE-ONLY: sent to Azure, never persisted by Terraform.
  value_wo = ephemeral.random_password.sql_admin.result

  # Because the value is not stored, Terraform cannot detect that it changed.
  # This integer is the explicit, reviewable trigger for a rotation: bump it
  # and the next apply writes a new secret version.
  value_wo_version = 1

  content_type = "password"
}

Level 3 · Troubleshoot The vault that cannot be recreated

A team destroys their dev environment nightly and rebuilds it each morning. Since last Tuesday the morning build fails:

error
Error: creating Key Vault "kv-analytics-dev-weu-01": ConflictError:
Exist soft deleted vault with the same name.

Last Tuesday's change was adding purge_protection_enabled = true for a compliance requirement. Explain what happened and give three options with their trade-offs.

Show answer

Cause. The nightly destroy soft-deletes the vault. Previously the provider's purge_soft_delete_on_destroy setting could purge it, freeing the name. With purge_protection_enabled = true, purging is impossible — Azure refuses, for anyone, until the soft-delete retention expires. The name stays reserved for up to 90 days, so the morning build cannot create a vault with it.

Worse, purge protection cannot be disabled once enabled, so there is no way to undo this on the existing soft-deleted vault.

Option A — recover instead of recreating.

option A
provider "azurerm" {
  features {
    key_vault {
      recover_soft_deleted_key_vaults = true
    }
  }
}

The provider recovers the soft-deleted vault rather than failing. Simple, and it works today. Trade-off: the “fresh” environment is not fresh — it comes back with its previous secrets and access configuration, which undermines the point of rebuilding nightly and can mask configuration drift.

Option B — stop destroying the vault.

Move the Key Vault into a separate, long-lived “platform” state that the nightly teardown does not touch, and have the ephemeral environment reference it as a data source. Trade-off: two states to manage, and the environment is no longer fully reproducible from nothing. This is usually the right answer — vaults are not really ephemeral resources, and treating them as such is the actual mistake.

Option C — unique names per build.

Suffix the vault name with a build ID or date so each rebuild uses a new name. Trade-off: soft-deleted vaults accumulate for 90 days each, quietly consuming the subscription's vault quota, and every consumer of the vault name must be dynamic. Rarely worth it.

Recommended: Option B, with Option A as the immediate unblock. And revisit whether purge_protection_enabled was needed in dev at all — compliance requirements usually apply to environments holding real data. Setting it per environment via a variable is the correct expression of that policy.

Interview questions

Why shouldn't secrets be stored in Terraform code?

Because git history is permanent — removing a committed secret does not remove it from the repository, so remediation means rotating the credential. Repositories are also scanned continuously by automated tooling, and leaked cloud credentials have been exploited within minutes. Beyond git, hardcoding breaks environment portability and makes rotation a code change. Secrets should come from a secret store or the runtime environment.

Does marking a value sensitive keep it out of state?

No. sensitive only redacts the value from plan and apply output and propagates that marking to derived values. The value is still written to state in plaintext, still present in a saved plan file, still retrievable with terraform output -raw, and still visible in TF_LOG=DEBUG output. It is a display control. For values that must not persist, Terraform 1.10's ephemeral values and 1.11's write-only arguments are the actual mechanism.

How do you manage secrets with Terraform on Azure?

In order of preference. First, eliminate the secret: use managed identities and Azure RBAC so that nothing needs a credential — this covers storage, SQL, Service Bus, Event Hubs and most Azure-to-Azure access. Second, where a value must exist, use Key Vault references in app settings so Terraform stores only a pointer and the runtime resolves the value with its own identity. Third, where Terraform must handle a value, use ephemeral resources and write-only arguments such as value_wo so it never reaches state or the plan file.

Fourth, provision the vault and its RBAC with Terraform but populate values out of band, outputting the secret ID rather than the value. Only as a last resort accept the value in state, and then mitigate: encrypted remote backend, tightly scoped state access, plan artefacts treated as secrets, and the sensitive resources isolated in their own small state.

Access policies or RBAC for Key Vault?

RBAC — it is Microsoft's recommendation and it gives one consistent authorization model across Azure, works with PIM and access reviews, and supports scoping to an individual secret rather than only to the whole vault. Access policies are vault-only, capped at 1024 entries, and a separate mental model. The migration caveat is that switching an existing vault to RBAC breaks every consumer that does not already have an equivalent role assignment, so you grant the roles first and flip the flag afterwards.

What happens when you destroy and recreate a Key Vault?

Destroying soft-deletes it, which keeps the name reserved for the retention period — 7 to 90 days — so creating a new vault with the same name fails with a conflict error. If purge protection is enabled, the soft-deleted vault cannot be purged by anyone, so you must wait out the retention or recover it. The provider's features.key_vault block controls this: recover_soft_deleted_key_vaults recovers instead of failing, and purge_soft_delete_on_destroy purges on destroy, which is acceptable in throwaway dev and dangerous elsewhere.

Is reading a secret with a data source safe?

No — and this is the part people miss. data "azurerm_key_vault_secret" caches the retrieved value in state, so reading is exactly as exposing as writing. If you need a secret's value inside Terraform without persisting it, use the ephemeral "azurerm_key_vault_secret" form instead; if you only need to point something at the secret, construct the Key Vault reference URI or the secret ID yourself and never read the value at all.

Key takeaways

  • Any secret that flows through Terraform — written or read — is persisted in state in plaintext.
  • sensitive = true controls display, not persistence. Ephemeral values and write-only arguments control persistence.
  • The best pattern is having no secret: managed identities plus RBAC.
  • Second best: Key Vault references in app settings, so state holds a pointer and rotation needs no apply.
  • Use rbac_authorization_enabled = true (renamed in v5) and scope roles to individual secrets.
  • Purge protection is permanent and interacts badly with nightly destroy-and-rebuild. Keep vaults out of ephemeral state.

Sales Analytics Platform — Implementation

dev applied, converged prod coded, not yet applied

What is built, object by object. Architecture explains the design; this document lists every module, the objects it creates, and the mechanics that matter when operating it. The repo is the source of truth for exact arguments.

Status. dev is applied and converged (terraform plan shows no changes). prod is coded identically but never applied; see Prod bootstrap.

01Layout

modules/
├── naming/                name suffix and tags, no resources
├── azure/
│   ├── datalake/          RG, storage account, containers, landing retention
│   └── cost_budget/       RG-scoped budget with spend alerts
└── databricks/
    ├── workspace/         workspace, access connector, metastore assignment
    ├── compute/           once per environment: SQL warehouse, optional cluster
    ├── uc_storage/        once per environment: credential, external locations
    ├── uc_ingestion/      once per environment: ingestion catalog, bronze, volumes
    └── uc_domain_catalog/ once per domain: catalog, silver/gold, grants
platform/               the one root module for dev and prod
shared/                 root module: account-level metastore, applied by hand
config/
├── common.tfvars       values shared by every environment (passed with -var-file, not auto-loaded)
├── dev/                backend.hcl (state key) and values.tfvars
└── prod/               backend.hcl (state key) and values.tfvars
.github/workflows/      terraform.yml (plan/apply), drift-detection.yml (manual)

naming holds the region-code map and builds two values once per root: suffix (<workload>-<environment>-<region code>-<instance>, e.g. analytics-dev-neu-01) and tags (the base tags plus workload and environment). The root passes both to datalake and workspace, so no module carries its own copy of the naming rules. A new region is one line in modules/naming/main.tf.

uc_storage and uc_ingestion are separate from uc_domain_catalog because the credential, the locations and the raw ingestion layer are environment-wide, not per domain. Module state addresses come from the call label, not the source path.

Engineers use blanket MODIFY because the metastore's privilege version (1.0) rejects INSERT/UPDATE/DELETE at catalog level. databricks_grants (plural, authoritative) is used over databricks_grant so Terraform is the single source of truth.

enable_grants gates business-group grants only. Sales uses var.enable_grants (true in dev); marketing uses a literal false until its groups are registered.

modules/databricks/compute (once per environment, dev only so far)

Object What it is
databricks_sql_endpoint.shared Serverless SQL warehouse, 2X-Small, one cluster, stops after 10 idle minutes
databricks_permissions.warehouse CAN_USE for every workspace group
databricks_cluster.shared (off) Single-node all-purpose cluster, standard access mode, no Photon, on-demand, terminates after 10 idle minutes. Created only when enable_cluster = true
databricks_permissions.cluster (off) Data engineers CAN_RESTART; every other workspace group CAN_ATTACH_TO

The cluster is off. No classic cluster can start on the current subscription in northeurope. The subscription has a 4 vCPU regional quota. The 4-vCPU node types Databricks supports are either restricted (DS3_v2, F4s_v2, D4ads_v5, D4s_v3 and others are NotAvailableForSubscription) or have a family quota of 0 (DC4ads_v6 failed with AZURE_QUOTA_EXCEEDED_EXCEPTION), and the larger types exceed the regional quota. Turn enable_cluster on after the restriction and quota are lifted, by upgrading from a trial subscription or through an Azure support request, and check the node type first with az vm list-skus and az vm list-usage.

What runs where. The warehouse is serverless, so it uses no VM quota, but it runs SQL only: queries, dashboards, alerts and SQL cells. Python and Spark code run on serverless notebook compute, which needs no cluster and is billed per DBU while it runs.

Hourly cost (EUR, northeurope, Premium, pay-as-you-go list prices from Azure's retail price API):

Compute Calculation Per hour
Warehouse (serverless SQL, 2X-Small) 4 DBU × 0.7814, VM included 3.13
Cluster (when enabled) 0.75 DBU × 0.4723 (all-purpose) + the VM price about 0.35 + VM

The cluster's 0.75 DBU per hour is an assumption for a 4-vCPU node. Creating the warehouse starts it once, and each idle tail before the auto-stop costs about 0.52. Against the dev budget of 20 that is roughly 6 warehouse hours a month. The workspace's managed resource group, where cluster VMs would bill, has its own budget.

03Root module (platform)

One root serves both environments. Environment-specific pieces are switched by variables in each environment's values.tfvars: enable_compute and bronze_consumer_can_write (dev only so far) and workspace_user_domains (sales and marketing in both).

Object What it is
module.datalake, budget_alert Resource group, storage, and the budget (additional_domains = ["marketing", "ingestion"])
module.databricks_workspace, budget_alert_databricks_managed Workspace and access connector, plus a budget on the workspace's managed resource group
databricks_permission_assignment.ci_group Makes grp-databricks-ci-<env> a workspace ADMIN (needed to manage permission assignments)
databricks_entitlements.ci_group Gives that group workspace_access, without which the workspace API is unusable
databricks_permission_assignment.users, databricks_entitlements.users For each domain in workspace_user_domains (dev and prod: sales, marketing), the data engineers, analysts and stakeholders become workspace USERs with workspace_access and databricks_sql_access. Platform and governance groups are not added
databricks_grants.metastore_admins CREATE_CATALOG, CREATE_EXTERNAL_LOCATION, CREATE_STORAGE_CREDENTIAL for both CI groups. ignore_changes = [grant]
module.uc_storage, module.uc_ingestion The credential and locations, then the ingestion catalog; both depend on the metastore grant
module.unity_catalog_sales, module.unity_catalog_marketing The uc_domain_catalog module once per domain
module.compute (when enable_compute is set; dev) The shared serverless SQL warehouse (and the cluster, when enabled)

The metastore grant is in each root because databricks_grants needs the workspace-level provider, which the account-level shared root lacks. Dev's and prod's copies are identical so they converge. Grants go to the CI group, not the service principal, so a new CI identity is a membership change.

Why the workspace access is shaped this way.

  • The assignment is ADMIN, not USER: Terraform reads it on every plan, and reading permission assignments needs a workspace admin. group_name is a bare string because a workspace-scoped lookup would need the membership the resource creates. It is applied once by a human who is already a workspace member; CI cannot grant itself this.
  • Membership alone carries no entitlement to call the workspace API, so the entitlement resource grants workspace_access, the narrowest one accepted. The group lookup that feeds it is safe there because the group is already a member.
  • The platform and governance groups have no workspace presence. They only own Unity Catalog objects.
  • The metastore grant goes to the CI groups, not grp-databricks-account-admins, which would hand CI full account admin. Each environment's CI group therefore gets CREATE_* across the whole metastore, not only its own catalogs.

The root splits its configuration by concern: main.tf (naming, data lake, workspace, budgets), access.tf (workspace assignment, entitlements, metastore grant), catalogs.tf (uc_storage, uc_ingestion and the domain catalogs), compute.tf (shared compute), providers.tf and backend.tf. The backend is partial: terraform init -backend-config=../<env>.backend.hcl supplies the state key, and -reconfigure switches environment in the same checkout.

04Providers and authentication

The databricks provider's host comes from module.databricks_workspace.workspace_url. Its auth_type is the databricks_auth_type variable, null by default so DATABRICKS_AUTH_TYPE decides (azure-cli locally; in CI the dev jobs use OIDC); config/prod/values.tfvars pins azure-cli until a prod workflow supplies the variables. In CI it uses the same OIDC variables as azurerm. The account-level provider in shared sets its Databricks account ID inline; no other root needs it.

Two-stage first apply. A provider block cannot reference a computed attribute, so on a new environment the workspace must exist before the databricks provider can be configured: first terraform apply -target=module.databricks_workspace.azurerm_databricks_workspace.this, then a normal apply. The workspace stays azurerm permanently because the databricks provider cannot create Azure workspaces. Resource-group Contributor is enough to create it and the access connector.

05CI permission model

CI runs as sp-terraform-<env> (a member of grp-databricks-ci-<env>), which is not a metastore admin.

Constraint Consequence
Ownership does not cascade CI holds explicit grants on everything it reads or creates against (see the grants above)
Transferring ownership drops the creator's MANAGE A catalog CI creates and hands to a group cannot be finished by CI unless the CI group is nested in that owner group. Nest grp-databricks-ci-<env> in grp-databricks-platform-<env> and every grp-<domain>-data-governance-<env> in Entra ID before the first apply of a new domain or environment
Metastore grants are admin-only A non-admin cannot update them and only sees grants for its own groups, which shows as a phantom diff. Hence ignore_changes; apply them locally as an admin. Drift on them is not reported
Saved plans go stale apply-* applies the plan artifact from plan-*; on "Saved plan is stale" re-run the whole workflow

drift-detection.yml is a manual workflow that never applies. It runs plan -refresh-only (state vs Azure/Databricks; a warning, since it can show provider spelling noise) and a plain plan (code vs reality; fails on any diff). shared has no CI job.

07shared

Account-level root with its own state. It reads only common.tfvars and manages one object: databricks_metastore.primary (metastore_azure_northeurope, owned by grp-databricks-account-admins). terraform output metastore_id is the source of truth; copy it to common.tfvars if the metastore is ever recreated. storage_root is ForceNew.

08Bootstrap

Metastore. Created once by hand, like the App Registrations. Databricks auto-creates an empty default metastore when a region's first workspace appears; adopt it with terraform import rather than fighting it. The Account Console does not work until one Azure Databricks workspace exists, so for a new tenant: (1) apply the workspace for one environment, (2) in the Account Console create the metastore's resource group, storage account and access connector, then the metastore, and assign it, (3) if Databricks auto-created a metastore first, fill in its storage config instead of creating another. Never wire the pre-staged access connector in the workspace's managed resource group to anything: it inherits that workspace's lifecycle and cannot be deleted.

Groups. Create each grp-* group in Entra ID and register it in the Databricks account before any grant that references it applies.

09Prod bootstrap

Prod (platform with config/prod/values.tfvars) has never had a full apply; apply-prod waits on the production approval. Its state already holds an early resource group, storage account and budget, under the old module.analytics_group address; a moved block in main.tf maps them to module.datalake so an apply updates them in place instead of destroying the real prod storage. Before approving it:

  1. Run the first prod apply locally as a metastore admin (the metastore grant is admin-only and ignored by CI).
  2. Register the -prod groups the config references: grp-databricks-ci-prod, grp-databricks-platform-prod, and grp-sales-*-prod. grp-marketing-*-prod may stay unregistered.
  3. Expect the two-stage workspace apply on the first run.

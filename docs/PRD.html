This document contains no Terraform, Azure resource, or CI/CD implementation detail, and no data-pipeline/ transformation logic — only what the business needs the infrastructure to be capable of. See Architecture and Implementation for those layers.

01 Executive summary

The company operates a network of physical retail stores and an online store. Sales transaction data currently exists across two operational systems — the point-of-sale system and the e-commerce platform — with no centralized place to store or analyze it historically.

The company requires a centralized analytical platform that provides a consistent foundation for sales reporting and historical analysis. The initial project establishes the cloud infrastructure required to support this analytical platform, using Infrastructure as Code — intentionally focused on the underlying platform rather than implementing production data pipelines.

  • Centralized analytical data storage for sales data
  • Historical analytical data retention
  • Separate Development and Production environments
  • Secure access to analytical resources
  • Reproducible infrastructure
  • Controlled infrastructure changes
  • Future implementation of sales data ingestion and transformation workloads

02 Business problem

Sales data originates from the point-of-sale system (physical stores) and the e-commerce platform (online store) — each with a different schema and update frequency.

Inconsistent business information

Revenue and sales metrics may be calculated differently depending on which system's data is used.

Limited historical analysis

Both operational systems represent current transaction state; there's no durable, queryable historical record independent of their own retention.

Fragmented analytical data

Sales reporting depends on combining exports from two separate systems instead of a centralized foundation.

Limited scalability

Manual extraction and spreadsheet-based analysis don't scale as transaction volume grows.

Difficult environment management

Reproducible Dev/Prod environments are required; infrastructure shouldn't depend on manual cloud-console configuration.

03 Goals

Establish a cloud-based analytical platform foundation capable of supporting centralized sales storage, historical sales analysis, revenue/performance analysis, store- and channel-level analysis, and future ingestion/transformation workloads.

5yr
The one volume-related figure treated as a firm business requirement — historical analytical data retention. See §9.
Store count and daily transaction volume are deliberately not stated as targets. No capacity/throughput sizing study has been done yet, and this project doesn't include cluster or compute sizing work. The infrastructure is designed to scale horizontally regardless of the eventual number — publishing an unvalidated figure would let storage tiering, cluster sizing, and partitioning decisions silently anchor on something nobody actually confirmed. A real sizing study gets folded in here as a revision, not treated as a blocker to this phase.

07–08 Data requirements & organization

Initial scope is the Sales domain: transactions from POS and e-commerce. A second domain, Marketing, shares the platform with the same access model, so several domains can use it without seeing each other's data. Raw data from each source system is kept once; each domain builds its own refined and business-ready datasets from it. Sales data should be representable independently from either source system's structure — datasets designed around business questions about sales, not either system's schema.

The platform must support a logical separation between raw source extracts and business-ready, reportable datasets. This progression — raw, refined, business-ready — is commonly known as medallion architecture (bronze/silver/gold), and this document uses that vocabulary elsewhere: the report-consumer/analyst split above maps onto which of these stages each role can see. The exact storage/organizational implementation — including how many stages, and their concrete names — is an architecture decision, not fixed by this requirement.

09 Historical data retention

5yr
Sales analytical data is retained for five years from ingestion. Data older than five years may be deleted. Data does not need to remain queryable at full cost/performance for the entire period — a lower-cost tier is acceptable, provided it isn't deleted before the five-year mark.

Historical data remains available independently from the lifecycle of the POS and e-commerce source systems. See Architecture — data retention & lifecycle policy for how this is technically enforced.

10 Environment requirements

DEV PROD

Development and Production must be independently managed — a change or failure in Development must not unintentionally affect Production.

11 Security requirements

  • Users authenticate using the organization's identity platform where supported
  • Workloads use dedicated identities
  • Production data is intended to be written by automated identities, not people
  • Access follows least-privilege principles
  • Production access is more restricted than Development access
  • Credentials are not embedded in source code
  • Secrets that can't be eliminated via identity-based auth are securely managed
  • Development workloads must not accidentally gain unrestricted access to Production

12–13 Cost, ownership & reliability

Resources should consistently identify:

Each environment has a budget with spend alerts. The platform must make it possible to distinguish Development and Production infrastructure costs, and provide durable, source-controlled infrastructure without unnecessary coupling between environments.

Production data is protected against accidental loss. Deleted data stays recoverable for at least 14 days in Production (a shorter period is fine in Development), and an ordinary change cannot destroy Production storage — destroying it takes a deliberate, reviewed change.
Exception, not a loophole. "No manually configured resources that cannot be reproduced" doesn't prohibit a small number of one-time, account-/tenant-level objects Infrastructure as Code fundamentally cannot create for itself (an identity a pipeline authenticates as cannot be created by that same pipeline's own run) — provided each is created through a documented, repeatable procedure, not undocumented manual configuration. This platform already follows that pattern for its App Registrations, and extends the same exception to any account-level Databricks object a future architecture phase introduces.

16 Backlog / future scope

Networking

Private endpoints, private connectivity, Databricks network architecture, controlled outbound connectivity — a future architecture phase.

Data pipelines

Actual ingestion, transformation, orchestration — including how historical change is modeled — is future implementation work.

Additional business domains

Beyond Sales and Marketing, inventory, product, customer and supplier data are out of scope; a future extension gets its own review.

Data quality, monitoring, streaming, ML

All future capabilities, not required by this infrastructure phase.

17 Acceptance criteria

Infrastructure
  • Dev & Prod provisioned via Terraform
  • Reproducible from version-controlled definitions
  • Independently managed environments
  • Configuration durably stored centrally, not on any one engineer's machine
  • Changes reviewable before deployment
Security
  • Organizational identities used where supported
  • No unnecessary long-lived credentials
  • Production access appropriately restricted
  • No hardcoded secrets
  • Environment boundaries enforced
Analytical platform foundation
  • Durable analytical storage for sales data
  • Databricks provisioned as compute platform
  • Five-year retention enforced at infra level
  • Production storage protected against accidental deletion
  • Capacity for expected volumes validated once compute is sized
Engineering
  • Version-controlled Terraform
  • Reusable components separated from env config
  • Changes validated through automation
  • Drift between definitions and deployed infrastructure detectable on demand
  • Production requires appropriate approval
  • Resources identifiable by env/workload/owner/cost

19 Final business outcome

The project establishes a reproducible cloud foundation for a future sales analytics platform. The immediate objective is not to build the data pipelines — it's to demonstrate the ability to design and provision the underlying cloud infrastructure a production-oriented analytical data platform requires, using Terraform in a secure, reproducible, environment-separated manner.
